# 결정 기록 (ADR)

비싸거나 중요한 결정을 `docs/superdomain/adr/yyyy-MM-dd-slug.md`에 남긴다. 다음 사람(다음 세션의 Codex 포함)이 "왜 이렇게 했지?"에 답을 찾을 수 있게 하는 것이 목적이다.

**핵심 원칙:** 사실만 적는다. 검토하지 않은 대안이나 사용자가 말하지 않은 이유를 지어내지 않는다.

작업 기준은 git 루트다(`git rev-parse --show-toplevel`). 템플릿과 상태 규칙은 [adr-template.md](adr-template.md)에 있으니 쓰기 전에 읽는다.

이 문서의 상대 링크는 Codex가 제공한 실제 `SKILL.md` 위치를 기준으로 해석한다. 사용자 프로젝트의 현재 디렉터리나 원본 플러그인 경로를 기준으로 찾지 않는다.

## 1. 모드

| 요청 | 모드 |
|---|---|
| 새 결정을 기록한다 | 신규 |
| `proposed` ADR을 확정한다 | 승인 |
| 옛 결정을 전면 무효로 하고 새 결정으로 바꾼다 | 대체 |
| 옛 결정의 일부만 바꾼다 | 부분 조정 |
| 요청은 없지만 방금 끝낸 작업에 비싸거나 중요한 결정이 있었다 | 제안 |

**제안**: ADR을 바로 쓰지 않는다. 어떤 결정인지와 기록할 이유(2절 1번의 신호 중 무엇에 해당하는지)를 한두 줄로 제안하고, 동의하면 신규로 간다. 동의하지 않으면 끝내고, 이 세션에서 같은 결정을 다시 제안하지 않는다.

대체인지 부분 조정인지 애매하면 근거와 함께 하나를 제안하고 확인받는다. 옛 ADR이 이미 `superseded`면 `대체됨:` 링크를 따라가 현재 유효한 ADR을 대상으로 다시 판단한다.

## 2. 신규

먼저 `docs/superdomain/adr/`의 기존 ADR을 훑는다. 같은 주제의 ADR이 있으면 신규가 아니라 대체나 부분 조정을 제안한다.

1. **쓸 결정인가 판단한다.** 셋 중 하나라도 해당하면 쓴다.
   - 되돌리는 비용이 크다.
   - 실제로 여러 대안 중에서 골랐다.
   - 나중에 누군가 "왜?"라고 물을 것이다.

   해당하지 않으면 쓰지 않고 이유를 말한다. 판단이 서지 않으면 쓴다.
2. **한 ADR에 결정 하나.** 인터뷰 중 결정이 둘로 갈라지면 문서도 둘로 나눈다.
3. **인터뷰한다.** 한 번에 하나씩 묻고, 받은 답을 바로 초안에 반영해 보여 준다. 대화나 코드에서 본 것을 근거로 초안 문장을 먼저 제안해도 되지만 확정은 사용자가 한다.

   | 항목 | 묻는 것 | 실패 신호 |
   |---|---|---|
   | 제목 | 이 결정을 한 문장 결정문으로 | "인증 방식 검토" 같은 명사구 |
   | 문제 상황 | 무엇이 이 결정을 강제했는가 | 배경이 본문의 절반을 넘는다 |
   | 결정 | 무엇을 하기로 했는가 | "~를 고려한다" |
   | 검토한 대안 | 실제로 오간 대안과 기각 이유 | 아래 4번 |
   | 결과 | 긍정 / 부정 / 후속 작업 | 부정 칸이 비었다 |

4. **검토한 대안**: 사용자가 말한 대안, 또는 제안한 대안 중 사용자가 "그것도 봤다"고 확인한 것만 적는다. 기각 이유도 사용자에게서 받는다. 대안이 없으면 표 대신 "검토한 대안 없음."이라고 쓰고, ADR로 쓸 결정이 맞는지 다시 확인한다.
5. **부정적 결과가 비면 한 번 더 묻는다.** 그래도 없다고 하면 사용자의 답을 그대로 적는다. 없는 대가를 지어내지 않는다.
6. **분량은 한 화면(40~60줄)이다.** 넘치는 배경은 줄이거나 이미 있는 문서(README·DOMAIN.md 등)에 링크한다. 새 파일은 만들지 않는다.
7. **초안 전문을 보여 주고 확정받은 뒤 파일을 쓴다.** 이름은 `docs/superdomain/adr/<오늘 날짜>-<slug>.md`다(날짜는 `date +%F`, slug는 영문 소문자와 하이픈). 같은 이름이 있으면 slug를 바꾼다. 상태는 `proposed`로 시작한다.

## 3. 승인

확인받고 `- 상태: proposed`를 `- 상태: accepted`로 바꾼다. 본문은 고치지 않는다.

## 4. 대체

- 새 ADR을 2절 3~7번대로 쓴다. 상태는 확인받고 `accepted`로 쓰며, 머리에 `- 대체함: [<옛 파일명>](<옛 파일명>.md)`을 단다.
- 옛 ADR의 상태를 `superseded`로 바꾸고, 머리에 `- 대체됨: [<새 파일명>](<새 파일명>.md)`을 단다.
- **옛 ADR의 본문은 한 글자도 고치지 않는다.** 머리(메타데이터)만 고친다. 당시의 판단과 근거가 그대로 남아야 나중에 무엇이 왜 바뀌었는지 비교할 수 있다.
- 한쪽 링크만 걸고 끝내지 않는다. 어느 문서에 먼저 도착해도 현재 유효한 결정에 닿아야 한다.

## 5. 부분 조정

- 새 ADR을 2절 3~7번대로 쓰되, 본문에 "<옛 파일명>의 X 부분을 조정한다"고 적는다. 상태는 대체와 같이 확인받고 `accepted`로 쓴다(`조정됨:` 링크가 확정되지 않은 초안을 가리키지 않게).
- 옛 ADR은 `accepted`로 두고, 머리에 `- 조정됨: [<새 파일명>](<새 파일명>.md)`을 한 줄 더한다. 조정이 쌓이면 줄을 나열한다.

## 6. 후속 제안

- 결정이 도메인 정의(역할·기능·분류·코드·규칙·관계)를 바꾸면 superdomain의 [domain 스킬](../domain/SKILL.md)으로 DOMAIN.md를 고치자고 안내한다. DOMAIN.md는 이 스킬이 직접 고치지 않는다.
- ADR을 쓴 뒤 대상 지침 파일에 아래 포인터 줄이 없으면 추가할지 묻고, 동의하면 추가한다. 대상 지침 파일은 프로젝트 루트의 AGENTS.md다. 루트에 기존 CLAUDE.md나 `.claude/CLAUDE.md`가 있으면 저장소의 지침 파일 정책에 따라 그 파일을 사용한다. 이 경우 Codex가 그 파일을 자동으로 읽는다고 가정하지 말고, 다음 세션에서 명시적으로 읽도록 안내한다. CLAUDE.md 계열 파일을 새로 만들지 않는다. 대상 파일이 없으면 만들지 않고 줄을 제안만 한다. 이 줄이 있으면 다음 세션에서도 작업을 마칠 때 기록할 결정이 있었는지 돌아보게 된다.

  ```
  - 결정 기록: docs/superdomain/adr/ (비싸거나 중요한 결정을 내린 작업을 마치면 superdomain의 adr 스킬로 기록할지 제안한다)
  ```

## 하지 않는 것

- 검토하지 않은 대안, 사용자가 말하지 않은 기각 이유, 없는 부정적 결과를 지어내지 않는다.
- 확인 없이 상태를 바꾸지 않는다.
- `accepted`·`superseded` ADR의 본문을 고치지 않는다.
