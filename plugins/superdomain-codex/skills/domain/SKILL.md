# 도메인 정의

`docs/superdomain/DOMAIN.md` 한 파일에 도메인마다 역할·기능·분류·패키지를 적고, 도메인 사이의 관계를 표로 적는다. 사람과 Codex가 같은 도메인 그림을 보게 하는 것이 목적이다.

**핵심 원칙:** 판단은 근거와 함께 적극적으로 제안하고, 확정은 사용자가 한다. 질문은 한 번에 하나만 한다(한꺼번에 물으면 답이 섞이거나 빠진다).

DOMAIN.md 형식과 경계·분류 판단 기준은 [domain-guide.md](domain-guide.md)에 있다.

이 문서의 상대 링크는 Codex가 제공한 실제 `SKILL.md` 위치를 기준으로 해석한다. 사용자 프로젝트의 현재 디렉터리나 원본 플러그인 경로를 기준으로 찾지 않는다.

## 체크리스트

작업 기준은 git 루트다(`git rev-parse --show-toplevel`). 아래 단계마다 할 일을 만들고 순서대로 끝낸다.

1. **맥락 파악**: 지침 파일(AGENTS.md·CLAUDE.md), README, 모듈·패키지 구조, 최근 커밋을 읽는다. 외부 시스템과 주고받는 코드(외부 API 클라이언트·SDK·웹훅 수신)를 여기서 찾아 둔다. `docs/superdomain/DOMAIN.md`가 있으면 그 파일도 읽고 아래 "수정 모드"로 간다. 코드가 없으면 제품이 무엇을 하는지부터 묻는다.
2. **기준 읽기**: [domain-guide.md](domain-guide.md)를 읽는다.
3. **질문**: 한 번에 하나씩 묻는다. 가능하면 선택지를 주고 추천을 맨 앞에 둔다. 질문과 선택지는 제품과 프로젝트의 말로 쓴다. 가이드 용어가 필요하면 그 자리에서 풀어 쓴다. 목적은 도메인의 역할·기능·경계·관계와 외부 접점을 확정하는 것이다. 기능마다 정책도 정한다: 취소·환불 때 무엇을 되돌리는지, 수정·삭제가 되는지와 그 기한, 유효기간·한도, 중복·어뷰징을 어떻게 막는지. 정책은 기능마다 따로 묻지 않고, 도메인마다 초안을 먼저 제안해 한 번에 확인받는다(예: "주문을 취소하면 쿠폰과 포인트를 되돌린다 — 맞나요?"). 돈·상태·재화가 걸린 기능부터 다룬다. 기획 용어 하나가 성질이 다른 개념 둘로 갈리는지(쿠폰과 소유 쿠폰), 어떤 행위가 어느 개념에서 시작되는지(결제 취소인가 주문 취소인가)도 묻는다. 정책은 그 자리에서 정한다. 사용자가 망설이면 기본안(코드가 있으면 지금 동작, 없으면 범위를 좁힌 쪽. 예: 전체 취소만 된다)을 추천해 고르게 한다. 사용자가 확정한 것 가운데 가이드의 「간결하게 쓰는 기준」을 통과하는 것만 `규칙`에 적고, 나머지는 대화로만 확인한다. 지금 정할 수 없는 것(정할 사람이 따로 있다, 데이터를 봐야 한다)은 어느 칸에도 적지 않고 모아 두었다가 8단계에서 알린다.
4. **도메인 목록 제안**: 먼저 사용자가 생각하는 최상위 묶음이 있는지 묻는다. 있으면 그것을 출발점으로 삼고, 패키지 구조에서 읽은 후보를 거기에 맞춰 보여 준다. 없고 기존 코드가 있으면 패키지 구조에서 읽은 후보부터 보여 준다. 후보마다 가이드의 경계 기준에 비춘 근거를 붙여 제안하고 확인받는다. 외부 시스템마다 맡을 도메인을 제안해 확인받는다(가이드의 "외부 접점"). 맡을 도메인 밖에서 그 외부를 직접 부르는 코드는 어긋남 후보로 모아 둔다. 중심 도메인 후보가 여럿이면(예: 주문 중심이냐 결제 중심이냐) 경계를 두세 가지로 그려 보여 주고, 이 제품에서 무엇이 더 중요한지로 고르게 한다. 근거로는 목록 화면이 무엇의 목록인지, 다음 기능이 어디에 붙는지, 관계 표 초안에서 의존받는 수를 쓴다.
5. **섹션별 작성**: 처음에는 가이드의 기본 뼈대와 관계 표만 쓴다. 도메인마다 역할·기능·분류·패키지를 보여 주고 확인받는다. 외부를 맡은 도메인이면 `외부`를 빠뜨리지 않는다. 필요할 때만 쓰는 칸은 사용자가 원하거나 「간결하게 쓰는 기준」을 통과하는 내용이 있을 때 더한다. `개념`은 도메인 안에 개념이 여럿이라 알아야 할 것을 추려 둘 필요가 있을 때만 제안한다. 이어서 관계 표를 보여 주고 확인받는다. 4단계에서 모아 둔 어긋남 후보는 한 번에 확인받아 `알려진 어긋남`에 적는다. 개념도는 비개발자와 함께 보거나 사람이 자주 바뀌는 프로젝트일 때만 제안한다.
   - 방향은 가이드의 "관계의 방향"대로 제안한다(중심·내부 도메인이 의존받고, 외부 접점 도메인과 흐름의 뒤 단계가 의존한다). 두 도메인이 서로 의존하면 한 방향을 정하고, 반대 흐름은 이벤트나 배치로 바꾸자고 제안한다.
   - 모든 도메인이 의존하는 것처럼 보이는 도메인이 있으면 정말 기반 도메인인지 사용자에게 묻는다. 맞다고 확인받은 뒤에만 `모든 도메인이 참조` 한 줄로 적는다.
6. **저장 후 자체 검토**: `docs/superdomain/DOMAIN.md`에 쓴 뒤 domain-reviewer를 정의 검토 모드로 호출한다(아래 "자체 검토 호출"). 지적 중 무엇을 반영할지 사용자와 정해 고친다. 틀린 문장과 모순은 세부를 다른 칸으로 옮기지 않고 지우는 쪽을 먼저 제안한다. 새 사실을 더하자는 지적은 「간결하게 쓰는 기준」을 통과할 때만 제안하고, 통과하지 못한 사실은 대화로만 알린다.
7. **사용자 검토**: 파일을 검토해 달라고 요청하고, 고칠 곳이 있으면 반영한다. 여기서 도메인·관계·`외부`가 바뀌거나 섹션을 다시 쓰면 6단계를 한 번 더 한다.
8. **후속 제안**
   - 도메인 분리·병합이나 경계 변경처럼 비싸거나 중요한 결정이 있었으면 superdomain의 [adr 스킬](../adr/SKILL.md)로 기록하자고 제안한다. 4단계에서 중심 도메인을 고른 이유도 여기에 든다.
   - 아래 포인터 줄 중 대상 지침 파일에 없는 줄을 추가할지 묻고, 동의하면 추가한다. 두 포인터 줄 가운데 옛 줄이 있으면 새 줄로 바꿀지 묻는다. 대상 지침 파일은 프로젝트 루트의 AGENTS.md다. 루트에 기존 CLAUDE.md나 `.claude/CLAUDE.md`가 있으면 저장소의 지침 파일 정책에 따라 그 파일을 사용한다. 이 경우 Codex가 그 파일을 자동으로 읽는다고 가정하지 말고, 다음 세션에서 명시적으로 읽도록 안내한다. CLAUDE.md 계열 파일을 새로 만들지 않는다. 대상 파일이 없으면 만들지 않고 줄을 제안만 한다. `@import`는 쓰지 않고 일반 경로 포인터를 쓴다.

     ```
     - 도메인 정의: docs/superdomain/DOMAIN.md (도메인의 역할·관계를 바꾸는 작업 전에 읽는다. 고칠 때는 superdomain의 domain 스킬로 고친다)
     - 결정 기록: docs/superdomain/adr/ (정해진 구조·정책을 바꾸는 제안을 하거나 받으면 먼저 관련 기록을 찾아 읽는다. 비싸거나 중요한 결정을 내린 작업을 마치면 superdomain의 adr 스킬로 기록할지 제안한다. 기록에는 결정마다 이유·버린 안·비용을 적고, 결정이 아닌 코드 이름과 절차는 적지 않는다)
     ```
   - 3단계에서 모아 둔 정하지 못한 정책이 있으면 대화로 목록만 알린다. 이 스킬은 그것을 파일이나 이슈로 남기지 않는다.

## 수정 모드

1. 무엇을 바꿀지 확인한다(추가·분리·병합·이름 변경·관계 변경·외부 접점 변경·기준 개념이 바뀜). 기준 개념이 바뀌면(예: 주문의 단위가 상품에서 상품 옵션으로) 관계 표에서 그 도메인에 의존하는 도메인을 따라가며 영향받는 `규칙`과 `개념`을 확인한다. 기존 문서에 0.7.0의 형식(칸 이름 `코드`, `미정` 칸)이 남아 있으면 이번에 함께 고칠지 묻는다. `코드`는 이름을 `패키지`로 바꾼다. `미정`은 항목마다 가른다. 지금 정할 수 있으면 정해서 `규칙`으로 옮기고, 정한 방향·경계와 다른 코드를 적어 둔 것이면 `알려진 어긋남`으로 옮기고, 그 밖은 지운다. 규칙·관계를 바꾸는 변경이면 `docs/superdomain/adr/`에서 관련 기록을 찾아 읽고, 버린 안을 되살리는 변경이면 사용자에게 알린다.
2. [domain-guide.md](domain-guide.md)를 읽고, 바뀌는 부분의 전·후를 나란히 보여 주고 확인받는다. 고칠 때 「간결하게 쓰는 기준」을 지킨다. 관계를 바꾸면 한 방향인지, 방향이 가이드의 기준과 맞는지 확인하고(양방향이면 이벤트·배치로 바꾸자고 제안한다), 외부를 새로 맡거나 놓으면 `외부`도 함께 고친다. 관계를 바꾸는데 프로젝트에 허용 관계 테스트(가이드의 "허용 관계 테스트")가 있으면, 같은 변경에서 그 선언도 고쳐야 한다고 알린다. 테스트 코드는 이 스킬이 고치지 않는다.
3. 반영한다.
4. 도메인을 추가·분리·병합했거나 관계·`외부`를 바꿨으면 체크리스트 6단계의 자체 검토를 한다.
5. 체크리스트 8단계의 후속 제안을 한다.

## 자체 검토 호출

[리뷰어 실행 계약](../review/references/dispatch.md)을 읽고 `domain-reviewer` 역할의 새 서브에이전트 한 명을 실행한다. 역할 문서는 [domain-reviewer.md](../review/references/domain-reviewer.md)다. 세션 대화는 넘기지 않고 역할 문서의 절대 경로와 아래 입력만 전달한다. 서브에이전트를 실행할 수 없으면 자체 검토 미완료를 알리고, 독립 검토를 마쳤다고 보고하지 않는다.

```
모드: 정의 검토
프로젝트 루트: <절대 경로>
DOMAIN.md: <절대 경로>
기준 문서: <이 SKILL.md 옆 domain-guide.md의 절대 경로>
```

## 하지 않는 것

- 사용자 확인 없이 DOMAIN.md를 쓰거나 고치지 않는다.
- 코드를 쓰거나 패키지·디렉터리를 만들지 않는다.
- "알아서 해 달라"는 요청에도 근거와 함께 하나를 제안하고, 동의를 받은 뒤에 적는다.
- 리뷰어 지적을 사용자 확인 없이 반영하지 않는다.
- 사용자가 확정하지 않은 정책을 `규칙`에 적지 않는다. `알려진 어긋남`에는 정한 방향·경계와 다른 코드만 적고(목표는 "정하지 않음"일 수 있다), 정하지 못한 정책을 옮겨 적지 않는다.
- 빠진 패키지나 규칙을 찾는 검증을 따로 돌리지 않는다. 자체 검토에 쓰는 것은 domain-reviewer 호출 하나다(7단계에서 6단계를 다시 할 때도 같은 호출이다).
