## 개념

컨텍스트를 코드로 실현하는 방법은 세 가지뿐이고, `- 모듈 구성:` 라벨에 쓸 수 있는 값도 이 셋뿐이다.

| 값 | 모듈의 단위 | 컨텍스트가 실현되는 방식 | 선언 요건 |
|---|---|---|---|
| `multi-module` | 컨텍스트 × 레이어마다 Gradle 모듈 하나 | 모듈들의 묶음 | 모듈 표 필수 |
| `single-module` | 컨텍스트마다 모듈 하나 | 모듈 하나, 레이어는 그 안의 패키지 | 모듈 표 필수(보통 한 행, 레이어 `all`) |
| `app-embedded` | 실행 단위(애플리케이션)마다 모듈 | 여러 앱 모듈에 걸친 패키지들 | 애플리케이션 표 + 패키지 규약 표 필수, 모듈 표 금지 |

### 왜 세 형태를 모두 지원하면서도 규칙은 하나인가

파서는 어떤 형태든 **"컨텍스트 × 레이어 → 패키지 패턴"으로 정규화**한다. fitness·check_imports·
collect_signals는 정규화 결과만 소비한다.

```
multi-module   claim/domain 모듈           ─┐
single-module  claim 모듈의 domain 패키지   ─┼→  com.acme.claim.domain..
app-embedded   core-api 안의 domain.claim   ─┘
```

Konsist와 ArchUnit이 판정하는 단위가 패키지 패턴이기 때문에, 정규화를 거치면 강제 파이프라인이
실현 형태를 알 필요가 없어진다. 실용적 귀결이 둘이다.

- 레이아웃을 바꾸는 리팩터링(single → multi)이 **규칙을 바꾸지 않는다.** 패턴만 다시 계산된다.
- 반대로, 패키지 패턴이 컨텍스트를 구분하지 못하게 배치하면 어떤 형태를 골라도 컨텍스트 경계
  규칙을 생성할 수 없다(아래 안티패턴).

모듈 정보(경로) 자체는 강제에 쓰이지 않는다. sync가 존재 여부를 대조하고 scaffold가 생성 위치를
정하는 데만 쓴다.

### app-embedded — 실전에서 나오는 형태

레이어가 최상위 패키지이고 컨텍스트가 그 아래 하위 패키지로 들어가며, 여러 실행 애플리케이션이
같은 도메인 코드를 공유하는 형태다.

```
imstargg-backend/
├── core/
│   ├── core-api/       com.imstargg.core.domain.brawlstars..   ← 컨텍스트는 여기 있다
│   ├── core-admin/     com.imstargg.core.application.statistics..
│   ├── core-batch/
│   └── core-worker/
├── infrastructure/db-core/      (역할: infrastructure)
├── client/brawlstars-client/    (역할: client)
├── support/logging/             (역할: support)
└── core/core-enum/              (역할: shared-kernel)
```

앱 4개(api·admin·batch·worker), 역할별 공용 모듈 4개. 컨텍스트 `brawlstars`는 모듈 하나가 아니라
여러 모듈에 걸친 패키지들로 실현된다. 어느 앱이 어떤 컨텍스트를 쓸 수 있는지는 `### 애플리케이션`
표의 `포함 컨텍스트` 열이 선언하고, 각 레이어의 패키지 모양은 `### 패키지 규약` 표가
선언한다([[package-conventions]]).

**"걸친다"가 뜻하는 것 — 레이어마다 소유 모듈이 다르다는 뜻이지 한 레이어가 쪼개진다는 뜻이
아니다.**

- **컨텍스트의 각 레이어 패키지는 정확히 하나의 모듈이 물리적으로 소유한다.** 여러 앱이 함께
  쓰는 레이어(보통 domain·application)는 그 앱들이 **함께 의존하는 비실행 모듈**에 두고, 앱마다
  다른 레이어(보통 presentation)만 각 앱 모듈에 둔다. 위 예에서
  `com.imstargg.core.domain.brawlstars..`는 한 곳에만 있고 세 앱이 그것을 의존한다.
- 같은 패키지가 두 모듈에 동시에 존재하면 split package이거나 복제다. 정규화 패턴은 파일이 어느
  모듈에 있는지 구분하지 않으므로 **이 상태는 어떤 생성 규칙으로도 잡히지 않는다** — 사람이
  지켜야 하는 몇 안 되는 항목이다.
- 도메인·애플리케이션을 소유하는 비실행 모듈은 컨텍스트에 속하므로 `### 공용 모듈` 표에 적지
  않는다(그 표는 컨텍스트에 속하지 않는 모듈만 다룬다). app-embedded에는 모듈 표도 없으므로
  이 모듈은 어디에도 선언되지 않는다 — 선언되는 것은 패키지 패턴뿐이다.

모듈로 컨텍스트 자체를 표현하려면 앱 수 × 컨텍스트 수만큼 모듈이 필요해진다. 그래서 이 형태가
존재한다.

## 적용 기준

### 선택 절차 — 위에서부터 먼저 걸리는 것이 답이다

1. **이미 레이어-우선 패키지로 앱 모듈 안에 코드가 들어 있고, 옮기는 비용이 이득보다 큰가?**
   → `app-embedded`. 이 형태는 **있는 현실을 선언하기 위한 값**이지 그린필드에서 먼저 고르는
   값이 아니다. 새로 만들면서 여러 앱이 도메인을 공유해야 한다면 `multi-module`(컨텍스트 모듈 +
   그것을 의존하는 앱 모듈)이 더 명확하다. 그린필드에서 `app-embedded`를 고를 만한 유일한 이유는
   **컨텍스트 경계가 아직 유동적이라 모듈로 굳히기 이르다**는 것이다 — 패키지는 옮기기 싸고
   모듈은 비싸다.
2. **컨텍스트를 서로 다른 시점에 배포하는가(또는 12개월 안에 그럴 계획인가)?**
   → `multi-module`. 배포 단위가 다르면 빌드 단위도 달라야 한다.
3. **컨텍스트마다 소유 팀이 다른가?**
   → `multi-module`. 빌드 실패는 소유 경계에서 나야 남의 코드를 고치는 일이 생기지 않는다.
4. **레이어 방향 위반이 최근 3개월 리뷰·fitness에서 2회 이상 실제로 잡혔는가(또는 이행 중이라
   baseline에 레이어 방향 위반이 남아 있는가), 또는 클린 빌드가 5분을 넘는가?**
   → `multi-module`. 레이어를 별도 빌드 단위로 쪼개서 얻는 것은 이 둘뿐이다 — 컴파일러가
   fitness보다 먼저 잡아 주는 것과 증분 빌드. 둘 다 **관측된 사실이어야** 한다. "미리 막아
   두면 좋지 않을까"는 어느 시스템에서든 예가 나오므로 판정에 쓸 수 없다. 둘 다 아니면 모듈
   수만 컨텍스트 수의 3~4배가 된다. 컨텍스트가 이미 6개 이상이라면 이 선택은 모듈 20개
   가까이를 뜻하므로 이득이 확실할 때만 고른다.
5. 어디에도 걸리지 않으면 → `single-module`(컨텍스트당 모듈 하나)로 시작하고 아래 승격 신호를
   지켜본다.

### 승격·강등 신호

**single-module → multi-module** (하나라도 해당하면 검토)

- 컨텍스트 간 참조 금지 위반이 리뷰에서 반복해 잡힌다 → 패키지 경계로는 실수를 못 막는다.
- 클린 빌드가 5분을 넘는데 변경은 한 컨텍스트에 국한된다 → 증분 빌드 이득이 분할 비용을 넘었다.
- 두 번째 팀이 들어온다.

**multi-module → single-module** (과분할 신호)

- 모듈 수가 컨텍스트 수의 4배를 넘고, 그 대부분이 소스 파일 5개 미만이다.
- 기능 하나를 추가할 때마다 모듈 4개의 빌드 스크립트를 함께 고친다.

### 분류·스타일과의 관계

모듈 구성은 [[domain-classification]]의 분류나 스타일과 **직교한다.** core라서 multi-module이
되는 것이 아니고, layered-simple이라서 single-module이 되는 것도 아니다. 분류는 "얼마나 정교하게
모델링할 것인가", 모듈 구성은 "빌드·배포·소유를 어디서 자를 것인가"다.

## 규칙

### R1. 선언 요건

- `multi-module`·`single-module`: 컨텍스트 섹션에 모듈 표가 필수다(모듈 표가 없으면 sync가
  대조할 대상도, scaffold가 생성할 위치도 없다). 각 행의 `레이어` 값은 그 컨텍스트 스타일이
  선언한 레이어 이름이거나 `all`이어야 한다. multi-module에서 모듈 표가 없으면 파서가 오류로
  거부한다.
- `app-embedded`: 소속 프로젝트에 `### 애플리케이션` 표와 `### 패키지 규약` 표가 필수이며,
  컨텍스트에 모듈 표를 두면 오류다. 셋 다 파서가 검사한다.
- 같은 프로젝트의 app-embedded 컨텍스트들은 하나의 패키지 규약을 공유하므로 **같은 스타일이어야
  한다**(파서가 검사한다). 규약 표의 레이어 이름도 그 스타일의 레이어 이름과 일치해야 한다.
- 한 프로젝트 안에서 컨텍스트마다 다른 모듈 구성을 쓰는 것은 허용된다(레거시 컨텍스트만
  app-embedded로 남기는 등).

### R2. 공용 모듈 역할 4종과 방향 규칙

`### 공용 모듈` 표의 `역할` 칸에 쓸 수 있는 값은 넷뿐이다.

| 역할 | 담는 것 | 도메인 레이어에서 import |
|---|---|---|
| `shared-kernel` | 컨텍스트들이 **같은 뜻으로** 공유하는 도메인 개념(공용 식별자, Money, 공용 열거 — [[value-objects]]) | **허용 — 유일하게** |
| `infrastructure` | DB·메시징·캐시 등 기술 기반 | 금지(domain-pure 스타일의 domain 레이어) |
| `client` | 외부 시스템 호출 클라이언트 | 금지(위와 같음) |
| `support` | 로깅·측정 등 횡단 지원 | 금지(위와 같음) |

방향 규칙 — 모두 `forbid-import` 인스턴스로 fitness가 생성한다.

1. **공용 모듈은 어떤 애플리케이션·컨텍스트 코드에도 의존할 수 없다.** 역할 공통이며 예외 없다.
2. **애플리케이션 봉쇄**: 앱은 `포함 컨텍스트`로 선언된 컨텍스트의 코드만 참조한다(`all` 허용).
   반대로 컨텍스트·공용 코드는 앱 코드를 참조할 수 없다 — 조립은 앱에서만 일어난다.
   **앱 → 앱 의존도 금지한다.** 앱 B가 앱 A를 참조하면 A가 실행 단위이면서 동시에 라이브러리가
   되어 "조립은 앱에서만"이라는 전제가 깨진다. 공유가 필요하면 공유 대상을 앱이 아니라 비실행
   모듈로 내린다.
3. `shared-kernel` 외 세 역할은 domain-pure 컨텍스트의 domain 레이어에서 금지된다(기존 도메인
   순수성 규칙에 자연히 포함된다).

**shared-kernel 경고**: 여기 있는 코드는 모든 컨텍스트가 함께 소유하므로 변경 비용이 가장 비싸다.
타입을 하나 넣기 전에 [[bounded-contexts]]의 H1(언어 경계)을 적용한다 — 두 컨텍스트에서 **같은
뜻**이면 shared-kernel, 이름만 같고 라이프사이클이 다르면 각 컨텍스트에 하나씩 둔다. 이 판단을
건너뛰면 shared-kernel이 서서히 `common`이 된다.

### R3. 리뷰 체크리스트

- [ ] 모듈 표의 경로가 디스크에 없는가? → 오류가 아니다. 설계 선행 상태이며 scaffold의 입력이다.
- [ ] 공용 모듈에 특정 컨텍스트에서만 쓰이는 타입이 있는가? → 그 컨텍스트로 옮긴다.
- [ ] `support`나 `infrastructure` 모듈에 계산·판정 같은 도메인 규칙이 들어 있는가? → 역할
      오분류다. 도메인 규칙은 컨텍스트 안에 있어야 한다.
- [ ] app-embedded에서 앱마다 같은 컨텍스트의 도메인 코드가 복사되어 있는가? → 공유가 아니라
      복제다. **앱들이 함께 의존하는 비실행 모듈로 내린다.** 한 앱에 몰아넣고 다른 앱이 그 앱을
      참조하게 만들지 않는다(R2-2, 앱 → 앱 의존 금지).
- [ ] 모듈 이름이 레이어명만인가(`domain`, `api`)? → 컨텍스트 접두사를 붙인다(`claim-domain`).
      Gradle 모듈 이름은 저장소 전역에서 유일해야 한다.
- [ ] 컨텍스트를 하나 추가할 때 손대야 하는 파일이 몇 개인가? 10개를 넘으면 형태가 과하다.

## 사례

### 올바른 선언 — 세 형태

```markdown
## 컨텍스트: claim              (multi-module)
- 모듈 구성: multi-module
| 모듈 | 경로 | 레이어 |
|---|---|---|
| claim-domain | claim/domain | domain |
| claim-application | claim/application | application |
| claim-adapter-in | claim/adapter-in | adapter |
| claim-adapter-out | claim/adapter-out | adapter |

## 컨텍스트: admin              (single-module)
- 모듈 구성: single-module
| 모듈 | 경로 | 레이어 |
|---|---|---|
| admin | admin | all |

## 컨텍스트: brawlstars         (app-embedded — 모듈 표 없음)
- 프로젝트: imstargg-backend
- 모듈 구성: app-embedded
```

`adapter-in`과 `adapter-out`이 같은 레이어 `adapter`이므로 정규화 결과는 패턴 하나
(`com.acme.claim.adapter..`)로 합쳐진다. 모듈을 몇 개로 쪼갰는지는 규칙에 영향을 주지 않는다.

### 안티패턴 — 컨텍스트 없이 레이어만 모듈로 쪼개기

```
backend/
├── domain/          ← 모든 컨텍스트의 도메인이 여기 다 있다
├── application/
└── web/
```

레이어 경계는 생겼지만 컨텍스트 경계가 사라졌다. 정규화 결과가 `com.acme.domain..` 하나뿐이라
**컨텍스트 A의 도메인이 컨텍스트 B의 도메인을 부르는 것을 금지하는 규칙을 생성할 방법이 없다.**
컨텍스트 간 참조 금지는 이 플러그인이 선언에서 자동 생성하는 핵심 규칙인데, 이 배치에서는 그
규칙이 항상 0건을 검사하고 조용히 통과한다. 레이어보다 컨텍스트가 먼저 나뉘어야 한다.
