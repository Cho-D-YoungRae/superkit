## 개념

모든 아키텍처 규칙은 최종적으로 **패키지 패턴** 위에서 판정된다. Konsist·ArchUnit이 그 단위로
동작하고, 파서의 정규화 결과도 `(컨텍스트, 레이어, 패키지 패턴)`이다. 그래서 패키지 이름은 취향
문제가 아니라 **강제 가능성의 문제**다.

여기서 오는 가장 위험한 실패 모드를 먼저 적는다.

> 패턴이 실제 코드와 어긋나면 규칙은 오류를 내지 않는다. **0개 파일을 검사하고 통과한다.**
> 규칙이 지켜지는 것과 규칙이 아무것도 보고 있지 않은 것은 리포트에서 똑같이 보인다.

### 기본 관례

모듈 표가 있는 형태(`multi-module`·`single-module`)에서 패키지 규약 표가 없으면 아래 관례가
적용된다.

| 상황 | 패턴 |
|---|---|
| 일반 레이어 | `{기본 패키지}.{컨텍스트}.{레이어}..` |
| 레이어가 `all` | `{기본 패키지}.{컨텍스트}..` |

기본 패키지 `com.acme`, 컨텍스트 `claim`이면 `com.acme.claim.domain..`,
`com.acme.claim.application..`, `com.acme.claim.adapter..`가 된다.

- 패턴은 항상 `..`로 끝난다 — 그 패키지와 모든 하위 패키지를 뜻한다.
- 같은 레이어를 가진 모듈이 여럿이어도(`claim-adapter-in`, `claim-adapter-out`) 패턴은 레이어당
  하나로 합쳐진다.
- **강제의 기준은 디렉터리가 아니라 패키지다.** 모듈 디렉터리가 `claim/adapter-in`이든
  `claim/adapter/in`이든, 그 안의 코드가 `com.acme.claim.adapter..` 아래 있기만 하면 같은 규칙이
  적용된다.

## 적용 기준

### 기본 관례로 충분한 경우

기본 패키지 바로 아래에 컨텍스트가 오고, 그 아래 레이어가 오고, 레이어 이름이 패키지 세그먼트
이름과 같다면 규약 표를 쓰지 않는다. **표현 가능한 것을 굳이 표로 다시 적으면 같은 사실이 두 곳에
적히고, 둘은 언젠가 어긋난다.**

### 패키지 규약 표가 필요한 경우

아래 중 하나라도 해당하면 `### 패키지 규약` 표를 쓴다. (app-embedded 컨텍스트가 있으면 무조건
필수다.)

- [ ] 레이어가 컨텍스트보다 **위**에 온다 — `com.acme.domain.claim..` 형태.
- [ ] 레이어 이름과 패키지 세그먼트가 다르다 — 레이어는 `presentation`인데 패키지는 `web`.
- [ ] 기본 패키지와 컨텍스트 사이에 중간 세그먼트가 있다 — `com.imstargg.core.domain...`.
- [ ] 어떤 레이어가 컨텍스트로 나뉘지 않는다 — 앱 단위로만 존재하는 presentation 등.

규약 표가 존재하면 **모든 실현 형태에서 기본 관례를 덮는다.**

### 표 작성 규칙

```markdown
### 패키지 규약
| 레이어 | 패턴 |
|---|---|
| domain | com.imstargg.core.domain.{컨텍스트}.. |
| application | com.imstargg.core.application.{컨텍스트}.. |
| presentation | com.imstargg.{앱}.. |
```

| 변수 | 치환 규칙 |
|---|---|
| `{컨텍스트}` | 컨텍스트 이름 그대로. 패턴에 없으면 그 레이어는 **컨텍스트로 분할되지 않는다**(정규화 결과의 컨텍스트가 `*`) |
| `{앱}` | 애플리케이션 이름의 하이픈을 점으로 치환한 값. `core-api` → `core.api`. 패키지 세그먼트에 하이픈을 쓸 수 없기 때문이다. 애플리케이션 표의 모든 앱에 대해 전개된다 |

레이어 **아래**에 무엇이 더 있든 규약 표는 손대지 않는다. 패턴이 `..`로 끝나므로 하위 패키지는
자동으로 포함된다 — `패턴: cqrs`가 선언돼 생기는 `command`·`query` 하위 패키지도 마찬가지다
([[cqrs]]). 규약 표에 적는 것은 **레이어까지**다.

위 표의 정규화 결과(앱이 core-api·core-admin·core-batch·core-worker, 컨텍스트가 brawlstars일 때):

| 컨텍스트 | 레이어 | 패턴 |
|---|---|---|
| brawlstars | domain | `com.imstargg.core.domain.brawlstars..` |
| brawlstars | application | `com.imstargg.core.application.brawlstars..` |
| `*` | presentation | `com.imstargg.core.api..` (앱마다 하나씩, 총 4개) |

### 명명 규칙

- 소문자만. 하이픈·언더스코어 금지, 숫자로 시작 금지. 두 단어는 붙여 쓴다(`brawlstars`,
  `orderitem`). 붙여 쓰면 읽기 어려운 이름이 계속 나온다면 도메인 용어를 다시 찾을 신호다.
- **컨텍스트 패키지 세그먼트는 `ARCHITECTURE.md`의 컨텍스트 이름과 글자 그대로 같아야 한다.**
  다르면 정규화 패턴이 실재하지 않는 패키지를 가리키고, 그 컨텍스트의 규칙 전부가 0건을 검사한다.
- 단수/복수는 하나로 고정한다. 권장은 단수(`order`, `claim`) — 컨텍스트는 개념이지 컬렉션이
  아니다. 이미 복수를 쓰고 있다면 바꾸기보다 일관성을 지킨다. 이름 변경은 패턴·fitness·baseline을
  한꺼번에 흔든다.
- 컨텍스트·레이어 자리에 넣지 않는 것:
  - 기술·프레임워크 이름(`jpa`, `redis`, `kafka`) — 어댑터 **안쪽**의 세부 패키지로는
    정상이다([[persistence]]).
  - 조직·팀 이름, 버전·날짜.
  - `common`, `util`, `misc`, `etc`, `base` — 소유자와 경계를 지우는 이름이다.

**`common`이 필요하다고 느낄 때의 판정**: 거기 넣으려던 타입은 셋 중 하나다.

1. 두 컨텍스트에서 **같은 뜻**이다 → `shared-kernel` 역할의 공용 모듈로([[module-composition]]).
2. 사실 한 컨텍스트에서만 쓰인다 → 그 컨텍스트 안으로.
3. 도메인과 무관한 기술 유틸이다 → `support` 역할의 공용 모듈로.

이 셋 밖은 없다. 어디에도 안 맞는다고 느껴지면 대개 1번인데 "같은 뜻"인지 검증하지 않은
경우다([[bounded-contexts]] H1).

## 규칙

### R1. 패턴 문법

- 패턴은 반드시 `..`로 끝난다.
- 변수는 `{컨텍스트}`와 `{앱}` 둘뿐이다. 다른 이름의 변수는 없다.
- 패턴에 하이픈을 직접 쓰지 않는다. `{앱}` 치환이 하이픈을 점으로 바꾸는 이유가 그것이다.
- 레이어 이름은 그 컨텍스트 스타일이 선언한 레이어 이름과 정확히 일치해야 한다. **이 일치는
  `resolve_rules`가 스타일 문서를 읽어 검사한다** — 어긋난 이름은 오류로 보고되므로 R2와 같은
  결과(그 레이어의 규칙이 통째로 사라짐)로 조용히 새지 않는다.

### R2. 규약 표는 선언한 레이어만 만든다

규약 표에 적히지 않은 레이어는 **패턴이 생성되지 않고, 따라서 그 레이어에 걸린 규칙이 전부
사라진다.** 오류로 잡히지 않으므로 스타일이 선언한 레이어를 빠짐없이 적는다. 이것이 규약 표에서
가장 흔한 사고다.

### R3. `{컨텍스트}` 없는 패턴은 경계를 여는 선언이다

`{컨텍스트}`가 없는 패턴의 정규화 결과는 컨텍스트 `*`가 되고, 그 레이어에는 컨텍스트 간 참조
금지가 적용되지 않는다. presentation처럼 실제로 앱 단위인 레이어에서는 의도된 선택이지만,
domain·application에서 실수로 `{컨텍스트}`를 빠뜨리면 그 순간 도메인 경계가 통째로 무력화된다.

### R4. 리뷰 체크리스트

- [ ] 규약 표가 스타일이 선언한 레이어를 **전부** 덮는가?
- [ ] 각 패턴이 실제 소스에서 파일을 하나 이상 잡는가? 검증법: 패턴의 점을 슬래시로 바꿔
      디렉터리 존재를 확인한다(`com.acme.claim.domain..` → `**/com/acme/claim/domain`).
      **패턴 오타는 실패가 아니라 "위반 0건"으로 보이므로 이 확인이 유일한 방어선이다.**
- [ ] `{컨텍스트}`가 없는 패턴이 하나라도 있다면, 그것이 의도한 비분할 레이어인가?
- [ ] 컨텍스트 이름과 패키지 세그먼트가 글자 그대로 같은가?
- [ ] 이번에 추가한 패키지가 어떤 패턴에도 걸리지 않는가? → 규칙 사각지대다. 규약을 넓히거나
      코드를 패턴 안으로 옮긴다.
- [ ] 컨텍스트·레이어 세그먼트에 `common`·`util`이 있는가? → 위 3분기 판정을 수행한다.
- [ ] 단수/복수가 컨텍스트마다 섞여 있는가?

## 사례

### 올바른 예 1 — 기본 관례로 충분한 경우

```markdown
## 프로젝트: backend
- 기본 패키지: com.acme

## 컨텍스트: claim
- 모듈 구성: multi-module
- 스타일: hexagonal
```

규약 표 없음 → `com.acme.claim.domain..`, `com.acme.claim.application..`,
`com.acme.claim.adapter..`. 소스 트리는 `claim/domain/src/main/kotlin/com/acme/claim/domain/`.

### 올바른 예 2 — 규약이 필요한 경우

레이어가 컨텍스트보다 위에 오고 presentation은 앱 단위인 구조:

```markdown
### 패키지 규약
| 레이어 | 패턴 |
|---|---|
| domain | com.imstargg.core.domain.{컨텍스트}.. |
| application | com.imstargg.core.application.{컨텍스트}.. |
| presentation | com.imstargg.{앱}.. |
```

`presentation`에 `{컨텍스트}`가 없는 것은 의도다 — 컨트롤러는 앱마다 있고 컨텍스트로 나뉘지
않는다. 반면 `domain`에서 같은 실수를 하면 도메인 경계가 사라진다.

### 안티패턴 1 — 조용히 통과하는 오타

```markdown
| domain | com.acme.claim.domian.. |     ← domain 오타
```

fitness가 생성되고, 테스트가 돌고, 초록불이 켜진다. 검사한 파일은 0개다. 컨텍스트의 도메인
순수성 규칙은 6개월 동안 아무것도 막지 못했고, 아무도 모른다.

### 안티패턴 2 — 컨텍스트 이름과 패키지 세그먼트 불일치

```markdown
## 컨텍스트: claim
```
```kotlin
package com.acme.claims.domain   // 컨텍스트는 claim, 패키지는 claims
```

기본 관례가 만드는 패턴은 `com.acme.claim.domain..`이므로 실제 코드를 한 줄도 잡지 못한다.
컨텍스트 이름을 `claims`로 바꾸거나 패키지를 `claim`으로 바꾸거나 — 둘 중 하나를 반드시 해야
하고, 세 번째 선택지는 없다.
