## 개념

바운디드 컨텍스트는 **하나의 모델이 일관되게 통하는 범위**다. 그 안에서는 한 단어가 한 뜻이고,
한 규칙이 예외 없이 성립한다. 밖으로 나가면 같은 단어라도 뜻이 달라질 수 있다.

경계는 코드에서 발견되는 것이 아니라 **그어지는 것**이다. 그리고 그으면 비용이 든다 — 변환 코드,
호출 왕복, 최종 일관성. 그러므로 "여기 경계가 있다"가 아니라 **"여기에 경계를 긋는 값이 있는가"**를
묻는다.

> **구현 상태**: 아래의 "fitness가 생성한다"는 이제 사실이다. 다만 **생성까지가 이 플러그인의
> 몫이고 실행은 대상 프로젝트의 빌드가 한다** — 생성된 테스트를 돌리지 않으면 선언한 경계는
> 여전히 아무것도 막지 않는다.

이 플러그인에서 경계는 선언되어야 존재한다. `ARCHITECTURE.md`의 `## 컨텍스트: <name>` 섹션이
없으면 그 경계는 없는 것이고, 선언된 순간부터 컨텍스트 간 직접 참조는 기본 금지가 되어
fitness가 이를 강제한다([[context-mapping]]).

## 적용 기준

경계 후보를 찾을 때 아래 네 질문을 순서대로 던진다. 각 질문에는 답이 어느 쪽을 가리키는지를
정하는 판정선이 붙어 있다.

### H1. 언어 경계 — 같은 단어를 서로 다른 뜻으로 쓰는가

**질문**: 회의에서 이 단어가 나왔을 때 "어느 쪽 ○○요?"라고 되물어야 하는가.

**판정선**: 두 의미의 차이가 **필드 구성의 차이**뿐이면 같은 컨텍스트의 서로 다른 뷰다.
두 의미가 **서로 다른 상태 전이(라이프사이클)를 갖는다면 서로 다른 컨텍스트**다.

> 커머스의 '주문'. 판매 쪽 주문은 `장바구니확정 → 결제완료 → 취소`를 오간다. 물류 쪽 주문은
> `접수 → 피킹 → 포장 → 출고`를 오간다. 같은 주문번호를 공유하지만 상태 기계가 다르다 →
> 두 컨텍스트. 반대로 "관리자 화면에서는 주문에 담당자 메모가 더 보인다"는 필드 차이일 뿐이므로
> 경계가 아니다.

라이프사이클을 판정선으로 삼는 이유: 상태 전이가 다르면 불변식도 다르고, 불변식이 다르면 한
모델로 둘 다 만족시킬 수 없다.

### H2. 팀·소유권 경계 — 이 변경을 누가 승인하는가

**질문**: 이 영역을 바꾸는 PR을 누가 승인해야 하는가. 항상 두 사람(두 팀)의 승인이 필요한가.

**판정선**: **한 컨텍스트에는 승인자가 한 팀이어야 한다.** 한 배포에 늘 두 팀의 승인이 필요하다면
경계가 그 사이를 지나가야 한다. 반대로 한 팀이 컨텍스트 셋을 소유하는 것은 문제가 아니다 —
경계는 팀보다 잘게 그을 수 있고, 그 반대만 안 된다.

> 정산 로직 변경은 재무팀 승인이 필요하고 주문 화면 변경은 프로덕트팀이 승인한다. 두 코드가 한
> 모듈에 있으면 모든 배포가 두 팀 일정에 묶인다 → 정산과 주문은 다른 컨텍스트.

### H3. 트랜잭션 일관성 경계 — 지금 맞아야 하는가, 잠시 뒤 맞아도 되는가

**질문**: 이 두 데이터가 몇 초 동안 어긋나 있으면 **누가 무엇을 잘못하는가**.

**판정선**: 구체적인 피해자와 잘못된 행동이 나오면 즉시 일관성이 필요하고, 그 둘은 같은 컨텍스트
안에 있어야 한다(나아가 같은 애그리거트 후보다 — [[aggregates]]). "그냥 찜찜하다"만 나오면
최종 일관성으로 충분하므로 경계를 그어도 된다.

> 재고 차감과 주문 확정이 몇 초 어긋나면 → 초과 판매가 발생하고 고객에게 취소를 통보해야 한다.
> 피해자와 행동이 명확하다 → 같은 컨텍스트.
> 주문 확정과 포인트 적립이 몇 초 어긋나면 → 아무도 아무것도 잘못하지 않는다 → 경계를 그어도 된다.

### H4. 데이터 소유 경계 — 이 테이블에 누가 쓰는가

**질문**: 이 테이블에 write 하는 코드가 몇 군데인가. 컬럼을 하나 추가할 때 누구에게 물어봐야 하는가.

**판정선**: **한 테이블의 write 주체는 정확히 하나의 컨텍스트여야 한다.** 둘 이상이면 선택지는
두 개뿐이다 — (a) 경계를 다시 긋는다, (b) 한쪽을 read-only로 만들고 [[context-mapping]]의 관계로
선언한다. "둘 다 쓰되 조심한다"는 선택지가 아니다. 그것은 경계가 없다는 뜻이다.

> `user` 테이블에 인증 컨텍스트와 프로필 컨텍스트가 모두 write 한다. 해법은 컬럼 소유를 나눠
> 테이블을 분리하거나, 프로필이 인증에 `customer-supplier`로 변경을 요청하는 것이다.

### 휴리스틱이 서로 어긋날 때

우선순위: **H1 언어 > H4 데이터 소유 > H3 트랜잭션 > H2 팀**.

팀이 가장 뒤인 이유는 팀이 가장 자주 바뀌기 때문이다. 조직 개편마다 아키텍처가 흔들리면 안 된다.
다만 H1과 H2가 어긋난다면(도메인 경계와 팀 경계가 다르다) 그것은 무시할 신호가 아니라 조직과
도메인이 어긋나 있다는 관측이다 — 경계는 H1대로 긋고, 그 사실을 ADR에 기록한다.

**순위가 이긴 뒤에는 진 쪽의 요구를 반드시 해소한다.** 특히 가장 흔한 충돌인 H1 vs H3(라이프
사이클은 다른데 즉시 일관성이 필요하다)에서, 순위만 적용하고 멈추면 경계는 그어졌는데 일관성
요구는 갈 곳이 없어진다. 셋 중 하나를 **고르고 ADR에 남긴다** — 고르지 않으면 다음 사람이
"그냥 한 트랜잭션으로 묶자"로 되돌린다.

| 해소 방식 | 무엇을 하는가 | 고르는 조건 |
|---|---|---|
| 동기 호출 + 계약 | 경계는 긋되 한쪽이 상대의 동기 API로 그 순간 값을 확인한다. 일관성 창이 밀리초로 줄어든다 | **읽어서 확인만** 하면 되고 두 쪽을 함께 쓰지는 않을 때 |
| saga | 두 컨텍스트를 순서대로 진행시키되 각 단계가 자기 트랜잭션을 갖는다 | 두 쪽 모두 **써야 하고**, 중간 실패에 명확한 역연산이 있을 때 |
| 보상 | 낙관적으로 진행하고 어긋나면 사후 정정한다 | 어긋남이 드물고 정정(환불·취소 통보)이 업무적으로 수용 가능할 때 |

saga·보상은 경계를 넘는 이벤트로 구현되므로 발행 신뢰성이 곧 일관성이 된다([[domain-events]],
[[outbox]]). 그리고 이 선택을 기록해 두면 아래 R2의 "경계를 넘는 트랜잭션" 항목이 걸렸을 때
**무엇으로 고쳐야 하는지가 이미 정해져 있다** — H3으로 되돌아가지 않는다. 순위는 이미
결정됐고, 되돌아가면 무한 루프다.

### 경계를 긋지 않는 경우

- 컨텍스트 안에 애그리거트가 하나뿐이고 CRUD만 있다면 경계를 만들지 않는다. 그것은 컨텍스트가
  아니라 다른 컨텍스트의 일부다.
- "나중에 커질 것 같아서" 긋지 않는다. 경계는 나중에 그을 수 있고(패키지 → 모듈), 잘못 그은
  경계를 지우는 것이 훨씬 비싸다.
- 화면·API·배치 같은 **전달 채널**로 나누지 않는다. 그것은 레이어이지 컨텍스트가 아니다.
- 네 질문 중 **어느 것에도** 답할 수 없다면 경계를 그을 정보가 없는 것이다. 억지로 긋지 말고
  [[event-storming]] 세션으로 도메인 이벤트를 먼저 나열한 뒤 다시 온다.

## 규칙

### R1. 선언되지 않은 경계는 없는 경계다

경계 결정은 `ARCHITECTURE.md`의 `## 컨텍스트: <name>` 섹션으로만 존재한다. 코드에 패키지를
갈라 놓고 선언하지 않으면 강제되지 않고, 다음 세션의 Claude는 그 패키지 분리를 우연으로 취급한다.

선언의 부작용을 알고 선언한다: 선언된 순간부터 그 컨텍스트와 다른 컨텍스트 사이의 직접 참조는
기본 금지가 되고, 허용하려면 `### 관계` 표에 줄을 추가해야 한다(`forbid-import` 인스턴스를
fitness가 생성한다).

### R2. 경계가 잘못 그어졌다는 신호 — 리뷰 체크리스트

각 항목은 예/아니오로 답할 수 있고, 예가 나오면 지정된 조치를 검토한다.

- [ ] **왕복**: 하나의 유스케이스를 처리하는 데 컨텍스트 경계를 3회 이상 넘나드는가?
      → 경계가 유스케이스를 가로지르고 있다. 경계를 옮기거나 두 컨텍스트를 병합한다.
- [ ] **공유 테이블**: 두 컨텍스트가 같은 테이블에 write 하는가(근사 검사: 같은 엔티티 타입을 두
      컨텍스트의 저장소가 다루는가)? → H4의 두 선택지 중 하나를 택한다.
- [ ] **동반 변경**: 최근 20개 커밋 중 두 컨텍스트를 함께 건드린 커밋이 절반 이상인가?
      → 병합 후보. evolve의 신호 수집이 이 수치를 낸다.
- [ ] **경계를 넘는 트랜잭션**: 하나의 트랜잭션 안에서 두 컨텍스트의 저장소를 호출하는가?
      → **항상 위반이다.** 세 해소 방식 중 어느 것도 이 코드 모양을 낳지 않는다 — 동기 호출은
      상대의 저장소를 부르지 않고, saga·보상은 단계마다 자기 트랜잭션을 갖는다. 갈리는 것은
      조치뿐이다: 해소 방식이 ADR에 기록돼 있으면 **코드를 그 방식대로 고친다**(무엇으로 고칠지는
      이미 정해져 있다). 기록이 없으면 위 세 방식 중 하나를 골라 기록한 뒤 그대로 고친다.
      **H3으로 되돌아가지 않는다** — 경계는 이미 결정됐다.
- [ ] **이름이 도메인 용어가 아님**: 컨텍스트 이름이 `common`, `기타`, `backend-core`,
      팀 이름인가? → 도메인 이름을 못 붙이는 경계는 도메인 경계가 아니다.
- [ ] **과분할**: 컨텍스트에 애그리거트가 하나뿐이고 도메인 규칙 없이 CRUD만 있는가?
      → 인접 컨텍스트로 흡수한다.
- [ ] **용어 누출**: 컨텍스트 A의 도메인 문서에 컨텍스트 B의 필드명·타입명이 등장하는가?
      → 관계 유형이 `conformist`인데 그렇게 선언되지 않았거나, `acl`이 이름뿐이다.

### R3. 기계 검증으로 넘어가는 것과 넘어가지 않는 것

경계의 **타당성**은 기계가 판정할 수 없다(위 체크리스트가 사람의 몫인 이유다). 기계가 판정하는
것은 선언된 경계가 **지켜지는가**뿐이며, 그 경로는 정규화된 패키지 패턴 위의 `forbid-import`
인스턴스 하나다. 그래서 경계 선언은 [[package-conventions]]의 패턴이 실제 코드에 정확히 대응할
때만 의미가 있다 — 패턴이 어긋나면 위반이 0건으로 조용히 통과한다.

## 사례

### 올바른 분리 — 커머스의 '주문'

분리 전: 컨텍스트 `order` 하나. `Order` 엔티티에 결제 상태와 출고 상태가 함께 있고, 상태 필드가
두 개인 이유를 아무도 설명하지 못한다.

분리 후:

```markdown
## 컨텍스트: sales
- 분류: core
- 스타일: hexagonal

### 관계
| 상대 | 유형 | 계약 |
|---|---|---|
| fulfillment | customer-supplier | order-confirmed-v1 |

## 컨텍스트: fulfillment
- 분류: supporting
- 스타일: layered-domain
```

`sales`의 주문 확정이 이벤트가 되고, `fulfillment`는 그 이벤트로 출고 지시서를 만든다. 두
라이프사이클이 각자의 모델에서 독립적으로 돈다.

### 안티패턴 1 — 테이블 목록을 컨텍스트로 착각

```markdown
## 컨텍스트: user
## 컨텍스트: product
## 컨텍스트: order
```

엔티티 하나에 컨텍스트 하나를 붙인 것이다. H1(라이프사이클), H3(일관성 요구), H4(소유) 어느
질문에도 답한 적이 없다. 증상은 즉시 나타난다 — 어떤 유스케이스든 세 컨텍스트를 다 호출한다.

### 안티패턴 2 — 전달 채널을 컨텍스트로

```markdown
## 컨텍스트: api
## 컨텍스트: batch
## 컨텍스트: admin
```

이것은 레이어이거나 애플리케이션(실행 단위)이다. 실행 단위는 컨텍스트가 아니라
[[module-composition]]의 `### 애플리케이션` 표로 선언한다. 같은 도메인 규칙이 세 곳에 복제되는
결과가 나온다.

## 관련 문서

- [[domain-classification]] — 경계를 그은 다음 각 컨텍스트를 분류한다
- [[context-mapping]] — 경계를 넘는 연결을 선언하는 방법. 선언되지 않은 쌍은 참조 금지다
- [[module-composition]] — 그은 경계를 모듈·패키지로 실현하는 세 가지 형태
- [[package-conventions]] — 경계가 강제되려면 패키지 패턴이 코드와 정확히 맞아야 한다
- [[event-storming]] — 경계 질문에 답할 정보 자체가 없을 때 먼저 하는 세션
- [[aggregates]] — 경계 안에서 트랜잭션 단위를 다시 나누는 다음 단계
