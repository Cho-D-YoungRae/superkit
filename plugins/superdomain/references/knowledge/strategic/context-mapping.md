## 개념

컨텍스트를 그으면 그 사이에 연결이 생긴다. 관계 유형은 그 연결에서 **누가 누구에게 맞추는가**를
정하는 이름이다. 6종뿐이고, 이것이 `### 관계` 표의 `유형` 칸에 쓸 수 있는 값의 전부다.

```markdown
### 관계
| 상대 | 유형 | 계약 |
|---|---|---|
| policy | customer-supplier | claim-events-v1 |
```

> **구현 상태**: 아래의 "금지가 강제된다"는 이제 사실이다 — `scripts/check_imports.py`가 선언에서
> 파생되는 `derived.context-isolation`을 실측으로 검사한다. 다만 그 검사는 `.kt`·`.java`의
> `package` 선언과 `import` 목록만 보므로, import 없이 쓰는 완전 수식 이름과 같은 패키지 안의
> 참조는 보지 못한다. **위반 0건은 경계 누수 0건이 아니다.**

**이 표는 문서가 아니라 allow-list다.** 표에 선언되지 않은 컨텍스트 쌍은 서로를 참조할 수 없고,
`check_imports.py`가 그 금지를 위반으로 보고한다. 그러므로 표에서 한 줄이 빠지면 문서가
불완전해지는 것이 아니라 **검사가 빨간불을 낸다**. 반대로 필요 없어진 줄을 지우는 것은 문서 정리가
아니라 새 금지를 세우는 행위다.

`계약` 칸에는 그 연결이 실제로 통과하는 물건의 이름을 쓴다 — 이벤트 스키마 이름, 공개 API 이름,
ACL 패키지·클래스 이름. 칸이 비어 있으면 "연결은 있는데 무엇을 통해 연결되는지 모른다"는 뜻이고,
그 상태에서는 관계가 검증될 수 없다.

## 적용 기준

### 언제 관계를 선언하는가

- 두 컨텍스트 사이에 **코드 참조 · 런타임 호출 · 이벤트 소비** 중 하나라도 있으면 선언한다.
- 같은 DB 테이블을 한쪽이 읽기만 하더라도 관계다. 데이터 결합도 결합이다.
- **한 쌍에 한 줄이다.** v1에서 허용 단위는 **쌍**이고 방향을 구분하지 않는다 — 한 줄을 쓰면 그
  쌍의 참조가 양방향으로 열린다. 방향이 한쪽뿐이어도 줄 수는 그대로 하나다.
- 같은 쌍에 두 번째 줄을 쓰지 않는다. 두 줄일 때 어느 유형이 이기는지는 정의되어 있지 않다.

### 언제 선언하지 않는가

- 지금 연결이 없는 쌍은 쓰지 않는다. **"나중에 쓸지도 모르니까" 미리 선언하는 것은 스스로 세운
  금지선을 지우는 일이다.** 필요해질 때 한 줄 추가하는 비용은 1분이다.
- **같은 컨텍스트 안의 코드 배치는 여기에 쓰지 않는다.** 관계 표는 컨텍스트 **사이**의 것이고,
  경계 안을 어떻게 나누는지는 이 플러그인이 정하지 않는다.
- 선언되지 않은 것과의 관계는 쓸 수 없다. `상대` 칸은 `DOMAIN.md`에 선언된 컨텍스트 이름이어야
  하고, 아니면 파서가 깨진 참조로 거부한다. 여러 컨텍스트가 함께 쓰는 개념을 관계로 표현하고
  싶으면 그 개념을 **컨텍스트로 선언한 뒤** 쌍을 긋는다.

### 유형 선택 결정 절차

<!-- 0단계 수정 시 재진술 동반 스위프: 표기 규칙 문단·acl 행·open-host 행(grep "0단계") -->

0. **이 쌍의 어느 쪽에라도 상대 모델을 번역해 들이는 경계가 있는가?** 있으면 `acl` — 이하 단계로
   가지 않는다. 번역 계층을 두는 쌍은 partnership의 정의(서로 맞춰 바꿈)와 양립하지 않는다.
   - **경계가 아직 없더라도 `core`가 하류인 쌍은 `acl`이 기본값이다.** 번역 경계를 두는 것이
     기본 결정이므로 여기서 `acl`로 적고, 그 경계를 세우기로 한 근거를 ADR로 남긴다. 두지 않기로
     결정했다면 그것이야말로 ADR이 필요한 예외다 — 표를 관측이 아니라 결정으로 채운다.
1. **이 쌍에서 한쪽이 상대의 모델을 바꿀 수 있는가?**
   - 바꿀 수 있고, 두 쪽이 함께 릴리스된다 → `partnership`
   - 바꿔 달라고 요청할 수 있고, 상대가 그 요청을 백로그로 받는다 → `customer-supplier`
   - 바꿀 수 없다 → 2로
2. **(0단계를 통과했으니 번역하지 않는 쌍이고, `core`가 하류라면 ADR로 기본값을 물린 쌍이다)
   들이는 그 모델이 무엇인가?** 상대가 무엇을
   내주는지만 보면 답이 나온다:
   - 상대의 **내부 모델**이다(그쪽 엔티티·테이블 모양이 그대로 보인다) → `conformist`
   - 상대가 **교환용으로 따로 공개하고 버전 관리하는 스키마**다(Avro·IDL·이벤트 스키마, 공개
     REST/OpenAPI) → 그 스키마를 상대가 **서비스로 호스트하는지**로 마지막으로 가른다:
     - 호스트한다(공개 API 뒤에서 그 스키마를 내준다) → `open-host` — 아래 표기 규칙대로
       `계약` 칸에 버전 포함 스키마 이름을 적는다
     - **호스트 서비스가 없다**(버전 관리되는 스트림 구독, 발행된 스펙 문서 등 스키마 자체가
       계약의 전부다) → `published-language`
3. **(공급자 쪽에서 볼 때) 소비자가 몇인가?** 0~2단계가 값을 냈으면 **그 값이 이긴다** — 이
   단계는 앞 단계가 값을 내지 못한 쌍에만 적용한다(번역이 있는 쌍은 0단계에서 끝났고, `core`가
   하류인 쌍도 기본값이 거기서 정해진다).
   - 1~2 → `customer-supplier`
   - 3 이상 → `open-host`. 계약을 버전 관리하며 배포한다면 바로 아래 표기 규칙을 따른다

**두 유형이 동시에 성립할 때 표에 적는 법**: `유형` 칸은 6종 중 **하나**만 받고 한 쌍에 한 줄만
쓰므로, "함께 쓴다"를 그대로 옮길 수 없다. **`open-host`와 `published-language`가 동시에 성립할
때의 규칙은 하나다** — **`유형`은 `open-host`로 두고 `계약` 칸에 버전을 포함한 스키마 이름을
적는다**(`claim-events-v1`). 계약 칸에 버전이 있다는 사실이 published-language의 존재를 나타낸다.
`유형`을 `published-language`로 쓰는 경우는 호스트 서비스 없이 **교환용 스키마만이 계약의 전부이고
그것을 번역 없이 받을 때**다(2단계) — 버전 관리되는 이벤트 스트림을 그대로 소비하는 관계가
전형이다([[domain-events]]). 같은 스트림·공개 API라도 이 쌍의 어느 쪽이든 상대 모델을 번역해
들이면 그것은 `acl`이고 `core`가 하류일 때도 기본값이 `acl`이며(둘 다 0단계), 스키마 이름은
`계약` 칸에 남는다.

**0단계가 `core` 하류에 `acl`을 기본값으로 두는 이유**: core 모델이 남의 모델 모양에 맞춰지는
순간 차별화 자산이 상대의 스키마에 종속된다([[domain-classification]]의 "기본값이 순수 도메인
모델인 근거" 절과 같은 논리다). 기본값을 물리려면 그 종속을 감수할 이유를 ADR에 적어야 한다는
뜻이지, 물릴 수 없다는 뜻이 아니다.

### 6종 유형

| 유형 | 뜻 | 고르는 시점 | 잘못될 때의 모습 |
|---|---|---|---|
| `partnership` | 두 컨텍스트가 함께 성공하거나 함께 실패한다. 서로 맞춰 바꾸고 릴리스를 조율한다 | 같은 목표·같은 릴리스 열차. 한쪽만 배포하면 깨진다. 번역 계층이 보이면 이 유형이 아니다 — 0단계(`core`가 하류일 때도 기본값은 `acl`) | 매 스프린트 조율 비용이 나고 어느 쪽도 독립 배포를 못 한다 → 사실은 한 컨텍스트 |
| `customer-supplier` | 하류가 요구를 내고 상류가 백로그로 받는다. 우선순위는 상류에 있다 | 상류에 하류를 고려할 유인이 있을 때. 번역 계층이 보이면 이 유형이 아니다 — 0단계(`core`가 하류일 때도 기본값은 `acl`). 공급자 쪽 소비자가 3 이상이면 `open-host`를 검토한다 | 상류가 요구를 계속 미룬다 → 실질은 conformist인데 문서만 남는다 |
| `conformist` | 하류가 상류의 **내부 모델**을 변환 없이 그대로 수용한다 | 상류가 안정적이고 그 모델이 하류에게 나쁘지 않으며 번역 비용을 아끼고 싶을 때 — 단, `core`가 하류면 기본값이 `acl`이다(0단계). 받는 것이 교환용으로 따로 공개된 버전 스키마라면 이 유형이 아니다 — 호스트 서비스가 없으면 `published-language`, 공개 서비스 뒤라면 `open-host`(위 표기 규칙) | 상류의 개념이 하류의 도메인 용어를 밀어낸다. 도메인 문서에 상류 필드명이 등장하기 시작한다 |
| `acl` | 하류가 번역 계층을 두고 상류 모델을 자기 모델로 바꾼다 | 이 쌍의 어느 쪽이든 상대 모델을 번역해 들이는 모든 경우 — 전형은 상류가 레거시·외부 벤더거나 모델이 근본적으로 다를 때. 경계가 아직 없어도 `core`가 하류면 이 값이 기본값이다(둘 다 0단계) | ACL이 얇은 DTO 매퍼에 그치고 상류 타입이 ACL 밖으로 흘러나온다 |
| `open-host` | 상류가 다수 하류를 위한 공개 프로토콜을 제공한다 | 하류가 3개 이상이라 각각에 맞춰 줄 수 없을 때 — 단, 이 쌍의 어느 쪽에라도 번역 경계가 있으면 이 값이 아니라 `acl`이다(0단계 — `core`가 하류일 때도 기본값은 `acl`). 하류로서 상대가 호스트하는 공개 프로토콜을 번역 없이 소비할 때도 이 값이다(위 표기 규칙) | 하류마다 특수 엔드포인트가 늘어난다 → open-host가 아니라 customer-supplier N개 |
| `published-language` | 관계의 계약이 버전 관리되는 공유 스키마(이벤트 스키마·IDL)로 존재한다 | 호스트 서비스 없이 **교환용 스키마를 번역 없이 그대로 수용**할 때(Avro·IDL 스트림 구독 등) — 단, `core`가 하류면 기본값이 `acl`이다(0단계). 번역하면 `acl`, 상대의 내부 모델을 그대로 받으면 `conformist`, 공개 서비스와 짝이면 `open-host`(위 표기 규칙) | 특정 소비자만 쓰는 필드가 스키마에 쌓이거나, 버전 규칙 없이 필드를 지운다 |

`partnership`은 가장 비싼 관계다. 두 컨텍스트의 독립성을 포기하는 대가로 조율을 얻으므로, 6개월
이상 유지되고 있다면 병합이 더 싸지 않은지 검토한다.

## 규칙

### R1. 관계 표는 allow-list이며 정규 값은 6종뿐이다

- 유형 칸에 쓸 수 있는 값: `partnership`, `customer-supplier`, `conformist`, `acl`, `open-host`,
  `published-language`. 그 외 값은 `parse_domain.py`가 라인 번호와 함께 거부한다.
- 표에 없는 컨텍스트 쌍의 직접 참조는 금지되고, 그 금지는 정규화된 패키지 패턴 위에서
  `check_imports.py`가 `derived.context-isolation` 위반으로 보고한다.
- **유형은 허용 방향을 바꾸지 않는다.** 열리는 단위는 쌍이고 방향 구분이 없으므로, 유형은
  설계 의도의 기록이지 강제의 입력이 아니다(정본
  `references/governance/domain-template.md` §5.1).
  "`acl`이니까 상류→하류는 막혀 있겠지"라고 가정한 리뷰는 틀린 판정을 낸다 — 원치 않는 역방향
  참조도 함께 열려 있으며, 그것을 조이려면 템플릿 버전을 올려야 한다.
- **줄의 소속 섹션은 v1에서 규정하지 않는다.** 같은 쌍을 상류 컨텍스트 섹션에 적든 하류 컨텍스트
  섹션에 적든 같은 선언이다 — 파서의 허용 단위가 쌍이므로 두 관례를 동일하게 처리한다(정본
  `domain-template.md` §5.1). **유형은 쌍의 성질이지 작성자 관점의 성질이 아니므로**, 어느 쪽에서 쌍을 선언하든
  결정 절차 0단계가 먼저 반대편의 번역 경계까지 묻는다 — 있으면 `acl`이고, `core`가 하류면
  기본값이 `acl`이다.

### R2. 계약 칸은 실재하는 이름이어야 한다

`계약`에 적은 이름을 코드에서 검색했을 때 나와야 한다 — 이벤트 클래스, API 경로 상수, ACL
패키지. 검색해서 안 나오는 이름은 관계가 문서에만 있다는 뜻이다.

### R3. 리뷰 체크리스트

- [ ] 이번 변경에서 새로 생긴 컨텍스트 간 import가 관계 표의 어떤 줄에 대응하는가? 대응하는 줄이
      없으면 줄을 추가하거나(그리고 유형을 고르거나) import를 되돌린다.
- [ ] `계약` 칸의 이름을 코드에서 grep 하면 나오는가?
- [ ] `customer-supplier`로 선언된 관계에서 최근 2개 분기에 하류의 요구가 상류에 실제 반영된
      적이 있는가? 없으면 **번역 계층이 실재하면 `acl`로, `core`가 하류면 기본값인 `acl`로,
      그 밖에는 `conformist`로 정정한다**(0단계)
      — 지켜지지 않는 관계 선언은 거짓말이고, 거짓말은 다음 설계 결정을 오염시킨다.
- [ ] `acl`로 선언된 관계에서 상류 타입이 ACL 패키지 밖에 등장하는가? 등장하면 ACL이 이름뿐이다.
      번역기가 도메인 타입을 반환하도록 고치거나 유형을 `conformist`로 정정한다 — **기계는
      이것을 잡지 못한다.** 쌍이 열려 있으면 격리 검사는 통과하므로 리뷰의 판정 대상이다.
- [ ] core 컨텍스트가 `conformist`로 무언가를 수용하고 있는가? 근거 ADR이 있는가?
- [ ] `partnership`이 6개월 이상 유지되고 있는가? → 병합 또는 계약화(유형을
      `customer-supplier`로 낮추고 `계약` 칸에 버전 스키마 이름을 넣기) 검토.
- [ ] 한 컨텍스트의 관계 줄이 5개를 넘는가? → 허브가 됐다. 경계 자체를 다시 본다
      ([[bounded-contexts]]).

## 사례

### 올바른 선언 — 청구 시스템

```markdown
## 컨텍스트: claim
- 분류: core

### 관계
| 상대 | 유형 | 계약 |
|---|---|---|
| policy | customer-supplier | policy-snapshot-v2 |
| billing | acl | BillingTranslator |
```

`policy`는 사내 팀이 소유하고 요구를 받아 준다 → customer-supplier. `billing`은 10년 된 레거시라
모델이 우리와 전혀 다르다 → acl, 계약 칸에 번역기 이름을 적어 검증 가능하게 만든다.

### 안티패턴 — 이름만 ACL

```kotlin
// com.acme.claim.adapter.out.billing.BillingTranslator   (ACL 이라고 부르는 곳)
class BillingTranslator(private val client: LegacyBillingClient) {
    fun fetch(id: String): LegacyInvoiceDto = client.getInvoice(id)   // 그대로 반환
}

// com.acme.claim.application.ClaimSettlementService
import com.acme.legacy.billing.LegacyInvoiceDto      // 상류 타입이 ACL 밖으로 나왔다
class ClaimSettlementService(private val translator: BillingTranslator) {
    fun settle(id: String) {
        val invoice = translator.fetch(id)
        if (invoice.stat_cd == "03") { /* 레거시 코드값이 도메인 로직에 박힌다 */ }
    }
}
```

번역기가 번역을 하지 않으므로 `acl`이 아니라 사실상 `conformist`다. 둘 중 하나를 해야 한다 —
번역기가 도메인 타입을 반환하게 고치거나, 관계 유형을 `conformist`로 정정하고 그 대가(레거시
코드값이 도메인에 들어옴)를 ADR로 받아들이거나. 문서와 코드 중 하나는 바뀌어야 한다.
