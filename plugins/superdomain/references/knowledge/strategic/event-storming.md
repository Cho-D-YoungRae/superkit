## 개념

이벤트 스토밍은 **업무에서 실제로 일어난 일을 과거형으로 늘어놓아 모델을 발견하는 기법**이다.
명사(테이블·엔티티)에서 시작하면 나오지 않는 것 — 순서, 분기, 결정을 내리는 주체, 그리고 사람마다
다르게 알고 있는 지점 — 이 사실을 시간순으로 늘어놓는 순간 드러난다.

원래는 벽과 색 스티커로 한다. 텍스트 채팅에는 **벽이 없다** — 방금 모은 것이 스크롤 밖으로 나가면
없는 것과 같다. 그래서 이 규약의 절반은 벽을 대신하는 규율이다: **모델은 매 단계 끝에 그 단계의
목록 전체를 다시 출력한다.** 이 한 가지를 빼면 나머지 절차는 채팅에서 동작하지 않는다. 스티커 색은
아래 표기로 대체한다.

| 워크숍의 색 | 이 규약의 표기 | 무엇인가 |
|---|---|---|
| 주황 — 도메인 이벤트 | `E<번호>` + 과거형 문장 | 이미 일어난 업무 사실. 거부할 수 없다 |
| 파랑 — 커맨드 | S3 표의 `커맨드:` | 거절될 수 있는 요청 |
| 노랑 — 액터 | S3 표의 액터 칸 | 그 요청을 내는 사람·외부 시스템 |
| 보라 — 정책 | S3 표의 `정책:` | "…하면 **항상** …한다" — 사람의 결정이 끼지 않는 연결 |
| 분홍 — 핫스팟 | `❓H<번호>` | 답이 갈리거나, 아무도 모르거나, 아프다고 말한 지점 — **사람의 불일치**다. evolve가 git 이력에서 뽑는 변경 빈도 핫스팟과 이름만 같다 |

**세션의 산출물은 전부 후보다.** 스토밍은 애그리거트를 확정하지 않고, 경계를 선언하지 않으며,
불변식을 `confirmed`로 올리지 않는다. 하는 일은 그 결정들이 필요로 하는 재료를 모아 각각의
주인에게 넘기는 것이다(R3).

> **구현 상태**: 이 규약을 실행하는 주체(`/superarchitect:model`의 스토밍 모드)와 결과를 받는
> domain 문서 표준은 **이 Phase에서 함께 도착한다.** 둘 다 착지하면 이 블록을 지운다.

## 적용 기준

model의 기본 세션 유형은 인터뷰다. 스토밍은 인터뷰가 헛도는 상황에서만 고른다.

### 스토밍으로 시작하는 신호 — 둘 이상이면 제안한다

- **경계를 못 고른다.** "서로 다른 용어를 쓰는 업무 영역이 있나요?"에 답이 나오지 않는다 —
  [[bounded-contexts]]의 네 질문 중 **어느 것에도** 답할 수 없는 상태가 이것이다.
- **명사부터 나온다.** 도메인을 설명해 달라고 하면 "회원·상품·주문 테이블이 있고요"로 시작하고,
  "그다음에 무슨 일이 일어나나요"라고 물으면 말이 끊긴다.
- **사람마다 다른 시스템을 설명한다.** 같은 업무를 두 사람이 다르게 말하고 결론이 나지 않는다.
- **한 건이 여러 손을 거친다.** 시작부터 끝까지 담당 부서·시스템이 세 번 이상 바뀐다.

### 스토밍이 과한 경우

- **컨텍스트 하나 안의 규칙 하나를 파는 것이 목적일 때.** 스토밍은 넓게 훑고 얕게 판다. 불변식은
  인터뷰가 캔다 — "이 규칙은 ~한 경우에도 성립합니까"를 S1~S2에서 물으면 발산이 그 자리에서 멈춘다.
- **domain 문서에 이미 애그리거트와 불변식이 쌓여 있을 때.** 다시 열면 있는 것을 다시 나열한다.
  신규 업무 흐름이 들어올 때 **그 흐름 하나만** 범위로 잡아 다시 연다.
- **도메인을 아는 사람이 자리에 없을 때.** 스토밍은 사람의 기억에서 사실을 꺼내는 기법이다. 개발자와
  코드만 있으면 산출물은 추측 목록이고 코드 관측보다 정확하지 않다 — 이때는 코드를 읽는다.
- **목적이 저장 방식 결정일 때.** 산출물이 이벤트 목록이라는 이유로 [[event-sourcing]]을 고르지
  않는다 — 발견 기법과 저장 방식은 서로 독립이다.

### 세션 범위와 중단 조건

- **한 세션은 업무 흐름 하나(end-to-end 시나리오 1개)만 다룬다.** 전사 스토밍을 채팅으로 하지
  않는다. 이벤트가 40개를 넘어서면 목록이 벽 노릇을 못 하므로 흐름을 잘라 다음 세션으로 넘긴다.
- **S5까지 못 가도 세션은 성공이다.** S3에서 멈추고 나머지를 열린 질문으로 넘기는 편이, 자리에 없는
  사람의 답을 지어내며 끝까지 가는 것보다 낫다.
- **애그리거트 후보가 하나도 안 나오면 그것이 결과다.** 상태 변화가 필드 갱신뿐인 흐름은
  [[layered-simple]] 후보이지 실패한 세션이 아니다.

## 진행 규약

다섯 단계를 순서대로 밟는다. 각 단계 안에서 **촉진 질문 → 답 → 산출 목록 갱신 → 재출력**을 "다음
단계 조건"이 충족될 때까지 반복하고, 그때 다음 단계를 제안한다 — 한 단계가 한 번의 문답이 아니다.
**재출력은 지금 단계의 산출 형식 하나뿐이다**(앞 단계 표를 다시 붙이지 않는다). 질문 문형은 그대로 쓴다.

### S1. 이벤트 수집 — 판단 없이 모은다

**촉진 질문**
- "이 업무가 시작해서 끝날 때까지 **일어난 일**을 순서 상관없이 말해 주세요. `~되었다`로 끝나는
  문장이면 됩니다."
- "그러고 나서 무슨 일이 일어나나요?"(앞으로 밀기) / "그 일이 일어나려면 그 전에 무엇이 일어나
  있어야 하나요?"(뒤로 당기기)
- "잘 안 풀리는 경우에는 무슨 일이 일어나나요?" — **끊기 전에 반드시 한 번 던진다.** 예외 흐름은
  묻지 않으면 나오지 않고, 나중에 경계와 불변식이 거기서 나온다.

**산출 형식** — 번호 붙인 과거형 문장 목록.

```
E1. 주문이 접수되었다
E2. 결제가 승인되었다
E3. 재고가 차감되었다
E9. 결제가 거절되었다          (예외 흐름)
```

번호는 **수집 순서이지 시간 순서가 아니다.** 정렬은 S2에서 하고, 이미 불린 번호는 다시 매기지 않는다.

**다음 단계 조건**: 사용자가 "더 없다"고 말할 때. 모델이 충분하다고 판단해 끊지 않는다.

### S2. 타임라인 정렬 — 순서와 분기를 세운다

**촉진 질문**
- "E3과 E7 중 어느 것이 먼저입니까? 아니면 동시에 일어날 수 있나요?"
- "여기서 흐름이 갈라지나요? 어떤 조건에서요?"
- "이 사이에 시간이 오래 걸리는 구간이 있나요?" — 시간 간격이 큰 지점은 S5의 경계 후보 1순위다.

**산출 형식** — 정렬된 목록. 분기와 대기는 줄에 표시한다.

```
1. E1 주문이 접수되었다
2. E2 결제가 승인되었다     ─┬ 한도 초과 → E9 결제가 거절되었다
3. E3 재고가 차감되었다
   ⏳ 며칠 (출고 준비)
4. E7 상품이 출고되었다
```

**mermaid는 여기서 그리지 않는다.** 순서가 흔들리는 동안 다시 그리는 비용이 크다 — 흐름도는 확정된
뒤 domain 문서로 옮길 때 그린다(R3).

**다음 단계 조건**: 모든 이벤트가 자리를 잡거나 "모르겠다"로 표시되었을 때. 모르는 것은 핫스팟
후보로 남기고 넘어간다.

### S3. 커맨드·액터 연결 — 무엇이 이 일을 일으켰나

이벤트를 일으키는 것은 셋뿐이다: **사람의 결정(커맨드+액터), 다른 이벤트(정책), 시간(스케줄).**

**촉진 질문**
- "E2가 일어나게 만든 것은 무엇입니까 — 누가 무엇을 했나요?"
- "E1이 일어나면 E2는 **항상** 자동으로 일어납니까, 아니면 누가 결정합니까?" — 항상이면 정책이다.
- "그 요청이 거절될 수 있나요? 어떤 조건에서요?" — **거절 조건은 불변식 후보다.** 여기서 캐지
  말고 목록에만 적어 둔다. 파고들면 인터뷰가 되고 스토밍이 끝난다.

**산출 형식** — 표 하나와 별도 후보 목록 하나.

```
| 이벤트 | 원인 | 액터·트리거 |
|---|---|---|
| E1 주문이 접수되었다 | 커맨드: 주문하기 | 고객 |
| E2 결제가 승인되었다 | 커맨드: 결제요청 | 결제사(외부) |
| E3 재고가 차감되었다 | 정책: E2 직후 자동 | — |
| E7 상품이 출고되었다 | 스케줄: 매일 14시 마감 | 배치 |

거절 조건 후보: 재고보다 많은 수량은 주문할 수 없다 / 한도 초과 결제는 승인되지 않는다
```

**다음 단계 조건**: 모든 이벤트에 원인이 붙었을 때. "그냥 그렇게 된다"는 정책인지 되묻고, 아니면
핫스팟으로 올린다.

### S4. 애그리거트 후보로 묶기 — 무엇의 상태가 바뀌었나

**촉진 질문**
- "E1·E3·E7은 **무엇**의 상태가 바뀐 겁니까? 그것을 업무에서 뭐라고 부르나요?"
- "이 둘은 **동시에** 맞아야 합니까, 잠깐 어긋나도 됩니까?" ([[bounded-contexts]] H3)
- "그 요청을 거절하려면 무엇을 알고 있어야 하나요?" — 후보가 들고 있어야 할 상태가 나온다.

**산출 형식** — 후보 이름별로 그 후보가 겪는 이벤트와 받는 커맨드를 묶는다. `E번호`는 S1 문장을
가리키는 참조이므로 여기서는 축약해 적는다 — R2의 문장 규율은 S1 목록에 적용된다.

```
[주문]  E1 접수됨 → E2 결제승인됨 → E4 확정됨 → E8 취소됨
        커맨드: 주문하기 · 취소하기
[재고]  E3 차감됨 → E6 복구됨
        커맨드: 차감 · 복구
```

이름은 **사용자가 쓰는 업무 용어 그대로** 적는다(영어 클래스명으로 옮기지 않는다 — 용어 등록은
superglossery의 몫이다). 크기 판단도 하지 않는다 — [[aggregates]]의 절차는 불변식이 문장으로 있어야
돌아가고, 스토밍은 후보까지다.

**다음 단계 조건**: 모든 이벤트가 정확히 하나의 후보에 배정되었을 때. 두 후보에 걸치는 이벤트는
핫스팟이다(경계가 그 사이를 지날 수 있다).

### S5. 경계·핫스팟 표시 — 선을 그을 자리와 모르는 것

**촉진 질문**
- "이 두 묶음에서 같은 단어가 서로 다른 뜻으로 쓰이나요?" ([[bounded-contexts]] H1)
- "이 지점을 넘어가면 담당하는 팀이 바뀌나요?" (H2)
- "여기서 몇 초 어긋나면 **누가 무엇을 잘못하게** 되나요?" (H3)

**산출 형식**(경계 후보 1순위는 S2의 ⏳ 긴 대기 구간과 S3의 액터 전환 지점이다)

```
경계 후보 A: [주문 · 결제] | [출고 · 재고]
  근거: ⏳ 며칠 간격 · 액터 전환(고객 → 창고) · '주문'의 뜻이 다름(판매 건 / 출고 지시)
  넘는 이벤트: E4 주문이 확정되었다
핫스팟:
  ❓H1 확정 후 취소가 가능한가 — 담당자마다 답이 다름 (E8)
  ❓H2 재고 차감이 결제 전인가 후인가 — 실제 운영과 문서가 다름 (E3)
```

**다음 단계 조건**: 없다. 세션은 여기서 끝나고, 결론이 나지 않은 것은 전부 열린 질문으로 간다.

## 규칙

### R1. 한 번에 한 단계 — 진행 규율 체크리스트

- [ ] 단계를 앞질러 가지 않았는가? S1에서 애그리거트 이름이 이미 보여도 S4까지 말하지 않는다.
      먼저 이름을 주면 사용자가 그 이름에 맞춰 나머지를 말한다 — 발견이 아니라 확인이 된다.
- [ ] 한 번에 하나만 물었는가? 질문 두 개를 붙이면 뒤의 것만 답이 온다.
- [ ] 그 단계의 목록 **전체**를 매 회전 끝에 다시 출력했는가? 채팅에는 벽이 없다.
- [ ] 사용자가 말하지 않은 항목을 확정 목록에 넣지 않았는가? 모델의 제안은 적극적으로 하되
      `E9? 결제가 거절되었다 (제안 — 맞습니까?)`처럼 **제안 표기**로 넣고, 확인 전에는 세지 않는다.
- [ ] 사용자의 문장을 다듬어 바꿔 적지 않았는가? 다듬기는 제안으로만 하고 목록에는 사용자 어휘를
      남긴다 — 용어가 바뀌면 그 자리에서 도메인이 바뀐다.

### R2. 이벤트 문장 규율 — 과거형, 주어 금지

- **과거형 문장으로만 쓴다.** `결제 승인`(명사구) ✗, `결제를 승인한다`(현재형) ✗, `결제가 승인되었다` ✓.
- **주어를 넣지 않는다.** `관리자가 청구를 승인했다` ✗ → `청구가 승인되었다` ✓. 행위자는 S3의 액터
  칸으로 간다 — 문장에 박으면 액터가 바뀔 때마다 같은 사실이 중복 등재된다(관리자/자동/배치 승인).
- **명령형이 나오면 그것은 커맨드다.** 이벤트 목록에서 빼 S3 표로 옮긴다 — [[domain-events]] R3과
  같은 판정선이며, 실무에서 가장 자주 어겨지는 줄이다.
- **시스템 용어를 쓰지 않는다.** `row가 insert되었다`, `API가 호출되었다`, `큐에 적재되었다`는
  구현이다. 되묻는다 — "그때 **업무에서는** 무슨 일이 일어난 겁니까?"
- **CRUD 이름을 쓰지 않는다.** `주문이 수정되었다`는 무엇이 왜 바뀌었는지 말하지 못한다
  ([[domain-events]]의 "CRUD 감사 로그" 항목).

### R3. 결과를 넘기는 곳 — 스토밍이 직접 확정하지 않는다

| 스토밍 산출 | 넘기는 곳 | 넘길 때의 상태 |
|---|---|---|
| 거절 조건(S3) | domain 문서의 **불변식 표** | `proposed`. 문장 다듬기는 인터뷰의 일이고 `confirmed` 승격은 사용자 확인 후 |
| 애그리거트 후보(S4) | domain 문서의 **애그리거트 절** | 후보로만. 경계·크기 확정은 불변식이 모인 뒤 [[aggregates]] 절차로 |
| 이벤트 목록(S1~S2) | domain 문서의 **도메인 이벤트 절**(흐름 mermaid 병기) | 전부 옮기지 않는다 — [[domain-events]]의 4단계 거름망을 통과한 것만 |
| 경계 후보(S5) | ARCHITECTURE.md의 컨텍스트 선언 | 곧바로 쓰지 않는다. [[bounded-contexts]]의 네 휴리스틱으로 다시 판정한 뒤 init·adr이 선언한다 |
| 경계를 넘는 이벤트(S5) | 컨텍스트 `### 관계` 표의 `계약` 칸 후보 | 경계가 선언된 뒤에만. 관계 유형은 [[context-mapping]]의 결정 절차로 고른다 |
| 핫스팟(S5) | domain 문서의 **열린 질문 절** | 그대로 옮긴다. 답을 지어내지 않는다 |

- **스토밍 세션은 ARCHITECTURE.md를 고치지 않는다.** 경계는 선언 행위로만 생기고, 선언되는 순간
  컨텍스트 간 직접 참조 금지가 함께 생긴다([[bounded-contexts]] R1). 스토밍은 후보와 근거만 만든다.
- `## 컨텍스트 맵` 구역은 **생성물**이다. 경계 후보를 그 구역에 손으로 적지 않는다 — 컨텍스트
  선언과 관계 표가 원본이고 맵은 거기서 나온다.
- 옮긴 뒤 무엇이 어디로 갔는지 되짚어 준다. 옮겨지지 않은 항목(거름망에 걸린 이벤트, 배정 못 한
  사실)은 **버렸다고 말하거나 열린 질문에 남긴다** — 조용히 사라지면 다음 세션에 다시 수집한다.

### R4. 세션 결과 리뷰 체크리스트

- [ ] 이벤트 목록에 명령형·명사구·시스템 용어가 남아 있거나, 문장에 주어가 박혀 있는가?
- [ ] 어느 애그리거트 후보에도 배정되지 않은 이벤트가 있는가? → 아직 모델링되지 않은 사실이다
      ([[domain-events]] 승격 경로 1번). 이벤트 타입을 만들 것이 아니라 후보를 다시 본다.
- [ ] 핫스팟이 0개인가? → 이견 없는 업무 흐름은 드물다. 한 사람의 설명만 받아 적었을 수 있다.
- [ ] 예외 흐름 이벤트가 하나도 없는가? → S1의 마지막 질문을 던지지 않은 것이다.
- [ ] 애그리거트 후보가 하나뿐이고 커맨드가 CRUD 3종뿐인가? → 독립 컨텍스트가 아닐 수 있다
      ([[bounded-contexts]]의 과분할 항목) 또는 [[layered-simple]] 후보다.
- [ ] 이벤트 목록이 그대로 클래스 목록이 되었는가? → 거름망을 건너뛴 것이다(R3).

## 사례

### 올바른 진행 — S1에서 S3으로 넘어가는 대목

```
모델   지금까지 모은 것을 다시 정리하면 이렇습니다.
       E1. 주문이 접수되었다   E2. 결제가 승인되었다
       E3. 재고가 차감되었다   E4. 상품이 출고되었다
       잘 안 풀리는 경우에는 무슨 일이 일어나나요?

사용자 아, 재고가 모자라면 출고가 보류돼요. 그리고 결제가 거절되기도 하고요.
모델   두 개를 제안 표기로 넣었습니다 — 맞으면 확정하겠습니다.
       E5? 출고가 보류되었다   E6? 결제가 거절되었다
사용자 맞아요. 더는 없습니다.        (…S2 정렬 후…)
모델   E3(재고가 차감되었다)이 일어나게 만든 것은 무엇입니까 — 누가 무엇을 했나요?
사용자 그건 자동이에요. 결제만 되면 바로 빠집니다.
모델   정책으로 적었습니다: "E2 직후 자동".
       그 차감이 거절될 수 있나요? 어떤 조건에서요?
사용자 재고보다 많이 주문하면 안 되죠. 그런데… 예약 판매는 재고가 없어도 받거든요.
모델   거절 조건 후보에 적고, 예약 판매 예외는 핫스팟으로 올립니다.
       ❓H2 예약 판매에서 재고 규칙이 어떻게 되는가 (E3)
       여기는 파고들지 않고 넘어가겠습니다 — 인터뷰 세션의 안건입니다.
```

예외 흐름을 묻고서야 E5·E6이 나온 것, 거절 조건이 나왔을 때 인터뷰로 새지 않고 목록에만 적은 것,
발견한 예외를 그 자리에서 결론짓지 않고 핫스팟으로 올린 것이 이 발췌의 핵심이다.

### 안티패턴 1 — 모델이 먼저 이름을 붙였다

```
사용자 주문이 들어오면 결제하고, 재고 빼고, 출고합니다.
모델   Order 애그리거트와 Inventory 애그리거트가 보이네요. Order의 상태 전이를 확인하면…
```

S1을 두 문장 만에 건너뛰고 S4의 결론을 먼저 냈다. 이후 사용자는 그 두 이름에 맞는 것만 말하게 되고,
세션은 모델이 이미 아는 구조를 확인받는 절차로 끝난다. 스토밍의 값은 **모델이 예상하지 못한 이벤트가
나오는 데** 있다 — 예약 판매·부분 출고·반품처럼 이름을 먼저 정하면 물을 생각조차 못 하는 것들이다.

### 안티패턴 2 — 시스템 흐름을 받아 적었다

```
E1. 주문 API가 호출되었다
E2. 주문 테이블에 row가 insert되었다
E3. 결제 서비스로 요청이 전송되었다
E4. 주문 상태가 PAID로 업데이트되었다
```

전부 구현 서술이라 업무 사실이 하나도 없다. 이 목록으로는 S4에서 애그리거트가 나오지 않는다 —
`row가 insert되었다`는 **무엇의** 상태 변화인지 말하지 못하기 때문이다. 되묻는다: "그때 업무에서는
무슨 일이 일어난 겁니까?" 답은 대개 한 문장이다 — "주문이 접수된 거죠."

## 관련 문서

- [[bounded-contexts]] — S5의 경계 후보를 실제 경계로 판정하는 네 휴리스틱. 그 네 질문에 아무 답도
  못 할 때 이 세션으로 온다
- [[aggregates]] — S4의 후보를 불변식으로 확정하는 다음 단계. 크기 판단은 그쪽 절차다
- [[domain-events]] — 과거형 문장을 이벤트 타입으로 승격시키는 4단계 거름망과 명명 규칙
- [[context-mapping]] — 경계를 넘는 이벤트가 관계 표의 `계약` 칸으로 등재되는 경로
- [[event-sourcing]] — 이벤트를 나열했다는 사실은 저장 방식의 근거가 되지 않는다
- [[layered-simple]] — 애그리거트 후보가 나오지 않는 흐름의 정상적인 착지점
