## 개념

대부분의 컨텍스트에는 불필요하다. 이 문서의 절반은 채택하지 않을 근거를 주기 위해 있고, 나머지
절반은 이미 채택한 컨텍스트를 판정하기 위해 있다.

이벤트 소싱은 **현재 상태를 저장하지 않고 상태 변화(이벤트)를 append-only로 저장하며, 현재
상태는 이벤트를 처음부터 접어(fold) 얻는** 영속 방식이다. 진실의 원천이 행이 아니라 이벤트 열이다.

| | 상태 저장(일반) | 이벤트 소싱 |
|---|---|---|
| 저장하는 것 | 현재 상태 한 벌 | 일어난 일의 전체 열 |
| 현재 상태 | 읽으면 나온다 | 리플레이로 계산한다 |
| 과거 상태 | 남아 있지 않다 | 이벤트 열을 잘라 계산한다 |
| 수정·삭제 | UPDATE·DELETE | **없다** — 보정도 새 이벤트다 |
| 조회 | 같은 테이블에서 | 프로젝션(리드 모델)에서만 |

**도메인 이벤트를 발행하는 것은 이벤트 소싱이 아니다.** 가장 흔한 혼동이다. 애그리거트가
`ClaimApproved`를 발행하고 [[outbox]]로 내보내면서도 상태는 여전히 테이블 한 행에 UPDATE로
저장하는 것이 정상이며, 그 컨텍스트는 이벤트 소싱이 아니다([[domain-events]]). 이벤트 소싱은
**이벤트가 저장의 유일한 형태**일 때를 말한다.

**되돌리기가 비대칭이다.** 상태 저장 → 이벤트 소싱은 설계 시점에 결정하면 되는 일이지만, 이벤트
소싱 → 상태 저장으로 내려오는 것은 이벤트 열을 최종 상태로 접어 넣고 그 위에 쌓인 프로젝션·리플레이
가정을 전부 걷어내는 작업이다. 그래서 기본값은 채택하지 않는 쪽이고, 채택은 근거 ADR을 요구한다.

## 적용 기준

### 0단계 — 더 싼 수단이 그 요구를 이미 만족하는가

요구를 한 줄로 적고 이 표에서 찾는다. **"추가로 주는 것: 없음"** 행에만 해당하면 채택하지 않는다.

| 실제 요구 | 더 싼 수단 | 이벤트 소싱이 추가로 주는 것 |
|---|---|---|
| 누가 언제 무엇을 바꿨는가 | 감사 테이블(변경 로그) | 없음 |
| 특정 필드의 변경 이력을 보여 준다 | 이력 테이블, DB의 시간 테이블 | 없음 |
| 다른 컨텍스트에 변경을 알린다 | [[domain-events]] + [[outbox]] | 없음 |
| 장애 시점 상태를 복구한다(운영) | 백업·시점 복구 | 없음 |
| 조회 부하를 쓰기와 분리한다 | [[cqrs]] L2·L3 | 없음 |
| **과거 시점 기준 재계산이 업무 기능이다** | — | 여기서부터 값이 있다 |
| **왜 그 상태가 되었는지(결정의 이력)가 필요하다** | — | 여기서부터 값이 있다 |

감사 요구의 열에 아홉은 첫 두 행이다. "감사 로그가 필요하다"는 이 패턴을 채택할 근거가 아니다.

### 채택을 정당화하는 조건

(a)~(c) 중 **하나 이상**이 참이고, 0단계에서 더 싼 수단이 없으며, (d)가 참일 때만 채택한다.

- **(a) 감사가 법·계약으로 강제되고, 필요한 것이 "상태의 이력"이 아니라 "결정의 이력"이다.**
  가르는 질문: 감사인이 "값이 A에서 B로 바뀌었다"로 만족하는가, "무엇 때문에 B가 되었는지"를
  요구하는가? 앞이면 감사 테이블이다.
- **(b) 시간 여행이 업무 기능이다.** 과거 시점의 상태로 **다시 계산해야** 하는 요구 — 사고 발생
  시점의 약관으로 보험금 재산정, 소급 적용된 요율로 정산 재실행. 과거를 **보여 주기만** 하는 것은
  이력 테이블로 충분하다.
- **(c) 이벤트가 곧 도메인이다.** 도메인 전문가가 상태가 아니라 사건 단위로 말하고, 현재 상태가
  사건들의 합계로 **정의되는** 영역 — 원장·거래·적립금·재고 이동. 잔액은 저장된 숫자가 아니라
  전표의 합이라고 말하는 곳이다.
- **(d) 팀이 운영 비용을 감당한다.** 아래 세 비용의 값을 실제로 적을 수 있다.

### 채택 전에 값을 적어 보는 비용 셋

숫자를 적지 못하는 항목이 하나라도 있으면 (d)는 거짓이다.

1. **스냅샷** — 애그리거트 하나에 쌓이는 이벤트 수의 평균과 **상한**이 얼마인가? 상한이 없는
   애그리거트(계좌·장바구니·구독)는 스냅샷 없이는 반드시 느려진다. 스냅샷 주기를 정하고, 스냅샷도
   버전을 가지며 스키마가 바뀌면 통째로 무효가 된다는 것을 계산에 넣는다.
2. **리플레이** — 프로젝션 하나를 처음부터 다시 만드는 데 몇 분이 걸리는가? 그동안 조회는 어떻게
   답하는가(구 프로젝션 유지 후 교체 / 조회 중단)? 이 시간은 이벤트가 쌓일수록 늘어난다.
3. **스키마 진화** — 3년 전에 쓴 v1 이벤트를 오늘 코드가 읽어야 한다. 이벤트 타입에 버전을 두고
   업캐스터를 유지하는 비용, 그리고 **잘못 설계한 이벤트를 지울 수 없다**는 사실을 받아들이는가?

### 고르지 않는 조건

- **감사 로그가 필요해서** → 감사 테이블. 0단계 표의 첫 행이다. 이 오해가 이 패턴의 최대 도입
  경로이자 최대 후회 경로다.
- **[[cqrs]]를 도입했으니 세트로** → 독립이다. CQRS는 이벤트 소싱을 요구하지 않는다.
- **이벤트 스토밍을 했으니까** → [[event-storming]]은 모델을 발견하는 기법이지 저장 방식 결정이
  아니다. 벽에 붙은 과거형 스티커는 이벤트 소싱의 근거가 아니다.
- **마이크로서비스라서 / 서비스 간 통신에 이벤트를 쓰니까** → 그것은 [[domain-events]] + [[outbox]]다.
  발행과 저장은 다른 문제다.
- **개인정보를 담는 컨텍스트이고 삭제 요구가 있다** → append-only와 정면으로 충돌한다. 잊힐 권리를
  이벤트 스토어에서 이행하려면 개인정보를 이벤트 밖 별도 저장소에 두고 키만 담거나 암호화 키를
  파기하는 방식이 필요하고, 그 설계와 검증 비용은 채택 결정을 뒤집을 만큼 크다. 값을 적어 보기
  전에는 채택하지 않는다.
- **CRUD·조회 위주 컨텍스트, `generic` 분류** → 검토 대상이 아니다([[domain-classification]]).
- **"나중에 감사가 필요해질 것 같아서"** → 세지 않는다. 상태 저장에서 감사 테이블을 나중에 붙이는
  것은 국소 작업이고, 이벤트 소싱을 나중에 걷어내는 것은 재작성이다.

### 부분 적용이 정답인 경우가 많다

이벤트 소싱은 **컨텍스트 단위가 아니라 애그리거트 단위**로 채택할 수 있다. 원장 하나만 이벤트
소싱이고 나머지는 상태 저장인 구성이 정상이며, 대개 그것이 맞는 답이다. `- 패턴: event-sourcing`을
선언할 때는 근거 절에 **어느 애그리거트인지**를 반드시 함께 적는다. 컨텍스트 전체를 이벤트 소싱으로
올리는 선택에는 (a)~(c)가 그 컨텍스트의 모든 애그리거트에 대해 참이라는 근거가 따로 필요하다.

## 규칙

채택한 컨텍스트에 적용하는 **리뷰 판정 도구**다 — 이 플러그인의 유일한 기계 강제 규칙
(`derived.context-isolation`)은 컨텍스트 사이의 참조만 보므로 아래를 아무것도 잡지 않는다.
R1~R5는 diff 위에서 판정할 수 있도록 적었다.

### R1. 저장된 이벤트는 수정·삭제되지 않는다

**어디를 보는가**: 이벤트 스토어 테이블을 대상으로 하는 코드와 마이그레이션 스크립트.

**위반 문형**: 이벤트 테이블에 대한 `UPDATE`·`DELETE`, JPA 엔티티의 setter·`merge`, 이벤트 행을
고치는 마이그레이션(`ALTER`로 값 치환), 이벤트 클래스의 `var` 필드.

**위반이 아닌 것**: 보존 기간이 지난 이벤트의 아카이브 이관(정책 문서가 있을 때), 스냅샷 삭제.

**보정은 새 이벤트로 한다.** 잘못 기록된 입금은 취소 이벤트를 덧붙여 상쇄한다 — 원래 이벤트를
고치면 그 이벤트를 이미 읽어 간 프로젝션·다운스트림과 진실이 갈라진다.

**보고**: `type=violation`, `severity=blocker`. 이 규칙이 깨지면 저장소가 더는 진실의 원천이 아니다.

### R2. 리플레이는 결정적이다

**어디를 보는가**: 이벤트를 만드는 코드(커맨드 처리)와 이벤트를 적용하는 코드(`apply`/`on`).

**위반 문형**

- (a) `apply`/`on` 함수 안에서 `Instant.now()`·`UUID.randomUUID()`·`Random`을 호출한다.
- (b) `apply`/`on` 함수가 리포지토리·외부 API·다른 애그리거트를 조회한다.
- (c) `apply`/`on` 함수가 예외를 던지거나 불변식을 검증한다 — 검증은 커맨드 처리에서 하고, 적용은
  이미 일어난 사실을 반영만 한다. 과거 이벤트가 오늘의 규칙으로 거부되면 애그리거트를 아예 적재할
  수 없게 된다.
- (d) 이벤트가 참조만 담고 값은 조회로 채운다(`productId`만 담고 가격은 리플레이 시점에 조회) —
  가격이 바뀌면 과거가 바뀐다.

**가르는 한 문장**: 같은 이벤트 열을 1년 뒤에 접어도 **같은 상태**가 나오는가? 아니면 위반이다.

**보고**: `type=violation`, `severity=blocker`((a)(b)(d)), `warn`((c)).

### R3. 스냅샷은 최적화일 뿐 진실이 아니다

**어디를 보는가**: 애그리거트 적재 경로.

**위반 문형**: 스냅샷이 없으면 적재가 실패한다, 스냅샷에만 있고 이벤트로는 복원되지 않는 필드가
있다, 스냅샷을 쓰기 경로의 진실로 삼아 이벤트 없이 스냅샷을 갱신한다.

**요구**: 스냅샷을 전부 지워도 리플레이만으로 같은 상태가 나와야 하고, 그것을 확인하는 테스트가
있어야 한다. 스냅샷에는 버전이 있고, 애그리거트 구조가 바뀌면 그 버전의 스냅샷은 무효로 취급해
다시 만든다.

**보고**: 스냅샷 없이 복원되지 않으면 `type=violation`, `severity=blocker`. 검증 테스트가 없으면
`type=missing`, `severity=warn`.

### R4. 이벤트에는 버전이 있고, 진화는 업캐스터로만 한다

**어디를 보는가**: 이벤트 타입 정의와 역직렬화 경로.

**위반 문형**: 이벤트 타입에 버전 표시가 없다, 기존 이벤트 타입에서 필드를 **제거**하거나 의미를
바꾼다, 새 필드를 기본값 없이 추가한다(과거 이벤트가 읽히지 않는다), 진화를 마이그레이션으로
처리한다(R1 위반이기도 하다).

**허용되는 진화**: 기본값이 있는 필드 추가, 새 버전 타입 추가 + 업캐스터로 구 버전을 신 버전으로
변환. 업캐스터는 이벤트 스토어 어댑터에 두고 도메인에서 보이지 않게 한다.

**보고**: `type=violation`, `severity=warn`. 필드 제거·의미 변경은 `blocker`.

### R5. 조회는 프로젝션에서만 한다

이벤트 소싱은 [[cqrs]] L2 이상을 사실상 강제한다 — 이벤트 열에는 조회할 수 있는 모양이 없기
때문이다.

**위반 문형**: 이벤트 스토어 테이블에 대고 업무 질의를 한다(이벤트 payload를 `LIKE`·JSON 질의로
검색), 애그리거트를 여러 개 적재해 목록을 만든다(리플레이 N번), 화면 조회가 애그리거트 적재를
거친다.

**보고**: `type=violation`, `severity=warn`.

### R6. 리뷰 체크리스트 (기계가 보지 않는 것)

- [ ] 채택 근거 ADR에 (a)~(c) 중 무엇이 참인지, 0단계 표의 더 싼 수단을 왜 배제했는지가 있는가?
- [ ] 근거 절에 **어느 애그리거트**를 이벤트 소싱하는지 적혀 있는가? 컨텍스트 전체라면 그 근거는?
- [ ] 이벤트 이름이 과거형이고 업무 언어인가(`ClaimApproved`)? 기술 언어(`ClaimUpdated`·
      `RowChanged`)면 결정의 이력이 아니라 상태 변경 로그를 이벤트라고 부른 것이다 — (a)의
      전제가 무너진다
- [ ] 이벤트에 개인정보가 들어 있는가? 삭제 요구가 오면 어떻게 이행하는지 문서에 있는가?
- [ ] 애그리거트당 이벤트 수 상한과 스냅샷 주기가 정해져 있는가?
- [ ] 프로젝션 전체 재구축 소요 시간을 최근에 **측정**했는가? 추정치는 답이 아니다
- [ ] 이벤트 소싱 애그리거트가 늘고 있는가? 처음 하나에서 멈추지 않았다면 (a)~(c)를 다시 센다

## 사례

### 올바른 예 — 이벤트가 곧 도메인인 애그리거트 (Kotlin)

```kotlin
// com.acme.ledger.domain — 이벤트는 불변, 과거형, 값을 그대로 담는다
sealed interface LedgerEvent
data class Deposited(val amount: Money, val occurredAt: Instant) : LedgerEvent
data class Withdrawn(val amount: Money, val occurredAt: Instant) : LedgerEvent
data class WithdrawalReversed(val of: EventId, val amount: Money, val occurredAt: Instant) : LedgerEvent

class LedgerAccount private constructor(val id: AccountId) {
    var balance: Money = Money.ZERO; private set

    // 적용은 검증하지 않는다 — 이미 일어난 사실이다 (R2 c)
    private fun apply(event: LedgerEvent) {
        balance = when (event) {
            is Deposited -> balance + event.amount
            is Withdrawn -> balance - event.amount
            is WithdrawalReversed -> balance + event.amount
        }
    }

    // 검증은 커맨드 처리에서 한다. 시각은 밖에서 주입받는다 (R2 a)
    fun withdraw(amount: Money, now: Instant): Withdrawn {
        require(balance >= amount) { "잔액 부족" }
        return Withdrawn(amount, now).also { apply(it) }
    }

    companion object {
        fun replay(id: AccountId, events: List<LedgerEvent>): LedgerAccount =
            LedgerAccount(id).apply { events.forEach(::apply) }   // 스냅샷 없이 복원된다 (R3)
    }
}
```

취소는 `Withdrawn`을 지우는 것이 아니라 `WithdrawalReversed`를 덧붙이는 것이다(R1). 잔액은 저장된
숫자가 아니라 전표의 합이며, 그것이 이 도메인의 원래 모습이다 — (c) 조건이 참인 자리다.

### 안티패턴 1 — 리플레이가 비결정적인 "이벤트"

```kotlin
data class ClaimUpdated(val claimId: ClaimId, val snapshot: ClaimRow)   // 상태 전체를 담았다

private fun apply(event: ClaimUpdated) {
    this.status = event.snapshot.status
    this.updatedAt = Instant.now()                       // R2 (a) 위반: 접을 때마다 값이 달라진다
    this.productPrice = priceApi.fetch(event.snapshot.productId)  // R2 (b)(d) 위반: 과거가 바뀐다
}
```

이름은 과거형이지만 내용은 상태 스냅샷이고(`ClaimUpdated`는 R6의 기술 언어 신호다), 접을 때마다
다른 상태가 나온다. 이 코드는 이벤트 소싱의 비용을 전부 치르면서 이익은 하나도 얻지 못한다 —
감사 테이블 한 장으로 대체 가능한 상태다.

### 안티패턴 2 — 저장된 이벤트를 고쳐 스키마를 진화시킨다

```sql
-- V12__fix_event_payload.sql
UPDATE ledger_event
   SET payload = jsonb_set(payload, '{amount}', to_jsonb((payload->>'amount')::numeric * 100))
 WHERE event_type = 'Withdrawn';   -- R1·R4 위반
```

원화 단위를 바꾸려고 과거를 다시 썼다. 이미 이 이벤트를 읽어 간 프로젝션과 다운스트림 컨텍스트는
옛 값을 갖고 있으므로 진실이 두 개가 되고, 어느 쪽이 맞는지 판정할 근거는 남아 있지 않다. 맞는
방법은 `WithdrawnV2`를 추가하고 업캐스터가 v1을 변환해 읽는 것뿐이다(R4).
