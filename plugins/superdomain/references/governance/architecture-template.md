# 결정 템플릿 (ARCHITECTURE.md) — 정본

구조 SSOT인 루트 `ARCHITECTURE.md`의 형식을 정의한다. 어떤 섹션·라벨·표가 존재해야 하는지, 파서가
무엇을 어떻게 읽는지, 선언이 패키지 패턴으로 어떻게 정규화되는지의 정본이다. 파서와 이 문서의 해석이
갈리면 **이 문서가 정본이고 파서가 고쳐져야 한다** — 그렇지 못한 지점은 §5.3에 전부 적어 두었다.

| 새 `ARCHITECTURE.md`를 처음부터 쓰기 | [§2 템플릿 스켈레톤](#2-템플릿-스켈레톤) |

## 1. 개요

**결정 템플릿이 곧 스키마다.** 별도의 yaml 설정 문법은 없다. 무엇을 결정해야 하는지는 템플릿의 필수
섹션·라벨·표가 알려주고, 결정이 비면 파서가 통과시키지 않는다. 스키마를 사람이 읽는 문서와 같은
파일에 두었기 때문에 "설정은 최신인데 문서는 옛날"이라는 상태가 구조적으로 생기지 않는다.

**템플릿 밖의 서술은 완전히 자유다.** 파서는 아는 섹션·라벨·표만 읽고 나머지는 전부 무시한다. 근거
문단, 회의 메모, 다이어그램, 링크 목록 — 무엇을 얼마나 쓰든 파싱 결과가 달라지지 않는다. 이것이 서로
다른 모양의 프로젝트가 하나의 형식을 공유할 수 있는 확장 지점이다. 대신 반대 방향의 대가가 있다:
**파서가 모르는 것은 조용히 무시된다.** 오타 난 라벨은 오류가 아니라 "없는 라벨"이 되므로, 선언을
고친 뒤에는 반드시 파서를 돌려 결과를 확인한다.

**구조의 진실은 루트 `ARCHITECTURE.md` 한 파일이다(SSOT).** 모노레포여도 하나다 — 컨텍스트는 도메인
개념이라 프로젝트 소속과 무관하고, 프로젝트를 넘는 관계도 한 문서에서만 표현할 수 있다.

**중간 캐시를 만들지 않는다.** json 미러 같은 파생 구조 파일은 존재하지 않는다. `check_imports.py`,
`collect_signals.py` 등 다른 스크립트는 `parse_architecture.py`의 파서 함수를 import해 그 자리에서
파싱한다. 수백 줄 마크다운 파싱은 밀리초이므로 캐시가 이득이 없고, 캐시가 없으면 **재생성 누락으로
인한 드리프트가 원천적으로 불가능**해진다. 캐시를 도입하자는 제안은 이 문장을 뒤집는 제안이다.

## 2. 템플릿 스켈레톤

아래 블록은 그대로 복사해 쓸 수 있고, 실제로 파서를 통과한다.

```markdown
# <프로젝트명> — Architecture
<!-- superarchitect:template v1 -->

## 프로젝트: backend
- 경로: backend                      (저장소 루트 기준 상대경로. 단일 레포는 ".". 미생성 경로 허용 — 설계 선행)
- 프로파일: kotlin-spring            (profiles/ 하위 디렉토리명)
- 기본 패키지: com.acme
- 아키텍처 테스트 위치: architecture-test/src/test/kotlin/arch   (프로젝트 경로 기준)

## 컨텍스트 맵
<!-- superarchitect:generated:context-map -->
<!-- /superarchitect:generated -->

## 컨텍스트: claim
- 프로젝트: backend                  (프로젝트가 1개뿐이면 생략 가능 — 파서가 유일 프로젝트로 귀속)
- 분류: core                         (core | supporting | generic)
- 스타일: hexagonal                  (프리셋 이름 또는 custom/<name>)
- 모듈 구성: multi-module            (multi-module | single-module | app-embedded)
- 패턴: cqrs, outbox                 (knowledge/patterns/ 문서 키)
- 규칙 예외: -hex.ports-owned-inside (ADR-0002)
- 이행: layered-simple → hexagonal   (점진 이행 중일 때만)

| 모듈 | 경로 | 레이어 |
|---|---|---|
| claim-domain | claim/domain | domain |
| claim-application | claim/application | application |
| claim-adapter-in | claim/adapter-in | adapter |
| claim-adapter-out | claim/adapter-out | adapter |

### 관계
| 상대 | 유형 | 계약 |
|---|---|---|
| admin | customer-supplier | claim-events-v1 |

### 구조 다이어그램
<!-- superarchitect:generated:structure:claim -->
<!-- /superarchitect:generated -->

### 근거
자유 서술이다. 소제목은 얼마든지 추가할 수 있고 파서는 알지 못하는 소제목의 내용을 무시한다.

## 컨텍스트: admin
- 분류: generic
- 스타일: layered-simple
- 모듈 구성: single-module

| 모듈 | 경로 | 레이어 |
|---|---|---|
| admin | admin | all |
```

**주석은 괄호로만 쓴다.** 라벨 값 뒤의 `(...)`는 파서가 제거하므로 위처럼 설명을 붙여도 안전하다.
그러나 `←` 화살표 설명은 값의 일부로 읽힌다 — 정규 값 라벨이면 오류가 되고, 자유 값 라벨(`경로`,
`기본 패키지` 등)이면 오류 없이 값이 오염된다. 헤딩(`## 프로젝트: ...`),
소제목(`### 애플리케이션`), 그리고 `규칙 예외` 라벨은 괄호 주석조차 값의 일부가 되므로 **어떤 설명도
같은 줄에 붙이지 않는다**(§5.2). 설명이 필요하면 다음 줄에 쓴다 — 파서는 라벨도 표도 아닌 줄을
무시한다. 유일한 예외는 표의 데이터 행으로, 마지막 `|` 뒤의 글자는 버려진다(§3의 `presentation` 행).

### 생성 구역 마커

스킬이 갱신하는 구역은 여는 마커와 닫는 마커 **한 쌍**으로 감싼다. v1의 구역은 둘이다.

| 구역 | 여는 마커 | 닫는 마커 |
|---|---|---|
| 컨텍스트 맵 | `<!-- superarchitect:generated:context-map -->` | `<!-- /superarchitect:generated -->` |
| 컨텍스트별 구조 다이어그램 | `<!-- superarchitect:generated:structure:<컨텍스트> -->` | `<!-- /superarchitect:generated -->` |

- **두 줄 모두 줄 전체가 정확히 일치해야 하고, 설명 접미사를 붙일 수 없다.** 스킬은 구역을 문자열
  완전 일치로 찾아 두 마커 **사이만** 통째로 교체한다. 접두 일치를 허용하면
  `...:structure:claim -->`이 컨텍스트 `claim-detail`의 여는 줄과도 매칭되어 엉뚱한 구역을 덮어쓴다.
- 닫는 마커는 구역 종류를 구분하지 않는다. 따라서 **구역을 중첩할 수 없고**, 여는 마커 하나 뒤에는
  가장 가까운 닫는 마커가 짝이다.
- 닫는 마커가 없는 여는 마커는 구역이 아니다 — 어디까지가 생성물인지 알 수 없으므로 스킬은 그
  구역을 갱신하지 않고 오류로 보고해야 한다.
- 두 마커 **사이만** 생성물이다. 바깥은 전부 자유 서술이고 스킬이 건드리지 않는다. 파서는 두 줄을
  다른 주석과 똑같이 무시한다.

## 3. 멀티 애플리케이션·app-embedded

실행 단위(애플리케이션) 모듈이 여럿이고, 컨텍스트가 모듈 하나가 아니라 **여러 앱 모듈에 걸친
패키지들**로 실현되는 형태다(검증 사례: imstargg-backend). 프로젝트 섹션의 선택 표 세 가지가 이를
선언한다. 아래 블록도 그대로 파서를 통과한다.

```markdown
# imstargg-backend — Architecture
<!-- superarchitect:template v1 -->

## 프로젝트: imstargg-backend
- 경로: imstargg-backend
- 프로파일: kotlin-spring
- 기본 패키지: com.imstargg
- 아키텍처 테스트 위치: architecture-test/src/test/kotlin

### 애플리케이션
| 이름 | 모듈 경로 | 포함 컨텍스트 |
|---|---|---|
| core-api | core/core-api | brawlstars, statistics, operation, renewal |
| core-batch | core/core-batch | brawlstars, statistics |
| core-worker | core/core-worker | brawlstars |
| core-admin | core/core-admin | all |

### 공용 모듈
| 모듈 | 경로 | 역할 |
|---|---|---|
| core-enum | core/core-enum | shared-kernel |
| db-core | infrastructure/db-core | infrastructure |
| brawlstars-client | client/brawlstars-client | client |
| logging | support/logging | support |

### 패키지 규약
| 레이어 | 패턴 |
|---|---|
| domain | com.imstargg.core.domain.{컨텍스트}.. |
| application | com.imstargg.core.application.{컨텍스트}.. |
| presentation | com.imstargg.{앱}.. |    ← {컨텍스트} 없는 패턴 = 컨텍스트 비분할 레이어

## 컨텍스트: brawlstars
- 프로젝트: imstargg-backend
- 분류: core
- 스타일: layered-domain
- 모듈 구성: app-embedded

### 관계
| 상대 | 유형 | 계약 |
|---|---|---|
| statistics | customer-supplier | brawlstars-events-v1 |

## 컨텍스트: statistics
- 프로젝트: imstargg-backend
- 분류: core
- 스타일: layered-domain
- 모듈 구성: app-embedded

## 컨텍스트: operation
- 프로젝트: imstargg-backend
- 분류: supporting
- 스타일: layered-domain
- 모듈 구성: app-embedded

## 컨텍스트: renewal
- 프로젝트: imstargg-backend
- 분류: supporting
- 스타일: layered-domain
- 모듈 구성: app-embedded
- 패턴: cqrs, outbox
- 규칙 예외: -ld.domain-pure (ADR-0007)
- 이행: layered-simple → layered-domain
```

### 세 표는 언제 필요한가

| 표 | 쓸 때 | 안 써도 될 때 |
|---|---|---|
| `### 애플리케이션` | 실행 가능한 모듈이 둘 이상이고, 앱마다 접근 가능한 컨텍스트가 다를 때. **app-embedded 컨텍스트가 있으면 필수** | 실행 단위가 하나뿐일 때 |
| `### 공용 모듈` | 컨텍스트에 속하지 않는 공유 모듈(로깅, DB 공통, 외부 API 클라이언트, 공유 enum)이 있을 때 | 모든 모듈이 어느 컨텍스트에 속할 때 |
| `### 패키지 규약` | 실제 패키지가 기본 관례(§6)와 다를 때. **app-embedded 컨텍스트가 있으면 필수** | 기본 관례가 실제 패키지와 일치할 때 |

세 표는 서로 독립이다. app-embedded 컨텍스트가 없어도 패키지 규약 표만 쓸 수 있고(§6), 앱이 여럿이어도
패키지가 관례를 따르면 애플리케이션 표만 쓰면 된다.

### app-embedded에서 레이어를 소유하는 모듈

파서는 app-embedded 컨텍스트의 모듈을 알지 못한다(모듈 표가 금지되어 있다). 선언되는 것은 패키지 패턴
뿐이므로, 어느 모듈이 그 패키지를 담는지는 **규약 패턴의 모양이 결정한다.**

- **한 레이어 패키지의 소유 모듈은 정확히 하나다.** 같은 패키지가 두 모듈에 동시에 존재하면 split
  package이거나 복제이고, 정규화 패턴은 파일이 어느 모듈에 있는지 구분하지 않으므로 어떤 생성 규칙도
  이를 잡지 못한다 — 사람이 지켜야 하는 항목이다.
- **패턴에 `{앱}`이 있으면 앱마다 사본이 하나씩 있는 레이어**이고, 그 사본은 각 앱 모듈이 소유한다.
  위 예에서는 `presentation`이 그렇다.
- **패턴에 `{앱}`이 없으면 프로젝트에 사본이 하나뿐인 레이어**이고, 앱들이 **함께 의존하는 비실행
  모듈**이 소유한다. 위 예의 `domain`·`application`이 그렇다. 이 모듈은 컨텍스트에 속하므로
  `### 공용 모듈` 표에 적지 않는다 — 그 표는 컨텍스트에 속하지 않는 모듈만 다룬다.
- **앱 모듈은 다른 앱 모듈에 의존하지 않는다.** 앱 A가 앱 B를 참조하면 B의 코드는 A의 `포함 컨텍스트`
  선언에 없는 코드이고, 조립 지점이 두 곳으로 갈라진다. 이는 §5.1 규칙 5의 "애플리케이션 봉쇄"에서
  따라 나오는 결과다(`derived.app-confinement`가 이 금지까지 함께 만든다).

공유해야 할 도메인 코드가 앱마다 복제되어 있다면 그것은 app-embedded가 아니라 복제다. 답은 그 레이어를
비실행 모듈로 내리는 것이지, 규약 패턴에 `{앱}`을 붙이는 것이 아니다.

## 4. 라벨·표 사전

라벨 형식은 `- 키: 값` 한 줄이다. 파서가 읽는 라벨은 아래가 전부이며, 그 밖의 키는 무시된다.

| 라벨 | 소속 | 필수 | 값 형식 | 정규 값 |
|---|---|---|---|---|
| `경로` | 프로젝트 | 필수 | 저장소 루트 기준 상대 경로. 단일 레포는 `.`. 아직 없는 경로도 허용(설계 선행) | — |
| `프로파일` | 프로젝트 | 필수 | `profiles/` 하위 디렉터리명 | `kotlin-spring` \| `java-spring` |
| `기본 패키지` | 프로젝트 | 필수 | 점으로 구분한 패키지 접두 (`com.acme`) | — |
| `아키텍처 테스트 위치` | 프로젝트 | 필수 | 프로젝트 `경로` 기준 상대 경로 | — |
| `프로젝트` | 컨텍스트 | 프로젝트가 2개 이상이면 필수 | 프로젝트 섹션의 이름 | 선언된 프로젝트 이름 |
| `분류` | 컨텍스트 | 필수 | 단일 값 | `core` \| `supporting` \| `generic` |
| `스타일` | 컨텍스트 | 필수 | 단일 값 | `layered-simple` \| `layered-domain` \| `hexagonal` \| `clean` \| `custom/<이름>` |
| `모듈 구성` | 컨텍스트 | 필수 | 단일 값 | `multi-module` \| `single-module` \| `app-embedded` |
| `패턴` | 컨텍스트 | 선택 | 쉼표 구분 목록 | `references/knowledge/patterns/`의 문서 key |
| `규칙 예외` | 컨텍스트 | 선택 | `-<규칙 id> (ADR-NNNN)`의 쉼표 구분 목록. ADR 참조 필수 | 규칙 id 규약은 `rule-vocabulary.md` §4 |
| `이행` | 컨텍스트 | 선택(점진 이행 중일 때만) | `<출발 스타일> → <목표 스타일>` | 목표는 `스타일` 라벨과 같아야 한다 |

표는 다섯 종류다. **파서는 헤더 셀의 이름을 읽지 않는다 — 계약은 열의 순서다.** 헤더 이름은 사람을
위한 것이므로 아래 이름을 쓰되, 이름을 바꿔도 파싱 결과는 달라지지 않는다.

| 표 | 위치 | 소속 | 필수 | 열 (순서 고정) | 정규 값 |
|---|---|---|---|---|---|
| 애플리케이션 | `### 애플리케이션` | 프로젝트 | app-embedded 컨텍스트가 있으면 필수 | 이름, 모듈 경로, 포함 컨텍스트 | 포함 컨텍스트: 선언된 컨텍스트 이름의 쉼표 목록 또는 `all`. `이름`은 한 프로젝트 안에서 유일해야 한다 |
| 공용 모듈 | `### 공용 모듈` | 프로젝트 | 선택 | 모듈, 경로, 역할 | 역할: `shared-kernel` \| `infrastructure` \| `client` \| `support`. `모듈`은 한 프로젝트 안에서 유일해야 한다 |
| 패키지 규약 | `### 패키지 규약` | 프로젝트 | app-embedded 컨텍스트가 있으면 필수 | 레이어, 패턴 | 패턴 변수는 `{컨텍스트}`·`{앱}` (§6) |
| 모듈 | 소제목 없는 **첫** 표 | 컨텍스트 | `multi-module`·`single-module`이면 필수, `app-embedded`면 금지 | 모듈, 경로, 레이어 | 레이어: 스타일이 선언한 레이어 이름 또는 `all`(어긋나면 오류). 경로는 프로젝트 `경로` 기준 |
| 관계 | `### 관계` | 컨텍스트 | 선택 | 상대, 유형, 계약 | 유형: `partnership` \| `customer-supplier` \| `conformist` \| `acl` \| `open-host` \| `published-language` |

애플리케이션·공용 모듈 **이름의 중복은 파스 타임 오류다**(스코프는 프로젝트 하나). 이 이름들은
생성물의 식별자가 되므로 중복은 조용한 덮어쓰기가 된다. 두 표에 걸친 동명은 사람이 피한다.

`관계` 표의 `유형` 칸은 **단일 값**이다. 두 유형을 한 칸에 적는 문법도, 같은 `상대`에 두 줄을 써서
조합을 표현하는 문법도 없다(두 줄을 써도 파서는 거부하지 않지만 어느 유형이 이기는지 정의되어 있지
않다). 두 유형이 동시에 성립할 때 무엇을 적을지, 어떤 유형을 고를지의 규범은
`references/knowledge/strategic/context-mapping.md`가 정한다. `계약` 칸은 파서가 검증하지 않는 자유 문자열이다.

## 5. 파싱 계약

### 5.1 열 개 규칙

1. **섹션 열거** — `## 프로젝트: <이름>`이 거버넌스 대상 프로젝트를(1개 이상 필수),
   `## 컨텍스트: <이름>`이 컨텍스트를 열거한다. 각 섹션 아래의 라벨과 알려진 표를 읽고, 알려지지 않은
   헤딩·소제목·문단은 무시한다.
2. **정규 값만 허용** — §4의 정규 값 집합을 벗어나면 오류다. 파서는 필수 결정 누락·비정규 값·깨진
   참조(없는 프로젝트·컨텍스트를 가리키는 라벨과 표 칸)를 **라인 번호와 함께** 보고한다.
   지목할 줄이 없는 **문서 전체 수준의 오류는 라인 0**으로 보고된다 — 출력에서
   `ARCHITECTURE.md:0: ...` 꼴이다. v1에 이런 오류는 정확히 둘이다: 템플릿 마커 누락(§8),
   프로젝트 섹션 부재. `:0:`을 보면 문서 어딘가의 한 줄이 아니라 문서 자체가 성립하지 않는다는
   뜻이므로, 줄을 찾지 말고 두 가지 중 무엇인지부터 본다.
3. **실현 정규화** — 모듈 표든 패키지 규약이든, 파서가 **"컨텍스트 × 레이어 → 패키지 패턴"**으로
   정규화한다(§6). fitness·check_imports·collect_signals는 정규화 결과만 소비한다. 모듈의 경로 정보는
   sync(존재 대조)와 scaffold(생성 위치)만 쓴다.
4. **app-embedded 제약** — 해당 컨텍스트가 있으면 소속 프로젝트에 패키지 규약 표와 애플리케이션 표가
   필수이고, 그 컨텍스트에 모듈 표를 두면 오류다. 같은 프로젝트의 app-embedded 컨텍스트들은 하나의
   규약을 공유하므로 **같은 스타일이어야 한다**. 규약 표의 레이어 이름은 그 스타일이 선언한 레이어
   이름과 일치해야 한다(어긋나면 오류).
5. **선언에서 파생되는 표준 규칙** — 아래 셋은 스타일 문서에 쓰지 않고 선언에서 직접 생성되며,
   전부 `forbid-import` 인스턴스다. id는 `derived.` 접두를 갖는다.
   - `derived.shared-module-direction` — 공용 모듈 → 앱·컨텍스트 코드 의존 금지. `shared-kernel`만
     도메인 레이어에서 import를 허용하고, 나머지 역할은 domain-pure 컨텍스트의 domain 레이어에서
     금지된다.
   - `derived.app-confinement` — 앱은 `포함 컨텍스트`로 선언된 컨텍스트의 코드만 참조한다(`all`은
     전부 허용). 반대로 컨텍스트·공용 코드는 앱 코드에 의존할 수 없다. 조립은 앱에서만 한다.
   - `derived.context-isolation` — 컨텍스트 간 직접 참조는 기본 금지이고 `### 관계` 표에 나타난
     쌍만 열린다. **v1에서 허용 단위는 쌍이며 방향을 구분하지 않는다** — 유형이 방향 해석을 바꾸지
     않는다. 유형에 따라 방향을 달리 읽으면 하류가 선언하는 유형(`acl`·`conformist`)과 상류가
     선언하는 유형(`open-host`)이 한 표에 섞여 같은 줄이 두 가지로 읽힌다. 느슨한 쪽(쌍 단위)의
     대가로 원치 않는 역방향 참조도 함께 열리며, 조이려면 템플릿 버전을 올려야 한다(§8).

   파생 규칙은 **`규칙 예외`의 대상이 아니다** — 해제 레버는 선언 쪽이다(관계 표의 쌍, 앱의 `포함
   컨텍스트`, 공용 모듈의 `역할`). 앱·공용 모듈의 **패키지는 선언에 없을 수 있다** — 패키지 규약의
   `{앱}` 행이 있으면 그 전개가 선언이고, 없으면 모듈 경로 아래 소스의 `package`를 관측해 채운다(0건
   이면 검사하지 않고 고지한다). **domain-pure 판별자는 `confine-type`이다** — 예외 적용 **후**의
   유효 규칙에 인스턴스가 하나라도 있으면 그 컨텍스트가 domain-pure다.
6. **스타일은 선언되어야 한다** — 프리셋이 아닌 변형은 `docs/architecture/styles/<이름>.md`에 §7의
   형식으로 선언하고 `- 스타일: custom/<이름>`으로 채택한다. 선언 없는 임의 변형은 모든 스킬이
   거부하며, 문서가 없으면 오류다.
7. **규칙 어휘는 폐쇄형이다** — 스타일이 선언할 수 있는 규칙은 `rule-vocabulary.md`의 primitive 5종과
   그 파라미터 조합뿐이다. 어휘 밖 검증이 필요하면 어휘에 정식 등록하는 것이 유일한 경로다.
8. **이행과 baseline 래칫** — `이행` 라벨이 있으면 목표 스타일 기준의 현재 위반 전량을
   `baseline.jsonl`로 동결한다. 이후 baseline에 있는 위반은 warn(기존 부채), 없는 위반은 blocker다 —
   부채는 늘 수 없고 줄기만 하는 래칫이다. baseline은 migrate로만 축소되고, 비면 `이행` 라벨을
   제거한다. 출발 스타일은 근사 기록일 뿐 정밀할 필요가 없다 — 실제 차이는 baseline이 흡수한다(§5.3).
9. **캐시 없음** — §1을 보라. 중간 캐시 파일을 만들지 않는다.
10. **템플릿 버전 관리** — 상단 마커로 버전을 표시한다. 해석이 갈리면 이 문서가 정본이다(§8).

### 5.2 구현이 확정한 세부

선언만 보고는 알 수 없고, 파서를 읽어야 알 수 있는 것들이다.

- **후행 괄호 주석은 값에서 제거된다.** 값 끝의 `(...)` 한 덩어리를 제거한 뒤 남은 문자열이 값이다.
  따라서 `- 분류: core (core | supporting | generic)`의 값은 `core`다.
- **`규칙 예외`만 예외다.** 이 라벨에서 괄호는 주석이 아니라 ADR 참조 문법이므로 제거하지 않는다.
  항목 형식은 `-<규칙 id> (ADR-NNNN)`이고 ADR 번호는 **네 자리**여야 한다. 앞의 `-`는 "제외"를
  뜻하며 파서가 떼어낸다(v1에는 제외 말고 다른 연산이 없다). 이 라벨에 설명을 덧붙이면 그 설명까지
  항목의 일부가 되어 ADR 누락 오류가 난다.
- **`이행`은 `출발 → 목표` 형식이고 화살표는 유니코드 `→`다**(`->`는 인식되지 않는다). 목표는 현재
  `스타일` 라벨과 같아야 한다 — 다르면 오류다. 이행 중에도 `스타일`은 **목표 스타일**을 적는다.
  선언의 현재 시제는 언제나 "우리가 지키기로 한 것"이지 "지금 코드가 그런 것"이 아니다.
- **`이행`의 원문 값은 파싱에 실패해도 보존된다.** 그래서 "라벨이 없다"와 "라벨이 있는데 형식이
  틀렸다"가 구분되고, 후자는 조용히 무시되는 대신 오류로 보고된다.
- **형식이 깨진 `규칙 예외` 항목도 버려지지 않는다.** 앞의 `-`만 뗀 원문이 그대로 남아 검증이 그
  항목을 지목해 보고할 수 있다. 파싱 단계에서 버리면 "예외를 선언했는데 아무 일도 일어나지 않는"
  상태가 되기 때문이다.
- **표의 의미는 바로 앞의 `###` 소제목이 결정한다.** 프로젝트 섹션에서 소제목 없는 표는 무시되고,
  컨텍스트 섹션에서 **소제목 없는 첫 표**가 모듈 표다. 소제목이 한 번 나오면 그 뒤로는 소제목 없는
  상태로 돌아갈 수 없으므로, **모듈 표는 어떤 `###`보다 먼저** 와야 한다. 두 번째 소제목 없는 표는
  무시된다.
- **표는 헤더 행 + 구분선 행 + 데이터 행이다.** `|`로 시작하는 연속된 줄 묶음이 하나의 표이고 빈 줄이
  표를 끝낸다. 구분선(`|---|---|`)이 없으면 첫 데이터 행이 구분선 자리에서 버려진다.
- **읽는 칸 수는 헤더 행이 정한다.** 데이터 행의 마지막 `|` 뒤에 글자가 있어도 버려지므로, 표 행에는
  설명을 붙여도 안전하다(§3의 `presentation` 행). 반대로 헤더 행에 설명을 붙이면 칸이 하나 늘어난
  것으로 읽히지만, 각 표가 쓰는 칸은 앞쪽 2~3개로 고정이라 결과는 달라지지 않는다.
- **알 수 없는 `##` 헤딩은 열려 있던 섹션을 닫는다.** `## 컨텍스트 맵` 아래에 쓴 라벨과 표는 아무
  섹션에도 귀속되지 않는다. 프로젝트의 세 표는 반드시 그 프로젝트 섹션과 다음 `##` 사이에 둔다.
- **같은 라벨을 두 번 쓰면 마지막 값이 남는다.** 중복은 오류로 보고되지 않는다.
- **프로젝트가 하나뿐이면 `- 프로젝트:` 라벨이 없는 컨텍스트가 그 프로젝트로 자동 귀속된다.** 둘
  이상이면 생략은 오류다.

### 5.3 아직 시행되지 않는 조항

> **구현 상태 — 아래 두 조항만 남았다.** 정본이 요구하지만 오늘 도구가 하지 않는 일이며 그때까지
> 사람이 확인한다. 구현되면 그 줄을 지우고, 표가 비면 이 절을 지운다. 교차 파일 검증(레이어 이름
> 대조·세그먼트 유효성·`custom` 문서 실존·`패턴` key 실존)과 파생 규칙 3종 생성은 착지해 빠졌다.

| 조항 | 정본 위치 | 상태 |
|---|---|---|
| 마커의 버전에 따라 해석 규칙을 고르는 것 | §8 | 미구현. 파서는 `v1` 마커 문자열의 포함 여부만 본다 — 마커를 `v2`로 올린 문서는 "템플릿 마커가 없습니다"로 거부된다. 이것이 구현되기 전에는 버전 상향이 불가능하다 |
| `이행` 선언 시 baseline 동결 | §5.1 규칙 8 | 미구현 (Phase 5). 지금은 라벨만 선언되고, 생성된 테스트는 모든 위반을 blocker로 다룬다 |

두 항목의 실패 모드는 침묵이 아니다 — 마커 분기는 **거부**로(버전을 올리면 문서가 통과하지 않는다),
baseline 부재는 **과잉 차단**으로 드러난다. 매칭 0건 규칙의 침묵은 `resolve_rules`·`check_imports`의
경고 층위가 계속 담당한다(어휘 §1).

## 6. 모듈 패키지 관례

정규화의 결과는 `(프로젝트, 컨텍스트, 레이어, 패키지 패턴)` 목록이다. 패턴은 언제나 `..`로 끝난다.

**왜 정규화하는가.** 강제 도구(Konsist·ArchUnit)는 패키지 패턴 위에서만 판정하고 Gradle 모듈이라는
개념을 알지 못한다. 모든 실현 형태를 "컨텍스트 × 레이어 → 패키지 패턴"이라는 한 모양으로 눌러 두면
규칙 생성기가 레이아웃을 몰라도 된다. 실용적 귀결: `single-module`에서 `multi-module`로 옮기는
리팩터링이 **규칙을 하나도 바꾸지 않는다** — 패턴만 다시 계산된다.

**기본 관례** — 프로젝트에 패키지 규약 표가 없을 때. 모듈 표에 등장하는 레이어 값마다 하나씩 만든다.

| 상황 | 패턴 |
|---|---|
| 일반 레이어 | `{기본 패키지}.{컨텍스트}.{레이어}..` |
| 레이어가 `all` | `{기본 패키지}.{컨텍스트}..` |

기본 패키지 `com.acme`, 컨텍스트 `claim`이면 `com.acme.claim.domain..` 식이 된다. 같은 레이어를 가진
모듈이 여럿이어도(`claim-adapter-in`, `claim-adapter-out`) 패턴은 레이어당 하나로 합쳐진다.

이 경로에서는 **레이어 이름이 그대로 패키지 세그먼트가 되므로 유효한 세그먼트여야 한다**(§7). 아래
`{앱}`이 하이픈을 점으로 바꾸는 것과 같은 제약이며, 하이픈이 든 이름은 오류로 거부된다.

**패키지 규약 표가 있으면 언제나 이긴다.** 규약은 그 프로젝트에 속한 **모든** 컨텍스트에 적용되며,
컨텍스트의 `모듈 구성`이 무엇이든 상관없다. 한 프로젝트 안에서 컨텍스트마다 다른 관례를 쓸 수단은
없다 — 그런 프로젝트는 규약 표에 두 관례를 모두 표현할 수 있는 레이어 이름으로 나눠야 한다.

**변수 치환 규칙**

- `{컨텍스트}` — 컨텍스트 이름으로 치환하고, 프로젝트의 컨텍스트마다 하나씩 만든다.
- `{앱}` — 애플리케이션 이름으로 치환하되 **하이픈을 점으로 바꾼다**(`core-api` → `core.api`).
  패키지 세그먼트에 하이픈을 쓸 수 없기 때문이다. 애플리케이션마다 하나씩 전개된다.
- `{컨텍스트}`가 없는 패턴은 **컨텍스트로 분할되지 않는 레이어**를 뜻하고, 프로젝트당 한 번만 만들어져
  모든 컨텍스트에 공통으로 적용된다.
- 두 변수는 한 패턴에 함께 쓸 수 있고, 그때는 컨텍스트 × 애플리케이션만큼 전개된다.

`{앱}`을 쓰면서 애플리케이션 표가 없으면 **오류다.** 전개할 대상이 없어 그 레이어의 패턴이 하나도
생기지 않는데, 그것은 규칙이 조용히 사라지는 상태이기 때문이다. 파서는 `{앱}`을 쓰는 레이어마다 한
건씩, 프로젝트 섹션 헤딩 라인에 오류를 붙인다 — `프로젝트 'p'의 패키지 규약 레이어 'presentation'가
'{앱}' 패턴을 쓰는데 '애플리케이션' 표가 없습니다`. app-embedded 컨텍스트가 있으면 애플리케이션 표가
이미 필수이므로, 이 검사가 실제로 걸리는 곳은 규약 표만 쓰는 비-app-embedded 프로젝트다.

패키지 규약 표를 언제 쓰는지, 어떤 패키지 이름을 고를지는 `references/knowledge/structure/package-conventions.md`에 있다.

## 7. 스타일 선언 형식

프리셋(`references/knowledge/styles/<이름>.md`)과 커스텀 스타일
(대상 프로젝트의 `docs/architecture/styles/<이름>.md`)은 **같은 형식**을 쓴다. 레벨 2 소제목
`## 선언` 아래 레이어 목록 라벨 하나와 규칙 인스턴스 표 하나다. 프리셋처럼 문서 표준을 따르는
문서에서는 `## 적용 기준`과 `## 규칙` **사이**에 둔다(문서 표준의 5단계 순서는 권장이지 강제가
아니므로 충돌하지 않는다).

**레벨 2는 권고가 아니라 요구다.** 이 저장소에 실재하는 유일한 헤딩 매처인 `build_index.py`의
`_is_mature()`는 `("## 적용 기준", "## 규칙")`을 **줄 전체 정확 일치**로 찾고 `###`은 매칭하지
않는다. 같은 하우스 스타일로 쓰일 선언 파서가 `### 선언`을 놓치면 그 실패는 조용하다 — 스타일의
규칙이 0개 생성되고, 리포트에서는 "위반 없음"과 구분되지 않는다.

아래는 `hexagonal` 프리셋의 선언부다. 커스텀 스타일도 파일 위치만 다를 뿐 형식은 글자 그대로 같다.

```markdown
## 선언
- 레이어: domain, application, adapter    (안 → 밖 순서)

| 규칙 id | primitive | 파라미터 |
|---|---|---|
| hex.deps-inward | layer-order | layers=domain,application,adapter |
| hex.domain-pure | confine-type | type=jpa-entity; allowed_layer=adapter |
| hex.domain-no-framework | forbid-import | from=domain; to=org.springframework..,jakarta.persistence.. |
| hex.ports-owned-inside | naming-suffix | scope=application; suffixes=Port,UseCase |
```

- `- 레이어:` — 이 스타일이 가진 레이어 이름의 쉼표 목록. 개수도 이름도 자유다. 이 목록이 컨텍스트
  모듈 표의 `레이어` 칸과 패키지 규약 표의 `레이어` 칸에 쓸 수 있는 값을 정한다. 기본 관례를 쓰면
  **레이어 이름이 그대로 패키지 세그먼트가 되므로**(§6) 실제 소스의 패키지 이름과 맞춘다.
  - 이름의 자유에는 제약이 하나 붙는다 — **기본 관례를 쓰는 프로젝트에서 레이어 이름은 유효한 패키지
    세그먼트여야 한다.** 패키지 세그먼트에 하이픈을 쓸 수 없으므로(§6이 `{앱}`에서 하이픈을 점으로
    바꾸는 것과 같은 이유) `interface-adapter` 같은 이름은 성립하지 않는 패턴을 만들어 오류로
    거부된다. 한 단어로 줄이거나(`adapter`), 패키지 규약 표로 실제 세그먼트를 명시 매핑한다.
- `규칙 id` — `<스타일 접두사>.<하이픈-이름>`. 컨텍스트가 `규칙 예외`로 지목하는 유일한 수단이므로
  한 번 배포된 id는 이름을 바꾸지 않는다. 규약의 정본은 `rule-vocabulary.md` §4다.
- `primitive` — `rule-vocabulary.md` §3의 5종 중 하나. 그 밖의 이름은 존재하지 않는다.
- `파라미터` — **이 셀의 문법은 `rule-vocabulary.md` §2가 정본이며 여기서 다시 정의하지 않는다.**
  두 문서가 각자 정의하면 파서와 프로파일이 갈라진다.

커스텀 스타일을 새로 만들 때 밟을 절차와 체크리스트는 `rule-vocabulary.md` §5에 있다. 컨텍스트는
`- 스타일: custom/<이름>`으로 채택하며, 이름은 파일명(`<이름>.md`)과 같아야 한다.

## 8. 버전 관리

문서 상단 두 번째 줄에 마커를 둔다. 정확히 이 문자열이어야 하고, 없으면 파서가 문서 전체 수준의
오류로 거부한다.

```markdown
<!-- superarchitect:template v1 -->
```

마커는 "이 문서가 어느 판 템플릿의 규칙으로 읽혀야 하는가"를 선언한다 — **선언하도록 설계되었을 뿐,
아직 그렇게 동작하지 않는다.** 오늘 파서는 위 문자열이 문서 안에 있는지만 보고 버전으로 해석 규칙을
고르지 않으므로, 마커를 `v2`로 올린 문서는 지금 그대로 돌리면 `템플릿 마커(...v1...)가 없습니다`로
거부된다(§5.3). 따라서 **v1만 존재하는 지금 버전 상향은 불가능하며**, 아래 절차는 2단계가 구현된
뒤에 성립한다.

1. **이 문서를 먼저 고친다** — 파서보다 정본이 먼저다. 파서가 정본과 다르게 동작하면 그것은 파서의
   결함이며, 고쳐질 때까지 §5.3에 적어 둔다.
2. **파서가 마커의 버전을 읽어 분기하게 만든다** — 나머지 단계의 선행 조건이다. 이것 없이 마커만
   올리면 모든 문서가 거부된다.
3. **버전 마커를 올린다** — `v1` → `v2`.
4. **마이그레이션 노트를 남긴다** — 무엇이 달라졌고, 기존 문서를 어떻게 고쳐야 하며, 고치지 않으면
   무슨 오류가 나는지. 자동 변환이 가능하면 그 수단도 함께 제공한다.

**판단 기준은 하나다 — 같은 문서를 새 파서로 읽었을 때 결과가 달라진다면 버전을 올린다.** 라벨·표·정규
값의 추가·삭제·의미 변경, 필수 여부의 변경, 정규화·치환 규칙의 변경이 여기 해당한다. 서술·예시·오류
문구의 개선과, §5.3의 항목이 구현되어 그 줄이 지워지는 것은 해당하지 않는다.
