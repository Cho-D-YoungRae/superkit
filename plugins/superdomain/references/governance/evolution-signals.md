# 진화 신호 (evolution signals) — 정본

선언된 아키텍처와 실제 코드가 어긋나기 시작했다는 신호를 정의하고, 그 해석 규칙과 제안 문구를 고정한다. `collect_signals.py`가 신호를 기계적으로 수집하고 `evolve` 스킬이 이 문서를 판정 기준으로 읽는다.

이 문서가 전제하는 넷은 전부 실재한다: 수집기 `scripts/collect_signals.py`, 유일한 소비자 `evolve` 스킬, 신호 4의 입력 `baseline.jsonl`(`이행` 선언 시 init이 동결한다), 신호 4의 제안이 가리키는 조치 `migrate` 스킬. 신호 2·5의 입력 `review-log.jsonl`은 `review`가 append하고, 신호 3의 입력은 `check_imports.py`다. **그러므로 본문의 현재형 서술은 그대로 현재형으로 읽는다.**

## 0. 이 문서를 지배하는 세 규칙

1. **모든 해석은 제안으로 끝난다.** 자동 변경은 없다. 사용자가 수락한 제안만 문서에 반영되고 파생물·fitness가 갱신된다. "신호가 떴으니 고쳤다"는 이 플러그인이 하지 않는 일이다.
2. **신호는 증거이지 결론이 아니다.** 각 신호에는 여러 해석이 가능하고, 이 문서는 그중 무엇을 먼저 의심할지를 정한다. 제안에는 항상 관측 수치를 함께 제시해 사용자가 해석을 뒤집을 수 있게 한다.
3. **임계값은 기본값이다.** 프로젝트마다 조정할 수 있고, 조정한 값은 ADR로 남긴 뒤 `evolve` 실행 시 명시한다. 조정 근거 없이 임계값을 낮춰 신호를 늘리면 제안이 소음이 되고, 소음이 된 제안은 전부 무시된다.

## 1. 신호 요약

| # | 신호 | 데이터 출처 | 기본 임계값 | 제안 유형 |
|---|---|---|---|---|
| 1 | 변경 빈도 대비 분류 불일치 | git log (90일) | 상위 25% **이고** 평균의 1.5배 이상 | 분류 재검토 |
| 2 | 동일 규칙의 반복 위반 | review-log.jsonl (90일) | 같은 rule id 3회 이상 | 규칙 재검토 |
| 3 | 컨텍스트 쌍의 결합 급증 | check_imports (4주 비교) | 2배 이상 **이고** 절대 10 이상 | 관계 재정의 / 병합·분리 |

| 5 | 반복되는 의미론 지적 | review-log.jsonl (90일) | 같은 주제 3회 이상 | conventions 문서 승격 |

### 수집 항목 ↔ 해석 규칙 대응

`collect_signals.py`가 수집하는 항목이 해석 규칙 5종과 1:1이 아니다. 어떤 항목은 독립 규칙이 아니라 다른 규칙의 입력이거나 보조 지표다. 수집했는데 아무 규칙도 소비하지 않는 항목이 생기지 않도록 대응을 명시한다.

| 수집 항목 (스펙 §6.7) | 소비하는 해석 규칙 | 역할 |
|---|---|---|
| 컨텍스트별 변경 빈도 (git log) | 신호 1 | 주 입력 |
| 핫스팟 (파일 → 컨텍스트 귀속) | 신호 1 | **입력** — 독립 규칙이 아니다. 컨텍스트 귀속의 근거이자 제안에 첨부하는 근거 파일 목록. migrate(스펙 §6.8)의 우선순위 산정에도 같은 값이 쓰인다 |
| 컨텍스트 간 의존 edge 수 | 신호 3 | 주 입력 |
| 모듈 크기 추이 | 신호 3 | **보조 지표 — 그리고 오늘 수집되지 않는다.** 결합 급증이 "한 컨텍스트가 비대해지며 책임이 섞인 결과"인지 판별하는 데 쓸 값이지만 `collect_signals.py`는 이 값을 내지 않는다. 없으면 없다고 적는다 — 보조 지표라 그 부재가 신호 3의 산출을 막지는 않는다 |
| review-log 반복 위반 (rule id별) | 신호 2 | 주 입력 |
| review-log 의미론 지적 | 신호 5 | 주 입력 |
| baseline.jsonl 크기 추이 | 신호 4 | 주 입력 |

보조 지표만으로는 제안을 만들지 않는다. 모듈이 커지는 것 자체는 문제가 아니며, 임계값도 두지 않는다.

**컨텍스트 쌍 동시 변경(수집기의 `cochanges`)에 이 표의 행이 없는 것은 의도된 부재다.** "한 커밋이 두 컨텍스트를 함께 건드렸다"는 의존 edge 수(신호 3의 주 입력)와 다른 척도이고, 다른 척도에 신호 3의 배수·절대 하한을 얹으면 관측처럼 보이는 추측이 된다. 그 값이 서는 자리는 하나다 — 신호 3을 **산출한 뒤** §4 해석 표의 어느 행인지 가르는 정황으로 함께 싣는 것이며, 단독으로는 어떤 제안도 만들지 않고 신호 3의 대체 입력도 되지 않는다.

**공통 오탐 방지 조건** — 아래를 만족하지 못하면 신호를 산출하지 않는다.

- 저장소 이력이 4주 미만이면 시계열 신호(1·3·4)를 내지 않는다.
- 컨텍스트가 2개 이하면 신호 1·3을 내지 않는다(비교 대상이 없어 상대 순위가 무의미하다).
- 관측 표본이 신호별 최소 기준에 못 미치면 산출하지 않는다(각 절에 명시).
- 한 번 사용자가 기각한 제안은 같은 신호·같은 대상에 대해 4주간 다시 내지 않는다.

## 2. 신호 1 — 변경 빈도 대비 분류 불일치

**정의** — `generic` 또는 `supporting`으로 분류된 컨텍스트가 변경 빈도 상위권에 있다.

**측정** — 최근 90일 git log에서 변경된 파일 경로를 정규화된 패키지 패턴으로 컨텍스트에 귀속시키고, 컨텍스트별 커밋 수를 센다. 한 커밋이 여러 컨텍스트를 건드리면 각 컨텍스트에 1회씩 계상한다.

**기본 임계값** — 분류가 `generic`·`supporting`이면서, 컨텍스트별 커밋 수가 **상위 25% 이내이고 동시에 전체 평균의 1.5배 이상**. 최소 표본: 해당 컨텍스트 커밋 20건.

> 근거: 상위 25%만으로는 컨텍스트 수와 무관하게 항상 누군가 걸린다. 균등 분포라면 각 컨텍스트의 몫은 1/N이므로 평균의 1.5배는 "우연한 편차가 아니라 쏠림"의 최소선이다. 90일과 20건은 분기 단위 개발 리듬에서 추세라고 부를 만한 최소 관측이다.

**해석** — 자주 바뀌는 코드는 대개 경쟁 차별화가 일어나는 자리다. `generic`(사면 되는 것)·`supporting`(있어야 하지만 차별화 아님)으로 분류해 두었는데 계속 손대고 있다면 분류가 현실을 못 따라간 것일 수 있다. 분류가 바뀌면 기본 스타일 매핑(core→hexagonal, supporting→layered-domain, generic→layered-simple)도 함께 바뀐다.

**제안 전에 확인할 것** — 빈도가 높은 이유가 아래라면 재분류가 아니라 다른 조치가 답이다.

- 미완성·불안정해서 계속 고치는 중이다 → 안정화가 먼저다
- 특정 마이그레이션·일괄 수정이 있었다 → 일시적 편차다
- 여러 책임이 한 컨텍스트에 섞여 있다 → 신호 3과 함께 분리를 검토한다

**제안 문구**

```
[분류 재검토] 컨텍스트 `{컨텍스트}`
관측: 최근 90일 변경 {N}건 — 전체 {M}개 컨텍스트 중 {순위}위, 평균({평균}건)의 {배수}배.
현재 분류: {현재 분류} → 기본 스타일 {현재 스타일}.
해석: 차별화가 일어나는 자리일 가능성이 있습니다. 분류가 `core`라면 기본 스타일은 {제안 스타일}입니다.
선택지: ① core로 재분류하고 스타일 이행 검토 ② 분류 유지(빈도 원인이 불안정·일괄 수정이라면) ③ 컨텍스트 분리 검토
```

## 3. 신호 2 — 동일 규칙의 반복 위반

**정의** — 같은 rule id가 여러 리뷰에 걸쳐 반복해서 걸린다.

**측정** — 최근 90일 `review-log.jsonl`에서 rule id별 위반 건수를 집계한다. 위반이 발생한 서로 다른 파일 수와 컨텍스트 수도 함께 센다.

**기본 임계값** — 같은 rule id가 **3회 이상**, 그리고 **서로 다른 리뷰 2건 이상**에서 발생.

> 근거: 2회는 우연이고 3회부터 패턴이다. "서로 다른 리뷰"를 요구하는 이유는 한 번의 큰 PR에서 같은 위반이 여러 개 나온 것과 시간에 걸쳐 반복되는 것을 구분하기 위해서다.

**해석** — **코드가 틀렸다고 먼저 가정하지 않는다.** 규칙이 낡았거나, 현실과 맞지 않거나, 파라미터가 과하게 넓을 가능성을 같은 무게로 본다. 반복 위반은 사람들이 규칙을 어기고 싶어 한다는 뜻이고, 규칙이 실제 설계 압력과 싸우고 있다는 관측이다. 위반이 흩어진 모양이 판단을 가른다.

| 위반이 퍼진 모양 | 유력한 해석 | 방향 |
|---|---|---|
| 여러 파일·여러 컨텍스트 | 규칙이 현실과 맞지 않는다 | 규칙 완화 또는 파라미터 축소 |
| 한 컨텍스트에 집중 | 그 컨텍스트의 스타일 선택이 안 맞는다 | 스타일 재검토, 또는 예외 + ADR |
| 한두 파일에 집중 | 국소적 부채다 | 규칙이 아니라 코드를 고친다(migrate 대상) |

**제안 문구**

```
[규칙 재검토] 규칙 `{규칙 id}` ({primitive})
관측: 최근 90일 {N}회 위반 — 리뷰 {R}건, 파일 {F}개, 컨텍스트 {C}개에 분포.
해석: {분포에 따른 해석}. 코드가 아니라 규칙이 낡았을 가능성을 먼저 검토하십시오.
근거 ADR: {규칙을 도입한 ADR 번호 또는 "없음"}
선택지: ① 파라미터 축소(스코프를 좁힌다) ② 해당 컨텍스트에 규칙 예외 + ADR ③ 스타일 자체 재검토 ④ 규칙 유지 — 코드를 고친다
```

## 4. 신호 3 — 컨텍스트 쌍의 결합 급증

**정의** — 두 컨텍스트 사이의 의존 edge 수가 짧은 기간에 크게 늘었다.

**측정** — `check_imports`로 컨텍스트 간 import edge 수를 센다(방향 구분). `check_imports`는 현재 상태만 보는 도구이므로, 과거 값은 4주 전 커밋을 체크아웃한 트리에 같은 도구를 돌려 얻는다(신호 4와 같은 방식). 두 값을 비교한다.

**기본 임계값** — **2배 이상 증가**하고 동시에 **현재 절대값이 10 이상**.

> 근거: 배수만 보면 2→4 같은 노이즈가 걸린다. 절대 하한 10은 "이 쌍이 이미 실질적으로 얽혀 있다"의 최소선이다. 4주는 추세로 인정할 만한 최소 구간이면서 원인이 된 작업을 아직 기억할 수 있는 길이다.

**해석** — 셋 중 하나다. 어느 쪽인지는 edge의 방향과 관계 표 선언 여부가 가른다.

| 관측 | 해석 | 제안 |
|---|---|---|
| 관계 표에 선언되지 않은 쌍 | 문서화되지 않은 결합이 자라고 있다 | 관계를 선언하거나(유형·계약 포함) 의존을 끊는다 |
| 양방향 edge가 모두 늘었다 | 경계가 잘못 그어졌다 | 병합, 또는 공유 개념을 shared-kernel로 추출 |
| 한 방향으로만 늘었다 | 상류 컨텍스트가 여러 책임을 지고 있다 | 상류 분리, 또는 관계 유형을 명확히(customer-supplier/acl) |

**보조 지표** — 같은 기간 한쪽 컨텍스트의 모듈 크기가 함께 늘었다면 3행(책임 비대) 해석의 근거가 되고, 크기는 그대로인데 edge만 늘었다면 1·2행(경계 문제) 쪽이다. 보조 지표 단독으로는 제안을 만들지 않는다.

**제안 문구**

```
[관계 재정의] `{컨텍스트 A}` → `{컨텍스트 B}`
관측: 의존 edge {이전}개 → {현재}개 (4주, {배수}배). 관계 표 선언: {선언된 유형 또는 "없음"}.
해석: {위 표의 해당 행}.
선택지: ① 관계 표에 {제안 유형}으로 선언 ② 두 컨텍스트 병합 ③ 공유 개념을 shared-kernel 공용 모듈로 추출 ④ acl을 두어 결합을 격리 ⑤ 유지 — 의도된 일시적 작업의 결과라면(다음 실행에서 재평가)
```

## 5. 신호 4 — baseline 정체

**정의** — 이행 중인 컨텍스트의 동결 위반(baseline)이 오랫동안 줄지 않는다.

**측정** — `baseline.jsonl`의 줄 수를 시점별로 비교한다(git 이력으로 과거 시점의 크기를 얻는다).

**기본 임계값** — **4주(28일) 동안 10% 미만 감소**. 최소 조건: baseline이 비어 있지 않고 `이행` 라벨이 있는 컨텍스트.

> 근거: 4주는 2스프린트다. 이행이 실제로 진행 중이라면 그 사이에 클러스터 하나는 정리된다. 10%는 "우연히 몇 줄 사라진 것"과 "의도적으로 줄인 것"을 가르는 선이다.

**해석** — 이행이 멈췄다는 사실만 확실하다. 원인은 둘 중 하나이고, 이 둘은 정반대의 조치를 요구한다.

- **이행할 여력이 없었다** → migrate를 한 클러스터만 실행한다. 부채는 래칫으로 늘지는 않고 있으니 급하지 않다.
- **목표 스타일이 과했다** → 애초에 도달 불가능한 목표였는지 본다. 이 경우 계속 밀어붙이는 것보다 목표를 낮추는 편이 정직하다.

구분 방법: baseline 위반이 소수 규칙(1~2개 rule id)에 몰려 있으면 목표가 과했을 가능성이 크다. 여러 규칙에 고르게 퍼져 있으면 단순히 손을 못 댄 것이다.

**baseline이 커진 경우는 신호가 아니라 오류다.** 래칫 위반이므로 제안이 아니라 경고로 보고한다 — baseline은 migrate로만 축소되며 어떤 경로로도 증가하지 않아야 한다.

**제안 문구**

```
[이행 정체] 컨텍스트 `{컨텍스트}` — {출발 스타일} → {목표 스타일}
관측: baseline {이전}건 → {현재}건 (4주간 {감소율}% 감소). 위반이 몰린 규칙: {상위 rule id 목록}.
해석: {소수 규칙 집중이면 "목표 스타일이 과했을 가능성" / 고른 분포면 "이행 작업이 진행되지 않음"}.
선택지: ① migrate로 클러스터 1개 실행({추천 클러스터}) ② 목표 스타일을 {완화 후보}로 낮추고 ADR 기록 ③ 이행 포기 — 현재 스타일을 정식 선언으로 인정 ④ 유지 — 다음 분기에 재평가
```

## 6. 신호 5 — 반복되는 의미론 지적

**정의** — 리뷰의 의미론 판단(기계 검증이 아닌 지적)에서 같은 주제가 반복된다.

**측정** — 최근 90일 `review-log.jsonl`에서 semantic 유형 지적을 주제별로 묶는다. 주제 분류는 기계적으로 완전하지 않으므로 `evolve`가 후보를 제시하고 사용자가 확인한다.

**기본 임계값** — 같은 주제 **3회 이상**, 그리고 **서로 다른 파일 2개 이상**에서 발생.

> 근거: 신호 2와 같은 기준을 쓴다. 서로 다른 파일을 요구하는 것은 "한 곳의 문제"와 "프로젝트 전반의 판단 기준 부재"를 가르기 위해서다.

**해석** — 같은 지적이 반복된다는 것은 그 판단 기준이 리뷰어(사람이든 LLM이든)의 머릿속에만 있고 프로젝트에 기록되어 있지 않다는 뜻이다. 문서로 승격하면 다음 리뷰부터는 판단이 아니라 인용이 되고, 리뷰 경험이 프로젝트 지식으로 축적된다.

**분기** — 승격 대상이 어느 쪽인지 먼저 가른다.

- **기계 검증이 가능하다** → 문서가 아니라 규칙이다. `rule-vocabulary.md` §6 체크리스트로 기존 primitive 조합인지 보고, 아니면 어휘 확장을 검토한다.
- **사람의 해석이 필요하다** → `docs/architecture/conventions/<key>.md`로 승격한다. `knowledge-doc-template.md` 표준을 따르고, 최소한 "적용 기준"과 "규칙"(체크리스트) 섹션을 갖춰야 판정 근거로 쓰인다.

**제안 문구**

```
[컨벤션 승격] 주제 "{주제}"
관측: 최근 90일 의미론 지적 {N}회 — 파일 {F}개, 컨텍스트 {C}개.
반복된 지적: {대표 지적 문구 2~3개}
해석: 판단 기준이 프로젝트에 기록되어 있지 않습니다.
선택지: ① `docs/architecture/conventions/{제안 key}.md` 초안 생성 ② 기계 검증이 가능하다면 규칙화 검토(rule-vocabulary §6) ③ 기존 conventions 문서에 항목 추가 ④ 일회성으로 판단 — 승격하지 않음
```

## 7. 제안 리포트 규약

`evolve`의 출력은 제안 목록이며, 각 제안은 다음을 모두 포함한다.

1. **관측 수치** — 임계값과 실제 값을 함께. 사용자가 해석을 뒤집을 수 있어야 한다.
2. **해석** — 이 문서의 어느 규칙을 적용했는지.
3. **선택지** — 항상 "변경하지 않음"을 포함한다. 선택지가 하나뿐인 제안은 제안이 아니다.
4. **ADR 초안** — `proposed` 상태로. 사용자가 수락하면 `accepted`가 된다(`adr-template.md` §3).

**우선순위** — 여러 제안이 동시에 뜨면 이 순서로 제시한다: 신호 4(오류에 가까움) → 신호 3(구조 문제) → 신호 1(분류) → 신호 2 → 신호 5. 한 번에 제시하는 제안은 5개를 넘기지 않는다 — 그 이상은 읽히지 않고, 읽히지 않는 제안은 소음이다.

**도메인 모델 재편 제안(용어·추상화 개선, 애그리거트 재편 — 스펙 §6.7.3)은 여섯 번째 신호가 아니다.** 전용 수집 항목도 임계값도 없으므로 단독으로 산출되지 않는다. 이 제안이 서는 자리는 위 다섯 신호의 **해석 안**이다 — 신호 1의 「제안 전에 확인할 것」 셋째 갈래(여러 책임이 한 컨텍스트에 섞여 있다)와 신호 5의 반복 지적 주제가 용어·경계 문제를 가리킬 때, 그 제안의 선택지 하나로 붙인다. 관측은 그 신호의 것을 그대로 쓰고 새 임계값을 만들지 않는다. 처분은 언제나 **`/superarchitect:model` 세션의 안건으로 넘기는 것**이며 `evolve`는 domain 문서를 쓰지 않는다(`domain-doc-template.md` §5가 「열린 질문」의 출처를 `model`·`review`·`apply` 셋으로 닫아 두었다).
