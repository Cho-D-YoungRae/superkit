# superdomain 0.9.0 — ADR을 이유의 기록으로 쓰는 설계 스펙

- 날짜: 2026-11-11
- 상태: 승인됨(2026-11-11). 구현하면서 고친 곳은 본문에 날짜와 함께 적었다
- 근거: [ADR 개선 검토](2026-11-11-superdomain-adr-review.md). 숫자, 실험, 버린 안은 그 문서에 있다
- 전제: [0.8.0](2026-11-10-superdomain-external-conciseness-design.md)이 먼저 적용된다. 아래의 "지금 문구"는 0.8.0을 적용한 뒤의 문구다

## 1. 목표

ADR을 결정을 내린 때의 이유를 남기는 기록으로 쓴다. 저장소 다른 곳에 있는 것은 적지 않고, ADR에만 있는 것(이유, 버린 안, 받아들인 비용, 바뀐 관계)을 결정마다 붙인다.

| 문제 | 0.9.0에서 고치는 곳 |
|---|---|
| 지위가 정해져 있지 않아 규칙의 사본이 ADR에 쌓인다 | 목적 문장, 살아 있는 문서와의 구분 |
| 코드 이름·값·절차가 들어가 낡고, 코드가 바뀔 때마다 따라 고친다 | 템플릿의 "적지 않는 것" |
| 분량 기준이 줄 수라 한 줄이 길어지면 막지 못한다 | 글자 수, 결정 블록 |
| 결정이 바뀐 표시가 빠지거나, 있어도 무엇이 바뀌었는지 없다 | `바뀜` 줄 |
| 쓰이지 않는 절차가 있다(`proposed`, 승인 모드, 한 번에 하나씩 인터뷰) | 삭제 |
| 승인 화면에서 초안 전문이 그대로 통과된다 | 요지를 먼저 보여 준다 |
| 쓰게 하는 지점만 있고 읽게 하는 지점이 없다 | 포인터 줄, 찾아 읽기 |
| ADR 대부분이 스킬을 거치지 않고 쓰인다 | 포인터 줄에 쓰기 규칙 한 문장 |

원칙:

1. ADR에는 저장소 다른 곳에 없는 것만 적는다.
2. 지금 따를 규칙은 살아 있는 문서(DOMAIN.md, 지침 파일)가 갖는다.
3. 한 벌로 쓴다. 사람용과 에이전트용을 나누지 않고 색인 파일도 두지 않는다.
4. 0.4.0의 원칙(스크립트 없음, 지식은 주제마다 파일 하나, 확정은 사용자, 지어내지 않는다)을 그대로 따른다.

### 비목표

- 색인 파일, ADR 파싱, 글자 수를 세는 스크립트
- 쓰는 기준(세 신호, 판단이 서지 않으면 쓴다)과 제안 시점(작업을 마치면)의 변경. 둘 다 사용자가 요청해 넣은 것이다. 기준에 예시를 더하는 것(D18)은 기준 문구를 바꾸지 않는다
- 파일 이름(`yyyy-MM-dd-slug.md`)과 경로(`docs/superdomain/adr/`)의 변경
- review 스킬과 두 리뷰어의 변경
- 기존 ADR을 새 형식으로 다시 쓰기
- noguesstoday의 지침과 ADR 수정(§9)

## 2. 확정된 결정

검토서 결정표의 추천대로다(2026-11-11).

| # | 결정 |
|---|---|
| D1 | 사용자는 ADR 파일을 세션 밖에서 거의 읽지 않는다. 파일은 다음 세션의 Claude가 찾아 읽는 기록으로 쓰고, 사람은 승인 화면과 Claude가 찾아서 보여 주는 답에서 본다 |
| D2 | ADR은 이유의 기록이다. 지금 따를 규칙은 살아 있는 문서가 갖고, 둘이 다르면 살아 있는 문서를 따르고 사용자에게 알린다 |
| D3 | 저장소 다른 곳에 있는 것은 적지 않는다. 규칙의 조건·예외 전문, 프로젝트 코드의 이름, 맞추려고 고른 값, 절차, 경위, 변경 이력이다 |
| D4 | 긴 기록은 따로 만들지 않는다. 설계 문서가 있으면 `상세` 한 줄로 가리킨다 |
| D5 | 함께 확정한 결정은 한 ADR에 묶고 결정마다 블록으로 쓴다. "한 ADR에 결정 하나"는 없앤다 |
| D6 | 분량은 글자 수로 재고 결정 블록에 건다. 블록 하나 1,000자가 점검선이다. 파일 전체 길이는 묶지 않는다 |
| D7 | 병합 전에는 고친다. 병합 뒤에는 문장을 고치지 않고 바뀐 결정에 `바뀜` 한 줄만 붙인다. 코드가 바뀌었다고 ADR을 고치지 않는다 |
| D8 | 승인 화면에는 요지를 먼저 보여 준다. 결정문 목록, 바뀌는 기존 결정의 전후, Claude가 사용자의 말 없이 채운 문장이다. 전문은 그 아래에 둔다 |
| D9 | 색인 파일을 두지 않는다. Claude가 제목 줄을 훑어 찾고, 포인터 줄에 읽는 때를 더한다 |
| D10 | 쓰는 기준과 제안 시점은 바꾸지 않는다. 묶음 안에서 버린 안도 받아들인 비용도 없는 결정은 블록으로 세우지 않는다 |
| D11 | 기존 ADR은 다시 쓰지 않는다. 결정이 바뀌면 머리의 표시에 어느 결정이 무엇으로 바뀌었는지를 적는다 |
| D12 | 구현 전에 시험한다(§8) |
| D13 | 0.8.0과 나눠 0.9.0에 싣는다 |
| D14 | `proposed` 상태와 승인 모드를 없앤다. 한 번도 쓰이지 않았다 |
| D15 | 한 번에 하나씩 묻는 인터뷰를 초안 한 번으로 바꾼다 |
| D16 | ADR은 날짜가 아니라 파일 이름으로 가리킨다 |
| D17 | 옛 포인터 줄이 있으면 새 줄로 바꿀지 묻는다 |
| D18 | 쓰는 기준에 쓰는 예와 쓰지 않는 예를 짝으로 더한다. "비싸거나 중요한"만으로는 경계가 흐리다. 검토서에는 없던 결정이고 2026-11-11에 사용자가 정했다 |

결정표에 추천이 없어 기본값으로 정한 것(검토 때 바꿀 수 있다):

- **상태 줄을 없앤다.** `proposed`가 없으면 폴더의 ADR은 모두 확정된 결정이라 상태 줄에 정보가 없다. 모든 결정이 바뀐 ADR은 머리에 `대체됨` 한 줄을 단다.
- **새 ADR을 쓰지 않는 변경에도 `바뀜` 줄을 붙인다.** 링크 없이 무엇이 무엇으로 바뀌었는지만 적는다. 새 ADR은 그 변경이 쓰는 기준에 들 때만 쓴다. 새로 더한 결정은 바뀜이 아니라 새 기록이다.
- **`바뀜` 줄은 블록 제목 바로 아래에 둔다.** 블록의 분량에는 세지 않는다. 결정 번호는 병합 뒤에 바꾸지 않는다.
- **"병합 뒤"는 ADR을 쓴 브랜치가 PR의 대상 브랜치에 병합된 뒤다.** 브랜치 없이 일하면 커밋한 뒤다.
- **옛 형식의 기록은 본문을 건드리지 않는다.** 이 템플릿의 결정 블록을 쓰지 않은 파일은 머리에 `바뀜` 줄을 달고, 결정에 번호가 있으면 번호를 함께 적는다. 새 형식의 기록은 블록 제목 아래에 단다.
- **형식을 따로 정하는 것은 지침 파일뿐이다.** 지침 파일이 ADR 형식을 정했으면 그것을 따른다. 폴더의 옛 기록이나 ADR에 적힌 형식 결정은 본으로 삼지 않는다.
- **리뷰어의 `바뀜` 짝 검사는 넣지 않는다.** 리뷰어는 가이드의 절을 기준으로 지적하는데 ADR 규칙은 가이드에 없고, review 스킬이 넘기는 기준 문서도 바꿔야 한다. §8의 시험에서 `바뀜` 줄이 빠지면 다시 본다.
- **찾는 방법을 스킬에 한 절로 둔다.** 새 모드는 아니다. description에 찾아볼 때의 요청 문구를 더한다.
- 버전은 0.9.0이다.

## 4. `adr-template.md`

아래 코드 블록과 인용 블록은 템플릿에 들어갈 문구의 초안이다.

### 4.1 형식

```markdown
# <무엇을 정했는지 한 문장>

- 날짜: YYYY-MM-DD
- 지금 규칙이 있는 곳: <이 결정의 규칙을 적어 둔 문서와 절>
- 정하지 않은 것: <이 기록의 범위 밖>
- 상세: <설계 문서 링크>

## 1. <결정문 한 문장>
<따라 나오는 규칙 한두 문장>
- 이유: <왜 이렇게 정했는가. 두세 문장>
- 버린 안: <안> — <버린 이유>
- 비용: <받아들인 제약·위험>
- 다시 볼 때: <이 결정을 다시 볼 조건>

## 2. <결정문 한 문장>
```

> - **제목**: 결정문 한 문장이다. "인증 방식 검토" 같은 명사구로 쓰지 않는다. 결정이 여럿이면 묶음을 한 문장으로 말한다.
> - **지금 규칙이 있는 곳**: 프로젝트가 이 결정의 규칙을 적어 둔 문서와 절. 이 기록과 그 문서가 다르면 그 문서가 맞다. 적을 곳이 없으면 줄을 지운다.
> - **정하지 않은 것**: 이 기록이 다루지 않기로 한 범위. 버린 것과 정하지 않은 것을 가른다. DOMAIN.md에서 뺀 미정 정책을 모으는 자리가 아니다. 없으면 줄을 지운다.
> - **상세**: 구현의 모양과 경위가 적힌 설계 문서. 없으면 줄을 지운다.
> - **결정 블록**: 함께 확정한 결정마다 하나씩 쓴다. 제목은 결정문이고 "~를 고려한다"로 쓰지 않는다. 결정이 하나면 블록 제목을 두지 않고 머리 아래에 바로 쓴다.
> - **따라 나오는 규칙**: 결정문만으로 알 수 없는 것 한두 문장. 이 규칙을 깨야 할 때 가는 길, 미뤄 둔 것을 언제 어디서 정하는지를 적는다. 조건과 예외를 모두 풀어 쓰지 않는다.
> - **이유·버린 안·비용·다시 볼 때**: 그 결정에 해당하는 것만 적는다. 없으면 줄을 지운다. 버린 안은 안마다 한 줄씩 쓴다. 버린 안도 비용도 없는 결정은 블록으로 세우지 않고, 관련된 결정의 따라 나오는 규칙에 넣는다.

예시는 이렇게 둔다.

```markdown
# 주문 취소는 배송 시작 전까지만 받고, 환불은 payment가 실행한다

- 날짜: 2026-03-11
- 지금 규칙이 있는 곳: DOMAIN.md의 order·payment 규칙
- 정하지 않은 것: 부분 취소. 필요해지면 따로 정한다
- 상세: [주문 취소 설계](../../design/2026-03-order-cancel.md)

## 1. 배송이 시작된 주문은 취소하지 않는다
- 바뀜(2026-05-02): 배송 시작 전까지 → 출고 지시 전까지 → [2026-05-02-cancel-until-dispatch-order](2026-05-02-cancel-until-dispatch-order.md)
배송이 시작된 뒤에는 반품으로 받는다.
- 이유: 배송이 시작되면 물류사에 회수를 요청해야 해서 취소가 아니라 반품과 같은 일이 된다.
- 버린 안: 수령 전까지 취소 — 회수 비용을 누가 내는지 정하지 못했다
- 비용: 배송 직후 마음을 바꾼 고객은 반품 절차를 밟아야 한다

## 2. 환불은 order가 아니라 payment가 실행한다
order는 취소를 확정하고 환불을 요청만 한다.
- 이유: 환불 금액에는 PG 수수료와 부분 승인 내역이 필요하고 그것은 payment만 안다.
- 버린 안: order가 PG를 직접 호출 — PG 연동이 두 도메인에 흩어진다
- 다시 볼 때: 결제 수단이 하나로 줄어 환불 금액 계산이 단순해지면
```

### 4.2 결정이 바뀌었을 때

> - 바뀐 결정의 블록 제목 바로 아래에 `- 바뀜(YYYY-MM-DD): <무엇이 무엇으로>`를 붙인다. 그 변경을 새 ADR로 썼으면 줄 끝에 `→ [<새 파일명>](<새 파일명>.md)`를 단다. 결정이 하나뿐인 기록은 머리에 붙인다.
> - 새 ADR에는 옛 결정을 `버린 안`에 적는다. `- 버린 안: <옛 결정>([<옛 파일명>](<옛 파일명>.md) 결정 N, 따르다가 버렸다) — <바꾼 이유>`. 바꾼 이유가 그 블록의 이유와 같으면 "이유와 같다"고 적는다.
> - 결정이 둘 이상인 기록에서 모든 결정이 바뀌었으면 블록마다 달지 않고 머리에 `- 대체됨: [<새 파일명>](<새 파일명>.md)` 한 줄을 단다. 결정이 하나뿐인 기록은 `바뀜` 줄만 쓴다.
> - 옛 형식의 기록(이 템플릿의 결정 블록을 쓰지 않은 파일. 상태 줄이 있으면 옛 형식이다)은 본문을 건드리지 않는다. 머리에 `- 바뀜(YYYY-MM-DD): <무엇이 무엇으로> → [<새 파일명>](<새 파일명>.md)`를 단다. 결정에 번호가 있으면 `결정 N — `을 앞에 적는다(`결정 3 — <무엇이 무엇으로>`). 프로젝트가 머리 표시에 다른 이름을 쓰고 있으면 그 이름을 따르되 무엇이 무엇으로 바뀌었는지는 적는다.
> - 블록을 읽을 때는 제목부터 다음 제목 앞까지 읽는다. `바뀜` 줄이 있으면 그 블록의 나머지는 바뀌기 전의 내용이다.

### 4.3 적지 않는 것

> | 적지 않는 것 | 대신 |
> |---|---|
> | 프로젝트 코드의 클래스·함수·테이블·모듈 이름. 이름 자체가 결정이면 적는다 | 역할로 풀어 쓴다. 가리키는 줄(지금 규칙이 있는 곳, 상세)에는 문서와 절 이름을 적는다 |
> | 맞추려고 고른 값(타임아웃, 재시도 횟수). 정책으로 정한 기간·한도는 결정이므로 적는다 | 그 값을 고른 이유 한 줄과 값이 있는 곳 |
> | 규칙의 조건과 예외를 모두 푼 전문 | 살아 있는 문서. ADR에는 결정문과 따라 나오는 규칙 한두 문장만 |
> | 구현 절차, 검증 기록, 후속 작업 목록 | 설계 문서, 계획, 이슈 |
> | 논의가 오간 경위, 다른 문서에 미친 영향 목록, 수정 이력 | 커밋과 PR |
> | 검토하지 않은 대안, 사용자가 말하지 않은 이유, 없는 비용 | 적지 않는다 |

### 4.4 분량

> 공백을 포함한 글자 수로 잰다. 링크 주소, 목록 기호, `바뀜` 줄은 세지 않는다. 결정 블록 하나가 1,000자를 넘으면 적지 않는 것이 들어갔는지, 결정 여럿이 한 블록에 묶였는지 본다. 파일 전체 길이에는 한도를 두지 않는다. 줄 수로는 재지 않는다.

## 5. `adr/SKILL.md`

절 순서는 목적, 1 모드, 2 신규, 3 바꿈, 4 고쳐도 되는 것, 5 찾아 읽기, 6 후속 제안, 하지 않는 것이다. 승인(지금 3절)과 부분 조정(지금 5절)은 없앤다.

### 5.1 description과 목적

description은 "기존 ADR을 승인·대체·부분 조정할 때"를 "기록해 둔 결정이 바뀌었을 때, 정해진 것을 바꾸기 전에 관련 기록을 찾아볼 때"로 바꾼다. 예시 요청에서 "ADR 승인", "ADR 대체"를 빼고 "이 결정 바뀌었어", "전에 왜 이렇게 정했지"를 넣는다.

목적 문단은 이렇게 바꾼다.

> 비싸거나 중요한 결정을 `docs/superdomain/adr/yyyy-MM-dd-slug.md`에 남긴다. 이 기록은 그 결정을 왜 그렇게 내렸는지를 남긴다. 읽는 쪽은 정해진 것을 바꾸려 하거나 버린 안을 다시 꺼내려는 다음 세션의 Claude다. 지금 따를 규칙은 DOMAIN.md와 지침 파일에 있다. 이 기록과 그 문서가 다르면 그 문서를 따르고 다르다는 것을 사용자에게 알린다.
>
> **핵심 원칙:** 사실만 적는다. 검토하지 않은 대안이나 사용자가 말하지 않은 이유를 지어내지 않는다. 저장소 다른 곳에 있는 것은 옮겨 적지 않는다.

### 5.2 모드

> | 요청 | 모드 |
> |---|---|
> | 새 결정을 기록한다 | 신규 |
> | 기록해 둔 결정이 바뀌었다 | 바꿈 |
> | 요청은 없지만 방금 끝낸 작업에 비싸거나 중요한 결정이 있었다 | 제안 |

제안의 문구는 지금 그대로 둔다. 모드 표 아래의 "대체인지 부분 조정인지 애매하면…" 문단은 "바꾸려는 결정에 이미 `바뀜` 줄과 새 기록 링크가 있거나 기록에 `대체됨` 줄이 있으면, 링크를 따라가 지금 유효한 기록의 결정을 대상으로 한다"로 바꾼다(결정이 하나뿐인 기록에는 `대체됨`이 붙지 않으므로 `바뀜` 줄의 링크도 따라가게 했다. 전체 리뷰 뒤 2026-11-12에 고쳤다).

### 5.3 신규

지금의 "기존 ADR을 훑는다"는 그대로 둔다. 기록해 둔 결정을 바꾸는 것이면 바꿈을 제안한다. 같은 주제의 기록이 있어도 결정을 새로 더하는 것이면 바꿈이 아니라 새 기록으로 쓴다(§2의 기본값 "새로 더한 결정은 바뀜이 아니라 새 기록이다"가 스킬 문구에 빠져 있었다).

1번(쓸 결정인가)은 세 신호와 "판단이 서지 않으면 쓴다"를 그대로 두고, 그 아래에 예시를 더한다.

> 아래는 예시이고 전부가 아니다. 표에 없는 종류의 결정도 세 신호로 판단한다.
>
> | 신호 | 쓰는 예 |
> |---|---|
> | 되돌리는 비용이 크다 | 주문의 단위를 상품에서 상품 옵션으로 바꾼다. 도메인을 나누거나 합친다. 밖에 공개한 API 계약을 정한다 |
> | 여러 대안 중에서 골랐다 | 환불을 order가 아니라 payment가 실행한다. 재고 차감을 이벤트가 아니라 동기 호출로 한다 |
> | 나중에 "왜?"라고 물을 것이다 | 보통과 다르게 했다(결제 호출을 재시도하지 않는다). 일부러 하지 않기로 했다(부분 취소는 받지 않는다). 규칙에 예외를 뒀다 |
>
> | 쓰지 않는 예 | 대신 남기는 곳 |
> |---|---|
> | 클래스·패키지 이름, 타임아웃 값 같은 구현 세부 | 코드와 설정 |
> | 코드 한 곳에서 끝나는 이유 | 코드 주석 |
> | 버린 안도 받아들인 비용도 없는 규칙 | DOMAIN.md `규칙`이나 지침 파일의 한 줄 |
> | 대안이 없던 표준 선택, 버그 수정, 이름 바꾸기 | 커밋 메시지 |
> | 아직 검토 중인 것 | 정한 뒤에 쓴다 |

2번부터는 이렇게 바꾼다.

> 2. **함께 확정한 결정은 한 ADR에 묶는다.** 결정마다 블록을 쓴다. 버린 안도 받아들인 비용도 없는 결정은 블록으로 세우지 않고, 관련된 결정의 따라 나오는 규칙에 넣는다.
> 3. **초안을 한 번에 쓴다.** 대화와 코드에서 확인한 것으로 전체를 쓴다. 사용자가 직접 말하지 않았는데 대화나 코드에서 읽어 채운 문장은 따로 적어 둔다.
> 4. **버린 안**: 사용자가 말한 안, 또는 제안한 안 중 사용자가 "그것도 봤다"고 확인한 것만 적는다. 버린 이유도 사용자에게서 받는다. 버린 안이 하나도 없으면 ADR로 쓸 결정이 맞는지 다시 확인한다.
> 5. **비용이 비면 한 번 묻는다.** 그래도 없다고 하면 줄을 지운다. 없는 비용을 지어내지 않는다.
> 6. **적지 않는 것과 분량은 템플릿을 따른다.**
> 7. **결론이 살아 있는 문서에 있는지 본다.** 있으면 머리의 `지금 규칙이 있는 곳`에 적는다. 없으면 어느 문서에 한 줄로 적을지 제안한다. DOMAIN.md는 이 스킬이 직접 고치지 않고 `/superdomain:domain`을 안내한다. 지침 파일은 넣을 문장을 보여 주고 동의를 받아 쓴다(대상 지침 파일은 6절과 같다).
> 8. **요지를 먼저 보여 주고 확정받는다.** 요지는 결정문 목록과, 3번에서 따로 적어 둔 채운 문장이다. 채운 문장은 문장마다 맞다·고친다·뺀다로 묻는다. 전문은 그 아래에 보여 준다. 확정받은 뒤 파일을 쓴다. 이름은 `docs/superdomain/adr/<오늘 날짜>-<slug>.md`다(날짜는 `date +%F`, slug는 영문 소문자와 하이픈이고 결정의 방향이 드러나게 짓는다). 같은 이름이 있으면 slug를 바꾼다.
> 9. **다른 작업의 일부로 쓸 때**(하위 에이전트, 계획의 문서 작업)는 사용자가 확정한 결정문을 넘겨받아 쓰고 새로 짓지 않는다. 채운 문장의 목록을 부른 쪽에 돌려주고, 부른 쪽이 병합 전에 사용자에게 확인받는다.

형식을 따로 정하는 것은 지침 파일뿐이고 지침 파일이 정했으면 그것을 따른다는 문장과, 폴더의 옛 기록이나 ADR에 적힌 형식 결정은 본으로 삼지 않는다는 문장을 이 절 끝에 둔다(§2의 기본값).

### 5.4 바꿈

> 병합된 기록의 결정이 바뀌었을 때 쓴다. 병합 전의 기록이면 `바뀜` 줄을 달지 않고 4절대로 문장을 고친다.
>
> - 어느 기록의 어느 결정이 무엇에서 무엇으로 바뀌었는지 사용자에게 확인받는다.
> - 옛 기록에 `바뀜` 줄을 붙인다(템플릿 "결정이 바뀌었을 때"). 다른 문장은 고치지 않는다.
> - 그 변경을 새 ADR로 쓸지는 2절 1번으로 판단한다. 쓴다면 2절의 1번부터 끝까지 따라 쓰고, 옛 결정을 `버린 안`에 옛 파일 링크와 함께 적는다. 요지에는 바뀌는 결정의 전후를 넣는다.
> - 한쪽만 적고 끝내지 않는다. 새 ADR을 썼으면 옛 기록의 `바뀜` 줄에 그 링크가 있어야 한다.
> - 살아 있는 문서의 규칙이 함께 바뀌었는지 본다. 바뀌지 않았으면 고치자고 안내한다.

### 5.5 고쳐도 되는 것

> - **병합 전**: 자유롭게 고친다. 사용자가 확정한 문장을 바꾸면 다시 확인받는다. 병합 전은 ADR을 쓴 브랜치가 PR의 대상 브랜치에 병합되기 전이고, 브랜치 없이 일하면 커밋하기 전이다.
> - **병합 뒤**: `바뀜`·`대체됨` 줄, 머리의 가리키는 줄(지금 규칙이 있는 곳, 상세), 깨진 링크, 오타만 고친다. 결정 번호는 바꾸지 않는다.
> - 코드가 바뀌었다고 기록의 문장을 따라 고치지 않는다. 기록에는 코드를 따라 바뀔 내용을 적지 않는다.

### 5.6 찾아 읽기

> 정해진 구조·정책을 바꾸는 제안을 하거나 받았을 때, 또는 "전에 왜 이렇게 정했지"라는 물음에 쓴다.
>
> - `docs/superdomain/adr/`에서 `#`과 `##`으로 시작하는 줄을 훑어 관련 기록을 고른다. 색인 파일은 만들지 않는다.
> - 해당 결정 블록을 제목부터 다음 제목 앞까지 읽는다. 머리의 `정하지 않은 것`과 `대체됨`도 본다. 옛 형식의 기록은 머리의 바뀜 표시를 함께 읽는다.
> - 답할 때는 결정문, 이유, 버린 안을 파일 이름과 결정 번호와 함께 보여 준다.
> - 기록과 살아 있는 문서가 다르면 살아 있는 문서를 따르고 다르다는 것을 알린다.

### 5.7 후속 제안과 하지 않는 것

후속 제안의 첫 항목(도메인 정의를 바꾸면 domain 스킬 안내)은 0.8.0의 문구 그대로다. 포인터 줄 항목은 줄을 아래로 바꾸고 "옛 줄이 있으면 바꿀지 묻는다"를 더한다.

```
- 결정 기록: docs/superdomain/adr/ (정해진 구조·정책을 바꾸는 제안을 하거나 받으면 먼저 관련 기록을 찾아 읽는다. 비싸거나 중요한 결정을 내린 작업을 마치면 /superdomain:adr로 기록할지 제안한다. 기록에는 결정마다 이유·버린 안·비용을 적고, 결정이 아닌 코드 이름과 절차는 적지 않는다)
```

하지 않는 것은 이렇게 둔다.

> - 검토하지 않은 대안, 사용자가 말하지 않은 이유, 없는 비용을 지어내지 않는다.
> - 확인 없이 `바뀜`·`대체됨` 줄을 달지 않는다.
> - 병합된 기록의 문장을 고치지 않는다. 코드에 맞춰 고치지도 않는다.
> - 옛 기록을 새 형식으로 다시 쓰지 않는다.
> - 색인 파일을 만들지 않는다.
> - DOMAIN.md를 직접 고치지 않는다.

## 6. 그 밖의 파일

- `conventions.md` 「자명하지 않은 규칙은 KDoc으로 남긴다」 끝에 "여러 클래스에 걸친 결정이면 이유는 ADR에 두고 KDoc에는 그 파일 이름을 적는다"를 더한다.

## 8. 구현 전 시험

스킬과 템플릿의 초안 문구가 나온 뒤, 파일을 확정하기 전에 한다. 하위 에이전트 몇 개로 하고 플러그인에 스크립트를 남기지 않는다. 검토서의 재실험이 잰 형식과 이 스펙의 형식은 다르다(`바뀜` 줄의 위치, 빈 줄 지우기, 결정이 하나일 때의 모양, 값의 예외). 이 차이는 아직 시험되지 않았다.

| 시험 | 방법 | 통과 | 실패하면 |
|---|---|---|---|
| 조정 | 새 형식 ADR 둘(템플릿 예시 수준 하나, 실제 프로젝트 ADR을 옮긴 것 하나)에 변경 셋을 시킨다. 결정 하나가 뒤집힘, 결정이 좁혀짐(새 ADR 없이), 코드 이름만 바뀜. 조건은 스킬 문구를 준 경우와 포인터 줄만 준 경우 둘이다 | 앞의 둘에서 `바뀜` 줄이 제목 아래에 무엇이 무엇으로와 함께 붙고 옛 문장은 그대로다. 뒤집힌 경우 새 기록의 `버린 안`에 옛 파일 링크가 있다. 코드 이름만 바뀐 경우 기록을 고치지 않는다 | 스킬 문구 조건에서 실패하면 문구를 고쳐 다시 한다. 포인터 줄 조건에서만 실패하면 결과를 이 스펙에 적고 리뷰어 짝 검사(§2의 기본값)를 다시 정한다 |
| 블록만 읽기 | 실제 프로젝트 ADR 셋을 새 형식으로 옮기고 ADR마다 문제 다섯을 새로 낸다(결정 2, 버린 안 2, 상태·조정 1). 문서를 통째로 읽은 답과 해당 블록만 읽은 답을 견준다 | 블록만 읽은 답에 오답이 없다. 머리에만 있는 내용 때문에 갈린 문항은 따로 센다 | `정하지 않은 것`을 해당 블록 안에 두도록 형식을 고친다 |
| 판단 | 결정 여섯을 주고 ADR로 쓸지 판단하게 한다. 셋은 쓰는 쪽, 셋은 쓰지 않는 쪽이고 예시 표의 문구와는 다른 사례로 낸다. 하나는 표에 없는 종류다 | 쓰지 않는 쪽은 대신 남길 곳을 말한다. 표에 없는 종류를 "표에 없으니 쓰지 않는다"고 하지 않는다 | 예시의 문구를 고쳐 다시 한다 |
| 쓰기 | 설계 논의가 담긴 대화 하나를 주고 신규 ADR을 쓰게 한다 | 적지 않는 것이 들어가지 않고, 블록이 1,000자 이하이며, 채운 문장이 요지에 따로 나온다 | 템플릿의 문구를 고쳐 다시 한다 |

결과는 이 스펙의 끝에 절을 더해 적는다. 시험으로 형식이 바뀌면 §4와 §5를 함께 고친다.

## 9. 이행과 문서

CHANGELOG 0.9.0에 적을 이행 안내(기존 ADR은 플러그인이 고치지 않는다):

- 새 ADR부터 새 형식으로 쓴다. 옛 기록은 다시 쓰지 않는다.
- 상태(`proposed`·`accepted`·`superseded`)와 승인 모드가 없어졌다. 옛 기록의 상태 줄은 그대로 둔다.
- 부분 조정과 대체는 `바뀜` 줄로 합쳤다. 옛 기록의 결정이 바뀌면 머리에 무엇이 무엇으로 바뀌었는지를 적는다(결정에 번호가 있으면 번호도 적는다).
- ADR은 이유의 기록이다. 지금 따를 규칙을 ADR에만 적어 둔 프로젝트는 그 규칙을 DOMAIN.md나 지침 파일로 옮긴다. ADR을 규칙의 기준으로 삼는다고 지침 파일에 적어 둔 프로젝트는 그 지침이 우선한다.
- 지침 파일의 결정 기록 포인터 줄을 새 문구로 바꾼다.
- 코드 주석에서 ADR을 날짜로 가리키고 있으면 파일 이름으로 바꾼다.

noguesstoday에서 따로 정할 일(이 스펙의 범위 밖):

- 지침의 "채택 ADR이 기준이다"와 "채택 ADR에 없는 것은 아직 결정이 아니다"를 고칠지 정한다. 뒤 문장은 결정 로그를 없앤 ADR의 결정이기도 하므로, 고치려면 그 결정에 `바뀜`을 다는 일이 함께 필요하다.
- 옛 ADR에만 있고 살아 있는 문서에 없는 유효한 규칙을 한 번 훑는다.
- 표시 없이 바뀐 옛 ADR 10개의 머리에 표시를 단다.
- "ADR 본문은 고쳐 쓰지 않는다"와 형식을 정한 옛 ADR을 지침 파일로 옮길지 정한다. 옮기지 않으면 새 형식이 그대로 적용된다.

## 11. 구현 전 시험 결과

2026-11-12에 템플릿과 스킬의 새 문구로 시험했다. 시험 대상 에이전트는 하위 에이전트이고(조정·판단·쓰기·옮기기·문제 내기는 상위 모델, 답하기는 중간 모델), 통과 기준은 알려 주지 않았다. 사용자의 답은 "응, 그대로 해"로 고정했고 새 사실은 주지 않았다. 시험마다 한 번씩만 돌렸다.

| 시험 | 조건 | 결과 | 본 것 |
|---|---|---|---|
| 조정 | 스킬 문구를 따르게 함 | 통과 4/4 | 뒤집힘: 결정이 하나뿐인 기록의 머리에 `바뀜` 줄과 새 파일 링크가 붙었고 `대체됨`은 쓰지 않았다. 새 기록의 `버린 안`에 옛 파일 링크와 "따르다가 버렸다"가 있다. 좁혀짐: `## 1.` 바로 아래에 링크 없는 `바뀜` 줄만 붙고 새 파일은 없다. 이름만 바뀜: 기록을 고치지 않고 커밋 메시지를 안내했다. 옛 형식: 머리에 결정 번호와 무엇이 무엇으로가 적힌 줄이 붙었고(프로젝트가 쓰던 이름 `조정됨`을 따랐다) 본문은 그대로다 |
| 조정 | 포인터 줄과 스킬 목록만 줌 | 통과 4/4 | 위와 같은 모양이다. 따르라는 지시가 없었지만 에이전트가 스킬 파일과 템플릿을 스스로 읽었다 |

| 판단 | 결정 여섯 | 통과 6/6 | 쓰는 쪽 셋을 쓴다고 판단했고, 예시 표에 없는 종류(공급처 선택)를 표에 없다는 이유로 빼지 않았다. 쓰지 않는 쪽 셋은 코드와 설정, 코드 주석, DOMAIN.md `규칙`이나 지침 파일을 대신 남길 곳으로 말했다 |

처음 다섯 시험에서는 고친 문구가 없다. 그 뒤 전체 리뷰의 지적으로 넷을 고쳤고(§2의 옛 형식 기본값, §4.2의 옛 형식 항목, §5.2의 유효한 기록 따라가기, §5.3 끝 문장, §5.4 첫 문장), 위 재시험으로 다시 확인했다. 조정 시험이 두 조건에서 모두 통과했으므로 §2의 기본값(리뷰어의 `바뀜` 짝 검사는 넣지 않는다)을 그대로 둔다. 블록만 읽기에서 머리에만 있는 내용 때문에 갈린 문항이 하나 있었지만 오답이 아니라 "문서에 없음"이었고, 스킬의 찾아 읽기 절이 머리의 `정하지 않은 것`도 함께 보게 하므로 형식은 고치지 않았다.

옮기기에서 본 것: 블록 열하나가 모두 1,000자 이하였다(최대 889자). 버린 안도 비용도 없는 결정 셋은 블록으로 서지 않고 관련 블록의 따라 나오는 규칙이나 `다시 볼 때`에 들어갔다. 원문이 어느 결정이 바뀌었는지 적지 않은 머리 표시 하나는 `바뀜` 형식으로 옮기지 못하고 원문 줄 그대로 남았다(지어내지 않았다).

처음의 조정 시험은 §8과 조건이 둘 달랐다. 시험용 사본이 git 저장소가 아니어서 모든 기록을 병합된 것으로 다뤘고, 조정 재료에 실제 프로젝트 ADR을 새 형식으로 옮긴 것이 없었다(직접 쓴 기록, 템플릿 예시, 옛 형식 원문을 썼다). 둘 다 재시험에서 한 번씩 봤다.

시험하지 못한 것: 실제 사용자가 요지 화면에서 채운 문장을 가려내는지, 여러 세션에 걸쳐 `바뀜` 줄이 빠지지 않는지, 시험에 쓴 것과 다른 모델에서의 결과.

### 릴리스 전에 고친 것(2026-11-12)

전체 리뷰가 Minor로 남긴 것 가운데 하나를 사용자 결정으로 고쳤다. §2의 기본값 "새로 더한 결정은 바뀜이 아니라 새 기록이다"가 스킬에 없었고, 2절 머리에는 "같은 주제의 기록이 있으면 신규가 아니라 바꿈을 제안한다"만 있었다. 2절 머리를 "기록해 둔 결정을 바꾸는 것이면 신규가 아니라 바꿈을 제안한다. 같은 주제의 기록이 있어도 결정을 새로 더하는 것이면 바꿈이 아니라 새 기록으로 쓴다"로 고쳤다(§5.3). 3절의 "2절대로 쓰고"는 2절 머리로 되돌아가지 않게 "2절의 1번부터 끝까지 따라 쓰고"로 고쳤다(§5.4). 처음에는 "2절의 1~9번대로"라고 썼는데, 9번 뒤의 형식 문단(형식을 따로 정하는 것은 지침 파일뿐이다)이 빠진다는 독립 리뷰의 권고로 다시 고쳤다.

임시 git 저장소에서 시험했다. 병합된 기록 하나가 주문 취소를 다루고 부분 취소를 `정하지 않은 것`으로 두고 있다. 시험 대상은 상위 모델의 하위 에이전트이고, 통과 기준은 알려 주지 않았으며, 사용자의 답은 "응, 그대로 해"로 고정했다. 조건마다 한 번씩 돌렸다.

| 문구 | 요청 | 결과 |
|---|---|---|
| 고치기 전 | 같은 주제에 결정을 더한다(부분 취소를 받기로 정했다) | 새 기록 하나를 썼고 옛 기록은 그대로다. 다만 바꿈인지 신규인지를 사용자에게 먼저 물었고, 2절 머리가 바꿈으로도 읽힌다고 적었다 |
| 고친 뒤 | 같은 요청 | 새 기록 하나를 썼고 옛 기록은 그대로다. 모드를 묻지 않고 고친 문장을 근거로 댔다 |
| 고친 뒤 | 기록해 둔 결정을 바꾼다(취소 기한을 좁혔다) | 바꿈으로 처리했다. 옛 기록의 결정 1 아래에 `바뀜` 줄과 새 기록 링크만 붙었고, 새 기록의 `버린 안`에 옛 결정이 옛 파일 링크와 함께 있다 |

고치기 전 문구에서도 파일 결과는 같았다. 달라진 것은 모드를 묻는 질문 하나가 없어진 것이다.

시험에서 본 것(고치지 않았다): 옛 기록이 `정하지 않은 것`으로 둔 항목을 새 기록이 정해도, 병합된 옛 기록의 그 줄은 고쳐도 되는 것에 들지 않아 그대로 남는다. 두 기록을 잇는 표시는 정하지 않았다.
