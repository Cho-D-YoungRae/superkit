# superdomain 0.8.0 — 외부 정의·간결성 기준·DOMAIN.md 뼈대 설계 스펙

- 날짜: 2026-11-10
- 상태: 승인됨(2026-11-11). 구현 계획을 쓰고 구현하면서 고친 곳은 본문에 날짜와 함께 적었다
- 근거: [개선 검토](2026-11-10-superdomain-improvements-review.md). 측정값과 출처는 그 문서에 있다

## 1. 목표

DOMAIN.md를 사람(개발자·새로 온 사람·기획자)과 Claude가 함께 읽는 짧은 문서로 유지하고, `외부`를 어느 도메인에 적는지 흔들리지 않게 한다.

| 문제 | 0.8.0에서 고치는 곳 |
|---|---|
| `외부`를 코드 접촉으로 정해, 같은 API를 부르는 도메인마다 `외부`가 붙는다 | 가이드 「외부 접점」: 외부 시스템 판별 + 맡는 도메인 하나 |
| 분량·세부 수준 기준이 없어 문서가 커진다 | 가이드 새 절 「간결하게 쓰는 기준」 + 리뷰어 검사 |
| 리뷰·검증 지적을 반영할수록 세부가 쌓인다 | domain 스킬 6단계의 반영 규칙 |
| 프로젝트마다 형식 밖 칸을 즉석으로 만든다 | 가이드 형식: 기본 뼈대 + 필요할 때만 쓰는 칸 |
| 플러그인 용어("조율 계층")가 질문과 문서에 샌다 | 용어를 "조합 코드" 하나로 맞추고, 사용자에게는 풀어 쓴다 |
| 의존받는 도메인이 바뀔 때 파급을 놓친다 | 수정 모드의 계기 + 리뷰어 변경 검토 |

원칙:

1. DOMAIN.md에는 코드와 지침 파일을 읽어서는 바로 알 수 없는 것만 적는다.
2. 기준은 잴 수 있게 적는다. "핵심만" 대신 시험·목록·숫자로 적는다.
3. 칸을 함부로 늘리지 않는다. 새 칸은 실제 프로젝트에서 즉석으로 생긴 것과 외부 판별에 꼭 필요한 것만 받는다.
4. 0.4.0의 원칙(스크립트 없음, 지식은 주제마다 파일 하나, 확정은 사용자)을 그대로 따른다.

### 비목표

- 별도 템플릿 파일, DOMAIN.md 파싱, 분량을 재는 스크립트
- 정책 질문 범주 확장(참조냐 스냅샷이냐 등). 2026-09-30에 컨벤션 후보에서 뺀 것이라 이번에 다시 열지 않는다
- 「관계의 방향」 규칙 1~4와 한 트랜잭션 허용 조건(가이드 "관계가 어긋난다") 변경. 사용자가 강의를 따라 정한 것이다
- review 스킬 변경, 컨벤션 항목 추가
- noguesstoday·imstargg-v2의 DOMAIN.md 수정. 릴리스 뒤 프로젝트마다 따로 한다(§9)

## 2. 확정된 결정

| # | 결정 |
|---|---|
| D1 | `외부`는 그 외부 시스템의 응답을 우리 모델로 바꿔 저장·제공하는 도메인 하나에 적는다. 외부를 부르는 코드가 어디 있는지로 정하지 않는다 |
| D2 | 외부 응답을 직접 받더라도 다른 도메인의 모델로 바꿔 쓰는 도메인은 `외부`를 맡지 않는다 |
| D3 | 맡은 도메인 밖에서 그 외부를 직접 부르는 코드는 어긋남이다. `알려진 어긋남`에 적혀 있으면 리뷰어가 다시 지적하지 않는다. 목표를 정하지 않았으면 "정하지 않음"으로 적는다 |
| D4 | 결과를 기록하지 않는 발신·관측 수단(운영 알림, 오류 수집, 파일 업로드, 광고·분석 SDK, 외부 스케줄러)은 도메인의 `외부`가 아니다. 컨벤션의 외부 호출 규칙은 그대로 적용한다 |
| D5 | 연동만 맡는 도메인이 있으면 그 도메인은 감싸는 시스템을 `외부`에 적고, 데이터를 맡은 도메인은 `(연동: <key>)`를 붙여 적는다. 한 외부 시스템이 두 도메인에 적히는 것은 이 경우뿐이다 |
| D6 | 모든 도메인이 ID·인증 결과만 받는 별도 서비스(회원 등)는 도메인마다 적지 않고 관계 표 아래 한 줄로 적는다. 그 서비스가 우리 데이터를 만들거나 바꾸면 받는 도메인의 `외부`로 적는다 |
| D7 | 간결성 기준은 시험 셋 + 적지 않는 것 + 분량 예산이다. 리뷰어는 어긴 곳을 Minor로 알린다 |
| D8 | 템플릿 파일을 따로 두지 않는다. 가이드의 형식 예시를 기본 뼈대와 "필요할 때만 쓰는 칸"으로 넓힌다 |
| D9 | 새로 받는 칸은 `하위 도메인`, `알려진 어긋남`, 관계 표 아래 줄 둘(`모든 도메인이 쓰는 별도 서비스`, `의존으로 세지 않는 코드`), `외부`의 `(연동: <key>)`다. 그 밖의 절·칸은 막지 않고 리뷰어가 Minor로 알린다 |
| D10 | 도메인 맵(관계 표를 옮긴 그림)을 도메인 안 개념을 그리는 개념도로 바꾼다. 필요할 때만 쓰는 칸이다 |
| D11 | 가이드의 도메인은 강의의 영역에, 하위 도메인은 격벽(개념 무리)에 대응한다고 본다 |
| D12 | 소개는 1~2문장으로 둔다. 로드맵·착수 계획은 README에 둔다. 처음에는 "README나 ADR"이었고, ADR에는 결정의 이유만 두기로 하면서 2026-11-11에 고쳤다([ADR 개선 검토](2026-11-11-superdomain-adr-review.md)) |
| D13 | `미정` 칸을 없앤다. 정책은 정의할 때 사용자와 정하고, 지금 정할 수 없는 것은 DOMAIN.md의 어느 칸에도 적지 않는다. 검토서에는 없던 결정이고 2026-11-10에 사용자가 정했다 |
| D14 | `코드` 칸의 이름을 `패키지`로 바꾼다. 적는 것은 지금처럼 도메인의 패키지와 그 패키지가 있는 모듈이다. 검토서에는 없던 결정이고 2026-11-10에 사용자가 정했다 |

사용자 답이 없어 기본값으로 정한 것(검토 때 바꿀 수 있다):

- 칸 이름은 `하위 도메인`이다. 검토서는 "하위 영역"이라 불렀지만, imstargg-v2가 이미 쓰는 말을 따른다. `분류`(core·supporting·generic)와는 다른 축이라고 가이드에 한 구절로 밝힌다.
- 가이드와 컨벤션의 "외부 도메인의 복잡성"을 "외부 모델의 복잡성"으로 바꾼다. 사용자는 "외부 도메인"을 우리의 다른 도메인이라는 뜻으로도 쓴다.
- "조율 계층"·"조율 컴포넌트"를 "조합 코드"로 맞춘다.
- 분량 예산의 숫자(§4.2). imstargg-v2 최종판은 모두 통과하고 noguesstoday는 걸리는 값이다.
- 지침 파일 포인터 줄에 "고칠 때는 /superdomain:domain으로 고친다"를 더한다.
- 버전은 0.8.0이다.

## 4. `domain-guide.md`

아래 인용 블록은 가이드에 들어갈 문구의 초안이다.

### 4.1 「DOMAIN.md 형식」

형식 예시를 기본 뼈대로 줄인다. 예시의 `개념`·`하지 않는 것`은 아래 표로 옮긴다.

```markdown
# <제품명> 도메인

<제품이 무엇을 하는지 1~2문장>

## order — 주문
- 역할: 고객의 구매 요청을 받아 결제 완료까지의 상태를 관리한다
- 기능: 주문 생성, 주문 취소, 주문 내역 조회
- 분류: core
- 패키지: order-api `com.acme.order`
- 규칙:
  - 배송이 시작된 주문은 취소할 수 없다
  - 주문을 취소하면 쓴 쿠폰과 포인트를 되돌린다

## payment — 결제
- 역할: 결제의 승인과 취소·환불을 관리한다
- 기능: 결제 승인, 결제 취소, 부분 환불
- 분류: supporting
- 패키지: payment-api `com.acme.payment`
- 외부: PG사 — 결제 승인·취소, 결제 결과 웹훅, 정산 파일

## 관계
| 도메인 | 의존 대상 | 방식 | 설명 |
|---|---|---|---|
| payment | order | 동기 호출 | 결제가 승인되면 주문을 결제 완료로 바꾼다 |
| delivery | order | 이벤트 | 결제 완료된 주문으로 배송을 만든다 |
```

> 처음에는 이 뼈대만 쓴다. `외부`는 외부를 맡은 도메인만, `규칙`은 있을 때만 적는다. 아래 칸은 필요할 때만 더한다.
>
> | 칸 | 모양 | 언제 |
> |---|---|---|
> | `하위 도메인` | `- 하위 도메인:` 아래에 `<key> — <한 줄>` | 한 도메인 안에 개념 무리가 여럿일 때 |
> | `개념` | `- 개념: 쿠폰, 소유 쿠폰(내려받은 쿠폰. 주문·결제가 쓴다)` | 개념이 여럿이라 꼭 알아야 할 것을 추려야 할 때 |
> | `하지 않는 것` | `- 하지 않는 것: 결제 승인 (→ payment)` | 이웃 도메인과 헷갈릴 때 |
> | `외부`의 연동 표시 | `- 외부: 택배사 — 배송 상태 (연동: carrier)` | 연동만 맡는 도메인을 거쳐 받을 때 |
> | 관계 표 아래 줄 | `- 모든 도메인이 참조: <key>`<br>`- 모든 도메인이 쓰는 별도 서비스: <이름>`<br>`- 의존으로 세지 않는 코드: <모듈·패키지>` | 해당할 때 |
> | `## 알려진 어긋남` | `- <지금 코드> → <정한 목표 \| 정하지 않음>` | 정한 방향·경계와 다른 코드가 남아 있을 때 |
> | 개념도 | mermaid `flowchart LR` | 비개발자와 함께 보거나 사람이 자주 바뀔 때 |

칸 설명은 이렇게 바꾼다(제목·역할은 그대로다).

> - **소개**: 제품이 무엇을 하는지 1~2문장. 로드맵과 착수 계획은 README에 둔다.
> - **기능**: 이 도메인이 제공하는 일을 한 줄로 적는다. 화면이나 API 목록이 아니다.
> - **분류**: `core` · `supporting` · `generic` 중 값만 적는다(아래 분류 기준).
> - **패키지**: 이 도메인의 코드가 있는 패키지를 한 줄로 적는다. 모듈이 여럿이면 모듈 이름 뒤에 패키지를 적는다(예: order-api `com.acme.order`). 도메인 코드가 다른 이름의 패키지에 있거나 모듈마다 모델이 따로 있을 때만 한 단계 더 적는다(예: `core-api: 조회 모델, core-worker: 동기화 모델`). 클래스 이름은 적지 않는다. 패키지가 없는 프로젝트면 디렉터리를 적는다.
> - **외부**: 이 도메인이 맡은 외부 시스템과 주고받는 것. `<외부 시스템> — <주고받는 것>`으로 적고, 여럿이면 한 줄에 하나씩 하위 목록으로 적는다. 무엇이 외부 시스템이고 어느 도메인이 맡는지는 아래 "외부 접점"을 따른다. `외부`가 없는 도메인은 내부 도메인이다.
> - **규칙**: 지켜지는 것(불변식·정책)을 도메인 말로 적는다. 3~5개를 권장한다. 이번 범위에서 일부러 뺀 것도 여기에 적는다(예: 전체 취소만 된다). 아직 만들지 않았어도 정한 경계와 책임은 현재형으로 적는다. 다른 곳이 지켜 주는 전제에는 지키는 곳을 붙인다(예: 진열 중인 상품은 지워지지 않는다(보장: 어드민)). ADR이 있는 규칙은 결론 한 문장에 링크 하나만 단다.
> - **하위 도메인**: 한 도메인 안의 개념 무리다. `분류`와는 다른 축이다. 관계 표는 최상위 도메인 사이만 적고, 하위 도메인 사이의 의존은 도메인 안의 일로 본다. 하위 도메인이 따로 외부를 맡거나 생명주기·데이터 소유가 갈리면 도메인으로 나눌지 본다.
> - **개념**: 대표 개념과, 다른 도메인이 직접 쓰는 개념. 이름만 적고, 헷갈리는 이웃 개념과의 차이나 끝 상태가 있을 때만 한 구절을 붙인다. 영문 용어가 정해져 있으면 함께 적어도 된다. 테이블 이름과 저장 방식은 적지 않는다(개념은 클래스나 엔티티와 일대일이 아니고, 테이블 없이 논리로만 있는 개념도 있다). 상태는 우리 말로 적는다. 한 화면에서만 쓰이거나 대표 개념의 하위 구성인 개념은 적지 않는다. 다만 하위 구성이라도 다른 도메인이 직접 쓰거나(소유 쿠폰), 경계 결정을 담거나(리뷰 대상), 그 개념에만 걸린 규칙이 `규칙`에 있으면(장바구니 항목의 수량) 적는다.
> - **하지 않는 것**: 헷갈리기 쉬운 이웃 책임과 그 책임을 맡는 도메인. 앞으로의 계획은 적지 않는다.
> - **관계**: (지금 문구에 더한다) 방식은 관계의 종류다. 다른 프로세스를 HTTP로 불러도 `동기 호출`이고, 모듈·프로토콜 이름은 적지 않는다. 표에는 정한 방향을 적고, 아직 그렇게 구현하지 않은 것은 `알려진 어긋남`에 적는다. 표에 없는 도메인은 관계가 없는 것이므로 따로 적지 않는다.
> - **모든 도메인이 쓰는 별도 서비스**: 모든 도메인이 ID나 인증 결과만 받는 별도 서비스(회원·인증 등)는 도메인마다 `외부`에 적지 않고 관계 표 아래에 한 줄로 적는다.
> - **의존으로 세지 않는 코드**: 조합 코드(아래 "관계의 방향")와 여러 도메인이 함께 읽는 공유 모듈의 위치를 모듈·패키지로 적는다.
> - **알려진 어긋남**: 정한 방향·경계와 다른 지금 코드를 문서 끝에 한 줄씩 적는다. 목표를 정하지 않았으면 "정하지 않음"으로 적는다. 고치면 지운다. 누가 언제 고치는지는 적지 않는다. 코드와 상관없이 아직 정하지 못한 정책은 여기에 적지 않는다.
> - **개념도**: 도메인 안의 개념을 그림으로 보인다. `개념`에 적은 것만 그린다. 도메인(하위 도메인이 있으면 하위 도메인)을 묶음으로 두고 업무 흐름 순서로 왼쪽에서 오른쪽에 놓는다. 화살표는 "A가 B를 안다"이고, 묶음을 넘는 것만 대표 개념 단위로 긋는다(테이블 참조를 따라 긋지 않는다). 도메인을 넘는 화살표의 방향은 관계 표와 같아야 한다. 대표 개념과 그 밖의 개념은 모양으로 구분해도 된다. 외부 시스템은 노드로 그리지 않고 외부를 맡은 도메인에 표시만 한다. 모든 도메인이 참조하는 개념은 메모 한 줄로 둔다. 필드·상태·정책은 그리지 않는다.
> - 이 밖의 절이나 칸은 되도록 만들지 않는다. 담을 자리가 없는 내용은 지침 파일이나 이슈가 맞는 자리인지 먼저 본다. 결정의 이유와 버린 안은 ADR에 둔다.

`미정` 칸과 그 설명은 지운다(D13). 정하지 못한 정책은 「간결하게 쓰는 기준」의 적지 않는 것에 든다(§4.2). `코드` 칸은 이름만 `패키지`로 바꾸고 자리는 그대로 둔다(D14).

`기반 도메인`과 `허용 관계 테스트`의 문구는 그대로 둔다. `허용 관계 테스트`에는 "조합 코드의 패키지는 모듈 감지에서 뺀다"만 더한다.

### 4.2 새 절 「간결하게 쓰는 기준」

「DOMAIN.md 형식」 바로 뒤에 둔다.

> DOMAIN.md는 개발자, 새로 온 사람, 기획자, 에이전트가 함께 읽는다. 코드와 지침 파일을 읽어서는 바로 알 수 없는 것만 적는다.
>
> `외부`·`규칙`과 필요할 때만 쓰는 칸의 줄마다 아래를 묻는다.
>
> 1. **실수 시험**: 이 줄이 없으면 새로 온 사람이 저지를 실수를 하나 댈 수 있는가. 못 대면 적지 않는다.
> 2. **리팩터링 시험**: 동작을 바꾸지 않는 리팩터링(이름·패키지 이동, 락·라이브러리 교체, 재시도 횟수 조정)으로 이 줄이 틀려지는가. 그러면 수단을 지우고 지켜지는 것으로 다시 쓴다(예: "낙관적 락으로 한 워커만 진행한다" → "한 갱신은 한 워커만 실행한다").
> 3. **중복 시험**: 지침 파일에 같은 수준으로 이미 있는가. 있으면 적지 않는다. ADR에 결정문이 있거나 설계·운영 문서에 더 자세히 있다는 것은 규칙 한 문장을 빼는 이유가 아니다.
>
> 적지 않는 것:
>
> | 적지 않는 것 | 대신 |
> |---|---|
> | 클래스·컴포넌트·테이블·파일·API 경로 이름 | 개념의 이름 |
> | 완전한 패키지 경로 | 모듈과 도메인 패키지 |
> | 코드의 enum 표기, HTTP 상태 코드, 외부 엔드포인트 | 우리 말("요청됨 → 실행 중 → 완료", "외부에서 사라진 계정") |
> | 락·트랜잭션·재시도·해시 같은 수단 | 지켜지는 것 |
> | 수단의 설정값(재시도 횟수, 배치 간격, 호출 제한 주기) | 코드나 지침 파일. 규칙 문장의 일부인 값(재요청 대기 10초, 보관 10일)은 적는다 |
> | 라이브러리·프레임워크 이름, 아키텍처 테스트 번호, 이슈 번호 | 지침 파일 |
> | 검토한 대안과 버린 이유 | ADR. 규칙을 이해하는 데 필요한 이유 한 구절은 규칙 안에 둘 수 있다 |
> | 경위·이력·날짜 | 커밋과 PR |
> | 진행 상태(예정, 아직 구현 전) | `알려진 어긋남`이나 이슈 |
> | 아직 정하지 못한 정책, 사용자가 확정하지 않은 기본안 | 정해서 `규칙`에 적는다. 지금 정할 수 없으면 어느 칸에도 적지 않는다 |
> | 다른 칸이나 다른 문서에 이미 있는 내용 | 한 곳에만 |
> | 이 가이드의 용어(외부 접점 도메인, 기반 도메인, 조합 코드 등) | 프로젝트의 말 |
> | 작업·사례 이름이 붙은 절 | 해당 칸의 일반 규칙으로 |
>
> 분량(공백을 포함한 글자 수. 링크 주소와 목록 기호는 세지 않는다):
>
> - 소개 1~2문장, 역할 한 문장, 기능 한 줄
> - 패키지 한 줄 300자
> - 규칙 칸 합계 500자, 한 항목 120자
> - 관계 설명 150자
> - 도메인 한 섹션 1,500자
>
> 넘으면 줄일 수 있는지 먼저 보고, 줄일 수 없으면 하위 도메인으로 나누거나 도메인을 나눌지 본다. 넘치는 정책은 지침 파일·정책 문서·테스트에 둔다.
>
> 고칠 때:
>
> - 새 내용은 해당 칸의 기존 줄을 고쳐 담는 쪽을 먼저 본다.
> - 모순을 고칠 때는 세부를 다른 칸으로 옮기지 않고 한쪽을 지운다.

### 4.3 「외부 접점」

절 머리에 판별과 맡는 도메인을 둔다. 지금의 설명(외부에 의존한다, 두 복잡성)은 그 뒤에 그대로 두되 "외부 도메인의 복잡성"만 "외부 모델의 복잡성"으로 바꾼다.

> **무엇이 외부 시스템인가.** 다른 조직이나 다른 프로세스가 운영하는 시스템 가운데 아래 둘에 모두 해당하는 것이다. 같은 회사의 다른 팀 시스템도 둘에 해당하면 외부 시스템이다.
>
> 1. 주고받는 데이터의 모델(필드의 뜻·상태 값·오류의 뜻)을 상대가 정한다. 우리 데이터를 담아 두기만 하는 저장소·큐·캐시는 API 형식을 상대가 정해도 해당하지 않는다.
> 2. 그 시스템의 데이터가 우리 모델에 들어오거나, 그 시스템이 우리 기능을 수행하고 그 결과(승인됨·체결·이체 완료)를 우리 상태로 기록한다.
>
> | 외부 시스템이 아닌 것 | 다루는 법 |
> |---|---|
> | 우리가 운영·설정하는 인프라: DB·큐·캐시·스토리지(관리형 클라우드 포함) | 적지 않는다 |
> | 자사 클라이언트·어드민 | 통로다. 적지 않는다 |
> | 우리가 운영하는 어댑터·프록시 | 그 뒤의 외부 시스템을 적는다. 로컬 개발 전용은 적지 않는다 |
> | 프로세스 안 라이브러리 | 라이브러리에 담긴 외부 규칙이 도메인 규칙에 들어오면 그 원천(예: 거래소 휴장일)을 규칙에 적는다 |
> | 결과를 기록하지 않는 발신·관측: 운영 알림, 오류 수집, 파일 업로드, 광고·분석 SDK, 외부 스케줄러 | 적지 않는다. 고객에게 보내는 메일·문자도 보내기만 하면 여기에 든다 |
> | 모든 도메인이 ID·인증 결과만 받는 별도 서비스 | 관계 표 아래 한 줄. 그 서비스가 우리 데이터를 만들거나 바꾸면 받는 도메인의 `외부`로 적는다 |
>
> **어느 도메인이 맡는가.** 외부 시스템마다 맡는 도메인을 하나 정한다. 맡는 도메인은 그 외부의 응답을 우리 모델로 바꿔 저장하고 다른 도메인에 제공한다. `외부`는 맡은 도메인에만 적는다. 외부를 부르는 코드가 어디 있는지로 정하지 않는다.
>
> - 외부 응답을 직접 받더라도 다른 도메인의 모델로 바꿔 쓰는 도메인은 맡은 도메인이 아니다.
> - 같은 외부 시스템과 주고받는 기능은 맡은 도메인에 모은다(예: 결제 승인과 취소).
> - 맡은 도메인 밖에서 그 외부를 직접 부르는 코드는 `외부`를 더할 일이 아니라 "외부 영향이 번진다" 신호다. `알려진 어긋남`에 적는다.

"지키는 것" 가운데 연동 도메인 항목(지금 "외부 연동이 크면…")을 이렇게 바꾼다. 나머지 세 항목은 그대로다.

> - 외부 연동이 크면(외부 시스템이 여럿이거나, 자격증명·호출 한도·호출 기록을 여러 도메인이 함께 써야 하면) 연동만 맡는 도메인으로 떼어 낸다. 연동 도메인은 호출·인증·한도·재시도 같은 외부 시스템의 복잡성을 맡고 업무 규칙은 갖지 않는다. 외부 데이터를 해석해 우리 모델로 소유하는 일과 우리 규칙은 그 데이터를 맡은 도메인에 둔다. 이때 연동 도메인은 자기 `외부`에 감싸는 시스템을 적고, 데이터를 맡은 도메인은 `외부: <시스템> — <받는 것> (연동: <key>)`로 적는다. 한 외부 시스템이 두 도메인에 적히는 것은 이 경우뿐이다. 연동이 작으면 한 도메인 안에서 가장자리(연동 코드)에 모은다. 연동 도메인은 우리 규칙이 적어도 외부의 복잡성을 가두는 역할이 있으므로 「너무 작다」로 보지 않는다.

### 4.4 「관계의 방향」

규칙 1~4는 그대로 두고 두 곳만 고친다.

연동 도메인(규칙 목록 바로 아래에 더한다):

> 연동만 맡는 도메인은 그 외부를 `(연동: <key>)`로 적은 도메인에게서만 의존받고(요청하는 쪽이 의존한다), 다른 도메인에 의존하지 않는다.

조합 코드(지금 "어느 도메인에도 속하지 않는 위 계층(컨트롤러나 조율 컴포넌트)이…" 문단):

> 흐름상 내부 도메인의 일이 외부 접점 도메인의 결과에 달려 있어도(외부 확인을 거쳐야 주문이 확정되는 경우) 내부 도메인이 외부 접점 도메인을 부르지 않는다. 어느 도메인에도 속하지 않는 조합 코드가 두 도메인을 순서대로 부른다. 조합 코드는 여러 도메인을 차례로 부르거나 결과를 합치는 코드다(여러 도메인을 묶는 컨트롤러, 화면용 조회 조합, 배치 Job 구성). 조합 코드의 호출은 도메인 사이 의존으로 세지 않는다. 조합 코드는 도메인 패키지 밖에 두고, 그 위치를 관계 표 아래 `의존으로 세지 않는 코드:`에 적는다. 도메인 패키지 안의 코드가 다른 도메인을 부르면 그 도메인의 의존이다.

### 4.5 「잘못 그은 경계의 신호」

"외부 영향이 번진다"를 이렇게 바꾼다.

> - 외부를 맡지 않은 도메인이 그 외부 시스템과 직접 주고받는다(외부 API 클라이언트·SDK를 import하거나, 외부의 호출·웹훅을 직접 받는다). `(연동: <key>)`가 붙은 외부를 그 연동 도메인 밖에서 직접 부르는 것도 같다.
> - 외부의 용어·응답 타입·오류가 맡은 도메인 밖으로 새어 나간다.
> - 외부 시스템과 주고받는 코드가 있는데 어느 도메인의 `외부`에도 없다(맡을 도메인을 정하지 않았다).
> - 맡은 도메인이 자기 `외부`에 없는 외부 시스템과 주고받는다.
> - 인프라나 발신·관측 수단을 `외부`에 적었다.

"너무 크다"의 첫 항목에는 "하위 도메인이 있으면 기능 묶음은 하위 도메인 단위로 본다"를 더한다.

## 5. `domain` 스킬

체크리스트의 단계 수와 순서는 그대로 두고 내용을 고친다.

| 단계 | 바뀌는 것 |
|---|---|
| 1 맥락 파악 | 외부 시스템과 주고받는 코드(외부 API 클라이언트·SDK·웹훅 수신)를 여기서 찾아 둔다 |
| 3 질문 | 질문과 선택지는 제품과 프로젝트의 말로 쓴다. 가이드 용어가 필요하면 그 자리에서 풀어 쓴다. 정책은 지금처럼 도메인마다 초안으로 확인받되, 「간결하게 쓰는 기준」을 통과하는 것만 `규칙`에 적고 나머지는 대화로만 확인한다. 기획 용어 하나가 성질이 다른 개념 둘로 갈리는지(쿠폰과 소유 쿠폰), 어떤 행위가 어느 개념에서 시작되는지(결제 취소인가 주문 취소인가)도 묻는다. 정책은 그 자리에서 정한다. 사용자가 망설이면 기본안(코드가 있으면 지금 동작, 없으면 범위를 좁힌 쪽. 예: 전체 취소만 된다)을 추천해 고르게 하고, 사용자가 확정한 것만 `규칙`에 적는다. 지금 정할 수 없는 것(정할 사람이 따로 있다, 데이터를 봐야 한다)은 어느 칸에도 적지 않고 모아 두었다가 8단계에서 알린다. 지금 문구의 "정하지 못한 것은 `미정`에 적는다"는 지운다 |
| 4 도메인 목록 제안 | 먼저 사용자가 생각하는 최상위 묶음이 있는지 묻는다. 있으면 그것을 출발점으로 삼고 패키지에서 읽은 후보를 거기에 맞춰 보여 준다. 외부 시스템마다 맡을 도메인을 제안해 확인받는다. 맡을 도메인 밖에서 그 외부를 직접 부르는 코드는 어긋남 후보로 모아 둔다. 중심 후보의 예는 "주문 중심이냐 결제 중심이냐"로 바꾸고, 근거로 목록 화면이 무엇의 목록인지, 다음 기능이 어디에 붙는지, 관계 표 초안에서 의존받는 수를 쓴다 |
| 5 섹션별 작성 | 지금 문구의 "역할·기능·분류·코드"는 "역할·기능·분류·패키지"로 바꾸고, 선택 칸 목록(개념·외부·규칙·미정·하지 않는 것)은 지운다. 처음에는 기본 뼈대와 관계 표만 쓴다. 필요할 때만 쓰는 칸은 사용자가 원하거나 기준을 통과하는 내용이 있을 때 더한다. 어긋남 후보는 모아서 한 번에 확인받아 `알려진 어긋남`에 적는다. 개념도는 비개발자와 함께 보거나 사람이 자주 바뀌는 프로젝트일 때만 제안한다. 지금 문구의 "외부 시스템과 맞닿은 도메인이면"은 "외부를 맡은 도메인이면"으로 바꾼다 |
| 6 자체 검토 | 지적 중 무엇을 반영할지 지금처럼 사용자와 정한다. 틀린 문장과 모순은 세부를 다른 칸으로 옮기지 않고 지우는 쪽을 먼저 제안한다. 새 사실을 더하자는 지적은 기준을 통과할 때만 제안하고, 통과하지 못한 사실은 대화로만 알린다 |
| 7 사용자 검토 | 여기서 도메인·관계·`외부`가 바뀌거나 섹션을 다시 쓰면 6단계를 한 번 더 한다 |
| 8 후속 제안 | 포인터 줄을 `- 도메인 정의: docs/superdomain/DOMAIN.md (도메인의 역할·관계를 바꾸는 작업 전에 읽는다. 고칠 때는 /superdomain:domain으로 고친다)`로 바꾼다. 옛 줄이 있으면 바꿀지 묻는다. 3단계에서 모아 둔 정하지 못한 정책이 있으면 대화로 목록만 알린다. 이 스킬은 그것을 파일이나 이슈로 남기지 않는다 |

수정 모드:

- 1단계의 계기에 "기준 개념이 바뀜"(예: 주문의 단위가 상품에서 상품 옵션으로)을 더한다. 이때는 관계 표에서 그 도메인에 의존하는 도메인을 따라가며 영향받는 `규칙`과 `개념`을 확인한다.
- 2단계에 "고칠 때 「간결하게 쓰는 기준」을 지킨다"를 더한다. "외부 시스템과 맞닿게 되거나 떨어지면"은 "외부를 새로 맡거나 놓으면"으로 바꾼다.
- 기존 문서에 0.7.0의 형식(칸 이름 `코드`, `미정` 칸)이 남아 있으면 이번에 함께 고칠지 묻는다. `코드`는 이름을 `패키지`로 바꾼다. `미정`은 항목마다 가른다. 지금 정할 수 있으면 정해서 `규칙`으로 옮기고, 정한 방향·경계와 다른 코드를 적어 둔 것이면 `알려진 어긋남`으로 옮기고, 그 밖은 지운다.

하지 않는 것에 더한다:

- 리뷰어 지적을 사용자 확인 없이 반영하지 않는다.
- 사용자가 확정하지 않은 정책을 `규칙`에 적지 않는다. `알려진 어긋남`에는 정한 방향·경계와 다른 코드만 적고(목표는 "정하지 않음"일 수 있다), 정하지 못한 정책을 옮겨 적지 않는다.
- 빠진 패키지나 규칙을 찾는 검증을 따로 돌리지 않는다. 자체 검토에 쓰는 것은 domain-reviewer 호출 하나다(7단계에서 6단계를 다시 할 때도 같은 호출이다).

## 6. `domain-reviewer`

정의 검토:

- 형식: 뼈대에 없는 절·칸(가이드의 기본 뼈대와 필요할 때만 쓰는 칸 표 어디에도 없는 것)이 있으면 Minor로 알린다. 0.7.0까지 쓰던 `미정` 칸도 뼈대에 없는 칸으로 보고, 항목마다 정해서 `규칙`으로 옮기거나, 정한 방향·경계와 다른 코드를 적어 둔 것이면 `알려진 어긋남`으로 옮기거나, 지우자고 제안한다. 0.7.0까지의 칸 이름 `코드`는 `패키지` 칸으로 읽고, 이름을 바꾸자고 문서 전체에 한 번만 Minor로 알린다.
- 형식의 괄호 안 "필수 필드"는 "기본 뼈대의 역할·기능·분류·패키지가 도메인마다 있는가"로 바꾼다. 무엇이 필수인지 가이드가 그 이름으로 정하지 않아서다.
- 정의 품질에 간결성 검사를 더한다. 적지 않는 것이 적혔는가, 분량 예산을 넘는가(도메인마다 패키지 줄, 규칙 칸 합계와 항목, 관계 설명, 섹션을 빠짐없이 센다), 같은 내용이 두 칸에 있는가, `하지 않는 것`에 계획이 있는가. 모두 Minor이고, 제안은 지우거나 지켜지는 것으로 다시 쓰는 쪽을 먼저 낸다. 글자 수는 유니코드 문자 수로 센다(`wc -m`은 로캘에 따라 바이트를 센다).
- `개념`: 하위 구성 검사에 가이드의 예외(다른 도메인이 쓴다, 경계 결정을 담는다, 그 개념에만 걸린 규칙이 있다)를 따른다.
- 외부: 적힌 것이 가이드의 판별에 맞는 외부 시스템인가. 인프라나 발신·관측 수단이면 Minor다. 같은 외부 시스템이 `(연동: <key>)` 짝 없이 두 도메인에 적혔으면 지적한다. 역할·기능으로 보아 외부 시스템을 다루는데 어느 도메인의 `외부`에도 없으면 질문으로 남긴다.
- 관계 표: `(연동: <key>)`를 쓴 도메인이 그 연동 도메인에 의존하는 줄이 있는가, 연동 도메인이 다른 도메인에 의존하지 않는가. `(연동: <key>)`를 쓴 도메인이 그 연동 도메인에 의존하는 것은 "내부 도메인이 외부 접점 도메인에 의존한다"로 지적하지 않는다. 표시를 쓰지 않은 도메인이 연동 도메인에 의존하면 지적한다.

변경 검토:

- 변경된 파일을 도메인에 연결할 때 0.7.0 형식의 문서면 `코드` 칸을 `패키지` 칸으로 읽는다.
- 조합 코드: 관계 표 아래 `의존으로 세지 않는 코드:`에 적힌 위치의 호출은 도메인 사이 의존으로 세지 않는다. 그 줄이 없으면 지금처럼 도메인 패키지 밖에서 여러 도메인을 묶는 코드로 판단한다. 도메인 패키지 안의 코드가 다른 도메인을 부르면 그 도메인의 의존이다.
- 외부: 외부를 맡지 않은 도메인이 그 외부 시스템과 직접 주고받게 되는가(`(연동: <key>)`를 건너뛰는 것 포함), 외부의 용어·타입·오류가 맡은 도메인 밖으로 새는가. 새 외부 시스템이 생기면 맡을 도메인이 정해졌는가.
- 새 항목: 의존받는 도메인의 상태·타입·공개 조회 동작이 바뀌면, 관계 표에서 그 도메인에 의존하는 도메인의 코드도 함께 봤는가. 확인하지 못하면 질문으로 남긴다.
- 새 항목: 변경이 `규칙`과 어긋나는가. `규칙`에 적힌 값이 코드와 다른가.
- 변경이 `알려진 어긋남`에 적힌 어긋남을 넓히면 지적한다.

전체 점검:

- 외부: 외부 시스템과 주고받는 코드가 있는데 어느 도메인의 `외부`에도 없으면 질문(맡을 도메인), 맡은 도메인이 자기 `외부`에 없는 외부 시스템과 주고받으면 지적, 맡은 도메인 밖의 직접 접촉은 `알려진 어긋남`에 없을 때만 지적한다.
- 지침 파일과 겹치는 내용(중복 시험)은 여기서 본다. 정의 검토는 DOMAIN.md 안의 중복만 본다.
- `알려진 어긋남`에 적힌 것이 이미 고쳐졌으면 지우자고 Minor로 남긴다.

지키는 것:

- 보고하지 않는 것에 "가이드가 요구하지 않는 내용을 DOMAIN.md에 더하자는 제안"을 더한다. 알려야 할 사실은 질문으로 남긴다.
- 모순을 지적할 때 제안은 한쪽을 지우는 쪽을 먼저 낸다.
- `알려진 어긋남`에 적힌 것은 어느 모드에서든 다시 지적하지 않는다. 절 이름이 달라도 정한 방향과 다른 코드를 적어 둔 목록이면 같게 본다(처음에는 변경 검토 항목이었고, 정의 검토에서도 지켜지도록 전체 리뷰 뒤 2026-11-12에 옮겼다).
- 지적과 질문은 프로젝트의 말로 쓴다. `기준:`에는 가이드의 절 이름을 적고, 본문에 가이드 용어를 쓰면 한 구절로 풀어 쓴다.

출력 형식과 심각도 정의는 그대로다.

## 7. 그 밖의 파일

- `conventions.md` 머리말의 "외부 자원" 줄:

  > "외부 자원"은 우리 프로세스 밖의 자원이다. DB·메시지 큐처럼 우리가 운영하는 인프라와, 다른 조직이 운영하는 원격 서비스(외부 API, 알림·오류 수집·파일 저장 같은 발신 수단)를 모두 포함한다. 「외부 응답과 오류는 경계에서 우리 타입으로 바꾼다」와 「외부 호출은 DB 트랜잭션 밖에서 한다」는 원격 서비스 전체에 적용한다. DOMAIN.md의 `외부`에는 그중 도메인 모델에 들어오는 외부 시스템만 적는다.

- `conventions.md` 「도메인 사이 의존은 한 방향으로만 둔다」: "위 계층(컨트롤러나 조율 컴포넌트)"를 "조합 코드(여러 도메인을 묶는 컨트롤러, 조회 조합, 배치 Job 구성)"로 바꾸고 "조합 코드는 도메인 패키지 밖에 둔다"를 더한다. 「외부 응답과 오류는…」의 "외부 도메인의 복잡성"을 "외부 모델의 복잡성"으로 바꾼다.
- `conventions/SKILL.md` 3단계의 첫 경우: "지금 고치는 도메인이 맡지 않은 외부 시스템과 직접 주고받게 될 때"로 바꾸고, 그 외부를 맡은 도메인이 주고받게 하자고 제안한다. 경우를 하나 더한다. 지금 고치는 도메인의 `외부`에 `(연동: <key>)`로 적힌 외부 시스템과 주고받게 될 때는 직접 부르지 않고 그 연동 도메인을 부르게 한다. "위 계층(컨트롤러 등)"은 "조합 코드"로 바꾼다. 처음 문구("`외부`를 맡지 않은 도메인이 … `(연동: <key>)`가 있으면 그 연동 도메인을 거치게 한다")는 조건과 연동 문장이 서로 어긋나, 전체 리뷰 뒤 2026-11-12에 고쳤다.
- `convention-reviewer.md`: "조율 계층(컨트롤러 등)"을 "조합 코드"로 바꾼다.
- `architecture-tests.md` 「모듈 감지」에 더한다: 조합 코드를 둔 패키지도 역할 패키지로 보고 모듈에서 뺀다. DOMAIN.md의 `의존으로 세지 않는 코드:`와 같은 위치여야 한다.
- `adr/SKILL.md` 6절: "DOMAIN.md에는 결론 한 문장만 반영하고(필요하면 규칙 끝에 ADR 링크 하나), 이유와 버린 안은 ADR에 둔다"를 더한다. adr 스킬의 나머지는 0.9.0에서 고친다([설계 스펙](2026-11-11-superdomain-adr-reason-record-design.md)).
- `README.md` 산출물 표: "도메인별 역할·기능·분류·패키지(필요할 때: 외부·규칙·하위 도메인·개념·하지 않는 것·알려진 어긋남)와 도메인 간 관계"로 고친다.
- 칸을 가리키는 문구를 `패키지`로 맞춘다. 대상은 `domain/SKILL.md`의 description과 첫 문단("역할·기능·분류·코드 위치"), `adr/SKILL.md` 6절("역할·기능·분류·코드·규칙·관계"), `convention-reviewer.md`("도메인별 분류와 코드 위치를 읽는다"), `domain-reviewer.md`의 전체 점검("적힌 코드 위치가 없다"), 변경 검토 머리 문장(`DOMAIN.md의 "코드"로`), 지키는 것(`DOMAIN.md "코드"에`), 그리고 `domain-guide.md` 「같은 이름, 다른 모델」(`DOMAIN.md의 "코드"에`)이다. 두 리뷰어가 파일을 도메인에 연결하는 문장에는 0.7.0 형식의 문서면 `코드` 칸을 읽는다고 덧붙인다(구현 계획을 쓰며 2026-11-11에 더했다).

## 9. 이행과 문서

CHANGELOG 0.8.0에 적을 이행 안내(기존 DOMAIN.md는 플러그인이 자동으로 고치지 않는다):

- `외부`를 맡은 도메인에만 남긴다. 연동만 맡는 도메인을 거치면 `(연동: <key>)`를 붙인다. 발신·관측 수단은 `외부`에서 뺀다.
- 정한 방향·경계와 다른 코드를 적어 둔 절은 문서 끝의 `## 알려진 어긋남`으로 옮긴다.
- `미정` 칸은 없어졌다. 항목마다 지금 정해서 `규칙`으로 옮긴다. 정한 방향·경계와 다른 코드를 적어 둔 것이면 `알려진 어긋남`으로 옮긴다. 그 밖은 지운다(남겨야 하면 이슈처럼 프로젝트가 쓰는 곳에 둔다).
- 칸 이름 `코드`를 `패키지`로 바꾼다. 적는 것은 같으므로 값은 그대로 써도 된다.
- 「간결하게 쓰는 기준」에 걸리는 내용은 `/superdomain:review domain 전체`로 찾아 `/superdomain:domain` 수정 모드로 줄인다.
- "조율 계층" 같은 말을 문서에 썼으면 풀어 쓰고, 그 코드의 위치를 `의존으로 세지 않는 코드:`에 적는다.
- 지침 파일의 도메인 정의 포인터 줄을 새 문구로 바꾼다.

릴리스 뒤 두 프로젝트에서 따로 할 일(이 스펙의 범위 밖):

- **imstargg-v2**: 칸 이름 `코드` → `패키지`(값 머리의 "패키지"라는 말은 뺀다), `### 방향과 어긋난 코드` → `## 알려진 어긋남`, QueryComposer → 패키지, renewal의 enum 표기 → 우리 말, 관계 설명의 "(이벤트는 아직 구현 전)", 관계 표 아래 줄 정리, statistics의 `미정` 두 줄(정해서 `규칙`으로 옮기거나 지운다). `외부`와 `하위 도메인`은 그대로다.
- **noguesstoday**: 칸 이름 `코드` → `패키지`. 규칙·패키지·개념 칸을 크게 줄인다. market·indicator의 `외부`에 `(연동: provider)`를 붙이고, 관계 방식을 `동기 호출`로 고치고, 소개의 로드맵 문단을 옮긴다. provider의 수수료 계산 책임처럼 다른 문서에 없는 결정은 줄이기 전에 남길지 정한다.

저장소 루트에서:


기준이 뜻대로 움직이는지는 두 프로젝트의 지금 DOMAIN.md로 확인한다(읽기 전용, `claude --plugin-dir plugins/superdomain`으로 띄워 `/superdomain:review domain 전체`).

| 대상 | 기대하는 결과 |
|---|---|
| imstargg-v2 | 분량 예산 지적이 없다. renewal·statistics의 공식 API 직접 호출은 이미 적어 둔 어긋남으로 보고, `외부`를 더하라고 하지 않는다. QueryComposer, enum 표기, "(이벤트는 아직 구현 전)", statistics의 `미정` 칸, 옛 칸 이름 `코드`(문서에 한 번), 뼈대 밖 절과 줄을 Minor로 알린다. `패키지` 칸이 없다고 지적하지 않는다 |

## 11. 기준 확인 결과

2026-11-12에 0.8.0의 가이드와 리뷰어로 확인했다. 중첩 실행한 CLI(`claude --plugin-dir … -p`)가 인증 만료로 실패해, 하위 에이전트(리뷰어 frontmatter와 같은 모델)에게 `agents/domain-reviewer.md`의 본문을 지침으로 주고 같은 호출 프롬프트로 돌렸다. review 스킬이 리뷰어를 부르는 경로는 이번에 시험하지 않았다(0.8.0에서 바꾸지 않은 스킬이다). 두 프로젝트는 읽기만 했다.

| 대상 | 모드 | 없어야 하는 지적 | 있어야 하는 지적 | 기대와 다른 점 |
|---|---|---|---|---|
| imstargg-v2 | 전체 점검 | 4개 모두 없음 | 6개 모두 있음(모두 Minor) | 없음. `### 방향과 어긋난 코드`를 `알려진 어긋남`으로 읽었고, 분량은 모두 예산 안이었다(섹션 최대 1,303자, 패키지 줄 최대 280자, 규칙 합계 최대 332자) |
| noguesstoday | 전체 점검 | 없음 | 7개 중 6개 | indicator의 규칙 칸 합계(약 780자)를 빠뜨리고 넘는 항목 하나만 지적했다 |
| noguesstoday | 정의 검토(아래 문구를 고친 뒤) | 없음 | 분량 항목이 모두 있음(세 도메인의 규칙 칸 합계, market·provider의 섹션과 패키지 줄) | 없음 |
| noguesstoday의 사본(market·indicator의 외부 네 줄에 `(연동: provider)`를 붙였다) | 정의 검토 | 연동 표시 없이 두 도메인에 적혔다는 지적도, provider에 대한 의존을 방향이 어긋났다고 하는 지적도 없음 | 허용 목록 밖의 방식 값 지적 있음 | 없음 |

고친 문구는 하나다. 리뷰어 정의 검토의 "분량 예산을 넘는가" 뒤에 "(도메인마다 패키지 줄, 규칙 칸 합계와 항목, 관계 설명, 섹션을 빠짐없이 센다)"를 더했다(§6에 반영했다). 분량 숫자는 바꾸지 않았다. 세 실행 모두 글자 수를 유니코드 문자 수로 셌고, 옛 칸 이름 `코드`는 문서에 한 번만 알렸으며, `패키지` 칸이 없다는 지적은 없었다.

기대한 목록 밖에서 나온 지적은 기준의 문제가 아니라 프로젝트의 내용이다. imstargg-v2에서는 갱신 실행 코드가 다른 도메인의 패키지에 있어 의존이 양방향으로 보인다는 것(Important)이, noguesstoday에서는 연동만 맡는 도메인이 수수료 정책을 갖는다는 것(Important)과 그 도메인의 `외부`에 없는 외부 시스템이 나왔다. §9의 프로젝트별 후속 작업 때 함께 본다.

### 릴리스 전에 고친 것(2026-11-12)

전체 리뷰가 Minor로 남긴 것 가운데 셋을 사용자 결정으로 고쳤다. 리뷰어 문구가 둘 바뀌어 정의 검토를 한 번 다시 돌렸다(imstargg-v2 문서의 사본, `미정` 칸에 정한 방향과 다른 코드를 적은 항목 하나를 더했다). `미정`의 두 항목을 따로 다뤘다: 정하지 못한 정책은 정해서 `규칙`에 적거나 지우자고 했고, 어긋난 코드는 어긋남 목록으로 옮기자고 했다. `패키지` 칸이 없다는 지적은 없었고 옛 칸 이름 `코드`는 문서에 한 번만 알렸다. 위 표의 다른 실행은 다시 돌리지 않았다.

- `미정` 항목의 갈 곳이 §5·§6에서는 둘(`규칙`으로 옮기거나 지운다)이고 §9에서는 셋이었다. §9의 셋(`규칙`, `알려진 어긋남`, 지운다)으로 §5의 수정 모드 문장과 §6의 형식 항목을 맞췄다.
- 리뷰어 형식 항목의 "필수 필드"를 "기본 뼈대의 역할·기능·분류·패키지가 도메인마다 있는가"로 바꿨다(§6).
- CHANGELOG에 빠진 동작 변화 셋을 더했다: 뼈대에 없는 절·칸을 Minor로 알림, 전체 점검의 새 항목 둘, 연동만 맡는 도메인으로 떼어 내는 기준.
