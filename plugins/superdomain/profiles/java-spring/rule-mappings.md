# java-spring — primitive → ArchUnit 번역

대상 도구: **ArchUnit 1.4.1** (`com.tngtech.archunit:archunit`, 테스트 스코프). 어휘의 의미 정본은
`references/governance/rule-vocabulary.md`이고 이 문서는 그것을 코드로 옮기기만 한다. 두 문서가
어긋나면 어휘가 이긴다. 플레이스홀더 규약은 `profiles/README.md`.

**길잡이** — 헤더·배치·스코프·import·메서드 이름은 [§0.1](#01-헤더배치스코프), 파일마다 넣는 공통
조각은 [§0.2](#02-파일마다-한-번-넣는-조각), 0건 매칭이 조용히 통과하는지는 [§0.3](#03-0건-규율),
primitive 번역은 [§1](#1-layer-order)–[§5](#5-forbid-sibling-dependency), 파생 3종은
[§6](#6-파생-규칙-3종), 부채 강등은 [§7](#7-baseline-연동), 쓰지 않기로 한 기능은
[§8](#8-쓰지-않는-것), 쓴 API의 검증은 [§9](#9-검증-대장) → `api-verification.md`.

**검증 표기** — `✅`는 소스·공식 문서로, `✅ 실측`은 실행으로 확인한 API. 확인하지 못한 API에는
`⚠️ (미검증 — 첫 실행 시 확인)`을 남긴다(대장 기준 현재 없다). **패턴은 해석기가 만든다** —
정규화 산출(`layer_patterns`·`resolved`)을 쓰고 패키지를 손으로 조립하지 않는다.

## 0. 공통

### 0.1 헤더·배치·스코프

생성 파일 첫 두 줄(글자 그대로 — fitness가 이 헤더의 온전함으로 수동 수정 여부를 판정한다):

```java
// GENERATED by superarchitect from ARCHITECTURE.md
// 수정 금지 — 규칙 변경은 스타일 선언에서. 재생성: /superarchitect:fitness
```

| 대상 | 파일 |
|---|---|
| 컨텍스트의 스타일 유래 규칙 | `<아키텍처 테스트 위치>/<기본 패키지 경로>/architecture/{{Context}}ArchitectureTest.java` |
| 프로젝트의 파생 규칙 3종 | `<아키텍처 테스트 위치>/<기본 패키지 경로>/architecture/DerivedRulesTest.java` |

패키지 선언은 `package {{basePackage}}.architecture;`이고 **파일 이름과 같은 이름의 클래스** 하나에
`@Test` 메서드를 담는다.

**스코프는 클래스패스다.** ArchUnit은 소스가 아니라 컴파일된 클래스를 읽는다 ✅ 실측. 둘이 따라온다.
**아키텍처 테스트 모듈은 검사 대상 모듈을 의존해야 한다** — kotlin-spring의 정반대다(Konsist는 소스
트리를 읽어 의존 0을 규율로 삼는다). 의존이 없으면 스코프가 비고 §0.3에 따라 전 규칙이 "0건"으로
실패한다. 그리고 `DO_NOT_INCLUDE_TESTS`로 프로덕션만 남긴다 — 어휘의 대상이 프로덕션 소스이고(§3.4),
이 옵션이 없으면 **생성 파일이 자기 자신을 검사한다** ✅ 실측(스코프 14 → 22, 유입 목록에
`…architecture.ClaimArchitectureTest$1`). 판정이 위치 경로 정규식이라 테스트 코드가 jar로 실리면
놓친다(대장).

**import 목록(정본)** — 생성 파일은 **이 블록을 그대로 복사**하고 쓰지 않은 줄만 뺀다. 대장의 소스
경로에서 **유도하지 않는다** — 술어는 선언 인터페이스(`HasName`·`HasType`·`CanBeAnnotated`)에 흩어져
있고 `classes()`·`layeredArchitecture()`는 각각 `lang.syntax`·`library` 아래의 정적 메서드라, 유도하면
심볼 미해결이 연쇄해 파일 전체가 컴파일되지 않는다. 아래 블록은 프로브에서 **실컴파일·실행**으로
확인했다 ✅ 실측.

```java
import com.tngtech.archunit.base.DescribedPredicate;                                      // §0.2 이하 전부
import com.tngtech.archunit.core.domain.JavaClass;                                        // §0.2 이하 전부
import com.tngtech.archunit.core.domain.JavaClasses;                                      // §0.2
import com.tngtech.archunit.core.importer.ClassFileImporter;                              // §0.2
import com.tngtech.archunit.core.importer.ImportOption;                                   // §0.2
import org.junit.jupiter.api.DisplayName;                                                 // §0.1
import org.junit.jupiter.api.Test;                                                        // §0.1
import java.nio.file.Files;                                                               // §7
import java.nio.file.Path;                                                                // §7
import java.nio.file.Paths;                                                               // §7
import java.util.HashMap;                                                                 // §7
import java.util.HashSet;                                                                 // §7
import java.util.Map;                                                                     // §7
import java.util.Set;                                                                     // §7
import static com.tngtech.archunit.core.domain.JavaClass.Predicates.resideInAPackage;     // §0.2
import static com.tngtech.archunit.core.domain.JavaClass.Predicates.simpleName;           // §3
import static com.tngtech.archunit.core.domain.JavaClass.Predicates.simpleNameEndingWith; // §5
import static com.tngtech.archunit.core.domain.properties.CanBeAnnotated.Predicates.annotatedWith;  // §3
import static com.tngtech.archunit.core.domain.properties.HasName.Predicates.name;        // §0.2
import static com.tngtech.archunit.core.domain.properties.HasType.Predicates.rawType;     // §3
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.classes;                // §3·§4

```

§7 조각이 한두 번 쓰는 타입(`java.util.List`·`java.io.*`·`java.util.regex.*`)은 그 조각 안에서 **FQN**
이다 — 조건부 코드로 정본 블록이 길어지지 않게 한 선택이고, 조각을 그대로 붙이면 성립한다.

**메서드 이름 규약 — 안전 변환.** Java 메서드 이름에는 백틱이 없다. 이름에 들어가는 치환값은
`[A-Za-z0-9_$]` 밖의 문자를 `_`로 바꾼 형태를 쓴다 — `{{ruleIdSafe}}`가 그 변환을 `ruleId`에 적용한
이름이고(`hex.domain-pure` → `hex_domain_pure`), `{{context}}`·`{{subject}}`·파생의 `{{.}}`도 이름
자리에서는 같은 변환을 거친다(`core-api` → `core_api`). 메서드 이름은 `{{context}}_{{ruleIdSafe}}`
(파생은 §6.2 표), `@DisplayName`은 `"{{context}} — {{ruleId}}"` — **원본 id는 `@DisplayName`과
`because(...)`에 남는다.** 리포트에서 id가 사라지지 않게 하는 것이 이 이중 표기의 목적이다.
**한 파일 안에서 메서드 이름은 유일해야 한다**: 컨텍스트별 파일은 규칙 id가 유일 키라 자동이고,
프로젝트당 하나로 모이는 파생 규칙은 §6.2의 유일 키를 지킨다. 안전 변환이 `.`과 `-`를 같은 `_`로
접으므로 **한 파일에 구분자만 다른 두 id**(`a.b-c`와 `a-b.c`)가 있으면 이름이 겹치는데, 그때는 javac가
"already defined"로 즉시 죽는다 — 조용한 실패가 아니다. 답은 어휘 §4대로 id를 짓는 것이지 생성기가
이름을 지어내는 것이 아니다.

### 0.2 파일마다 한 번 넣는 조각

스코프 필드와 패턴 헬퍼는 생성 파일마다 한 번씩 들어간다.

```java
private static final JavaClasses CLASSES = new ClassFileImporter()
        .withImportOption(ImportOption.Predefined.DO_NOT_INCLUDE_TESTS)
        .importPackages("{{basePackage}}");

private static DescribedPredicate<JavaClass> matching(String... patterns) {
    DescribedPredicate<JavaClass> result = null;
    for (String pattern : patterns) {
        DescribedPredicate<JavaClass> one = pattern.endsWith("..")
                ? resideInAPackage(pattern)
                : resideInAPackage(pattern).or(name(pattern));
        result = (result == null) ? one : result.or(one);
    }
    return result.as(String.join(", ", patterns));
}
```

`matching`은 어휘 §2의 패키지 패턴 표기를 술어로 옮긴다. `..`로 끝나면 그 패키지와 하위 전체, 없으면
**정확히 그 패키지 또는 그 타입** — 어휘가 "정확히 그 패키지·타입"이라 정의한 두 갈래이고, ArchUnit의
`resideInAPackage`는 앞쪽만 안다 ✅ 실측. 인자는 최소 하나여야 한다(빈 목록은 `null`을 부른다) —
목록이 빌 수 있는 자리는 §6.2가 "생성하지 않는다"로 처리한다.

> **`name(pattern)` 갈래를 빼면 규칙이 조용히 통과한다.** `to`가 타입 FQN인 규칙을
> `resideInAnyPackage`만으로 옮기면 대상 매칭이 0건이 되는데 `that()` 쪽은 비어 있지 않으므로 §0.3의
> 0건 경보도 울리지 않는다 — 실측에서 실제 위반이 있는 트리가 **통과**했다. 어휘 §1이 "없는 규칙보다
> 나쁘다"고 부른 상태다.

### 0.3 0건 규율

**"위반 없음"과 "아무것도 검사하지 않음"은 구분되어야 한다.** ArchUnit의 기본값이 이미 그 편이다.

1. `that()` 매칭이 0건이면 규칙이 **실패한다** ✅ 실측 — `Rule '…' failed to check any classes.`
   `classes()`·`noClasses()`·스코프 자체가 0건인 경우가 모두 같다. Konsist의 `strict = false`(빈
   목록에서 성공)와 반대 방향의 기본값이다.
2. `layeredArchitecture()`의 레이어 중 하나라도 파일이 0건이면 규칙이 **실패한다** ✅ 실측(기본값
   `withOptionalLayers(false)`). 레이어 이름과 실제 패키지가 어긋나 규칙이 조용히 사라지는 실패
   모드(어휘 §5)를 이 검사가 잡는다.

따라서(어휘가 정하지 않은 번역 판단이므로 명시한다): **layer-order·forbid-import·naming-suffix·
forbid-sibling-dependency·파생 3종은 기본값 그대로** — 0건은 패턴이 실제 패키지와 어긋났다는 신호다.
**confine-type만 `allowEmptyShould(true)`** — 격리 대상이 정당하게 0개일 수 있다(JPA 미사용).
kotlin-spring §0.3과 같은 갈래이며 반대편 기본값을 각자의 방식으로 맞춘 것뿐이다. 0건 실패는 "그
레이어를 아직 구현하지 않은" 정상 상태에서도 뜨는데, 답은 경보를 끄는 것이 아니라 선언을 고치는
것이다 — 없는 레이어는 스타일에서 빼고, 이행 중이면 `이행` 라벨과 baseline이다(§7).
`archunit.properties`의 `archRule.failOnEmptyShould=false`는 이 경보를 **프로젝트 전역에서** 꺼
버리므로 쓰지 않는다(§8).

## 1. layer-order

**입력** — `params["layers"]`(안→밖), `params["strict"]`(기본 `false`), `layer_patterns[<레이어>]`
(레이어마다 패턴이 **여럿일 수 있다** — `{앱}` 규약이 앱마다 전개한다). **어휘의 `strict`는 파라미터가
아니라 허용 집합의 크기로 번역한다** — 레이어 `l0`(가장 안) … `ln`에 대해:

- 모든 레이어를 `.layer("<이름>").definedBy(matching(<그 레이어의 패턴 전부>))`로 등록한다. 등록하지
  않은 레이어는 §0.3-2의 빈 레이어 검사에서도 빠져 규칙이 조용히 빈다.
- `l0`은 `.whereLayer("l0").mayNotAccessAnyLayer()`. `i ≥ 1`인 `li`의 허용 집합은 비-strict면
  `{l0…l(i-1)}`, strict면 `{l(i-1)}`(인접 안쪽만) → `.whereLayer("li").mayOnlyAccessLayers(…)`.
  집합이 빌 일은 없다(`l(i-1)`이 언제나 있다).
- `consideringOnlyDependenciesInLayers()`를 **반드시 부른다** — 레이어에 속하지 않는 코드(앱·공용
  모듈·프레임워크)와의 의존은 이 규칙의 대상이 아니고 그쪽은 §6이 본다.
- `because(...)`가 **마지막**이다 — 반환형이 `ArchRule`이라 뒤에 `withOptionalLayers`·`as`를 부를 수
  없다 ✅ 실측(대장).

**템플릿** (`hexagonal`, 컨텍스트 `claim`, 기본 패키지 `com.acme`로 전개한 모습)

```java
@Test
@DisplayName("{{context}} — {{ruleId}}")
void {{context}}_{{ruleIdSafe}}() {
    layeredArchitecture().consideringOnlyDependenciesInLayers()
            .layer("domain").definedBy(matching("com.acme.claim.domain.."))
            .layer("application").definedBy(matching("com.acme.claim.application.."))
            .layer("adapter").definedBy(matching("com.acme.claim.adapter.."))
            .whereLayer("domain").mayNotAccessAnyLayer()
            .whereLayer("application").mayOnlyAccessLayers("domain")
            .whereLayer("adapter").mayOnlyAccessLayers("application", "domain")
            .because("규칙 {{ruleId}} — 컨텍스트 {{context}}")
            .check(CLASSES);
}
```

레이어마다 `.layer(…).definedBy(…)` 한 줄이고, 그 레이어의 패턴이 여럿이면 `matching`의 인자가 늘 뿐
모양은 같다. `strict=true`였다면 마지막 `whereLayer`가 `mayOnlyAccessLayers("application")`이 된다 —
건너뛴 의존(adapter → domain)이 비-strict에서 통과하고 strict에서만 실패하는 것을 트리 하나로 대조
실측했다 ✅.

**커버리지(아래 모든 primitive 공통)** — ArchUnit의 판정은 **바이트코드 의존**이다: 필드 타입·
파라미터·반환 타입·메서드 본문의 호출·애노테이션까지 본다 ✅ 실측. import 기반 검사(Konsist·
`check_imports`)가 놓치는 같은 패키지 참조와 FQN 인라인도 잡힌다. 반대로 **컴파일에서 지워지는 것은
보지 못한다** — 상수 인라인, SOURCE 보존 애노테이션, 쓰이지 않는 import, 리플렉션.

## 2. forbid-import

**입력** — `resolved["from"]`, `resolved["to"]`. §2.1(가) 파라미터라 레이어 항목은 resolve_rules가
이미 패턴으로 치환했다.

```java
@Test
@DisplayName("{{context}} — {{ruleId}}")
void {{context}}_{{ruleIdSafe}}() {
    noClasses()
            .that(matching({{items:resolved.from}}))
            .should().dependOnClassesThat(matching({{items:resolved.to}}))
            .because("규칙 {{ruleId}} — 컨텍스트 {{context}}")
            .check(CLASSES);
}
```

**라우트 분기가 없다.** kotlin-spring §2는 외부 라이브러리 패턴 때문에 라우트를 둘로 갈랐지만
(`Layer`가 소스 0건에서 예외를 던진다), ArchUnit은 **참조 대상이 스코프에 없어도 의존을 판정한다** ✅
실측 — `to=org.springframework..,jakarta.persistence..`도 `to`가 같은 프로젝트의 레이어일 때도 위 한
형태다(애노테이션 참조까지 잡힌다).

**주의** — `from` 매칭 0건은 §0.3-1로 실패한다. 정상이다: `from`은 이 프로젝트의 코드라 0건은 패턴이
어긋났다는 뜻이다. `to` 쪽 0건에는 경보가 없고(외부 패키지는 원래 스코프에 없다), `to`가 타입 FQN인
규칙이 조용히 통과하지 않는 것은 §0.2의 `matching`이 지킨다.

## 3. confine-type

**입력** — `params["type"]`(셀렉터), 허용 범위 목록 `allowed`(= `allowed_layer`가 있으면 각 레이어
이름의 `layer_patterns[<레이어>]`를 합친 것, `allowed_package`가 있으면 그 값 그대로 — (가)·(나)
어디에도 속하지 않는 순수 패키지 패턴 필드다), 범위 `contextScope`(= `layer_patterns` 값의 합집합).

셀렉터 `jpa-entity`의 술어는 `annotatedWith(rawType(simpleName("Entity"))).<JavaClass>forSubtype()`
✅ 실측이다. 애노테이션 타입이 클래스패스에 없어도 이름으로 매칭되므로 `annotatedWith(Entity.class)`를
쓰지 않는다 — 그쪽은 테스트 모듈에 JPA 컴파일 의존을 만든다(대장). `forSubtype()`이 없으면 타입이 맞지
않아 컴파일되지 않는다 ✅ 실측.

**수집도 검사도 그 컨텍스트 범위 안에서 한다.** `allowed_layer`가 §2.1(나)에 따라 **그 컨텍스트의**
레이어라, 전역 셀렉터는 `domain-pure`를 가진 두 컨텍스트가 서로의 `@Entity`를 위반으로 잡게 만든다 ✅
실측(컨텍스트 한정을 빼자 다른 컨텍스트의 엔티티가 위반으로 떴다). 교차 컨텍스트 참조는
`derived.context-isolation`(§6)의 몫이다 — `check_imports`의 `_scope_of`가 같은 필터다.

```java
private static final DescribedPredicate<JavaClass> JPA_ENTITY_{{ruleIdSafe}} =
        annotatedWith(rawType(simpleName("Entity"))).<JavaClass>forSubtype();

@Test   // 위반 A — 이 컨텍스트 안에서, 지정 범위 안에서만 선언
@DisplayName("{{context}} — {{ruleId}} (선언)")
void {{context}}_{{ruleIdSafe}}_declaration() {
    classes()
            .that(matching({{items:contextScope}}).and(JPA_ENTITY_{{ruleIdSafe}}))
            .should().resideInAnyPackage({{items:allowed}})
            .allowEmptyShould(true)
            .because("규칙 {{ruleId}} — @Entity는 허용 범위 안에서만 선언한다")
            .check(CLASSES);
}

@Test   // 위반 B — 이 컨텍스트 안에서, 지정 범위 밖에서 참조 금지
@DisplayName("{{context}} — {{ruleId}} (참조)")
void {{context}}_{{ruleIdSafe}}_reference() {
    noClasses()
            .that(matching({{items:contextScope}})
                    .and(DescribedPredicate.not(matching({{items:allowed}}))))
            .should().dependOnClassesThat(JPA_ENTITY_{{ruleIdSafe}}.and(matching({{items:contextScope}})))
            .allowEmptyShould(true)
            .because("규칙 {{ruleId}} — 격리 범위 밖에서 @Entity 타입 참조")
            .check(CLASSES);
}
```

필드 이름의 `{{ruleIdSafe}}` 접미는 §0.1의 유일성 규율이다(한 컨텍스트에 `confine-type`이 둘일 수
있다). 중첩 클래스에 붙은 `@Entity`도 위반이므로 §4와 달리 최상위 필터를 걸지 않는다. 위반 B가 이
primitive의 진짜 가치다(어휘 §3.3).

**커버리지 한계** (침묵 금지 — 이 목록은 대안이 도착했을 때만 지운다)

1. §1의 공통 한계(컴파일에서 지워지는 참조)를 그대로 받는다.
2. **엔티티가 스코프 밖에 있으면 위반 B가 보지 못한다** — 참조 대상의 애노테이션은 임포트된 클래스에만
   보이고 스코프 밖 클래스는 이름만 있는 껍데기로 들어온다.
3. 격리 대상 0건이면 두 어서션 모두 진공 통과하며 ✅ 실측, "JPA를 쓰지 않는 프로젝트"와 "셀렉터가
   아무것도 못 잡음"이 구분되지 않는다.
4. 컨텍스트 범위 밖(어느 레이어 패턴에도 들지 않는 패키지)의 `@Entity`는 보지 않는다 — 규약 레이어
   검증과 review의 몫이다.

## 4. naming-suffix

**입력** — `resolved["scope"]`(§2.1(가) — 레이어면 이미 패턴), `params["suffixes"]`.

```java
@Test
@DisplayName("{{context}} — {{ruleId}}")
void {{context}}_{{ruleIdSafe}}() {
    classes()
            .that(matching({{items:resolved.scope}}))
            .and().areTopLevelClasses()
            .and().arePublic()
            {{#params.suffixes}}
            .orShould().haveSimpleNameEndingWith("{{.}}")
            {{/params.suffixes}}
            .because("규칙 {{ruleId}} — 컨텍스트 {{context}}")
            .check(CLASSES);
}
```

`suffixes`는 OR이라 접미사마다 한 줄이고, **전개 뒤 첫 `.orShould()`를 `.should()`로 바꾼다** — 잊으면
`orShould()`로 체인을 시작할 수 없어 컴파일이 깨진다(조용한 실패가 아니다). 어휘가 정의한 대상이
"프로덕션 소스의 최상위 public 타입"이므로 두 필터를 **명시한다** — 빼면 중첩 공개 타입까지 검사한다
✅ 실측(`ClaimUseCase$Nested`가 위반으로 떴다). `classes()`는 클래스·인터페이스·열거형·레코드·
애노테이션 타입을 모두 포함하고 익명·지역 클래스는 최상위가 아니라 제외된다.

**주의 — `arePublic()`은 Konsist의 `withPublicOrDefaultModifier()`와 같은 것이 아니다.** Kotlin의 기본
가시성이 public이라 저쪽은 "public 또는 기본"을 함께 잡지만 Java의 기본은 package-private라 어휘가 말하는
"공개 타입"이 아니다 — 이름이 아니라 의미로 푼 자리다(`profiles/README.md`).

## 5. forbid-sibling-dependency

**입력** — `params["layer"]`(레이어 이름 1개) → `layer_patterns[<그 레이어>]`, `params["suffix"]`.

```java
@Test
@DisplayName("{{context}} — {{ruleId}}")
void {{context}}_{{ruleIdSafe}}() {
    DescribedPredicate<JavaClass> siblings =
            matching({{items:layer_patterns.<layer>}}).and(simpleNameEndingWith("{{suffix}}"));
    noClasses()
            .that(siblings)
            .should().dependOnClassesThat(siblings)
            .because("규칙 {{ruleId}} — {{suffix}}끼리 의존 금지")
            .check(CLASSES);
}
```

**자기 자신에 대한 의존은 위반으로 세지 않는다** ✅ 실측 — 어휘 §3.5의 주의가 코드 없이 만족된다.
검출 범위는 생성자 파라미터·필드 타입·반환 타입·**메서드 본문의 호출**까지다 ✅ 실측(kotlin-spring
§5가 놓친다고 적은 본문 호출이 여기 포함된다).

**커버리지 한계**

1. **접미사 이름으로만 판정한다** — 같은 레이어 패턴 안이면 다른 컨텍스트의 동명 접미사 타입도 위반이
   된다(과잉 검출). 과잉은 소리가 나고 과소는 조용하다 — v1은 이름으로 둔다.
2. 위반의 주체가 **중첩 클래스**면 단순 이름이 접미사와 달라 `that()`에 걸리지 않는다. 그 밖에 §1의
   공통 한계를 그대로 받는다.

## 6. 파생 규칙 3종

`derived.context-isolation`·`derived.app-confinement`·`derived.shared-module-direction`. 전부 어휘의
`forbid-import` 인스턴스이고 선언에서 나온다(의미 정본은 `architecture-template.md` §5.1 규칙 5).
**`규칙 예외`의 대상이 아니다** — 조절 수단은 `### 관계` 표, `포함 컨텍스트`, 공용 모듈 역할이다.

**앱·공용 모듈의 패키지를 얻는 두 경로 — 선언이 먼저, 관측이 폴백.**

| 경로 | 조건 | 출처 |
|---|---|---|
| ① 선언 | `app-confinement`의 `detail["app_patterns"]` 키가 **있을 때**(패키지 규약에 `{앱}` 행이 있는 프로젝트) | `{앱 이름: [패턴]}` — 하이픈은 이미 점으로 치환됐고 `{컨텍스트}` 전개까지 끝나 있다. **모든 앱의 표가 각 인스턴스에 담긴다** |
| ② 관측(D2) | `app_patterns` 키가 없을 때, 그리고 **공용 모듈은 언제나** | fitness가 `module_path`·`path` 아래 소스의 `package` 선언을 읽는다 |

②는 다른 항목의 접두가 되는 최소 집합만 남기고 각 항목에 `..`를 붙여 `private static final String[]`
리터럴로 굽고, 바로 위에 출처 주석을 병기한다 — 선언 유래는 `// 선언: 패키지 규약 {앱} 행 전개
(app_patterns)`, 관측 유래는 `// 관측: <모듈 경로> (package 선언 N건)`. **관측 0건이면 그 인스턴스를
생성하지 않고 생성 리포트에 고지한다**(침묵 금지). ①에는 이 생략 분기가 없다 — 선언이 곧 진실이므로
0건이 될 수 없다.

### 6.1 공통 어서션 모양

세 종류가 쓰는 어서션은 하나뿐이다 — **§2의 템플릿 그대로**이고 `.that(matching(<from>))`과
`.should().dependOnClassesThat(matching(<forbidden>))`의 두 자리만 바뀐다. 메서드 이름·`@DisplayName`·
`because` 문구는 §6.2의 표가 정한다. `matching`은 가변 인자라 리터럴 전개와 관측 변수(`String[]`)를
똑같이 넘긴다 ✅ 실측.

### 6.2 kind별 대입

두 파생 목록을 먼저 정의한다(§3의 `allowed`와 같은 방식 — 표는 이름으로만 참조한다).

- **`앱 패턴({{subject}})`** = `detail["app_patterns"][{{subject}}]`. 키가 없으면 `module_path` 관측 폴백.
- **`타 앱 패턴`** = `detail["app_patterns"]`에서 `{{subject}}`를 뺀 나머지 값들의 합집합. 키가 없으면
  프로젝트의 다른 앱 `module_path`들을 관측해 합친다.

| kind / 어서션 | 메서드 이름 | `<from>` | `<forbidden>` |
|---|---|---|---|
| `context-isolation` | `{{subject}}_derived_context_isolation` | `{{items:detail.from}}` | `{{items:detail.to}}` |
| `app-confinement` 정방향 | `{{subject}}_derived_app_confinement` | `앱 패턴({{subject}})` | `{{items:detail.forbidden}}` — **비면 생성하지 않는다**(`포함 컨텍스트: all`) |
| `app-confinement` 역방향 | `{{subject}}_derived_app_confinement_reverse` | `{{items:detail.reverse_from}}` | `앱 패턴({{subject}})` |
| `app-confinement` 앱 간 | `{{subject}}_derived_app_confinement_between_apps` | `앱 패턴({{subject}})` | `타 앱 패턴` — **비면 생성하지 않는다**(앱이 하나뿐인 프로젝트) |
| `shared-module-direction` 정방향 | `{{subject}}_derived_shared_module_direction` | 관측 패키지 | `{{items:detail.forbidden}}` **+ 앱 코드 합류**(아래) |
| `shared-module-direction` 도메인 제한 | `{{subject}}_derived_shared_module_direction_domain_{{.}}` | `{{.}}`의 domain 레이어 패턴 | 관측 패키지 |

메서드 이름의 `{{subject}}`·`{{.}}`에는 §0.1의 안전 변환이 걸린다. `@DisplayName`은
`"{{subject}} — derived.<kind>"`(방향이 있으면 ` (역방향)`·` (앱 간)`·` (domain {{.}})`)로 원본 이름을
보존하고, `because`는 `"파생 <id> — <무엇이 왜 금지되는지>"` 형식으로 쓴다. 마지막 행만
`{{#detail.domain_restricted_contexts}}` 반복 블록 **안**이라 그 `{{.}}`는 순회 중인 컨텍스트
이름이고, `profiles/README.md`가 정의한 `{{context}}`(= `EffectiveRule.context` — 이 `DerivedRule`에는
없다)와 **다른 값이다.**

**그 행의 이름에는 `{{subject}}`와 `{{.}}`가 둘 다 있어야 한다.** 파생 규칙은 프로젝트당 파일
하나(`DerivedRulesTest.java`)에 모이는데 resolve_rules는 shared-kernel 아닌 **모든** 공용 모듈에 같은
`domain_restricted_contexts`를 넣으므로, 그런 모듈이 둘 이상이면 컨텍스트 이름만으로는 같은 이름의
메서드가 여러 개 생겨 컴파일이 깨진다. 유일 키는 앞 다섯 행이 (subject, kind, 방향), 마지막 행이
(공용 모듈, 컨텍스트)다. **새 kind나 새 방향은 이 표에 이름을 넣기 전에 유일 키부터 정한다.**

- `context-isolation`의 `to`가 비면 resolve_rules가 인스턴스 자체를 보내지 않는다. 도메인 제한 행은
  `detail["domain_restricted_contexts"]`(D3)마다 하나씩이고, `role`이 `shared-kernel`이면 비어 있다.
- **앱 → 앱 의존 금지는 별도 어서션이 필요하다** — resolve_rules가 `forbidden`·`reverse_from`에서
  컨텍스트 비분할 레이어(`'*'`) 패턴을 빼는데 app-embedded에서는 **다른 앱의 패키지가 바로 그
  패턴**이라 두 목록 어디에도 타 앱 코드가 없다. "앱 간" 행의 이유다.
- **공용 모듈 정방향의 앱 코드 합류**: `{앱}` 규약이 있으면 그 전개형이 이미 `detail.forbidden`에 있고,
  **없으면** 앱마다 `app-confinement`의 `module_path`를 ②로 관측해 `<forbidden>`에 합류시킨다 — 빼면
  "공용 모듈 → 앱" 금지가 어느 어서션에도 남지 않는다(관측 0건인 앱은 그 몫만 빼고 고지). 대칭 구현은
  `check_imports`의 `_app_code_patterns`.

> **도메인 제한 행의 domain 레이어 패턴은 `detail`에 없다.** 같은 프로젝트에서 `context == {{.}}`인
> `EffectiveRule`을 찾아 그 `layer_patterns["domain"]`에서 가져온다. 그 컨텍스트에 유효 규칙이 하나도
> 없어 `EffectiveRule`이 없으면 패턴을 얻을 수 없으므로 **그 항목을 생략하고 고지한다.**

## 7. baseline 연동

`이행` 라벨이 있으면 기존 위반이 `docs/architecture/baseline.jsonl`에 동결돼 있다(정본 §5.1 규칙 8) —
한 줄 JSON `{"rule": …, "path": …}`(`note`는 선택), 경로는 git 루트 상대다. **동결은 init이 사용자 확인
뒤에 하고** 축소는 migrate만 한다. `FreezingArchRule`은 쓰지 않는다(§8) — **생성 테스트가 어서션의 대상
집합에서 동결분을 빼서 강등한다.** 조각은 파일마다 한 번(§0.2 자리), 합성은 어서션마다.

```java
private static final Map<String, Set<String>> BASELINE = loadBaseline();
private static final Set<String> REPORTED = new HashSet<>();

private static Map<String, Set<String>> loadBaseline() {        // 이 디렉터리부터 상위로, 가장 가까운 하나
    Map<String, Set<String>> baseline = new HashMap<>();
    for (Path dir = Paths.get("").toAbsolutePath(); dir != null; dir = dir.getParent()) {
        Path file = dir.resolve("docs/architecture/baseline.jsonl");
        if (!Files.isRegularFile(file)) continue;
        try {
            java.util.List<String> lines = Files.readAllLines(file);
            for (int i = 0; i < lines.size(); i++) {
                if (lines.get(i).isBlank()) continue;           // 빈 줄만 건너뛴다
                String where = file + ":" + (i + 1);
                baseline.computeIfAbsent(field(lines.get(i), "rule", where), key -> new HashSet<>())
                        .add(field(lines.get(i), "path", where));
            }
        } catch (java.io.IOException e) {
            throw new java.io.UncheckedIOException(e);
        }
        break;
    }
    return baseline;
}

private static String field(String line, String key, String where) {
    java.util.regex.Matcher matcher = java.util.regex.Pattern
            .compile("[{,]\\s*\"" + key + "\"\\s*:\\s*\"([^\"\\\\]+)\"").matcher(line);
    if (!matcher.find()) {
        throw new IllegalStateException(where + ": \"" + key + "\" 값이 없습니다 — baseline을 믿을 수 없습니다");
    }
    return matcher.group(1);
}

private static DescribedPredicate<JavaClass> notDemoted(String ruleId) {   // 동결분이면 대상에서 뺀다
    return new DescribedPredicate<>("baseline 동결분 제외") {
        @Override public boolean test(JavaClass klass) {
            String tail = klass.getPackageName().replace('.', '/') + "/"
                    + klass.getSourceCodeLocation().getSourceFileName();
            for (String path : BASELINE.getOrDefault(ruleId, Set.of())) {
                if (!path.equals(tail) && !path.endsWith("/" + tail)) continue;
                if (REPORTED.add(ruleId + " " + path)) {
                    System.out.println("[기존 부채] " + ruleId + " — " + path + " (baseline 동결분)");
                }
                return false;
            }
            return true;
        }
    };
}
```

| 어서션 | 강등 합성 |
|---|---|
| `noClasses().that(P)` — §2·§3B·§5·§6 | `.that(P.and(notDemoted("{{ruleId}}")))` — **파생의 `{{ruleId}}`는 `derived.<kind>`다**(§6.2) |
| `classes().that(P)` — §3A·§4 | 같다 |
| `layeredArchitecture()` — §1 | 레이어마다 `definedBy(P.and(notDemoted("{{ruleId}}")))` |

**경로 사상** — 위반의 소스 경로를 ArchUnit에서 직접 얻을 수는 없다(`getSource()`의 URI는 클래스 파일,
때로는 jar 안이다 ✅ 실측). 그래서 클래스의 **패키지 경로 + SourceFile 이름**을 만들어 baseline `path`의
**꼬리와 맞추고**(`com/acme/claim/domain/Claim.java`), 소스가 패키지 구조를 따라 배치돼 있다는 표준
Gradle·Maven 전제 위에 선다. 위 조각·강등 합성 2형·아래 한계 ①~⑤를 실행으로 확인했다 ✅ 실측:
동결 전 §1·§2 실패 → 동결 후 **통과 + `[기존 부채]` 출력**.

| 한계 — 침묵 금지 | 내용 |
|---|---|
| ① 매칭 키 | 키가 (규칙 id, 경로)뿐이고 대상 클래스가 규칙에서 통째로 빠지므로 **같은 파일·같은 규칙의 추가 위반도 흡수된다**(`check_imports` 푸터도 같은 고지) |
| ② 꼬리 일치 | 패키지와 디렉터리가 어긋난 배치에서는 매칭되지 않아 **강등이 일어나지 않는다**(계속 빨갛다 — 소리는 난다). 반대로 여러 프로젝트에 같은 패키지·같은 파일 이름이 있으면 **함께 강등된다** |
| ③ 스코프 소진 | 대상이 **전부** 동결분이면 `that()` 0건으로 §0.3-1, 레이어가 통째로 동결분이면 §0.3-2로 실패한다 ✅ 실측. 답은 migrate로 갚는 것이다 |
| ④ 사각 | baseline은 import 기반 근사가 만든다 — **ArchUnit만 보는 위반**(같은 패키지 참조·FQN 인라인·본문 호출)은 기존 부채여도 실패한다 |
| ⑤ 정규식 로더 | 값에 역슬래시·이스케이프가 들어가면 정규식이 놓쳐 **`"path" 값이 없습니다`로 중단**하는데 같은 줄을 `json.loads`로 읽는 `check_imports`는 통과해 **두 소비자가 갈린다** ✅ 실측 — 그 메시지는 값의 부재가 아니라 형태를 가리킨다. `note` 안의 `, "path": …` 꼴은 유효 JSON이면 `\"`로 이스케이프돼 오독하지 않는다 ✅ 실측 |
| ⑥ `UP-TO-DATE` | 이 파일은 소스가 아니라 Gradle이 변화를 보지 못한다. `_shared`의 archtest 조각이 `inputs.files`로 선언해 막는다(그 조각 주석대로 `Test.workingDir` 기본값이 전제다 — 로더가 그 디렉터리부터 올라간다). 구판 조각이나 다른 테스트 모듈에는 선언이 없으니 그때는 `--rerun-tasks`가 답이다 |

## 8. 쓰지 않는 것

**`FreezingArchRule`을 쓰지 않는다.** 이름만 보면 §7의 자리이지만 계약이 맞지 않는다:
`ViolationStore`는 `save(ArchRule, List<String>)`·`getViolations(ArchRule)`로 **위반 설명 줄**을 규칙
단위로 저장하고 동치 판정은 `ViolationLineMatcher`(줄 대 줄 문자열 비교)다 ✅ — 코어 계약의 매칭 키
`(rule, path)`로 사상되지 않고 경로를 되살릴 수도 없다. 게다가 store와 `baseline.jsonl`이 **이중
장부**가 되어 migrate의 축소가 store에 반영되지 않는 드리프트를 남긴다. 그래서 §7이 `baseline.jsonl`을
직접 읽는다. 스펙 §10의 "FreezingArchRule로 구현" 문장은 이 판단 앞에 쓰인 옛 서술이고, 그쪽에 정정
블록이 있다. **`archunit_ignore_patterns.txt`도 쓰지 않는다** — 위반 메시지 정규식으로 지우는 또 하나의
장부이고 지운 사실이 리포트에 남지 않는다. **`archRule.failOnEmptyShould=false`도 쓰지 않는다**(§0.3).

**Spring Modulith**는 single-module의 **보조** 검증 수단이 될 수 있다(`@ApplicationModule` +
`ApplicationModules.of(App.class).verify()`). **v1의 생성 대상은 ArchUnit뿐이다** — ① 경계가 앱 클래스
기준 패키지 트리에 묶여 정규화(§6)를 표현하지 못하고 ② 경계 선언이 소스로 가 SSOT가 갈라진다.
