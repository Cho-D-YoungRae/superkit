# 언어 프로파일 계약

프로파일은 **규칙 어휘를 특정 언어·도구로 번역하는 어댑터**다. 번역 단위는 스타일이 아니라
primitive다 — 프로파일은 `hexagonal`이라는 스타일을 모르고, `layer-order`·`forbid-import`·
`confine-type`·`naming-suffix`·`forbid-sibling-dependency` 다섯 개와 파생 규칙 3종만 안다. 그래서
프리셋이든 아무도 예상하지 않은 커스텀 스타일이든, 어휘의 조합이기만 하면 fitness가 테스트를 만든다.

어휘의 의미 정본은 `references/governance/rule-vocabulary.md`다. 프로파일은 그 의미를 바꾸지 않고
코드로 옮기기만 한다. 두 문서가 어긋나면 어휘가 이긴다.

## 현황

| 프로파일 | 도구 | 상태 |
|---|---|---|
| `kotlin-spring` | Konsist 0.17.3 (`com.lemonappdev:konsist`) | 네 가지 다 있음 — 매핑·검증 대장·프리셋 템플릿 4종·examples |
| `java-spring` | ArchUnit 1.4.1 (`com.tngtech.archunit:archunit`) | 빈 디렉터리 — 아래 구현 상태 |

이 계약의 소비자는 모두 도착했다: 매핑을 읽어 테스트를 만드는 `fitness` 스킬, 템플릿이 소비하는
`EffectiveRule`·`DerivedRule`을 내는 `scripts/resolve_rules.py`, 그리고 `profiles/` 디렉터리를
동적으로 읽는 `parse_architecture.py`.

> **구현 상태 — `java-spring`은 Phase 6이다.** `profiles/java-spring/`에는 아직
> `rule-mappings.md`가 없다. Java 프로젝트를 선언할 수는 있지만 fitness는 매핑 부재를 그대로
> 알리고 중단한다(생성하지 않는다). 어휘 확장 절차(`rule-vocabulary.md` §7)가 요구하는 "두
> 프로파일 매핑 동시 추가"도 그때까지 완주할 수 없다.

## 디렉터리 구조

```
profiles/<이름>/
├── rule-mappings.md          # 필수 — primitive → 도구 코드 번역
├── api-verification.md       # 필수 — 쓴 도구 API의 검증 대장
├── templates/<style>/        # 선택 — scaffold가 쓰는 골격. MANIFEST.md가 그 안의 계약
│   ├── MANIFEST.md
│   ├── settings.gradle.kts.fragment
│   ├── build.gradle.kts.<레이어>
│   ├── <레이어>/*.kt
│   └── test/*.kt
├── templates/_shared/        # 스타일과 무관한 조각. 앱 실행·아키텍처 테스트 모듈이 여기 산다
└── examples/{good,bad}/      # 선택 — 좋은 예 발췌 1, 나쁜 예 1~2
```

`templates/` 아래에서 **`_`로 시작하는 디렉터리는 스타일이 아니다.** 스타일 이름은 그 자체로
`- 스타일:` 라벨의 값이므로, 스타일이 아닌 묶음은 그 이름 공간에 들어갈 수 없다.

디렉터리 이름이 곧 프로파일 이름이고, `ARCHITECTURE.md`의 `- 프로파일:` 값이 그것을 가리킨다.
파서는 `profiles/` 아래 디렉터리 목록을 읽어 정규 값 집합을 만든다 — 상수 목록이 아니므로
디렉터리를 만드는 것만으로 새 프로파일 이름이 허용된다.

## ① `rule-mappings.md` + `api-verification.md` — 필수 2파일

**번역 사전과 검증 대장은 짝이다.** 둘 중 하나라도 없는 디렉터리는 프로파일이 아니다.
`rule-mappings.md`는 fitness의 유일한 번역 사전이며, 여기에 없는 primitive를 만나면 fitness는
**임의로 번역하지 않고 오류로 보고한다**. 두 파일이 나눠 담는 것은 다음과 같다.

`rule-mappings.md`:

1. **생성 파일 헤더**(고정 문자열)와 **파일 배치 규약** — 어떤 이름의 파일이 어디에 생기는가.
2. **import 목록(정본)** — 생성 파일이 **그대로 복사**할 블록. "검증 대장의 소스 경로에서
   유도하라"로 대신하지 않는다. 그 경로는 심볼이 아니라 선언 인터페이스의 위치이며, 유도가 틀리면
   파일 전체가 컴파일되지 않는다(kotlin-spring 실측).
3. **primitive 5종 각각**에 대해: 입력(어느 필드를 읽는가) → 코드 템플릿(그대로 컴파일되는 완전한
   형태) → 주의·커버리지 한계.
4. **파생 규칙 3종**(`derived.context-isolation`·`derived.app-confinement`·
   `derived.shared-module-direction`) 각각의 템플릿.
5. **검증 표기**의 뜻과 **커버리지 한계** — 그 도구가 원리적으로 보지 못하는 것. 침묵은 금지다.
   대장을 가리키는 포인터 절(§9)을 둔다.

`api-verification.md`:

6. **검증 대장** — 쓴 도구 API마다 한 행. 공식 문서·소스로 확인한 것(`✅`), 실행까지 확인한
   것(`✅ 실측`), 확인하지 못한 것에는 반드시 `⚠️ (미검증 — 첫 실행 시 확인)`을 남긴다. 미검증을
   검증된 것처럼 쓰는 것은 이 저장소가 가장 경계하는 실패다 — 생성은 되는데 강제되지 않는 규칙을
   만든다. **새 API는 여기에 행을 추가한 뒤에만 템플릿에 쓴다.**

번역 사전이 500줄에 닿으면 대장을 먼저 이 파일로 뺀다 — kotlin-spring이 그렇게 갈라졌다.

## 플레이스홀더 규약 — ①과 ②가 공유하는 한 계약

`rule-mappings.md`의 코드 템플릿과 `templates/`의 골격 템플릿은 **같은 치환 규약을 쓴다.** 이
절이 그 정본이다 — 두 곳이 다른 이름으로 같은 것을 가리키기 시작하면 scaffold와 fitness가 만든
파일이 서로 다른 패키지를 가리키게 된다.

치환 지점은 `{{...}}`로 쓴다. 네 가지 형태뿐이다.

| 형태 | 뜻 |
|---|---|
| `{{name}}` | 스칼라 1개를 그 자리에 치환 |
| `{{name:<인자>}}` | 인자를 받는 스칼라. 현재 `{{pkg:<레이어>}}` 하나뿐이다 |
| `{{items:<필드>}}` | 문자열 목록을 `"a", "b"` 꼴로 전개(따옴표 포함, 쉼표 구분) |
| `{{#<필드>}} … {{/<필드>}}` | 목록 항목마다 블록을 1회씩 반복. 블록 안에서 `{{.}}`는 현재 항목, `{{i}}`는 0-기준 순번. **블록 태그만 있는 줄은 전개 때 통째로 지운다**(들여쓰기는 블록 안의 줄이 갖는다) |

이름은 `resolve_rules.py`의 산출 스키마에서 온다. 프로파일이 이름을 새로 지어내지 않는다.

| 이름 | 출처 |
|---|---|
| `{{project}}` | `EffectiveRule.project` / `DerivedRule.project` |
| `{{basePackage}}` | 프로젝트 섹션의 `- 기본 패키지:` |
| `{{context}}` | `EffectiveRule.context` — 소문자 그대로 |
| `{{Context}}` | `context`의 PascalCase (파일명·클래스명용). **하이픈·언더스코어로 나눈 각 세그먼트의 첫 글자를 대문자로 올리고 구분자를 제거한다** — `core-api` → `CoreApi`, `order_mgmt` → `OrderMgmt` |
| `{{ruleId}}` | `EffectiveRule.rule_id` |
| `{{ruleIdSafe}}` | `ruleId`에서 대상 언어의 식별자에 쓸 수 없는 문자를 공백으로 바꾼 형태 (Kotlin 백틱 함수 이름은 `.`을 담을 수 없다 — `hex.domain-pure` → `hex domain-pure`) |
| `{{primitive}}` | `EffectiveRule.primitive` |
| `{{layerName}}` | §2.1(나) 파라미터가 담은 레이어 이름 1개 — `params[키]`의 항목 |
| `{{LayerName}}` | `layerName`의 PascalCase (도구가 오류 메시지에 쓰는 표시 이름) |
| `{{pattern}}` | 패키지 패턴 1개 — `layer_patterns[layerName]`의 항목 또는 `resolved[키]`의 항목 |
| `{{subject}}` | `DerivedRule.subject` (컨텍스트명 \| 앱명 \| 공용 모듈명) |
| `{{kind}}` | `DerivedRule.kind` |
| `{{modulePath}}` | `detail["module_path"]`(app-confinement) 또는 `detail["path"]`(shared-module-direction) |
| `{{role}}` | `detail["role"]` |
| `{{layer}}` | 골격에서 **지금 전개하는 레이어**의 이름 — 모듈 경로·gradle 경로·조각 파일 이름에 쓴다. 위의 `{{layerName}}`과 다르다: 저쪽은 규칙 파라미터가 담은 레이어 이름이다 |
| `{{pkg:<레이어>}}` | 그 레이어의 **정규화 패턴에서 끝의 `..`를 뗀 값** — `layer_patterns[<레이어>]`. 소스 템플릿의 `package` 선언·`import`·소스 디렉터리 경로에 쓴다 |
| `{{app}}` | 애플리케이션 표의 `이름`. 모듈 경로에서는 원형 그대로 쓰고, **패키지 위치에서는 하이픈을 점으로 바꾼다**(`core-api` → `core.api` — `architecture-template.md` §6의 `{앱}` 전개와 같은 규칙) |
| `{{App}}` | `app`의 PascalCase — `{{Context}}`와 같은 규칙(`core-api` → `CoreApi`). 앱 메인 클래스 이름에 쓴다 |

목록 필드도 하나 늘었다. `{{#app.contextModules}}`는 그 앱의 `포함 컨텍스트` 각각에 대해 **그
컨텍스트 스타일의 가장 바깥 레이어 모듈의 gradle 경로**를 담는다(`포함 컨텍스트: all`이면 그
프로젝트의 모든 컨텍스트). 출처가 해석기가 아니라 **선언 두 곳의 결합**(애플리케이션 표 ×
각 컨텍스트의 스타일)이므로, 어느 레이어가 가장 바깥인지는 그 스타일의 MANIFEST가 적는다.
**커스텀 스타일에는 MANIFEST가 없다** — 그때 가장 바깥은 그 스타일 `layer-order` 인스턴스의
`layers` 마지막 항목이다(그 파라미터는 언제나 안→밖이다). 스타일의 `레이어` 라벨 순서로 대신하지
않는다: `layered-simple`의 라벨은 위→아래 호출 방향이라 마지막이 가장 안쪽이라는 반례가
`rule-vocabulary.md` §3.1에 있다. `layer-order`가 없거나 `layers`가 레이어 전부를 담지 않아 판정이
갈리면 유도하지 않고 사용자에게 묻는다.

마지막 넷은 **골격 템플릿(②) 전용**이다.

`{{pkg:<레이어>}}`에는 규율이 둘 붙는다.

- **패키지를 손으로 조립하지 않는다.** `{기본 패키지}.{컨텍스트}.{레이어}`는 기본 관례일 뿐이고,
  패키지 규약 표가 있는 프로젝트에서는 그 조립이 틀린다. 값은 해석기가 이미 만든
  `layer_patterns`에서 가져온다(fitness가 `resolved`를 다루는 규율과 같다).
- **패턴이 둘 이상이면 패턴마다 한 벌씩 전개한다.** app-embedded에서 `{앱}` 행이 전개된 레이어가
  그렇고, "앱마다 레이어 패키지 하나씩"이라는 배치가 이 규칙 하나에서 나온다.

**`{{Context}}`의 하이픈 예시가 어디서 실효하는지**는 짚어 둘 값이 있다. 기본 관례에서는 컨텍스트
이름이 그대로 패키지 세그먼트가 되므로 하이픈 있는 컨텍스트가 애초에 성립하지 않는다
(`resolve_rules`가 오류로 거부한다). 하이픈이
실제로 들어오는 경로는 **`{컨텍스트}`를 쓰지 않는 패키지 규약 아래의 컨텍스트 이름**과
`{{app}}`의 앱 이름이며, 그때도 이 변환이 만드는 것은 **클래스·파일 이름**이지 패키지가 아니다
(패키지 쪽은 `{{pkg:<레이어>}}`와 `{{app}}`의 하이픈→점 규칙이 따로 담당한다).

`{{layer}}`가 프리셋 템플릿 안에 잘 보이지 않는 것은 정상이다 — 프리셋은 레이어 집합이 고정이라
`build.gradle.kts.adapter`처럼 이름을 그대로 적는다. 이 변수가 쓰이는 곳은 **레이어를 선언에서
읽어 전개하는 경로**, 즉 커스텀 스타일의 골격 유도다.

primitive마다 있는 스칼라 파라미터는 키 이름을 그대로 쓴다 — `{{suffix}}`, `{{type}}`. 어휘 §2에
따라 `params`의 **모든 값은 목록**이므로, 목록이 아닌 키(`type`·`layer`·`suffix`·`scope`·`strict`)의
스칼라 플레이스홀더는 그 목록의 유일한 항목을 뜻한다.
`{{items:...}}`·`{{#...}}`의 `<필드>`도 같은 출처를 쓴다: `resolved.from`, `resolved.to`,
`params.suffixes`, `layer_patterns.<레이어>`, `detail.forbidden`, `detail.reverse_from`,
`detail.domain_restricted_contexts` 등. `detail.app_patterns` 같은 **맵 필드는 목록
플레이스홀더의 대상이 아니다** — 매핑 문서가 이름 있는 파생 목록으로 풀어 쓴다(kotlin-spring
`rule-mappings.md` §6.2가 그 예). 위 표는 프로파일이 **공유하는 어휘**이고, 각 프로파일은
필요한 것만 쓴다. 파생 목록(예: `confine-type`의 허용 범위)을 쓰는 템플릿은 그 목록이 어떻게
만들어지는지를 자기 "입력" 줄에서 정의한다.

**규칙 어휘의 파라미터 이름과 도구 API 이름이 우연히 같아도 뜻은 같지 않을 수 있다.** 어휘의
`layer-order`에는 `strict` 파라미터가 있고 Konsist에도 `strict`가 있지만 두 뜻은 다르다 —
매핑 문서는 그런 충돌을 이름이 아니라 의미로 풀고, 푼 근거를 적는다.

## ② `templates/<style>/` — 선택

scaffold가 골격을 만들 때 쓰는 파일 묶음이다. 프리셋 스타일 이름(`layered-simple`,
`layered-domain`, `hexagonal`, `clean`)마다 하나씩 둔다. 커스텀 스타일에는 템플릿을 두지 않는다 —
스타일 선언(레이어 + 규칙)에서 골격을 유도하고, 가장 가까운 프리셋은 참고로만 제시한다.

**"참고로만"은 두 층으로 갈린다.** 프리셋 템플릿에는 그 스타일의 정체성이 배어 있고, 그것을
커스텀 스타일로 옮기면 **선언하지도 않은 규칙을 코드가 따르는 상태**가 된다 — 어휘가 폐쇄형인
이유가 그것이다.

| 층 | 처분 |
|---|---|
| 규칙 id, 규칙 근거, 규칙을 설명하는 주석(스타일 정체성) | **복사 금지.** 커스텀 스타일의 규칙은 그 선언에만 있다 |
| 빌드 조각의 기계적 부분 — jvm 플러그인, 테스트 배선, 컴파일러 플러그인 조건, 버전 규약 | **재사용하되 출처를 밝힌다.** 이것들은 스타일이 아니라 언어·프레임워크가 정하는 것이다 |

**수용 기준은 하나다.** 그대로 전개한 골격은 그 스타일의 유효 규칙(파생 포함)에 대해
`check_imports` 클린이고, fitness가 생성한 아키텍처 테스트를 통과해야 한다. 통과하지 못하는
템플릿은 미완성이 아니라 **틀린 것**이다 — 스킬이 만든 골격이 같은 스킬군이 만들 검사에 걸리는
상태이기 때문이다. 이 기준이 골격의 모양을 강하게 정한다. 특히 `strict = true` 규칙과 도구의 빈
레이어 검사 때문에 **스타일이 선언한 레이어마다 소스 파일이 최소 하나** 있어야 하며, 레이어를
비워 두는 "나중에 채울" 골격은 허용되지 않는다.

### `MANIFEST.md` — 스타일 디렉터리마다 하나, 필수

디렉터리 나열이 파일 목록을 대신하지 못한다. **같은 파일이 레이아웃에 따라 다른 곳에 놓이기
때문**이다. 여섯 절을 갖는다.

1. **이 골격이 통과해야 하는 규칙** — 규칙 id마다 "골격이 그것을 만족시키는 방식" 한 줄.
   골격의 어느 모양이 어느 규칙에서 나왔는지 추적되지 않으면 나중에 아무나 지운다.
2. **파일 목록** — 템플릿 파일 → 레이어 → 전개 뒤 무엇이 되는가.
3. **레이아웃 3형 배치** — `multi-module`(레이어별 모듈) / `single-module`(단일 모듈 + 레이어
   패키지) / `app-embedded`(규약 패턴 위치에 레이어 패키지만 — 모듈도 빌드 조각도 만들지 않는다).
   single-module 항목은 **빌드 조각 병합 규칙을 요소별로** 적는다. 조각을 그냥 이어 붙이면
   `plugins` 블록이 여럿이 되어 Gradle이 구성 단계에서 거부하므로, "합친다"는 지시만으로는
   실행할 수 없는 지시다.
4. **ARCHITECTURE.md 등록** — 이 골격이 함의하는 모듈 표. 프리셋 스타일에서 **행은 레이어마다
   하나씩**이며, single-module이어도 `모듈`·`경로` 값만 반복될 뿐 행이 줄지 않는다. 한 행으로
   줄이면서 레이어를 `all`로 적으면 그 스타일의 규칙이 **전부** 공허 레이어가 되어 아무것도
   검사하지 않는다(`resolve_rules`가 경고로 알린다).
5. **치환** — 이 골격이 쓰는 변수. 파일 이름과 디렉터리 이름에도 같은 치환을 적용한다.
6. **수용 기준 확인** — 전개한 프로젝트에서 돌릴 명령.

절 하나를 더 요구하지는 않지만, **골격의 어떤 파일이 규칙에 강제되고 어떤 파일이 교육 목적인지
구분해 적는다.** 강제되지 않는 파일을 "지우면 통과하지 못한다"로 적으면 첫 반증에서 문서 전체의
신뢰가 깎인다(clean의 트랜잭션 데코레이터가 그 예다).

### 파일 구성

| 파일 | 뜻 |
|---|---|
| `settings.gradle.kts.fragment` | 루트 settings에 **더할** include 줄들. 덮어쓰지 않는다 |
| `build.gradle.kts.<레이어>` | 그 레이어 모듈의 빌드 스크립트. **버전을 박지 않는다** — 대상 프로젝트의 plugins 블록·버전 카탈로그·BOM이 정한다 |
| `<레이어>/*.kt` | 그 레이어의 소스 템플릿 |
| `test/*.kt` | 테스트 골격. `test`는 레이어가 아니라 **소스셋**이며 가장 안쪽 레이어를 소유한 모듈의 `src/test`로 간다 |
| `_shared/build.gradle.kts.app` | **앱 실행 모듈**의 빌드 스크립트 |
| `_shared/<앱 메인 클래스>` | 실행 진입점 템플릿(kotlin-spring은 `{{App}}Application.kt`) |
| `_shared/build.gradle.kts.archtest` | **아키텍처 테스트 모듈**의 빌드 스크립트(검증 도구·JUnit 실행 설정, 그리고 생성 테스트가 런타임에 읽는 `baseline.jsonl`의 태스크 입력 선언 — 없으면 baseline만 바뀐 재실행이 `UP-TO-DATE`로 새어 간다). 테스트 **소스**는 여기 없다 — 아래 참조 |

**빌드 조각은 구조 검사가 보지 못하는 것을 담는 유일한 자리다.** 아키텍처 규칙은 import와 이름만
보므로, `@Entity`의 no-arg 생성자나 `@Transactional` 프록시를 위한 open 처리가 빠진 골격은
`check_imports`와 fitness를 **둘 다 통과하고 부팅에서 깨진다.** 그 언어·프레임워크의 그런 항목은
조각에 근거 주석과 함께 넣는다(kotlin-spring은 `kotlin("plugin.jpa")`·`kotlin("plugin.spring")`).

### 앱 실행 모듈 — 스타일 디렉터리에 두지 않는다

컨텍스트 골격만으로는 **돌아가는 것이 없다.** 실행 단위(앱)가 있어야 컨텍스트들이 조립되고, 그
모듈에는 스타일이 정하는 것이 하나도 없다 — hexagonal이든 layered-simple이든 앱 모듈은 똑같이
"부트 플러그인 + 메인 클래스 + 포함 컨텍스트 의존"이다. 그래서 조각을 스타일 4종에 복제하지 않고
`_shared/`에 하나 두고, 각 스타일의 MANIFEST가 **자기 쪽 접점 한 줄**(앱이 이 컨텍스트에서
의존하는 모듈 = 그 스타일의 가장 바깥 레이어)만 적는다.

| 항목 | 규약 |
|---|---|
| 용도 | 실행 단위. 프레임워크의 실행 산출물 플러그인(kotlin-spring은 `org.springframework.boot`), 메인 클래스, **`포함 컨텍스트` 조립 의존**이 전부다 |
| 배치 | `### 애플리케이션` 표의 **`모듈 경로`** 열. settings 조각에는 그 경로의 include 줄이 함께 들어간다 |
| 메인 클래스 패키지 | `{{basePackage}}.{{app}}`(하이픈→점). 단 `### 패키지 규약`에 `{앱}` 행이 있으면 **그 전개가 이긴다** — 그 행이 앱 패키지의 선언이다 |
| 의존 | 각 `포함 컨텍스트`의 **가장 바깥 레이어** 모듈 하나씩. 안쪽은 전이 의존으로 따라온다. 어느 레이어인지는 프리셋이면 그 MANIFEST, 커스텀이면 「플레이스홀더 규약」의 `layer-order` 규칙이 정한다 |
| 금지 | 업무 로직, `포함 컨텍스트`에 없는 컨텍스트 의존, 다른 앱 모듈 의존 — 셋 다 `derived.app-confinement`가 잡는다 |

앱 모듈은 **아키텍처 규칙의 대상이면서 스타일 규칙의 대상이 아니다.** 스타일 레이어에 속하지
않으므로 `layer-order`·`naming-suffix`는 이 모듈을 보지 않고, 파생 규칙 3종만 본다.

소스 템플릿의 최소 구성은 애그리거트 스텁 1, 포트 1, 유스케이스 1, 어댑터 1, 테스트 골격 1이다.
레이어가 넷 이상인 스타일은 빈 레이어를 남기지 않으려고 파일이 는다 — 그 초과분의 근거를
MANIFEST가 적는다. **아키텍처 테스트 소스는 템플릿에 없다.** 그것은 fitness의 생성물이고 배치
규약은 `rule-mappings.md` §0.1이 갖는다. 골격이 그것을 함께 만들면 두 개의 정본이 생긴다. 골격이
만드는 것은 그 모듈의 자리와 **빌드 스크립트**(`_shared/build.gradle.kts.archtest`)까지다 — 그
스크립트마저 없으면 include는 있는데 실행할 수 없는 모듈에 테스트가 생긴다.

## ③ `examples/` — 선택

그 프로파일의 규칙이 실제로 무엇을 잡는지 보여주는 최소 코드다. **좋은 예와 나쁜 예를 디렉터리로
나눈다.** 예제는 판정 근거가 아니라 읽는 사람의 이해용이므로 늘리지 않는다.

- `examples/good/*.kt` — 한 스타일의 규칙을 **모두** 만족하는 최소 발췌. 파일 2~3개, 각 20줄 내외.
- `examples/bad/*.kt` — 위반 발췌 1~2개. 각 20줄 내외.

**나쁜 예의 첫 줄 주석에 두 가지를 적는다**: 걸리는 **규칙 id 전부**와, 그 도구가 실제로 내는
**실패 메시지의 첫 줄**. 메시지는 지어내지 않는다 — 돌려서 받아 적는다(그러지 않으면 이 파일이
"검증되지 않은 것을 검증된 것처럼 쓰는" ①-6의 실패를 예제 쪽에서 반복한다). 한 파일이 규칙
여럿에 걸리면 전부 적는다 — 실무에서 흔한 모양이고, 어느 규칙이 먼저 잡는지가 고치는 순서를
정한다.

예제는 **읽는 코드**이므로 치환 변수를 쓰지 않고 구체적인 이름으로 쓴다. `kotlin-spring`은
`hexagonal`을 골랐다 — 프리셋 4종 중 규칙이 가장 많고 넷을 한 발췌에 담을 수 있어서다.

## ④ 제3 프로파일을 추가하려면

프로파일 추가는 "계약 구현"이다. 순서대로 한다.

1. `profiles/<이름>/` 디렉터리를 만든다. 이름은 `<언어>-<프레임워크>` 꼴을 쓴다. 파서가
   디렉터리를 읽어 정규 값으로 인정하므로 코드 수정은 필요 없다.
2. `rule-mappings.md`를 위 ①대로 쓴다. **어휘 5종 전부**를 커버해야 한다. 하나라도 그 도구로
   표현할 수 없으면 프로파일을 추가하는 대신 그 사실을 보고한다 — 반쪽 프로파일은 "선언은 되는데
   강제되지 않는 규칙"을 만들고, 그것이 폐쇄 어휘가 막으려던 상태다(`rule-vocabulary.md` §1).
3. `api-verification.md`에 쓴 API를 한 행씩 적는다 — 공식 문서 또는 릴리스 소스로 확인하고,
   확인하지 못한 것은 미검증으로 표기한다. 그리고 **import 목록(정본)을 실제 컴파일로 확인해**
   `rule-mappings.md`에 넣는다. 유도 지시로 대신하지 않는다(①-2).
4. (선택) `templates/`·`examples/`를 채운다. 템플릿을 두기로 했다면 ②의 수용 기준을 **전개해서
   확인한 뒤** 커밋한다 — 통과를 확인하지 않은 템플릿은 두지 않는 편이 낫다.
5. init이 그 스택의 프로젝트를 거버넌스 대상으로 제안하기 시작하는지 확인한다 — 제안 기준은
   "백엔드라서"가 아니라 **프로파일이 있어서**다(스펙 부록 A-6).
