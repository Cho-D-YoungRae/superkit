# 지식 베이스 성장 (추가·보완)

이 스킬은 `superarchitect` 저장소 자신의 지식 베이스를 키우는 저장소 로컬 도구다.
문서 형식·frontmatter 문법·성숙(draft 해제) 판정 규칙·분량 규칙은 전부
`references/governance/knowledge-doc-template.md`에 정본이 있다 — 여기서는
반복하지 않는다. 작업 전에 그 문서를 먼저 읽는다.

## 절차

1. **입력 파악.** 대화 내용, WebFetch로 읽은 URL, 붙여넣은 노트 등 스터디 결과를
   정리한다. 이 단계에서 이미 원칙 하나를 지킨다 — 문서화하는 것은 입력에 실제로
   있는 내용뿐이다. 입력에 없는 일반론·그럴듯한 배경 설명을 채워 넣지 않는다. 입력이
   얇으면 결과도 얇은 draft여야 정직하다(패딩 금지).

2. **대상 판정 — 신규 vs 보완.** `references/INDEX.md`를 읽고, 입력 주제와 겹치는
   문서가 있는지 key·topic·summary로 살핀다.
   - 겹치는 문서가 정확히 하나면 → **보완 모드**로 진행한다. 묻지 않는다.
   - 겹치는 문서가 없으면 → **신규 모드**로 진행한다.
   - 후보가 여럿이거나 겹침 여부가 애매하면, 후보 문서 목록(key·topic·summary)을
     제시하고 사용자에게 고르게 한다. "새 문서로 할까요, 기존 문서에 넣을까요?"처럼
     후보 없이 여는 질문으로 시작하지 않는다 — 먼저 찾아보고, 애매할 때만 후보를
     들고 묻는다.

3. **작성 또는 병합.**

   **3-a. 신규 모드**
   - topic은 `references/knowledge/` 아래 기존 디렉터리 중 맞는 것을 우선 제안한다.
     맞는 게 없을 때만 새 디렉터리를 만든다. 어느 경우든 경로는 정확히
     `knowledge/<topic>/<key>.md` 한 단계여야 한다 — `<topic>/<sub>/<key>.md`처럼
     중첩을 만들지 않는다.
   - 파일명(=key)은 kebab-case 영어로 짓고, `references/INDEX.md`에 같은 key가
     이미 없는지 확인한다(key는 topic이 달라도 knowledge/ 전체에서 유일해야 한다).
   - `references/governance/knowledge-doc-template.md` §8의 빈 템플릿을 복사해
     시작한다. frontmatter는 `summary` 한 줄이 유일한 필수 필드다.
   - 입력이 "언제 쓰는가/쓰지 않는가"와 검증 가능한 규칙까지 뒷받침하면
     "## 적용 기준"·"## 규칙"까지 채워 성숙 문서로 시작해도 된다. 뒷받침하지 않으면
     개념·메모만 자유 형식으로 쓰고 그 두 섹션은 비워 둔다 — draft로 등재되는 것이
     정상이며, 억지로 채우지 않는다.

   **3-b. 보완 모드(병합 — 절대 덮어쓰지 않는다)**
   - 대상 문서를 처음부터 끝까지 읽어 기존 구조와 서술을 파악한다. 구조를 모른 채
     병합할 수 없다.
   - 대상 문서에 아직 섹션 헤딩이 하나도 없는 자유 형식 스텁이라면(전형적인 초기
     스텁 형태), 먼저 `knowledge-doc-template.md` §3의 5단계 헤딩 구조를 만들고
     기존 자유 서술은 알맞은 헤딩(대개 "## 개념")으로 옮겨 보존한 뒤, 그 위에서
     아래 통합 규칙을 적용한다. 이미 헤딩이 있으면 이 단계는 건너뛴다.
   - 새 입력이 어느 섹션(개념/적용 기준/규칙/사례/관련 문서)에 속하는지 정하고,
     그 섹션의 문장 흐름 안으로 통합한다. 문서 맨 끝에 새 절을 이어 붙이기만 하는
     것은 병합이 아니라 방치다.
   - 새 입력이 이미 있는 내용과 같은 이야기면 중복을 남기지 말고 하나로 합친다.
   - 새 입력이 기존 서술과 모순되면 **임의로 어느 한쪽을 골라 지우지 않는다.** 두
     서술을 나란히 보여주고, 어느 쪽이 맞는지 혹은 조건에 따라 갈리는지 사용자에게
     확인한 뒤에만 반영한다.
   - 기존의 올바른 내용을 지우는 것은 병합의 일부가 아니다. 정말 대체가 필요하다고
     판단되면(예: 낡아진 규칙) 근거를 사용자에게 확인받고 나서만 지운다. 단, 스텁이
     담고 있던 "Phase N에서 완성 예정" 안내문이나 "담을 내용" 개조식 목차처럼, 그
     자체가 실제 내용이 아니라 앞으로 채울 자리를 표시해 둔 문장은 다르다 — 그
     목차가 가리키던 내용을 실제로 써넣었다면 자리표시 문장은 삭제 확인 없이
     걷어내도 된다(이것은 "기존의 올바른 내용 삭제"가 아니라 자리표시의 정상적인
     대체다). 이미 서술된 실질적 개념·기준·수치는 이 예외에 해당하지 않는다.
   - 대상 문서가 draft이고, 이번 병합으로 "## 적용 기준"과 "## 규칙" 레벨2 헤딩이
     (원래 없던 것을 포함해) 둘 다 채워진다면 — **이것이 draft 승격이다.** 이 승격은
     이 스킬이 보고해야 할 명시적 결과다: build_index.py 실행 후 INDEX.md에서 해당
     행의 draft 칸이 비었는지 확인하고, "draft → 성숙" 전환을 결과 보고에 분명히
     적는다. 이것이 이 스킬이 존재하는 이유의 절반이다 — 스텁을 판정 근거로 쓸 수
     있는 문서로 키우는 것.
   - 병합 후 문서가 500줄을 넘으면, 그 자리에서 분할하지 말고 주제를 쪼개 별도
     key로 나누고 `[[key]]`로 연결하는 방안을 사용자에게 제안한다.

4. **상호 참조.** 다른 knowledge 문서를 가리킬 때는 `[[key]]`를 쓴다. 쓰기 전에 그
   key가 `references/INDEX.md`(또는 `references/knowledge/` 트리)에 실재하는지
   확인한다 — 존재하지 않는 key를 참조하면 `build_index.py`가 오류로 거부한다.
   대상이 아직 없다면 링크를 보류하거나, summary만 있는 최소 스텁을 먼저 만드는
   방법을 사용자에게 제안한다.

5. **색인 재생성.** `python3 scripts/build_index.py`를 실행한다. 오류(summary
   누락·key 중복·중첩 경로·깨진 `[[key]]` 링크)가 나면 메시지가 지목하는 파일을
   고치고 재실행한다. `references/INDEX.md`는 생성물이다 — 직접 편집하지 않는다.

6. **보고와 커밋 제안.** 무엇을 새로 썼는지, 또는 어느 문서의 어느 섹션을 어떻게
   병합했는지(draft 승격 여부 포함)와 INDEX.md에서 바뀐 행을 보여준다. 아래 형태의
   커밋 명령을 제안만 하고, 실행 여부는 사용자가 정하게 둔다:

   ```bash
   git add references/knowledge/<topic>/<key>.md references/INDEX.md
   git commit -m "knowledge: <key> 추가|보완"
   ```

## 주의

- **창작 금지.** 입력에 없는 주장·수치·예시를 "그럴듯해서" 채워 넣지 않는다.
  확실하지 않으면 사용자에게 묻거나 비워 둔다. 이 지식 베이스는 판정 근거로
  쓰이므로, 그럴듯한 일반론으로 채워진 문서는 얇은 draft보다 해롭다.
- **삭제는 근거 확인 후에만.** 병합 중 기존의 올바른 내용을 지우는 경우는 없다 —
  모순 해소나 대체가 필요할 때만, 그것도 사용자 확인을 거친 뒤에만 지운다.
- **범위.** 이 스킬은 `references/` 안의 knowledge 문서와 INDEX.md 재생성만
  다룬다. `scripts/`나 `tests/`는 건드리지 않고, 실행하는 명령은
  `python3 scripts/build_index.py` 하나뿐이다.
- **커밋은 대신 하지 않는다.** 이 스킬은 항상 커밋 명령을 제안만 한다 — 플러그인의
  다른 스킬들과 마찬가지로 적용 여부는 사용자가 결정한다.
