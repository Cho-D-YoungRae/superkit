# 변경분 아키텍처 검토

이 스킬은 판정하지 않는다. **판정은 이미 세 곳에서 끝나 있다** — 결정적 검사(생성된 테스트·
check_imports·check_invariants)가 구조와 confirmed 불변식의 태그 존재를, 전달받은 지식 문서의
`## 규칙`이 의미론을, `ARCHITECTURE.md`가 무엇을 어디에 적용할지를 정한다. 이 스킬이 하는 일은
그 셋을 올바른 순서로 돌리고 결과를 한 리포트로 합치는 것이다. 그래서 불변이 셋이다.

1. **결정적으로 판정되는 것을 LLM 판단으로 대체하지 않는다.** import 방향·레이어 순서·타입
   봉쇄·명명·파생 규칙 3종, 그리고 confirmed 불변식의 테스트 태그 **존재**는 스크립트와 테스트의
   몫이다. 그것들을 "읽어 보고 판단"하는 순간 이 플러그인은 결정성을 잃고, 같은 코드에 대해
   세션마다 다른 답을 낸다.
2. **자동으로 고치지 않는다.** 수정은 제안까지다. 리뷰어가 코드를 고치기 시작하면 리뷰 결과가
   무엇에 대한 것인지 아무도 모르게 된다. 이 스킬이 쓰는 파일은 `review-log.jsonl`과 domain
   문서의 `## 열린 질문` 두 곳뿐이다.
3. **삼키지 않는다.** `[0건 경고]`·한계 푸터·생략 사유·`검사 불능`·변경 밖의 기존 위반·draft라서
   판정하지 못한 주제 — 전부 리포트에 남는다. "위반 없음"과 "아무것도 검사하지 않음"은 다른
   상태이고, 그 둘을 구별해 주는 것이 이 리포트의 값이다.

## 0. 위치와 초기화 게이트

```bash
git rev-parse --show-toplevel
```

그 경로의 `ARCHITECTURE.md`가 기준이다. 하위 디렉터리에서 시작했어도 여기로 올라와서 작업한다.
파일이 없으면 아래를 알리고 **중단**한다.

> superarchitect가 초기화되지 않았습니다. `/superarchitect:init`으로 아키텍처 거버넌스를 먼저 세우세요.

있으면 읽는다. 프로젝트 섹션(경로·프로파일·기본 패키지·아키텍처 테스트 위치)과 컨텍스트별
`분류`·`스타일`·`패턴`·`이행`, 모듈 표·패키지 규약 표가 이 스킬의 입력 전부다.

## 1. 대상 결정

### 1-a. 기본은 작업 트리 전체 변경

```bash
git diff --name-only HEAD                    # staged + 작업 트리
git ls-files --others --exclude-standard     # 아직 추적되지 않는 새 파일
```

인자가 오면 그것을 쓴다.

| 인자 | 대상 |
|---|---|
| 없음 | 위 두 명령의 합집합 |
| 경로(파일·디렉터리) | 그 경로 아래 파일 전체 — diff가 아니라 현재 내용이 대상이다 |
| 브랜치·커밋 범위(`main..HEAD`, `<sha>..<sha>`) | `git diff --name-only <범위>` |

- **대상이 비면 "변경 없음"으로 종료한다.** 검사도 위임도 하지 않고, `review-log.jsonl`에도
  아무것도 쓰지 않는다.
- 삭제된 파일은 읽을 수 없으므로 판정 대상에서 빼고 목록에만 남긴다.
- 선언된 프로젝트 경로 **밖**의 파일(미선언 프런트엔드 등)은 판정 대상이 아니다. 숨기지 말고
  "범위 밖"으로 목록에 남긴다.
- `ARCHITECTURE.md`나 스타일 선언 문서가 대상에 들어 있으면 그 사실을 리포트 맨 위에 적는다 —
  이번 검사 결과는 **바뀐 선언 기준**이고, 생성된 fitness 테스트는 아직 옛 선언 기준일 수 있다.
  선언과 코드의 대조 자체는 이 스킬이 아니라 sync의 일이다.

### 1-b. 컨텍스트 귀속

3단계의 지식 선별과 6단계의 domain 문서 선택이 여기에 달려 있다. 두 단계로 정한다.

1. **경로** — 컨텍스트 모듈 표의 `경로`는 **프로젝트 `경로` 기준 상대 경로**다. 앞에 프로젝트
   경로를 붙여 저장소 루트 기준으로 만든 뒤, 그것이 대상 파일 경로의 접두이면 그 컨텍스트다.
2. **패키지** — 모듈 표가 없는 컨텍스트(app-embedded)는 파일의 `package` 선언을 읽어 프로젝트의
   `### 패키지 규약` 표 패턴과 대조한다. `{컨텍스트}` 자리에 들어간 값이 답이다. `{컨텍스트}`가
   없는 패턴(컨텍스트 비분할 레이어)은 귀속을 주지 못한다 — 그 파일은 아래의 미귀속이다.

둘 다 걸리지 않으면 **미귀속**이다. 지어내지 않는다 — 4단계 위임 목록에는 넣되 "컨텍스트
미귀속"으로 표시하고 리포트에도 그대로 적는다.

## 2. 결정적 검사 먼저

의미론 위임보다 **반드시 먼저** 돈다. 순서가 뒤집히면 arch-reviewer가 이미 결정적으로 잡힌
위반을 다시 보고하고, 리포트에 같은 지적이 두 번 오른다.

**무엇을 돌리는가는 프로젝트마다 정한다.** 생성된 fitness 테스트를 돌릴 수 있으면 그것이
1순위이고, 없거나 돌리지 못했으면 2-b다. 사용자가 빠른 검사를 원하거나 테스트 실행이 오래 걸리면
테스트 대신 2-b만 돌려도 된다. **둘 다 돌려도 된다** — 그때는 5-b가 중복을 정리한다.

**2-c는 그 선택과 무관하게 돈다.** 2-a·2-b가 보는 것은 import 방향과 타입 배치이고 2-c가 보는
것은 불변식 태그의 존재다 — 겹치는 규칙이 없으므로 어느 하나가 다른 하나를 대신하지 않는다.

### 2-a. 생성된 fitness 테스트가 있으면 그것이 강제의 정본이다

프로젝트 섹션의 `아키텍처 테스트 위치` 아래에 생성 파일(`<Context>ArchitectureTest.kt`·
`DerivedRulesTest.kt`)이 있고 **첫 두 줄이 생성 헤더**이며 `./gradlew`가 실재하면 실행한다.

```bash
grep -n 'include' "<프로젝트 경로>"/settings.gradle*
./gradlew :<모듈 경로>:test
```

- 모듈 이름은 테스트 위치의 첫 세그먼트를 `include` 목록과 대조해 정한다(fitness와 같은 규약).
  `include`에 없으면 그 테스트는 빌드에 포함되지 않는다 — 실행되지 않는다는 사실을 리포트에 적는다.
- **실행하지 않았으면 실행했다고 쓰지 않는다.** gradle이 없거나, 빌드가 깨졌거나, 오래 걸려
  중단했으면 그 사실과 이유를 리포트에 적고 2-b로 간다.
- 생성 헤더가 없는(손으로 쓴) 테스트의 결과는 이 스킬의 판정 근거가 아니다. 참고로만 적는다.

#### 2-a-1. gradle 출력을 리포트 항목으로 옮기는 규약

생성 테스트의 함수 이름은 `<컨텍스트> - <ruleIdSafe>`이고 **원본 id는 `additionalMessage`에
남는다** — `ruleIdSafe`가 `.`을 공백으로 바꾸기 때문이다(fitness 4-c 3번, 매핑 §0.1). 그러니
id는 테스트 이름이 아니라 **실패 메시지**에서 읽는다. 이름의 공백을 점으로 되돌려 복원하지
않는다 — 원본 id에 원래 공백이 있었는지 알 수 없다.

**접두 두 개를 본다.** 매핑은 메시지를 두 형식으로 쓴다 — 스타일 유래 규칙은 `규칙 <id> — …`
(매핑 §1~§5), 파생 규칙 3종은 `파생 <id> — …`(매핑 §6.2). **`—` 뒤의 설명은 규칙마다 다르므로
(컨텍스트 이름일 때도, `@Entity는 허용 범위 안에서만 선언한다`처럼 서술일 때도 있다) 고정 문면을
기대하지 말고 접두와 그 뒤의 id만 추출한다.**

| 리포트 칸 | gradle 실패 출력에서 |
|---|---|
| `rule` | `additionalMessage`의 `규칙 <id>` 또는 `파생 <id>`에서 뽑은 id (`hex.domain-pure`, `derived.app-confinement`) |
| 경로:라인 | 실패 메시지가 지목한 파일·타입. 지목이 없으면 `(input)` 센티널 + 관측에 "테스트 이름만 있고 파일 지목 없음" |
| 분류 | 전부 `위반` |
| 심각도 | 5-c와 같다 — 대상 파일 안이면 `blocker`, 변경 밖이면 `warn` |
| 관측·근거 | 실패 메시지 원문 + 규칙이 유래한 스타일 문서 절(파생 규칙은 `architecture-template.md` §5.1 규칙 5) |

**아키텍처 규칙과 무관한 실패만 위반이 아니다.** 판정은 접두로 한다 — `규칙 `·`파생 ` **둘 중
어느 접두도 없는** 실패, 컴파일 오류, 그리고 생성 파일(`<Context>ArchitectureTest.kt`·
`DerivedRulesTest.kt`) **밖의** 테스트 클래스에서 난 실패가 "검토 불가 — 빌드 문제"다.
**`DerivedRulesTest.kt`의 실패는 여기에 해당하지 않는다** — 파생 규칙 3종의 위반이고, 5-c의
`rule` 칸이 `derived.*` id를 그대로 받는다. 빌드 문제로 분류한 것은 위반으로 집계하지도
`review-log.jsonl`에 넣지도 않는다. 그 상태에서는 어떤 규칙이 실제로 검사됐는지 알 수 없으므로
2-b를 함께 돌려 결정적 결과를 확보한다.

**2-a만 돌린 실행에는 check_imports의 승계분이 없다.** 승계 경고·`[0건 경고]`·한계 푸터는
check_imports의 출력이다. §8-2가 인용할 "검사한 규칙 N건 / 생략한 규칙 M건" 줄도 없으므로 gradle
요약(실행·성공·실패·건너뛴 테스트 수)으로 대체하고, **그 세 갈래가 이번 실행에 없다는 사실을
명시한다** — 자리를 비워 두면 "아무것도 검사하지 않은 규칙이 없었다"로 잘못 읽힌다.
**2-c의 승계분은 그와 별개로 남는다** — 2-c는 2-a/2-b 선택과 무관하게 돌므로 5-a 구역 3이 통째로
비는 일은 없다.

### 2-b. check_imports — 생성 테스트가 없거나 실행하지 못했을 때, 그리고 빠른 검사를 원할 때

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_imports.py" ARCHITECTURE.md
```

- exit **0** 클린 / **1** 위반 있음 / **2** 해석 불가·사용법 오류.
- **대상을 좁히는 옵션은 없다.** 인자는 `ARCHITECTURE.md` 경로 하나뿐이고 검사는 선언된 프로젝트
  전체를 돈다. `--paths` 같은 것을 붙이면 사용법 오류(exit 2)가 난다. diff로 좁히는 일은 실행이
  아니라 **5단계의 병합**에서 한다.
- **`--json`을 기본으로 쓰지 않는다.** JSON 페이로드에는 한계 고지 문면이 없다(`violations`·
  `zero_match`·`inherited`·`skipped`·`unreadable`·`checked`뿐). 위반이 많아 기계적 분류가
  필요하면 추가로 한 번 더 돌리되, **푸터는 텍스트 실행분에서 가져온다.**
- exit 2면 결정적 검사가 통째로 없는 상태다. stderr의 `경로:라인: 메시지` 줄을 **그대로** 보여주고
  멈춘다. 고치는 것은 이 스킬의 일이 아니다. 사용자가 그래도 진행하기를 원하면 의미론 리뷰만
  돌리되 리포트 맨 위에 "결정적 검사 없음 — 구조 규칙은 이번에 검사되지 않았다"를 박는다.

출력 네 갈래를 **전부** 받아 둔다. 5단계에서 갈 곳이 서로 다르다.

| 갈래 | 모양 | 5단계에서의 처리 |
|---|---|---|
| 승계 경고 | `ARCHITECTURE.md:<줄>: …` (공허 레이어) | 그대로 승계 |
| 위반 | `경로:라인: [rule id] 메시지` | diff 소속 / 변경 밖으로 나눈다 |
| 0건 경고 | `[0건 경고] <rule id>: …` | 그대로 승계 |
| 푸터 | 검사·생략 건수, `생략: …` 사유, 읽지 못한 소스, `한계: …` | 그대로 승계 |

### 2-c. check_invariants — confirmed 불변식에 대응 테스트 태그가 있는가

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_invariants.py" ARCHITECTURE.md
```

- exit **0** 클린 / **1** 위반 있음 / **2** 해석 불가·사용법 오류 — check_imports와 같은 의미다.
  다만 **1이 두 상태를 겸한다**: 위반 발견과 `검사 불능`(테스트 소스 0건)이다. 둘을 가르는 것은
  exit가 아니라 출력이므로, exit 1을 보고 "위반 N건"이라고 적기 전에 아래 표의 `검사 불능` 갈래가
  비었는지 확인한다.
- **대상을 좁히는 옵션은 `--context <이름>` 하나다.** 그것도 수집 코퍼스만 좁히고 배치 오류·미선언
  문서 경고는 좁히지 않는다. diff로 좁히는 일은 실행이 아니라 **5단계의 병합**에서 한다.
- `--json`도 있고, 이쪽은 `limitation`까지 담는다(check_imports의 JSON에는 없다). 그래도 푸터는
  텍스트 실행분에서 가져온다 — 두 검사의 승계 절차를 갈라 두지 않는다.
- exit 2면 문서 코퍼스를 신뢰할 수 없는 상태다(ID 형식·중복 ID·중복 배치). stderr의
  `경로:라인: 메시지` 줄을 **그대로** 보여주고 멈춘다. 고치는 것은 이 스킬의 일이 아니다.
- **domain 문서가 하나도 없어도 돌린다.** 고아 태그(문서에 없는 ID를 가리키는 태그)는 그 상태에서도
  나오고, 그것이야말로 드리프트다. 불변식이 0건이면 그 사실이 고지로 나온다.

출력 갈래를 **전부** 받아 둔다. 2-b와 마찬가지로 5단계에서 갈 곳이 서로 다르다.

| 갈래 | 모양 | 5단계에서의 처리 |
|---|---|---|
| 위반 | `<문서>:<줄>: [INV-...] …` (confirmed인데 태그 없음) | **경로가 코드가 아니라 domain 문서다.** 대상 파일 기준으로 가르지 말고 **1-b가 귀속한 컨텍스트** 기준으로 가른다 |
| 경고 | `<경로>:<줄>: 경고: …` (고아 태그·확정 전 구현·미선언 문서) | 그대로 승계 |
| 고지 | `고지: …: '## 불변식' 표가 없습니다 — 불변식 0건` 등 | 그대로 승계 |
| 검사 불능 | **두 줄이다** — `검사 불능: 테스트 소스가 없습니다 — …`와 `수집한 불변식 N건(confirmed X · proposed Y) — 대조하지 못했습니다` | 둘 다 승계. **이 줄이 있으면 클린이 아니다** |
| 푸터 | 집계 줄(`대조한 불변식 N건 …` — `검사 불능`이면 위의 `수집한 …` 줄이 그 자리를 대신한다), 읽지 못한 테스트 소스, `한계: …` | 그대로 승계 |

**이 검사가 보는 것은 존재뿐이다.** 리터럴 `@Tag("INV-...")`만 읽으므로 태그만 달린 빈 테스트나
불변식 서술과 다른 검증은 잡지 못한다(한계 줄이 그렇게 고지한다). 그것은 arch-reviewer C3의
의미론 범주다. 반대로 **대응 태그가 아예 없는 것은 이제 이 검사가 판정하므로, 같은 지적을
에이전트가 다시 올렸다면 5-b에서 중복으로 정리한다.**

### 2-d. 용어 검증은 이 스킬의 일이 아니다

사용 가능한 스킬·커맨드 목록에 `/glossary:` 네임스페이스가 있으면 superglossery가 설치된 것이다.

- 설치돼 있으면 용어 검증을 **중복하지 않는다.** 그쪽 검증 커맨드를 이 스킬이 대신 실행하지
  말고, 목록에서 검증에 해당하는 커맨드를 찾아 리포트에 안내한다.
- 설치돼 있지 않으면 "용어 일관성은 이번 리뷰가 판정하지 않았다"를 리포트에 남긴다. 용어집은
  이 플러그인이 만들지 않는다.

## 3. 지식 선별 — arch-reviewer의 어휘를 여기서 정한다

지금 `${CLAUDE_PLUGIN_ROOT}/references/INDEX.md`를 읽는다. `knowledge/`를 통째로 또는 디렉터리
단위로 읽는 것은 금지다. INDEX의 `key`·`topic`으로 경로가 정해진다 —
`${CLAUDE_PLUGIN_ROOT}/references/knowledge/<topic>/<key>.md`.

**후보를 모은다.**

| | 후보 |
|---|---|
| (a) | 대상 컨텍스트가 선언한 `스타일`·`패턴` 문서. 커스텀 스타일이면 대상 프로젝트의 `docs/architecture/styles/<이름>.md` |
| (b) | INDEX의 `read_when`에 `review`가 있는 문서 |
| (c) | 대상 프로젝트의 `docs/architecture/conventions/`·`docs/architecture/styles/` 문서 |
| (d) | 선언이 없어도 **diff에 패턴 징후가 보이는** patterns 문서 |

(d)의 징후 — 선언(`- 패턴:`)은 코드보다 늦게 따라오는 일이 흔하고, `cqrs.md`는 R1·R2를 "선언
여부와 무관하게 적용한다"고 명시한다(`## 규칙` 머리).

| 문서 | diff에서 보이는 징후 |
|---|---|
| `cqrs` | `*Command`·`*Query`·`*CommandHandler` 타입, `.command.`·`.query.` 패키지 세그먼트, 커맨드 메서드가 조회 결과를 반환 |
| `outbox` | outbox 테이블·엔티티·리포지토리, 트랜잭션 안의 이벤트 저장, 릴레이·퍼블리셔 |
| `event-sourcing` | 이벤트 스토어 append, 리플레이, 스냅샷, 이벤트 테이블 마이그레이션 |

**가지치기 — 후보에서 뺀다.**

1. **draft 문서.** INDEX의 `draft` 칸으로 판정한다. draft는 판정 근거가 아니므로 목록에 넣지
   않는다. 뺀 문서와 사유를 리포트에 남긴다 — 그 주제를 이번 리뷰가 판정하지 않았다는 뜻이다.
2. **대상 컨텍스트가 채택하지 않은 스타일 문서.** `read_when`에 review가 있다는 이유로
   `hexagonal.md`를 `layered-simple` 컨텍스트에 넘기면 채택하지도 않은 규칙으로 판정하게 된다.
3. **diff에 해당 주제의 코드가 없는 문서.** 컨텍스트 간 참조·통합 코드가 diff에 없으면
   `context-mapping`은 넣지 않는다. 같은 기준을 (b)의 나머지에도 적용한다.

**(d)로 들어온 문서의 지위.** 선언 없이 들어온 patterns 문서는 기본적으로 **근거가 아니라
안건**이다 — 그 규칙에 걸리는 관측은 "선언되지 않은 패턴이 코드에 들어와 있다"는 사실과 함께
`discussion`으로 낸다. 예외는 문서가 선언 무관 적용을 스스로 명시한 조항뿐이다(`cqrs` R1·R2).

**로컬 우선.** (c)와 (a)·(b)가 같은 주제를 다루면 대상 프로젝트 문서가 이긴다. 위임 프롬프트에
그 사실을 한 줄로 적어 넘긴다.

최종 목록은 리포트에 그대로 싣는다. 무엇을 근거로 판정했는지는 판정 결과의 일부다.

## 4. arch-reviewer 위임

`agents/arch-reviewer.md`가 인터페이스의 정본이다. Agent 도구로 `arch-reviewer` 서브에이전트를
불러 아래 넷을 전달한다. **없는 것을 채워 보내지 않는다** — 없으면 없다고 적어 보낸다.

| 입력 | 형태 |
|---|---|
| `docs/architecture/summary.md` | 경로가 아니라 **파일 내용**을 넣는다 |
| 검토 대상 파일·diff 목록 | 저장소 루트 기준 상대 경로 목록. 컨텍스트 귀속과 "미귀속" 표시를 함께 |
| 선별 지식 문서 | **경로 목록**. 절대 경로여야 한다 |
| domain 문서 | `docs/architecture/domain/<context>.md`(단일 컨텍스트면 `docs/architecture/DOMAIN.md`)가 있으면 경로 |

선택 입력 하나 — **2단계의 결정적 검사 결과**(위반의 `rule id`와 `path` 목록, 그리고 2-c가 낸
불변식 위반의 `INV-` id 목록). 주면 에이전트가 중복 제거에 쓴다. 2-c를 돌리지 못했거나
`검사 불능`으로 끝났으면 **그 사실을 적어 보낸다** — 목록이 비어 온 것과 검사가 없었던 것을
에이전트가 구별해야 C3의 `missing` 판정이 정직해진다. 실행하지 못했으면 "결정적 검사 미실행"이라고
적어 보낸다.

지켜야 할 것:

- **지식 문서 경로는 전개된 절대 경로로 적는다.** `${CLAUDE_PLUGIN_ROOT}`는 이 스킬의 셸에서만
  풀리는 변수라 문자열 그대로 넘기면 에이전트가 파일을 열지 못한다. `echo "${CLAUDE_PLUGIN_ROOT}"`로
  값을 확인해 붙인다.
- **대상 컨텍스트가 둘 이상이면 컨텍스트마다 따로 위임한다.** 스타일·패턴·domain 문서가
  컨텍스트마다 다르므로 한 번에 섞으면 엉뚱한 스타일로 판정한다. 미귀속 파일은 마지막 위임에
  묶고 미귀속임을 명시한다.
- 에이전트는 읽기 전용(Read·Grep·Glob)이다. 파일을 고치라고 지시하지 않는다.

**출력 수용.** 마지막 응답이 JSON 배열 하나다. 코드펜스가 붙어 있으면 벗겨서 파싱한다. 파싱할 수
없으면 **지어내서 채우지 않는다** — 원문을 리포트에 그대로 붙이고 "구조화 실패"로 표시한다.
`[]`은 정상적인 결과다.

배열 항목의 `related_rule`은 세 형태 중 하나이거나 비어 있고, `path`는 `(input)` 센티널일 수
있다. 셋 다 그대로 5·7단계로 흘려보낸다 — 자세한 것은 5단계의 `rule` 칸 표에 있다.

## 5. 리포트

### 5-a. 순서 — diff 안이 먼저, 밖은 뒤, 승계는 언제나

check_imports는 선언된 프로젝트 전체를 검사하므로 이번 변경과 무관한 위반도 함께 나온다.
**숨기지 않는다.** 세 구역으로 나눠 싣는다.

1. **이번 변경의 항목** — 대상에 속한 결정적 위반과 의미론 항목. 결정적 → 의미론 순,
   같은 갈래 안에서는 심각도 내림차순.
2. **변경 밖 기존 위반** — 대상 밖의 항목(결정적 위반은 파일 축, 2-c·의미론 항목은 아래
   이원 축이다). 별도 절로 구분해 표기하고, 이번 변경이 만든 것이 아니라는 사실을 한 줄로 밝힌다.
3. **승계 — 두 검사 공용 구역이다.** 2-b에서는 승계 경고, `[0건 경고]` 줄들, 푸터(검사·생략
   건수, 생략 사유, 읽지 못한 소스, 한계 고지). 2-c에서는 경고 3종(고아 태그·확정 전 구현·
   미선언 문서), 고지(`불변식 0건` 등), `검사 불능` 2줄, 푸터(집계 줄, 읽지 못한 테스트 소스,
   한계 고지). **diff와 무관하므로 필터링 대상이 아니다.** 문면을 고치지 말고 그대로 옮기되
   **어느 검사에서 온 승계인지 밝힌다.** 돌리지 않은 검사가 있으면 그 자리를 비우지 말고
   없다고 적는다(2-a-1의 대체 규약).

**2-c 위반은 안/밖의 축이 다르다.** 경로가 domain 문서라 "대상 파일 안"이 성립하지 않는다. **1-b가
귀속한 컨텍스트가 검토 대상에 들어 있으면 구역 1**, 아니면 구역 2다. 파일 축으로 가르면 domain
문서는 diff에 거의 들어오지 않아 모든 불변식 위반이 "변경 밖"으로 밀려난다. **의미론 항목도 같은
이원 축을 쓴다** — 1-b 귀속이 서면 컨텍스트 축(domain 문서는 그 문서의 컨텍스트다), 서지 않으면
파일 축이다. 두 축 다 서지 않으면(`(input)` 등) **구역 2에 두고 그 사유를 적는다.**

### 5-b. 중복 제거 — 같은 **사실**만 합친다

같은 `path`에서 같은 사실이 두 경로로 올라오면 **결정적 항목만 남긴다.** 판단 기준은 "주제가
primitive에 속하는가"가 **아니라** "결정적 검사가 그것을 실제로 볼 수 있는가"다. 둘을 혼동하면
검사가 원리적으로 못 보는 지적까지 지워지고, 그건 불변 3의 위반이다.

| 의미론 항목이 | 처리 |
|---|---|
| 결정적 검사가 같은 파일에서 낸 위반과 **같은 사실** | 뺀다. 건수는 집계에 남긴다 |
| primitive·파생 규칙이나 **불변식 태그 존재**가 판정하는 것과 같은 사실인데 **검사에는 안 나왔다** | **그 규칙이 이번 실행에서 실제로 검사됐고**(`[0건 경고]`에도 `생략:` 목록에도 없고) 통과했을 때만 뺀다 — 그때만 "안 나옴 = 통과"다. 그 밖에는 남긴다 |
| 그 검사가 **원리적으로 못 보는 것** — 판별 단서는 **두 검사의 한계 푸터**다(§8-6과 같은 목록) | **남긴다** |

2행의 전제("안 나옴 = 통과")가 깨지는 경우가 넷이다. 그 규칙에 `[0건 경고]`가 붙은 경우(패턴은
있는데 매칭 파일이 0건이라 아무것도 검사하지 않았다), 푸터의 `생략:` 목록에 오른 경우,
2-b가 exit 2로 끝나 의미론만 진행한 경우, 그리고 2-c가 `검사 불능`으로 끝나 태그를 하나도
대조하지 못한 경우. **전부 "검사가 통과시킨 것"이 아니라 "검사한 적이 없는 것"이므로 항목을
남긴다.** 2단계의 승계를 여기서 다시 보는 이유가 이것이다.

원리적으로 못 보는 것의 판별 단서는 둘이다 — **두 검사의 한계 푸터**가 열거하는 것(check_imports는
같은 패키지 안의 참조와 import 없는 FQN 사용, check_invariants는 상수로 간접 참조한 태그와
완전 수식 애너테이션, 그리고 태그가 달렸다는 것이 그 테스트가 불변식을 검증한다는 뜻은 아니라는 것),
그리고 `rationale`이 "기계 검사가 이것을 보지 못한다"를 근거로 들고 있는 것. 예: `naming-suffix`는
접미사만 보므로 `ClaimJpaPort`처럼 **이름 속에 새어든 기술 어휘**는 검사 대상 밖이다 — 주제가
명명이라는 이유로 지우면 안 된다.

에이전트는 §3에서 이미 "의심되면 보고하지 않는다"로 걸러 보낸다. 여기까지 올라온 항목을 주제만
보고 한 번 더 지우면 같은 필터를 두 번 거는 것이다. **애매하면 남긴다** — 중복 한 줄은 읽는
사람이 지울 수 있지만, 지워진 지적은 아무도 되살리지 못한다.

2-a와 2-b를 **둘 다** 돌렸다면 같은 규칙·같은 파일의 위반은 한 항목으로 합치고 테스트 쪽을
정본으로 삼는다.

### 5-c. 항목의 칸

`rule` · `분류` · `심각도` · `경로:라인` · `관측` · `근거` · `수정 제안`.

**`rule` 칸이 수용하는 다섯 형태와 센티널** — 어느 것도 다른 것으로 바꾸지 않는다.

| 형태 | 예 | 출처 |
|---|---|---|
| 문서 rule id | `hex.domain-pure` | 결정적 검사, arch-reviewer |
| 파생 규칙 id | `derived.context-isolation` | 결정적 검사 |
| 불변식 ID | `INV-CLAIM-001` | 결정적 검사(2-c) |
| 규칙 절 식별자 | `cqrs R1` | arch-reviewer |
| `semantic.*` 범주 태그 | `semantic.domain-leak` | arch-reviewer(문서 근거가 없을 때만) |

`path`가 `(input)`이면 파일을 지목할 수 없는 항목이라는 뜻이다. **그럴듯한 경로로 바꾸지 않는다.**

**분류** — `violation`→위반 · `missing`→누락 · `drift`→드리프트 · `discussion`→추가 논의.
결정적 검사의 위반은 전부 `위반`이다.

**심각도** — 의미론 항목은 arch-reviewer가 준 값을 **그대로** 쓴다. 구역과 무관하게 올리지도 낮추지도
않는다. 결정적 위반은 선언을 어긴 것이 확정된 상태이므로 대상 파일 안이면 `blocker`, 변경 밖 기존
위반이면 `warn`으로 낮춘다(이번 변경이 만든 것이 아니다). **2-c의 불변식 위반은 5-a의 컨텍스트
축을 그대로 쓴다** — 구역 1이면 `blocker`, 구역 2면 `warn`이다. 파일 축을 적용하지 않는다.

> **구현 상태 — `이행` 선언이 있어도 baseline 동결은 Phase 5다.** 지금은 기존 부채와 신규 위반을
> 위의 두 축(코드 위반은 대상 파일 안인가, 불변식 위반은 귀속 컨텍스트가 대상인가)으로만 가른다.
> 동결된 부채 목록이 없으므로 그보다 정확히는 구분하지 못한다.

**관측·근거 — 의미론 항목은 `rationale`이 여기에 착지한다.** arch-reviewer의 `rationale`은 규약상
**관측 한 문장 + 근거 한 문장**이고 "둘을 섞지 말고 둘 다 적는다"가 그 필드의 계약이다(에이전트
§7). 그 둘을 갈라 관측은 관측 칸에, 근거는 근거 칸에 싣는다. **요약해 버리거나 흘리지 않는다** —
rule id와 심각도만 남기면 왜 그것이 문제인지가 통째로 사라져 리포트가 판정의 근거를 잃는다.
결정적 항목의 관측은 검사 출력 메시지 원문이고, 근거는 규칙이 유래한 스타일 문서의 절
(`hexagonal.md ## 규칙 R5`)이다. arch-reviewer가 `related_adr`·`related_invariant`를 주면 근거에
함께 싣는다. **읽지 않은 문서를 근거로 적지 않는다.**

**수정 제안** — 문장으로만. 에이전트는 수정 제안을 rationale 안에 문장으로 쓰므로(에이전트
"하지 말 것" 1항) 그 문장을 옮긴다. rationale에 없으면 지어내지 말고 비운다. 이 스킬은 코드를
고치지 않는다.

## 6. "추가 논의"는 domain 문서로 간다

`docs/architecture/domain/<context>.md`(단일 컨텍스트면 `docs/architecture/DOMAIN.md`)가 있으면
그 문서의 `## 열린 질문` 섹션 **끝에 append**한다.

- **이 문서는 파생물이 아니라 SSOT다.** 생성물 헤더를 붙이지 않고, 통째로 재생성하지 않으며,
  다른 섹션을 건드리지 않는다. append만 한다.
- 형식은 **한 줄 체크박스 불릿**이고 정본은 `governance/domain-doc-template.md` §5다. arch-reviewer가
  질문 형태로 써 주므로 그 문장을 그대로 쓴다.
  ```
  - [ ] [<YYYY-MM-DD> review] 승인 이후의 금액 변경을 누가 막는가? (관측: <경로:라인>)
  ```
  **앞의 `- [ ]`를 빠뜨리지 않는다.** model이 미해결 항목을 고르는 기준이 그 빈 체크박스이고
  (`skills/model/SKILL.md` 2-c), 체크박스 없는 줄은 다음 세션의 안건으로 올라오지 않는다.
- `## 열린 질문` 섹션이 없으면 문서 끝에 그 헤딩을 만들고 그 아래에 쓴다.
- **같은 질문이 이미 있으면 넣지 않는다.** 리뷰를 돌릴 때마다 같은 줄이 쌓이면 그 섹션이 쓸모를
  잃는다.
- 추가한 줄 목록을 리포트에 그대로 보여준다.

문서가 없으면 만들지 말고 리포트에 남긴다 — 그 문서를 만드는 것은 `/superarchitect:model`이므로
그 스킬을 안내한다.

## 7. `review-log.jsonl`에 append

경로는 git 루트의 `docs/architecture/review-log.jsonl`이다. **append only** — 기존 줄을 고치거나
지우거나 정렬하지 않는다. 파일이 없으면 새로 만들고, 마지막 줄에 개행이 없으면 개행부터 넣는다.

한 항목당 **한 줄 JSON**, 키는 다섯이다.

```json
{"date": "2026-08-11", "rule": "hex.domain-pure", "path": "backend/src/main/kotlin/com/acme/claim/domain/Claim.kt", "severity": "blocker", "note": "도메인 타입이 jakarta.persistence.Entity를 import한다"}
```

| 키 | 값 |
|---|---|
| `date` | `date +%F`의 출력 |
| `rule` | 5-c의 다섯 형태 중 하나 |
| `path` | 항목의 경로. `(input)` 센티널도 그대로 |
| `severity` | `blocker` · `warn` · `info` |
| `note` | 항목의 한 줄 요약 — 의미론 항목은 **`rationale`의 관측 문장을 줄인 것**, 결정적 항목은 검사 메시지를 줄인 것. **줄바꿈·탭 금지**(한 줄이 한 레코드다) |

- `related_rule`이 비어서 온 의미론 항목은 `rule`에 `semantic.unspecified`를 넣고, **범주 태그
  없이 왔다는 사실을 리포트에 적는다.** 범주를 대신 지어내지 않는다.
- **변경 밖 기존 항목은 기록하지 않는다.** 매 리뷰마다 다시 관측되는 상수라서, 기록하면 evolve의
  반복 위반 신호(`evolution-signals.md` 신호 2·5)가 실제 반복이 아니라 리뷰 횟수를 세게 된다.
  신호 2의 "서로 다른 리뷰 2건"이라는 분모를 지키는 규약이다. 리포트에는 남고 로그에는 안 간다.
- **`check_invariants` 위반의 안/밖은 파일 경로가 아니라 귀속 컨텍스트로 가른다**(5-a). 구역 1의
  것은 `rule`에 `INV-` id를 담아 **기록하고**, 구역 2의 것은 구분 표기만 하고 기록하지 않는다.
  파일 축으로 가르면 경로가 domain 문서라 전부 "변경 밖"이 되어 한 건도 기록되지 않는다.
- 항목이 0건이면 아무것도 쓰지 않는다. 빈 리뷰 기록을 남기지 않는다.
- 쓴 뒤 전 줄이 파싱되는지 확인한다.
  ```bash
  python3 -c "import json,sys;[json.loads(l) for l in open('docs/architecture/review-log.jsonl') if l.strip()]" && echo OK
  ```

## 8. 마무리 보고

1. **대상** — 파일 수, 컨텍스트별 분포, 범위 밖·미귀속·삭제 파일.
2. **실행한 결정적 검사와 실행하지 못한 것** — 명령과 결과. 2-b를 돌렸으면 푸터의 "검사한 규칙
   N건 / 생략한 규칙 M건" 줄을 그대로 인용한다. 2-a만 돌렸으면 2-a-1대로 gradle 요약으로 대체하고
   **check_imports의 승계분이 없다는 사실**을 함께 적는다 — **2-c의 승계분은 그와 별개로 실린다.**
   2-c는 집계 줄(`대조한 불변식 N건 …`)을 그대로 인용하되 `검사 불능`으로 끝났으면 그 **두 줄**
   (`검사 불능: …`과 `수집한 불변식 N건 … — 대조하지 못했습니다`)을 대신 싣는다. 실행하지
   못했으면 이유를 적는다.
3. **선별한 지식 문서 목록**과 뺀 문서·사유(draft, 미채택 스타일, 주제 무관).
4. **항목 집계** — 분류 × 심각도. 중복 제거로 뺀 건수도.
5. **쓴 것** — `review-log.jsonl` 추가 줄 수, domain 문서에 append한 열린 질문 수.
6. **이번 리뷰가 판정하지 않은 것** — 용어 일관성(2-d), 두 검사의 한계 푸터가 말하는 것(같은
   패키지 안의 참조·FQN 사용, 상수로 간접 참조한 불변식 태그·완전 수식 애너테이션, 태그와
   실제 검증의 일치), draft라서 뺀 주제. **이 절을 비우지 않는다.**
7. **커밋은 사용자가 한다.** 실제로 쓴 파일만 넣어 명령을 제안한다.
   ```bash
   git add docs/architecture/review-log.jsonl        # + append한 domain 문서가 있으면 함께
   git commit -m "chore: 아키텍처 리뷰 결과 기록"
   ```

## 하지 말 것

- **코드를 고치는 것.** 수정 제안은 문장으로만 낸다. 이 스킬이 쓰는 파일은 `review-log.jsonl`과
  domain 문서의 `## 열린 질문` 둘뿐이다.
- **`ARCHITECTURE.md`·스타일 선언·파생물을 고치는 것.** 결정적 검사가 exit 2로 멈추면 어디를
  고쳐야 하는지 알리고 멈춘다. 통과시키려고 선언을 고치지 않는다.
- **결정적으로 판정되는 것을 읽어 보고 판단하는 것.** primitive 5종과 파생 3종, 그리고 confirmed
  불변식의 태그 존재는 스크립트·테스트의 몫이다. 검사를 돌리지 못했으면 "검사하지 못했다"고
  적는다 — 대신 판단하지 않는다.
- **`[0건 경고]`·한계 푸터·생략 사유를 리포트에서 빼는 것.** diff와 무관하니 필터 대상이 아니다.
- **변경 밖 기존 위반을 숨기는 것.** 구분해 표기하되 지우지 않는다.
- **draft 문서를 판정 근거로 인용하는 것.** INDEX의 `draft` 칸이 판정 기준이다.
- **`review-log.jsonl`의 기존 줄을 고치거나 파일을 다시 쓰는 것.** append only다.
- **domain 문서를 통째로 재생성하거나 생성물 헤더를 붙이는 것.** SSOT 문서다.
- **arch-reviewer가 준 severity를 올리는 것**, 비어 있는 `related_rule`을 그럴듯한 범주로 채우는 것,
  `(input)` 센티널을 지어낸 경로로 바꾸는 것.
- **`rationale`을 rule id와 심각도로 압축해 버리는 것.** 관측과 근거는 각각 칸이 있다(5-c).
- **결정적 검사가 원리적으로 못 보는 지적을 "주제가 primitive니까" 지우는 것.** 5-b의 기준은
  주제가 아니라 그 검사가 그것을 볼 수 있는가다.
- **아키텍처 규칙과 무관한 gradle 실패(컴파일 오류 등)를 위반으로 집계하는 것.** "검토 불가 —
  빌드 문제"다(2-a-1).
- **없는 것을 실행한 척하는 것** — `check_imports.py`의 대상 한정 옵션, superglossery의 검증 커맨드.
- **`검사 불능`으로 끝난 2-c를 "불변식 위반 없음"으로 적는 것.** 대조하지 못한 것과 통과한 것은
  다른 상태다.
- **`knowledge/`를 통째로 또는 디렉터리 단위로 읽는 것.** 언제나 INDEX 경유 선별 로드다.
