# 선언과 현실의 드리프트 대조

이 스킬은 두 개의 사실을 나란히 놓는다 — `ARCHITECTURE.md`가 말하는 구조와 디스크에 실제로 있는
구조. 어긋난 자리를 찾는 것이 이 스킬의 일이고, **어느 쪽이 맞는지 정하는 것은 이 스킬의 일이
아니다.** 없는 모듈은 "아직 안 만든 것"일 수도 "선언이 낡은 것"일 수도 있고, 그 둘은 처방이 정반대다.
그래서 불변이 셋이다.

1. **드리프트의 방향을 확인 없이 확정하지 않는다.** 각 항목에 [scaffold로 생성 / 코드 수정 /
   문서 수정 / 무시]를 제시하고 사용자가 고른다. 이것은 판단을 아끼라는 뜻이 **아니다** — 관측을
   근거로 어느 쪽이 맞아 보이는지 **한 줄로 권고하는 것이 이 스킬의 일**이고, 근거 없는 중립은
   친절이 아니라 판단 유기다. 금지는 확인 없는 **확정** 하나뿐이다(정본: `skills/init/SKILL.md`
   불변 1). "알아서 해주세요"는 확정 권한의 위임이 아니라 진행 속도의 요청이므로, 항목별 순회를
   **빠르게** 돌되 값과 근거를 보여주고 답을 받는다.
2. **대조하지 못한 것을 삼키지 않는다.** 파일이 없어서, 해석이 실패해서, 형식이 기계 대조를
   허락하지 않아서 보지 못한 축은 **생략이 아니라 고지**다. "드리프트 없음"과 "대조하지 않음"은
   다른 상태이고, 그 둘을 구별해 주는 것이 이 리포트의 값이다.
3. **코드를 고치지 않는다.** 이 스킬이 쓰는 파일은 확정받은 `ARCHITECTURE.md` 편집과 파생물
   (`docs/architecture/summary.md`, 생성 구역)뿐이다. 골격 생성은 scaffold, 코드 이동은 migrate,
   결정 기록은 adr이 한다. **SSOT를 고쳤으면** 마지막 편집 뒤 받은 `OK:` 출력이 완료 조건이다.

이 스킬은 `references/knowledge/`를 읽지 않는다 — 대조의 재료는 선언, 해석기 출력, 디스크 관측
셋뿐이다. 형식의 정본은 `${CLAUDE_PLUGIN_ROOT}/references/governance/architecture-template.md`이고
**아래의 `정본 §N`은 전부 이 문서를 가리킨다.** 그 내용을 여기 복제하지 않는다 — 각 단계가
지시하는 시점에 그 절을 읽는다.

> superarchitect가 초기화되지 않았습니다. `/superarchitect:init`으로 아키텍처 거버넌스를 먼저 세우세요.

## 1. 선언을 읽는다 — 두 실행과 문서 직접 읽기

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md --json
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md
```

- exit **0**이면 stdout 전체가 JSON이고 키는 넷이다: `projects`(name·path·profile·base_package·
  test_location), `effective`(project·context·rule_id·primitive·params·resolved·layer_patterns),
  `derived`(project·kind·subject·detail), `warnings`.
- exit **1은 해석 오류**다. **중단하지 않는다** — 해석 실패 자체가 이번 대조의 첫 결과이므로
  3-f의 드리프트로 올린다. 다만 이번 실행 전체를 **신뢰 불가**로 표시하고, 정규화 결과에 기대는
  축(3-a의 레이어, 3-b의 패키지, 3-c 전체)은 **대조 불능**으로 고지한다. 지어내서 메우지 않는다.
- exit **2는 사용법 오류**다. 인자를 고쳐 다시 돌린다.
- 텍스트 실행은 두 가지를 준다 — `warnings`(공허 레이어 경고)의 사람이 읽는 문면과 집계 줄
  `OK: 컨텍스트 N, 유효 규칙 M (스타일 A, 파생 B, 예외 제외 C)`. 예외 제외 건수는 JSON에 없다.

**어느 값을 어디서 얻는가.** 표를 손으로 읽는 것은 JSON이 주지 않는 것에 한한다.

| 입력 | 출처 |
|---|---|
| 프로젝트 경로·프로파일·기본 패키지·아키텍처 테스트 위치 | JSON `projects[]` |
| 컨텍스트별 레이어 → 패키지 패턴 | `effective[].layer_patterns` (정규화 완료) |
| 앱 이름·모듈 경로 | `derived[]` 중 `kind: app-confinement`의 `subject`·`detail.module_path` |
| 공용 모듈 이름·경로·역할 | `derived[]` 중 `kind: shared-module-direction`의 `subject`·`detail.path`·`detail.role` |
| **컨텍스트 모듈 표(모듈·경로·레이어)** | **JSON에 없다** — `ARCHITECTURE.md`에서 직접 읽는다 |
| 관계 표·`규칙 예외`·`이행`·`스타일`·생성 구역 | 같음 — 문서에서 직접 |

문서에서 직접 읽는 값에는 정본 §5.2의 읽기 규약이 그대로 걸린다: **값 끝의 괄호 주석은 값이 아니고**
(`규칙 예외`만 예외 — 거기서 괄호는 ADR 참조다), **표 데이터 행의 마지막 `|` 뒤 글자는 버려진다.**
파서가 버리는 것을 값으로 읽으면 있지도 않은 드리프트가 나온다.

## 2. 스캔 범위와 관측

### 2-a. 범위는 선언된 프로젝트 경로 안뿐이다

`projects[].path` 아래만 본다. 미선언 프로젝트(frontend 등)는 **오검출 대상이 아니다** — 거버넌스
대상이 아닌 것을 "미선언 모듈"로 올리면 리포트가 매 실행 같은 잡음으로 채워진다. 숨기지도 않는다:
루트에서 관측된 다른 빌드 루트는 **"범위 밖"** 목록에 이름만 남긴다. 거버넌스에 올릴지는 init·
scaffold의 인터뷰가 정한다.

프로젝트 경로가 `.`이면 저장소 루트가 프로젝트 루트다. **모듈 표·애플리케이션 표·공용 모듈 표의
경로와 `아키텍처 테스트 위치`는 전부 프로젝트 `경로` 기준 상대 경로**이므로(정본 §4), 저장소 루트
기준으로 만들 때 앞에 프로젝트 경로를 붙인다.

### 2-b. 관측 — 빌드 모듈

프로젝트마다 한 번 만든다.

```bash
grep -nE '^[[:space:]]*include' "<프로젝트 경로>"/settings.gradle*
grep -n '<module>' "<프로젝트 경로>"/pom.xml 2>/dev/null
find "<프로젝트 경로>" \( -name build -o -name .gradle -o -name node_modules \) -prune -o \
  \( -name 'build.gradle*' -o -name 'pom.xml' \) -print | sort
```

- Gradle의 `include(":a:b")`는 디렉터리 `a/b`를 뜻한다. `project(":x").projectDir = …` 줄이 있으면
  **그 줄이 정본**이므로 함께 읽는다.
- `include`에 없는 빌드 스크립트, 반대로 include는 있는데 디렉터리가 없는 항목은 각각 별개의
  관측이다. 둘 다 목록에 남긴다 — 전자는 빌드에 들어가지 않는 모듈이고, 후자는 3-a다.

### 2-c. 관측 — 프로덕션 패키지 인벤토리

```bash
find "<프로젝트 경로>" \( -path '*/build/*' -o -path '*/src/test/*' -o -path '*/.gradle/*' \) -prune \
  -o \( -name '*.kt' -o -name '*.java' \) -exec grep -hE '^[[:space:]]*package[[:space:]]' {} + \
  | sed -E 's/^[[:space:]]*package[[:space:]]+//; s/[;[:space:]]*$//' | sort -u
```

**패턴 매칭 규약** — 패턴은 언제나 `..`로 끝나고 "그 패키지와 그 하위 전부"를 뜻한다
(`${CLAUDE_PLUGIN_ROOT}/references/governance/rule-vocabulary.md` §2).
패턴 `x..`에 패키지 `p`가 드는 조건은 **`p == x` 또는 `p`가 `x.`로 시작**하는 것 하나다. 부분
문자열로 맞추지 않는다 — `com.acme.claim`이 `com.acme.claiming`을 삼킨다.

**이 관측의 한계를 리포트에 남긴다**: 테스트 소스와 `.kt`·`.java`가 아닌 소스는 보지 않는다.
그 자리에 있는 드리프트는 이번 실행이 판정하지 않았다.

## 3. 대조 축 여섯

각 축의 결과는 **항목**이고, 항목마다 축·경로(또는 문서:라인)·관측·권고 한 줄을 갖는다. 0건인
축도 "0건"으로 적는다.

### 3-a. 선언됐는데 없다

| 갈래 | 대조 |
|---|---|
| 프로젝트 | `projects[].path` 디렉터리와 빌드 파일(`settings.gradle*`·`pom.xml`)이 있는가 |
| 모듈 | 모듈 표의 경로, 앱 `module_path`, 공용 모듈 `path`, `아키텍처 테스트 위치`가 디스크에 있는가 |
| 레이어 | 그 컨텍스트의 `layer_patterns` 각 패턴에 매칭되는 패키지가 인벤토리에 하나라도 있는가 |

- **single-module 컨텍스트는 여러 행이 같은 경로를 가리킨다.** 경로로 중복을 없애 한 항목으로
  올린다 — 레이어 수만큼 같은 항목을 반복하면 리포트가 부풀 뿐이다.
- **app-embedded 컨텍스트에는 모듈 표가 없다**(금지되어 있다). 그 컨텍스트의 부재 판정은 모듈
  갈래가 아니라 **레이어 갈래**가 한다.
- 디렉터리는 있는데 빌드 스크립트가 없는 모듈은 "부분 부재"다. 사실 그대로 적는다.
- **1순위는 [scaffold로 생성]이다.** 선언이 코드보다 먼저 서 있는 상태는 오류가 아니라 정상
  플로우의 중간 단계이고(그린필드·설계 선행), scaffold의 트리거 분기가 바로 이 경우를 받는다.

### 3-b. 있는데 선언에 없다

- **모듈** — 2-b의 관측에서 선언된 경로 집합(모듈 표 ∪ 앱 ∪ 공용 모듈 ∪ 테스트 위치)을 뺀
  나머지.
- **패키지** — 2-c의 인벤토리 중 어느 `layer_patterns` 패턴에도 들지 않는 것. **곧바로 드리프트로
  올리지 말고 세 갈래로 가른다.**

| 무매칭 패키지가 | 판정 |
|---|---|
| 앱 모듈·공용 모듈·아키텍처 테스트 위치 **아래**에 있다 | 정상이다 — 앱·공용 모듈의 패키지는 선언에 없을 수 있다(정본 §5.1 규칙 5). 규약 표에 `{앱}` 행이 있으면 그 전개가 패턴이므로 애초에 무매칭으로 오지 않는다 |
| 선언된 프로젝트 경로 **밖**에 있다 | 범위 밖(2-a) |
| 그 밖 | 드리프트 후보 |

드리프트 후보의 해석은 최소 셋이다 — **새 컨텍스트가 생겼다 / 기존 컨텍스트에 선언되지 않은
레이어가 생겼다 / 패키지 규약 표가 실제 패키지를 덮지 못한다.** 어느 것인지는 사람만 안다.
관측(패키지 이름, 그 아래 파일 수, 어느 모듈에 있는지)을 붙여 셋을 나란히 제시하고 권고한다.

### 3-c. 레이어 매핑 불일치

두 얼굴이 있고 둘 다 **규칙이 조용히 아무것도 검사하지 않는 상태**를 만든다.

1. **공허 레이어** — 스타일이 선언한 레이어에 실현 패턴이 0건이다. 1단계 텍스트 실행의
   `warnings` 문면을 **그대로** 옮긴다(어느 규칙이 검사되지 않는지가 그 줄에 들어 있다). 모듈
   표·패키지 규약에 그 레이어 행이 없거나, 스타일이 쓰지 않는 레이어를 선언한 것이다.
2. **이름 어긋남** — 패턴은 있는데 매칭 패키지가 0건이다(3-a 레이어 갈래와 같은 관측). 선언은
   `presentation`인데 실제 소스는 `...web...`인 경우가 전형이고, **이 실패 모드는 파서도 게이트도
   잡지 못한다** — 이름은 정규 값이고 어긋난 곳은 이름과 실현 사이다(`rule-vocabulary.md` §5
   「새 커스텀 스타일을 선언할 때」가 이 대조를 sync에 맡긴 자리다).

3-b에 그 레이어와 **이름만 다른 무매칭 패키지**가 있으면 두 항목은 같은 사실의 양면이다. 한
항목으로 묶어 제시한다 — 고칠 곳은 레이어 이름(문서 수정)이거나 패키지 위치(코드 수정)이고,
어느 쪽인지는 사용자가 정한다.

### 3-d. 깨진 ADR·스타일 참조

```bash
grep -rnoE 'ADR-[0-9]{4}' ARCHITECTURE.md docs/architecture/ | sort -u
ls docs/architecture/decisions/
```

- **`규칙 예외`의 ADR이 이 축의 중심이다.** `- 규칙 예외: -<규칙 id> (ADR-NNNN)`마다 대응 파일
  (`decisions/NNNN-*.md`)이 있는지 보고, 있으면 그 문서의 `- 상태:`를 읽는다.

| 관측 | 뜻 |
|---|---|
| 파일 없음 | 깨진 참조 — 예외가 존재하지 않는 근거 위에 서 있다 |
| `superseded` | **근거가 폐기된 결정이다.** adr 7-c에서 「보류」로 남겨 둔 항목이 여기로 온다 |
| `proposed` | 근거가 아직 확정 전이다 — 오류는 아니지만 고지한다 |
| `accepted` | 정상 |

  처분 세 갈래는 `skills/adr/SKILL.md` 7-c의 표와 같다: **번호 갱신**(새 결정에서도 예외가
  유효하다) / **예외 제거**(근거가 사라졌다 — 규칙이 되살아난다) / **보류**. 파일·라인·원문을
  그대로 보여주고 고르게 한다. **번호만 갈아 끼우는 자동 처리를 하지 않는다** — 근거가 사라진
  예외가 새 ADR의 권위를 입는 것이 가장 나쁜 결과다.
- **그 밖의 ADR 참조**(`ARCHITECTURE.md` 본문, `conventions/`, domain 문서)는 없는 번호와 링크
  대상 파일 부재만 본다. **다른 ADR 본문이 옛 번호를 인용한 것은 드리프트가 아니다** — 그 문서들도
  `accepted`이고 양방향 링크가 독자를 현재 결정으로 데려간다(adr 7-b). 고치라고 하지 않는다.
- **스타일 문서** — 컨텍스트가 채택한 `custom/<이름>`의 문서 부재는 resolve가 오류로 잡으므로
  3-f로 온다. 여기서 보는 것은 **역방향**이다: `docs/architecture/styles/`에 있는데 어느 컨텍스트도
  채택하지 않은 고아 선언. 지우지 말고 고지한다 — 곧 채택할 초안일 수 있다.
- domain 문서의 불변식과 테스트 태그의 대조는 이 스킬이 아니라 `check_invariants.py`·review의
  몫이다. 여기서 다시 보지 않는다.

### 3-e. 파생물이 선언보다 낡았다

**mtime을 쓰지 않는다.** 체크아웃·포맷터가 파일 시각을 올리고, 반대로 손으로 고친 파생물은
mtime이 최신이어도 내용이 틀리다. 판정 근거는 언제나 **내용 대조**다.

| 파생물 | 대조하는 것 |
|---|---|
| `docs/architecture/summary.md` | 첫 줄의 생성물 헤더, 컨텍스트 표의 행 집합(이름·분류·스타일·모듈 수)이 선언과 같은가, 30줄 이하인가 |
| 컨텍스트 맵 생성 구역 | 노드 집합 == 컨텍스트 ∪ 앱, 엣지 == 관계 표의 쌍 ∪ 앱 → `포함 컨텍스트` |
| `structure:<컨텍스트>` 생성 구역 | 노드 == 모듈 표의 모듈(app-embedded면 패키지 규약의 레이어) |

- **마커 규약의 정본은 `architecture-template.md`의 「생성 구역 마커」다.** 두 줄 모두 줄 전체가
  정확히 일치해야 하고, 닫는 마커가 없는 여는 마커는 구역이 아니다 — **갱신하지 않고 오류로
  보고**한다. 구역 자체가 없으면 그것도 항목이다(생성된 적이 없다).
- **summary.md의 「전역 핵심 규칙」은 자유 서술이라 기계 대조가 성립하지 않는다.** 대조하지
  않았다고 적는다. 이 파일은 SessionStart 훅이 통째로 주입하는 유일한 산출물이라, 여기 남은
  낡은 규칙 문장은 매 세션 사실로 읽힌다 — 사용자에게 직접 확인을 권한다.
- 한 줄 더 본다: **`이행` 라벨과 `docs/architecture/baseline.jsonl`의 짝.** 라벨 없이 파일만
  있으면 래칫이 근거를 잃은 상태다. 라벨이 있는데 파일이 없으면 동결하지 않았다는 뜻일 수도,
  동결 시점에 위반이 0이었다는 뜻일 수도 있으므로 **판정하지 말고 고지**한다. 처분은 init(동결)과
  migrate(축소)의 몫이고 이 스킬은 그 파일을 쓰지 않는다.

### 3-f. 해석 오류 자체가 드리프트다

1단계가 exit 1로 낸 `경로:라인: 메시지` 줄을 **그대로** 항목으로 올린다. `resolve_rules.py`는
`parse_architecture.py`의 검사를 전부 포함하므로(init 6단계와 같은 게이트) 따로 돌리지 않는다 —
필수 결정 누락, 비정규 값, 깨진 참조(없는 프로젝트·컨텍스트를 가리키는 라벨), 커스텀 스타일 문서
부재, 모듈 표의 레이어 이름 불일치가 한 목록으로 온다. **지목된 경로가 `ARCHITECTURE.md`가 아닐
수 있다** — 스타일 선언 문서의 오류가 같은 목록에 섞인다.

이 축의 선택지는 **[문서 수정] 하나뿐이다.** 파싱되지 않는 선언 위에서는 코드와의 대조 자체가
성립하지 않으므로 scaffold도 코드 수정도 답이 될 수 없다. 사용자가 지금 고치지 않기로 하면 그대로
두되, 이번 실행이 **신뢰 불가**였다는 사실을 리포트 맨 위에 박는다.

## 4. 처분 — 네 선택지

**항목마다 넷을 제시하고 고르게 한다.** 축별 1순위와 각 선택지의 뜻은 아래가 전부다.

| 선택지 | 뜻 | 누가 하는가 |
|---|---|---|
| **scaffold로 생성** | 선언이 맞다 — 없는 것을 만든다 | `/superarchitect:scaffold` (5-b) |
| **코드 수정** | 선언이 맞다 — 있는 것을 옮기거나 지운다 | 사용자 또는 `/superarchitect:migrate`. **이 스킬은 코드를 쓰지 않는다** |
| **문서 수정** | 현실이 맞다 — 선언을 고친다 | 이 스킬(5-a) 또는 인터뷰가 필요하면 scaffold |
| **무시** | 지금 판단할 재료가 없거나 의도된 상태다 | 아무도. 리포트에만 남는다 |

| 축 | 1순위 | 근거 |
|---|---|---|
| 3-a 선언됐는데 없음 | **scaffold로 생성** | 설계 선행은 오류가 아니라 정상 플로우의 중간 단계다 — 정본 §4의 `경로` 행이 "아직 없는 경로도 허용(설계 선행)"이라고 적는다 |
| 3-b 있는데 미선언 | 없음 | 새로 생긴 코드인지 지워야 할 잔재인지는 관측으로 갈리지 않는다 |
| 3-c 레이어 불일치 | 없음 | 이름을 고칠지 패키지를 옮길지가 정확히 이 축의 질문이다 |
| 3-d 깨진 ADR 참조 | 문서 수정 | 코드와 무관하다. 갈래는 adr 7-c의 셋 |
| 3-e 낡은 파생물 | 문서 수정(재생성) | 파생물은 언제나 SSOT에서 다시 만든다 |
| 3-f 해석 오류 | 문서 수정 | 다른 선택지가 성립하지 않는다 |

- **1순위가 있다는 것은 기본값이 있다는 뜻이지 확정됐다는 뜻이 아니다.** 1순위를 포함해 넷을
  보여주고 답을 받는다.
- **1순위가 "없음"인 축에서 침묵하지 않는다.** 관측을 근거로 하나를 권고한다 — 예: "이 모듈은
  최근 3주 안에 생겼고 소스가 12개다 → 문서 수정(등재)을 권한다". 근거를 함께 적어, 사용자가
  근거를 보고 뒤집을 수 있게 한다.
- **무시는 이번 회차에만 유효하다.** 억제 목록 파일을 만들지 않는다(정본 §5.1 규칙 9 — 캐시
  없음). 다음 실행에 같은 항목이 다시 올라오는 것이 정상이고, 항구적으로 정당화하려면
  `/superarchitect:adr`로 결정을 남기는 것이 그 자리다.

## 5. 반영

**고른 것만 반영한다 — 자동 적용은 없다.** 4단계에서 답을 받지 못한 항목은 리포트에만 남고,
아무것도 고르지 않았으면 아무 파일도 쓰지 않고 리포트로 끝낸다.

### 5-a. 문서 수정 — 확정받은 편집만

- **편집 전에 원문과 변경안을 나란히 보여주고 확정을 받는다.** 표의 한 줄이어도 그렇다.
- **고쳐도 되는 것과 안 되는 것**의 경계는 `skills/init/SKILL.md` 6단계 「고쳐도 되는 것과 안 되는
  것」과 같다: 형식 오류(라벨 오타·표 위치·구분선·화살표·마커)는 고치고, **사용자가 결정한 값**
  (컨텍스트 이름·분류·스타일·모듈 구성·관계·프로파일)은 게이트를 통과시킬 목적으로 바꾸지 않는다.
  같은 오류가 두 번 반복되면 멈추고 파서 출력 원문을 보여주며 묻는다.
- **인터뷰가 필요한 등재는 이 스킬이 하지 않는다.** 새 컨텍스트·새 프로젝트를 선언에 올리려면
  경계·분류·스타일·모듈 구성을 정해야 하고, 그 인터뷰의 정본은 scaffold 2단계·4-a다. 그쪽으로
  넘긴다. 이 스킬이 쓰는 문서 수정은 **이미 결정된 것의 표기를 현실에 맞추는 편집**까지다 —
  모듈 표의 행 추가·경로 정정, `규칙 예외`의 ADR 번호 갱신·제거, 깨진 라벨 값 정정.

### 5-b. scaffold로 넘기기

`/superarchitect:scaffold`를 권하고, **무엇을 넘기는지 명시한다** — 드리프트 항목, 프로젝트·
컨텍스트 이름, 없는 경로 목록. scaffold의 트리거 분기 표가 그것을 그대로 받는다(선언된 프로젝트가
디스크에 없다 / 선언된 컨텍스트에 코드가 없다).

**넘긴 항목은 이 스킬이 다시 재생성하지 않는다.** scaffold가 선언 마무리 → 게이트 → 파생물
재생성까지 자기 절차로 끝내므로, 여기서 또 돌리면 두 스킬이 같은 구역을 두 번 쓴다.

### 5-c. 코드 수정으로 고른 항목

**이 스킬은 코드를 쓰지 않는다.** 무엇을 어디로 옮기면 선언과 맞는지(대상 경로·목표 패키지)를
정확히 제시하고 멈춘다. 기존 코드를 목표 스타일로 옮기는 것은 `/superarchitect:migrate`이고,
지우는 것은 사용자다.

### 5-d. 게이트 → 파생물 재생성 → 게이트

SSOT(`ARCHITECTURE.md`)를 한 글자라도 고쳤으면 돌린다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md
```

1단계의 수치와 비교한다 — **컨텍스트 수와 유효 규칙 수가 의도한 만큼만 변했는가.** 줄어들었는데
의도한 적이 없다면 헤딩이나 표를 건드린 것이다.

이어서 파생물을 재생성한다. 관례는 `skills/init/SKILL.md` 7-a·7-b가 정본이고 여기서 다시 정하지
않는다 — summary.md는 30줄 이하, 생성 구역은 **여는 마커가 이미 있으면 새로 쓰지 않고 그 쌍
사이만 교체**, 짝이 없는 마커는 갱신하지 않고 오류로 보고.

- **재생성은 파생물의 손 편집을 지운다.** 3-e가 낡음으로 판정한 것이 사실은 누군가 손으로 넣은
  내용일 수 있으므로, 쓰기 전에 diff를 보여주고 확정을 받는다.
- 생성 구역은 `ARCHITECTURE.md` 안이다 — 고쳤으면 **게이트를 한 번 더** 돌린다. 컨텍스트·유효
  규칙 수가 직전 실행과 같아야 하고, **이 실행의 `OK:` 출력이 이 스킬의 완료 조건이다.**
- **들어올 때 이미 깨져 있었고(3-f) 사용자가 고치지 않기로 했으면** 깨진 채로 끝낸다. 그때의
  완료 조건은 `OK:`가 아니라 **그 사실을 리포트에 박는 것**이다 — 남의 실패를 통과시키려고 선언을
  고치지 않는다.

## 6. 마무리 보고

1. **범위** — 대조한 프로젝트와 경로, "범위 밖"으로 남긴 빌드 루트, 2-c 관측의 한계(테스트 소스·
   다른 언어 소스 미대조).
2. **축별 집계** — 여섯 축 각각의 항목 수. **0건도 적는다.**
3. **대조하지 못한 것** — 해석 실패로 건너뛴 축, 파일이 없어 보지 못한 것, 기계 대조가 성립하지
   않는 것(summary.md의 전역 핵심 규칙). **이 절을 비우지 않는다.**
4. **처분** — 항목별로 사용자가 고른 것과 그 결과. 무시한 항목도 남긴다.
5. **쓴 파일** — `ARCHITECTURE.md`의 어느 줄·표, `summary.md`, 생성 구역. 게이트의 `OK:` 줄을
   1단계 수치와 나란히 인용한다. 아무것도 쓰지 않았으면 그렇게 적는다.
6. **넘긴 것** — scaffold·migrate·adr로 넘긴 항목 목록과 권하는 명령. 선언이 바뀌었으면
   `/superarchitect:fitness`도 함께 권한다(유효 규칙이 바뀌었는데 생성된 테스트는 아직 옛 규칙을
   검사하고 있다).
7. **커밋은 사용자가 한다.** 실제로 쓴 파일만 넣어 명령을 제안한다.

   ```bash
   git add ARCHITECTURE.md docs/architecture/summary.md
   git commit -m "docs: 선언과 코드의 드리프트 정정"
   ```

## 하지 말 것

- **드리프트의 방향을 확인 없이 정하는 것.** 없는 모듈을 "선언이 낡았으니" 지우거나, 미선언
  모듈을 묻지 않고 표에 올리는 것 둘 다다. 권고는 하고 확정은 받는다.
- **권고 없이 선택지만 나열하는 것.** 관측을 근거로 어느 쪽이 맞아 보이는지 한 줄로 적는다 —
  불변 1이 금지하는 것은 확정이지 판단이 아니다.
- **코드를 쓰거나 옮기거나 지우는 것.** 골격은 scaffold, 이행은 migrate, 삭제는 사용자다.
- **대조하지 못한 축을 리포트에서 빼는 것.** 해석 실패·파일 부재·기계 대조 불가는 전부 고지한다.
  "드리프트 없음"과 "대조하지 않음"은 다른 상태다.
- **미선언 프로젝트(frontend 등)를 드리프트로 올리는 것.** 스캔 범위는 선언된 프로젝트 경로
  안뿐이고, 범위 밖은 이름만 남긴다.
- **앱·공용 모듈 아래의 무매칭 패키지를 "미선언 패키지"로 올리는 것.** 그 패키지는 선언에 없을
  수 있다(정본 §5.1 규칙 5).
- **mtime으로 파생물의 신선도를 판정하는 것.** 근거는 내용 대조뿐이다.
- **`규칙 예외`의 ADR 번호를 확인 없이 갈아 끼우는 것.** 근거가 사라진 예외가 새 번호를 입는다.
- **다른 ADR 본문이 옛 번호를 인용한 것을 드리프트로 올리는 것.** 양방향 링크가 그 독자를 현재
  결정으로 데려간다.
- **파생물을 SSOT 대신 고치도록 유도하는 것**, 짝 없는 마커에 닫는 마커를 끼워 넣어 남의 서술을
  생성 구역 안에 가두는 것.
- **게이트를 통과시키려고 사용자가 결정한 값을 바꾸는 것.** 고쳐도 되는 것은 형식뿐이다.
- **들어올 때 깨져 있던 선언을 사용자 확인 없이 고쳐 놓고 통과했다고 보고하는 것.**
- **무시한 항목을 파일로 억제하는 것.** 캐시를 만들지 않는다 — 다음 실행에 다시 올라오는 것이
  정상이고, 항구적 정당화는 ADR이다.
- **위반을 검사하는 것.** 이 스킬은 규칙 위반을 판정하지 않는다 — 그것은 `check_imports`·생성된
  테스트·`/superarchitect:review`의 몫이고, 여기서 겹쳐 돌리면 같은 지적이 두 리포트에 오른다.
