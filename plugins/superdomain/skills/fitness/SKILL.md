# 아키텍처 피트니스 함수 생성

이 스킬은 번역기다. 판단은 `ARCHITECTURE.md`와 스타일 선언에서 이미 끝났고, 해석은
`resolve_rules.py`가 하고, 코드 모양은 프로파일의 `rule-mappings.md`가 정한다. 여기서 새로
정하는 것은 없다. 그래서 불변이 셋이다.

1. **SSOT를 고치지 않는다.** `ARCHITECTURE.md`와 스타일 선언은 입력이다. 게이트가 실패하면
   무엇을 어디서 고쳐야 하는지 알리고 멈춘다 — 강제 장치가 자기가 강제할 선언을 고치기 시작하면
   이 플러그인은 아무것도 보장하지 못한다.
2. **매핑에 없는 것을 지어내지 않는다.** 프로파일 매핑이 유일한 번역 사전이다. 없는 primitive는
   비슷한 것으로 갈음하지 않고 오류로 보고한다.
3. **조용히 빠뜨리지 않고, 확인 없이 덮지 않는다.** 생성하지 못한 규칙은 전부 사유와 함께
   리포트에 오른다. "위반 없음"과 "아무것도 검사하지 않음"은 다른 상태다.

이 스킬은 `references/knowledge/`를 읽지 않는다 — 판정 근거는 SSOT, 해석기 출력, 프로파일 매핑
셋뿐이다. 다른 문서를 근거로 규칙을 더하거나 빼지 않는다.

## 0. 위치와 초기화 게이트

```bash
git rev-parse --show-toplevel
```

그 경로의 `ARCHITECTURE.md`가 유일한 입력이다. 하위 디렉터리에서 시작했어도 여기로 올라와서
작업한다. 파일이 없으면 아래를 알리고 **중단**한다.

> superarchitect가 초기화되지 않았습니다. `/superarchitect:init`으로 아키텍처 거버넌스를 먼저 세우세요.

## 1. 유효 규칙 해석 — 이 명령이 게이트다

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md --json
```

- **exit 1이면 멈춘다.** 오류는 stderr에 `경로:라인: 메시지`로 나온다. 그 줄들을 **그대로**
  사용자에게 보여주고 중단한다. 경로가 ARCHITECTURE.md일 수도 스타일 선언 문서일 수도 있다 —
  어디를 고쳐야 하는지는 그 경로가 말해 준다. 고치는 것은 이 스킬의 일이 아니다.
- exit 0이면 stdout 전체가 JSON이고 키는 넷이다: `projects`(name·path·profile·base_package·
  test_location), `effective`(project·context·rule_id·primitive·params·resolved·layer_patterns),
  `derived`(project·kind·subject·detail), `warnings`.

집계를 위해 `--json` 없이 한 번 더 돌린다. **예외 제외 건수는 이 실행만 알려 준다**(JSON에 없다).

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md
```

→ `OK: 컨텍스트 N, 유효 규칙 M (스타일 A, 파생 B, 예외 제외 C)`. 이 줄을 6단계 보고에 옮긴다.

### 0건은 성공이 아니다

`effective`와 `derived`가 **둘 다 비면** 생성할 것이 없다. 중단하고 무엇이 비었는지 말한다 —
컨텍스트가 0건인지, 스타일 규칙이 전부 `규칙 예외`로 빠졌는지. 빈 테스트 파일을 만들지 않는다.

### `warnings`를 삼키지 않는다

`warnings`는 오류가 아니라 **공허 레이어 고지**다: 스타일이 선언한 레이어에 실현 패턴이 0건이라
그 레이어를 참조하는 규칙이 아무것도 검사하지 않는 상태. 각 항목의 `message`를 그대로 출력한다.

그 규칙들(`warnings[].rules`)은 **번역할 대상이 없다.** 처리는 이렇다.

- 해당 규칙을 **생성하지 않고**, 리포트에 규칙 id와 사유(`레이어 <이름> 패턴 0건`)를 남긴다.
- 있는 레이어만 넣어 반쪽으로 만들지 않는다. 매핑 §1이 경고하는 "등록되지 않은 레이어는 검사
  대상에서도 빠져 규칙이 조용히 비는" 상태가 된다 — 그건 없는 규칙보다 나쁘다.
- 처방은 어서션을 무르는 것이 아니라 선언을 고치는 것이다(매핑 §0.3). 모듈 표·패키지 규약에 그
  레이어가 없거나, 스타일이 쓰지 않는 레이어를 선언한 것이다. **고치는 것은 사용자의 몫**이고,
  고친 뒤 이 스킬을 다시 돌리면 규칙이 살아난다.
- `rules`가 빈 경고는 생성에 영향이 없다 — 고지만 한다.

## 2. 프로파일 매핑 — 유일한 번역 사전

`projects[].profile`마다 매핑이 있는지 본다.

```bash
ls "${CLAUDE_PLUGIN_ROOT}/profiles/<프로파일>/rule-mappings.md"
```

있으면 **지금 읽는다.** 이 스킬은 템플릿을 갖고 있지 않다 — 생성 헤더와 파일 배치(§0.1), 패턴
헬퍼(§0.2), 0건 규율(§0.3), primitive 5종(§1–§5), 파생 3종(§6)이 전부 그 문서에 있고 그것이
정본이다 — §9가 가리키는 검증 대장은 별도 파일일 수 있고, 필요할 때만 읽는다. 플레이스홀더 세
형태(`{{name}}`·`{{items:<필드>}}`·`{{#<필드>}}…{{/<필드>}}`)의 뜻은
`${CLAUDE_PLUGIN_ROOT}/profiles/README.md`에 있다.

없으면 그 프로젝트는 **여기서 멈춘다.** 정직하게 알린다.

> `<프로젝트>`의 프로파일 `<이름>`에는 아직 `rule-mappings.md`가 없습니다. 번역 사전 없이
> 테스트를 지어내지 않습니다.

> **구현 상태 — `java-spring` 매핑은 Phase 6이다.** 그때까지 이 프로파일의 프로젝트는 생성
> 대상이 아니다. 선언은 유효하고, 도착하면 같은 절차가 그대로 돈다.

대상이 그 프로젝트뿐이면 전체를 중단한다. 매핑이 있는 다른 프로젝트가 남아 있으면 건너뛴 사실을
리포트에 적고 나머지를 진행한다.

`primitive` 값에 해당하는 절이 매핑에 없으면(어휘 확장이 프로파일보다 먼저 도착한 경우) 그 규칙을
**생성하지 않고 오류로 보고**한다. 나머지 규칙 생성은 계속하되, 이 오류는 리포트 맨 위에 둔다.

## 3. 관측 — 패키지는 선언되지 않는다 (D2)

앱 모듈과 공용 모듈의 패키지는 결정 문서에 없다. `resolve_rules`는 경로만 전달하고
(`detail.module_path`·`detail.path`), 읽는 것은 이 스킬의 일이다.

프로젝트마다 패키지 인벤토리를 **한 번** 만든다. 4단계의 라우트 판정도 이것을 쓴다.

```bash
find "<프로젝트 경로>" \( -path '*/build/*' -o -path '*/src/test/*' -o -path '*/.gradle/*' \) -prune \
  -o \( -name '*.kt' -o -name '*.java' \) -exec grep -hE '^[[:space:]]*package[[:space:]]' {} + \
  | sed -E 's/^[[:space:]]*package[[:space:]]+//; s/[;[:space:]]*$//' | sort -u
```

모듈 하나의 패키지가 필요하면 경로만 `<프로젝트 경로>/<module_path>`로 바꾼다. 테스트 소스를 빼는
이유는 매핑의 모든 어서션이 `Konsist.scopeFromProduction()`(프로덕션 소스)에서 출발하기 때문이다.

얻은 목록은 매핑 §6의 규약대로 굽는다: **다른 항목의 접두가 되는 최소 집합만 남기고** 각 항목에
`..`를 붙인다(`com.acme.dbcore`와 `com.acme.dbcore.jpa`가 함께 나오면 앞의 것만 남긴다). 값 위에
`// 관측: <모듈 경로> (package 선언 N건)` 주석을 병기한다.

**관측 0건이면 그 인스턴스를 생성하지 않고 리포트에 고지한다.** 조용히 빠뜨리는 것이 이 단계에서
가장 하기 쉬운 실패다 — 모듈이 아직 비었을 수도(선언만 있고 코드가 없다면 골격을 만드는 것은
`/superarchitect:scaffold`다), 경로가 틀렸을 수도, 소스가 다른 언어일 수도 있고 셋의 처방이 전부
다르다. 선언 경로(`detail.app_patterns`)에는 이 분기가 없다.

## 4. 생성

### 4-a. 파일 배치

매핑 §0.1의 배치 규약에 `projects[]`의 값을 넣으면 경로가 나온다.

```
<git 루트>/<path>/<test_location>/<base_package의 .을 /로 바꾼 경로>/architecture/<Context>ArchitectureTest.kt
```

- `path`가 `.`이면 git 루트가 프로젝트 루트다. `test_location`은 **프로젝트 경로 기준** 상대
  경로다(`architecture-template.md` §4).
- `<Context>`는 컨텍스트 이름의 PascalCase — 하이픈·언더스코어는 지우고 다음 글자를 대문자로
  올린다(`order-mgmt` → `OrderMgmt`).
- 파생 규칙은 같은 디렉터리의 `DerivedRulesTest.kt` 하나에 **프로젝트 단위로** 모은다.
- 디렉터리가 없으면 만든다. 생성물은 이 파일들뿐이다.

### 4-b. 파일 뼈대 (매핑이 정하지 않은 부분만 여기서 정한다)

1. 첫 두 줄은 매핑 §0.1의 생성 헤더를 **글자 그대로**. 5단계가 이 두 줄로 수동 수정을 판정하므로
   한 글자도 바꾸지 않는다.
2. `package <base_package>.architecture`
3. **import는 매핑의 「import 목록(정본)」 블록을 그대로 복사한다**(kotlin-spring은 §0.1). 쓰지
   않은 줄만 빼고, **패키지를 스스로 유도하지 않는다** — 검증 대장의 소스 경로는 심볼이 아니라
   선언 인터페이스의 위치라, 유도하면 심볼 미해결이 연쇄해 파일 전체가 컴파일되지 않는다(실측).
   테스트 애노테이션은 그 프로젝트가 쓰는 프레임워크를 따른다(JUnit 5면
   `org.junit.jupiter.api.Test`).
4. 파일 이름과 같은 이름의 클래스 하나에 `@Test` 함수를 담는다(`class ClaimArchitectureTest { … }`).
5. 매핑 §0.2의 `matchesPattern` 헬퍼를 파일마다 한 번 넣는다.
6. **`이행` 중이면**(= git 루트에 `docs/architecture/baseline.jsonl`이 있으면) 매핑 §7의 baseline
   조각도 파일마다 한 번 넣는다. 파일이 없는 프로젝트에는 넣지 않는다 — 쓰지 않을 코드를 생성물에
   남기지 않는다.

### 4-c. 스타일 유래 규칙 — `effective` 항목마다

1. `primitive`로 매핑의 절을 찾는다(§1 layer-order, §2 forbid-import, §3 confine-type,
   §4 naming-suffix, §5 forbid-sibling-dependency).
2. 그 절의 "입력" 줄이 지시하는 필드를 JSON에서 읽는다. `resolved`는 §2.1(가) 파라미터의 레이어
   항목이 **이미 패키지 패턴으로 치환된** 결과이고, 레이어 이름으로 남은 (나) 파라미터
   (`layers`·`allowed_layer`·`layer`)는 `params`에서 이름을 읽어 `layer_patterns[<이름>]`으로
   번역한다. **패턴을 손으로 만들지 않는다** — 정규화는 해석기가 이미 했다.
3. 플레이스홀더를 치환한다. `{{ruleIdSafe}}`는 백틱 함수 이름에 들어갈 수 없는 문자를 공백으로
   바꾼 형태이고(매핑 §0.1), 원본 id는 `additionalMessage`에 남는다. 한 파일 안에서 함수 이름은
   유일해야 한다.
4. `forbid-import`는 **라우트를 먼저 판정한다**(매핑 §2의 표). ①② 패턴 문자열 조건은 값으로
   판정하고, ③ "스캔 스코프 안에 소스가 존재"는 3단계의 인벤토리로 판정한다 — `from`·`to`의 어느
   한 항목이라도 대응 패키지가 인벤토리에 없으면 **라우트 B**다. 외부 라이브러리 패턴
   (`org.springframework..`)은 언제나 0건이므로 항상 B다.
5. `strict` 인자와 기본값은 매핑 §0.3이 primitive별로 정해 두었다. 통과시키려고 뒤집지 않는다.
6. **baseline이 있으면 강등 합성을 얹는다**(매핑 §7의 표) — `assertFalse`는 위반식에
   `&& !demoted("<rule id>", <경로>)`, `assertTrue`는 통과식에 `|| demoted(…)`, `assertArchitecture`는
   수신 스코프에 `.slice { !demoted(…, it.projectPath) }`. **4-d의 파생 규칙도 같다** — 거기서는 rule
   id 자리에 `derived.<kind>`를 쓴다. check_imports가 baseline에 그 id로 적기 때문이다.

### 4-d. 파생 규칙 — `derived` 항목마다

매핑 §6.2의 표에서 kind와 방향으로 행을 찾는다. 테스트 이름·`<from>`·`<forbidden>`을 그 표가 전부
정한다. 이 스킬이 판단할 것은 넷뿐이다.

- **앱 패키지**: `detail.app_patterns`가 **있으면 선언**이 진실이다. 그 표에는 프로젝트의 **모든
  앱**이 들어 있으므로 `앱 패턴(subject)`은 그 표의 subject 항목이고, `타 앱 패턴`은 subject를 뺀
  나머지 값들의 합집합이다. 키가 **없으면 둘 다 관측이다**(3단계) — subject는 자기
  `detail.module_path`로, **타 앱은 같은 프로젝트의 다른 `app-confinement` 인스턴스들의
  `module_path`로** 관측해 합친다(매핑 §6.2의 `타 앱 패턴` 정의). `detail.module_path`에는 subject
  앱 자신의 경로밖에 없으므로, 여기서 형제 인스턴스를 훑지 않으면 `타 앱 패턴`이 비어 앱 간 행이
  통째로 빠지고 앱이 하나뿐인 프로젝트로 잘못 집계된다.
- **공용 모듈 패키지는 언제나 관측**이다. 그리고 `shared-module-direction` **정방향의
  `<forbidden>`에는 앱 코드가 합류한다** — `detail.app_patterns`가 없고 `### 애플리케이션` 표가
  있는 프로젝트에서는 앱 패키지가 선언에 없으므로, 각 `app-confinement` 인스턴스의 `module_path`를
  관측해 `detail.forbidden`에 더한다(매핑 §6.2). 빠뜨리면 "공용 모듈 → 앱" 금지가 어느 어서션에도
  남지 않는다. 관측 0건인 앱은 그 몫만 빼고 앱 이름과 함께 고지하되 인스턴스는 생성한다.
- 목록이 비면 매핑이 "생성하지 않는다"고 적어 둔 행들이다: `forbidden`이 빈 app-confinement
  정방향(`포함 컨텍스트: all`), 앱이 하나뿐일 때의 앱 간, `domain_restricted_contexts`가 빈 도메인
  제한. 생성하지 않은 사실은 집계에 남긴다.
- **도메인 제한 행의 domain 레이어 패턴은 `detail`에 없다.** 같은 프로젝트에서 `context`가 그 항목
  이름과 같은 `effective` 규칙을 찾아 `layer_patterns["domain"]`에서 가져온다. 그런 규칙이 없거나
  그 키가 비어 있으면 그 항목을 **생략하고 고지한다.**

주석 규약(매핑 §6): 선언 유래 목록 위에는 `// 선언: …`, 관측 유래 목록 위에는 `// 관측: …`.

## 5. 기존 파일 — 확인 없이 덮지 않는다

생성 대상 경로에 파일이 있으면 **첫 두 줄**을 읽어 매핑 §0.1의 헤더와 대조한다.

**헤더가 온전하면** 갱신한다. 새 내용을 임시 파일(`mktemp`)에 쓰고 **diff를 먼저 보여준다** —
대상 프로젝트 트리에 임시 파일을 남기지 않는다.

```bash
diff -u "<기존 파일>" "<새 내용 임시 파일>"
```

차이가 없으면 쓰지 않고 "변경 없음"으로 집계한다.

**헤더가 없거나 훼손됐으면** 누군가 손을 댔다는 뜻이다. 쓰기 전에 멈추고 세 가지를 알린 뒤
**덮어쓸지 묻는다.**

- 그 파일이 생성물 자리를 차지하고 있다는 것,
- 덮으면 손으로 넣은 어서션이 사라진다는 것,
- 손으로 쓴 규칙은 생성 파일이 아닌 다른 파일로 옮기면 계속 살아 있다는 것.

답을 받기 전에는 쓰지 않는다. 거부하면 그 파일은 건너뛰고 리포트에 남긴다.

선언에 없는 컨텍스트의 생성 파일이 그 디렉터리에 남아 있으면 **지우지 않고** 고지한다 —
이름이 바뀐 흔적인지 컨텍스트가 빠진 흔적인지는 사용자만 안다.

## 6. 마무리 보고

1. **파일 목록** — 생성 / 갱신 / 변경 없음 / 건너뜀(사유별).
2. **집계** — 1단계의 `OK:` 줄을 그대로 인용하고, 실제로 생성된 규칙 수와 제외분(공허 레이어,
   관측 0건, 매핑 부재, 덮어쓰기 거부)을 따로 적는다. **두 수가 다르면 그 차이가 리포트의
   핵심이다.**
3. **실행 안내** — 테스트 위치에서 Gradle 모듈을 유도한다. `architecture-test/src/test/kotlin`이면
   모듈 디렉터리는 `architecture-test`다. 그 디렉터리가 `include`에 어떤 이름으로 들어 있는지
   확인하고 그 이름을 쓴다.

   ```bash
   grep -n 'include' "<프로젝트 경로>"/settings.gradle*
   ./gradlew :<모듈 경로>:test
   ```

   `include`에 없으면 **그 사실을 먼저 알린다.** 빌드에 포함되지 않는 모듈에 테스트를 만든
   상태이고, 그 테스트는 영원히 실행되지 않는다.
4. **의존성** — 테스트 모듈의 빌드 스크립트에 Konsist가 없으면 좌표를 안내한다(설치하지 않는다).

   ```kotlin
   testImplementation("com.lemonappdev:konsist:0.17.3")
   ```

   JUnit 5 실행 설정(`useJUnitPlatform()`)이 없으면 함께 알린다.
5. **첫 실행에서 확인할 것** — `strict = true`라 0건에서 실패하는 규칙. "생성됐다"가 "통과한다"를
   뜻하지 않는 지점이다. 여기에 하나가 더 붙을 수 있다: 프로파일의 검증 대장(kotlin-spring은
   `${CLAUDE_PLUGIN_ROOT}/profiles/kotlin-spring/api-verification.md`)에
   `⚠️ (미검증 — 첫 실행 시 확인)` 행이 있으면 그 API를 쓴 규칙도 함께 적는다. **지금 그 대장은 전
   행이 `✅`이므로 해당 규칙이 없다** — ⚠️ 행이 새로 생겼을 때만 이 항목이 살아난다.
6. **이행 중이면 미리 말한다.**

   ```bash
   grep -n '^- 이행:' ARCHITECTURE.md; ls docs/architecture/baseline.jsonl
   ```

   > **baseline이 있으면 생성된 테스트가 기존 부채를 강등한다**(매핑 §7 — 4-b·4-c에서 이미 넣었다).
   > 부채는 `[기존 부채] …` 출력으로 나오고 실패는 신규 위반만 낸다. `이행` 라벨은 있는데 baseline이
   > 없으면 첫 실행에서 기존 부채가 전부 실패로 나오므로, 그 전에 `/superarchitect:init`의 동결을
   > 끝내라고 말한다. **baseline은 Gradle 태스크 입력이 아니다** — 부채를 갚고 그 파일만 고친 뒤
   > 테스트를 다시 돌리면 `UP-TO-DATE`로 건너뛴다. `--rerun-tasks`가 필요하다고 함께 알린다.
7. **커밋은 사용자가 한다.** 명령만 제안한다.
8. **다음 걸음** — 생성된 테스트가 원리적으로 못 보는 것(같은 패키지 안의 참조, import 없는 FQN
   사용, 리플렉션, 의미론)은 `/superarchitect:review`가 본다. 규칙 자체를 바꾸고 싶으면 테스트가
   아니라 스타일 선언을 고치고 이 스킬을 다시 돌린다 — 그 변경의 근거는 `/superarchitect:adr`이
   받는다.

## 하지 말 것

- **`ARCHITECTURE.md`·스타일 선언·파생물을 고치는 것.** 게이트가 실패하면 알리고 멈춘다.
  통과시키려고 선언을 고치면, 강제 장치가 자기가 강제할 대상을 고친 것이 된다.
- **매핑에 없는 primitive를 임의로 번역하거나 어휘 밖 규칙을 즉석에서 만드는 것.** 없으면 없다고
  보고한다.
- **0건을 통과로 만들려고 `strict`를 뒤집거나 어서션을 무르는 것.**
- **관측 0건·공허 레이어·생략한 파생 항목을 조용히 넘기는 것.** 전부 리포트에 사유와 함께 남는다.
- **헤더가 훼손된 파일을 확인 없이 덮는 것**, 선언에 없는 컨텍스트의 파일을 임의로 지우는 것.
- **생성 파일을 손으로 고치도록 유도하는 것.** 항상 선언을 고치고 다시 생성한다.
- **패키지 패턴을 손으로 만드는 것.** 정규화 결과는 `layer_patterns`·`resolved`에 이미 있다.
- **테스트를 실행하지 않고 결과를 말하는 것.** 실행 안내까지가 이 스킬의 몫이다.
