# 도메인 가이드

`docs/superdomain/DOMAIN.md`의 형식과, 도메인 경계를 긋고 검토하는 기준이다. domain 스킬과 domain-reviewer가 함께 읽는다.

## DOMAIN.md 형식

```markdown
# <제품명> 도메인

<제품이 무엇을 하는지 1~2문장>

## order — 주문
- 역할: 고객의 구매 요청을 받아 결제 완료까지의 상태를 관리한다
- 기능: 주문 생성, 주문 취소, 주문 내역 조회
- 분류: core
- 코드: order-api `com.acme.order`
- 규칙: 배송이 시작된 주문은 취소할 수 없다
- 하지 않는 것: 배송 추적 (→ delivery)

## payment — 결제
- 역할: 결제의 승인과 취소·환불을 관리한다
- 기능: 결제 승인, 결제 취소, 부분 환불
- 분류: supporting
- 코드: payment-api `com.acme.payment`
- 외부: PG사 — 결제 승인·취소 API, 결제 결과 웹훅, 정산 파일

## 관계
| 도메인 | 의존 대상 | 방식 | 설명 |
|---|---|---|---|
| order | payment | 동기 호출·이벤트 | 결제 승인을 요청하고, 결제 완료 이벤트를 받아 주문 상태를 바꾼다 |
| delivery | order | 이벤트 | 결제 완료된 주문으로 배송을 만든다 |
```

- **제목**: `## <key> — <이름>`. key는 영문 소문자와 하이픈이고, 관계 표에서 쓴다.
- **역할**: 한 문장. 두 문장이 필요하면 도메인이 둘일 수 있다.
- **기능**: 이 도메인이 제공하는 일. 화면이나 API 목록이 아니다.
- **분류**: `core` · `supporting` · `generic` (아래 분류 기준).
- **코드**: 모듈과 패키지. 여러 모듈에 걸치면 모두 적고, 모듈마다 모델이 따로 있으면 그렇게 적는다(예: `core-api: 조회 모델, core-worker: 동기화 모델`).
- **외부**(선택): 이 도메인이 맞닿은 외부 시스템과 주고받는 것. `<외부 시스템> — <주고받는 것>`으로 적고, 외부 시스템이 여럿이면 한 줄에 하나씩 하위 목록으로 적는다. 외부 시스템은 우리가 모델과 규칙을 정하지 못하는 시스템이다(다른 회사의 API, 다른 팀이 가진 시스템). 우리가 부르든 저쪽이 부르든(웹훅 등) 적는다. DB·메시지 큐처럼 우리가 운영하는 인프라는 외부가 아니다. `외부`가 없는 도메인은 내부 도메인이다(아래 "외부 접점").
- **규칙**(선택): 핵심 비즈니스 규칙 3~5개.
- **하지 않는 것**(선택): 헷갈리기 쉬운 이웃 책임과 그 책임을 맡는 도메인.
- **관계**: `도메인`이 `의존 대상`을 안다(부르거나, 그 이벤트를 구독하거나, 그 ID 타입이나 모델을 쓰거나, 그 데이터를 읽는다). 이벤트는 구독하는 쪽이 `도메인`이다. 한 쌍에는 한 방향만 둔다(아래 "관계의 방향"). 같은 방향에 방식이 여럿이면 한 줄에 `·`로 함께 적는다. 방식은 `ID 참조` · `동기 호출` · `이벤트` · `데이터 읽기` · `데이터 공유` 중에서 고른다. 데이터 읽기는 상대의 뷰나 테이블을 읽기 전용으로 읽는 것이다. 데이터 공유(두 도메인이 같은 테이블에 씀)는 경계 문제의 신호다.
- 도메인 맵(mermaid)은 선택이다. 쓴다면 관계 표를 원본으로 삼는다.

## 경계를 긋는 기준

위에 있는 기준이 우선한다.

1. **언어와 생명주기**: 같은 단어가 서로 다른 상태 전이를 가지면 다른 도메인이다. 필드 구성만 다르면 같은 도메인의 다른 뷰다.
   - 예: 판매의 주문(결제 완료 → 취소)과 물류의 주문(접수 → 출고)은 다른 도메인이다.
2. **데이터 소유**: 한 테이블에 쓰는 도메인은 하나다. 둘이 쓰면 경계를 다시 긋거나 한쪽을 읽기 전용으로 만든다.
3. **일관성**: 두 데이터가 잠시 어긋날 때 누가 무엇을 잘못하는지 구체적으로 나오면 같은 도메인에 둔다. 그렇지 않으면 나눠도 된다.
4. **변경 주체**: 변경마다 늘 두 팀의 승인이 필요하면 경계 후보다. 팀은 자주 바뀌므로 가장 약한 기준이다.

이렇게는 긋지 않는다.

- 실행 단위(api·batch·admin·worker)로 나누지 않는다. 같은 도메인을 드러내는 통로일 뿐이다.
- 테이블(엔티티) 하나마다 도메인 하나를 붙이지 않는다.
- "나중에 커질 것 같아서" 미리 나누지 않는다. 잘못 그은 경계를 지우는 것이 더 비싸다.

## 외부 접점

외부 시스템과 맞닿은 도메인(외부 접점 도메인)은 외부에 의존한다. 외부가 바뀌면 따라 바뀌고, 외부의 제약 때문에 우리가 원하는 만큼 깔끔하게 유지하지 못할 수 있다. 외부와 맞닿지 않은 내부 도메인은 우리 뜻대로 깔끔하게 유지할 수 있고, 기능 추가와 변경에도 유연하다. 그래서 둘을 정확히 구분하고, 외부의 복잡성을 외부 접점 도메인 안에 가둔다.

외부의 복잡성은 두 가지다.

- **외부 도메인의 복잡성**: 외부의 모델·용어·상태 코드·규칙(예: PG사의 승인 상태와 오류 코드).
- **외부 시스템의 복잡성**: 연동 중에 생기는 타임아웃·실패·장애, 재시도, 호출 제한, 늦게 오거나 중복으로 오는 응답(웹훅 등).

지키는 것:

- 외부 접점 도메인은 외부의 응답과 오류를 우리 모델로 바꿔서 내보낸다. 다른 도메인에는 우리 용어와 우리 상태(예: 결제 "확인 중")로만 말한다.
- 내부 도메인은 외부 시스템과 직접 주고받지 않고(부르지도, 호출받지도 않는다), 외부의 용어·타입·오류를 모른다. 외부가 필요하면 외부 접점 도메인을 거친다.
- 외부 연동이 크면(외부 시스템이 여럿이거나 재시도·대사 같은 연동 처리가 많으면) 연동만 맡는 도메인으로 떼어 내고, 우리 규칙은 내부 도메인에 둔다. 연동이 작으면 한 도메인 안에서 가장자리(연동 코드)에 모은다. 연동만 맡는 도메인은 대개 supporting이나 generic이고, 우리 규칙이 적어도 외부의 복잡성을 가두는 역할이 있으므로 「너무 작다」로 보지 않는다.
- 외부 접점은 분류와 다른 축이다. core 도메인도 외부와 맞닿을 수 있고, 그럴수록 외부의 복잡성이 도메인 모델에 스며들지 않게 한다.

## 관계의 방향

도메인 사이 의존은 한 방향이다. 두 도메인이 서로 의존하면 함께 바뀌고 따로 테스트할 수 없어 사실상 한 도메인이다. 셋 이상이 도는 순환도 같다.

반대쪽으로 알릴 일이 생기면 방향을 바꾸지 않고 이렇게 푼다.

- **이벤트**: 의존받는 쪽이 이벤트를 발행하고, 의존하는 쪽이 구독한다. 발행하는 쪽은 구독자를 모른다(예: payment가 결제 완료를 발행하고 order가 구독한다).
- **배치·조회**: 의존하는 쪽이 필요할 때 가져간다(예: order가 결제 상태를 확인하는 배치).

의존받는 쪽이 결과를 돌려주려고 상대의 식별자를 들어야 할 때가 있다(예: payment가 결제 완료 이벤트에 주문 번호를 싣는다). 이때는 상대의 ID 타입이나 모델을 쓰지 않고 불투명한 상관 키(문자열이나 자기 도메인의 타입)로만 들며, 그 의미를 해석하지 않는다. 이렇게 들고 있는 값은 의존으로 세지 않는다.

방향을 정하기 어려우면, 요청하고 응답을 받는 관계에서는 요청하는 쪽이, 알림 관계에서는 알림을 받는 쪽이 의존한다(예: order가 payment에 결제 승인을 요청한다, delivery가 order의 결제 완료 알림을 받는다).

## 잘못 그은 경계의 신호

**너무 크다 (분리를 검토한다)**
- 역할을 한 문장으로 말할 수 없거나, 기능이 서로 무관한 묶음으로 갈린다.
- 한 도메인 안에서 같은 단어가 다른 생명주기를 가진다. 상태 필드가 여러 개인 엔티티가 신호다.
- 서로 다른 이유와 주기로 바뀌는 코드가 섞여 있다.

**너무 작다 (병합을 검토한다)**
- 규칙 없는 CRUD 하나뿐이다.
- 이웃 도메인과 늘 함께 바뀐다.
- 유스케이스 하나를 처리하는 데 경계를 세 번 이상 넘나든다.

**관계가 어긋난다**
- 관계 표에 없는 의존(import·호출)이 있다.
- 다른 도메인의 객체를 필드로 직접 참조한다(ID로 참조해야 한다).
- 한 트랜잭션 안에서 두 도메인의 저장소를 쓴다.
- 두 도메인이 같은 테이블에 쓴다.
- 다른 도메인의 용어와 타입이 이 도메인의 모델에 새어 들어온다.
- 두 도메인이 서로 의존하거나(양방향), 셋 이상이 순환한다.

**외부 영향이 번진다**
- 내부 도메인이 외부 시스템과 직접 주고받는다(외부 API 클라이언트·SDK를 import하거나, 외부의 호출·웹훅을 직접 받는다).
- 외부의 용어·응답 타입·오류가 외부 접점 도메인 밖으로 새어 나간다.
- 외부 시스템과 맞닿은 코드가 있는데 그 도메인의 `외부`에 적혀 있지 않다.

**이름이 도메인 용어가 아니다**
- `common`·`util`·`core`·`etc`, 팀 이름, 실행 단위 이름. 도메인 이름을 붙일 수 없다면 도메인 경계가 아니다.

## 분류 기준

1. "경쟁사와 똑같이 만들면 무엇을 잃는가"에 구체적인 답이 나오면 **core**다.
2. 아니고, 요구의 80% 이상을 채우는 상용·오픈소스 제품 이름을 댈 수 있으며, 실패 비용(1시간 중단, 한 달간 조용히 틀린 데이터)이 낮으면 **generic**이다.
3. 그 밖은 **supporting**이다. 애매하면 supporting이다.

변경이 잦다는 이유만으로 core가 되지는 않는다.

분류는 코딩 컨벤션을 얼마나 엄격하게 적용할지 정한다. core·supporting에는 순수 도메인 모델과 컨벤션을 전부 적용하고, generic은 JPA 엔티티를 직접 써도 된다.

## 같은 이름, 다른 모델

모듈마다 책임이 다르면 같은 이름의 모델이 따로 있을 수 있다(조회 모듈의 `Player`와 동기화 모듈의 `Player`). DOMAIN.md의 "코드"에 그렇게 적혀 있으면 중복이 아니다.

**통합 기준**: 사본이 서로 어긋나면 곧 버그가 되는 비즈니스 규칙(예: 비율 계산의 분모)만 한곳으로 모은다. 우연히 닮은 코드는 중복을 유지하고 각각 테스트로 고정한다.
