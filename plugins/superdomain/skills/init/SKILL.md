# 도메인 경계 선언 초기화

이 스킬이 쓰는 `DOMAIN.md`는 이후 모든 superdomain 스킬이 읽는 도메인 SSOT다. 여기서 틀리게
적힌 것은 이후 스킬들이 성실하게 강제한다. 그래서 이 스킬에는 어길 수 없는 불변 두 가지가 있다.

1. **도메인 결정은 전부 사용자의 것이다.** 확정 대상의 정본 목록은 **5-e**이고, 그중 무엇도 사용자
   확인 없이 확정하지 않는다. 정보가 없으면 추측하지 말고 묻는다. 제안은 적극적으로 하고, 확인
   없는 **확정**만 하지 않는다(skill-protocol §4).
2. **파서가 거부하는 상태로 끝내지 않는다.** 파서 게이트는 선택이 아니고, **`DOMAIN.md`를 고칠
   때마다** 통과시킨다. 6단계에서 한 번(문서 작성 직후), 7-e에서 한 번(7-b가 생성 구역을 채운
   뒤). **완료 조건은 SSOT를 마지막으로 고친 뒤 받은 `OK:` 출력, 즉 7-e의 것이다** — 6단계의
   통과는 그 뒤의 편집으로 무효가 된다.

## 0. 위치 확정

산출물은 git 루트 아래 `docs/superdomain/`에 고정한다(skill-protocol §1). 모노레포여도 `DOMAIN.md`는
하나다 — 컨텍스트는 도메인 개념이라 프로젝트 소속과 무관하고, 프로젝트를 넘는 관계는 한 문서에서만
표현된다.

```bash
git rev-parse --show-toplevel
```

- 성공하면 그 경로가 작업 기준이다. cwd가 하위 디렉터리여도 여기로 올라와서 작업한다.
- git 저장소가 아니면 알리고 현재 디렉터리를 루트로 삼을지 확인한다. git submodule 등 멀티 레포
  워크스페이스는 v1 범위 밖임을 알린다.

배치 확인은 `${CLAUDE_PLUGIN_ROOT}/references/governance/skill-protocol.md` §3의 1~3을 따른다 —
배치 오류(exit 2)면 출력을 보여 주고 중단한다. 선언이 없는 경우(§3-4)가 이 스킬의 일이다.

## 1. 재초기화 확인

`docs/superdomain/DOMAIN.md`가 이미 있으면:

1. 파일을 읽고 선언된 프로젝트·컨텍스트를 표로 요약해 보여준다.
2. `git status --short docs/superdomain/DOMAIN.md`로 커밋되지 않은 변경이 있는지 확인한다. 있으면 덮어쓰면
   되돌릴 수 없다는 것을 먼저 알린다.
3. 세 선택지를 제시하고 **사용자가 고르게 한다.**
   - 그대로 두고 종료 (기본값)
   - 처음부터 다시 작성 — 기존 내용은 사라진다
   - 일부만 고치기 → 자리가 목적지를 정한다. 선언이 현실과 어긋난 것이면 `/superdomain:sync`,
     `### 관계` 표의 쌍이나 `- 분류:`·`- 패턴:` 하나만 바꾸는 것이면 `/superdomain:adr`, 표기만
     손보는 편집이면 사용자가 직접 고친 뒤 6단계의 파서 게이트만 실행해도 된다. **경계 재획정
     (컨텍스트 신설·병합·분리)과 `- 패키지:` 변경은 이 스킬이 받는다**(skill-protocol §9) — 경계는
     5-a부터, `- 패키지:`만이면 귀속 범위가 뒤집히므로 5-c부터 본다. 이때 6단계는 새로 쓰지 않고
     기존 `docs/superdomain/DOMAIN.md`를 제자리에서 고치며(원문과 변경안을 나란히 보여 주고 확정을
     받는다 — derived-artifacts §4), 7-c의 ADR은 이미 있으므로 건너뛴다. 그 밖은 안내하고 종료.

## 2. 거버넌스 후보 감지

**감지 단계에서는 아무것도 제외하지 않는다.** git 루트에서 빌드 파일을 넓게 훑는다.

```bash
find . -maxdepth 3 \
  \( -name .git -o -name node_modules -o -name build -o -name target \
     -o -name dist -o -name .gradle -o -name vendor -o -name .venv \) -prune -o \
  \( -name 'settings.gradle' -o -name 'settings.gradle.kts' -o -name 'pom.xml' \
     -o -name 'build.gradle' -o -name 'build.gradle.kts' -o -name 'package.json' \
     -o -name 'go.mod' -o -name 'Cargo.toml' -o -name 'pyproject.toml' \) -print
```

깊이가 모자라 보이면 `-maxdepth`를 늘린다. 후보가 하나도 안 나오면 3단계(그린필드)로 간다.

### 제안 기준은 kt/java 소스의 존재 하나뿐이다

이 플러그인의 결정적 검사는 `.kt`·`.java` 소스의 `package` 선언과 `import`만 읽는다(정본:
`scripts/check_imports.py`). 그런 소스가 없는 프로젝트는 선언할 수는 있어도 **격리 검사가 0건을
검사한 채 통과**하므로, 그 사실을 알고 넣는 것과 모르고 넣는 것은 다르다. 후보마다 센다 —
`find <후보 경로> -name build -prune -o \( -name '*.kt' -o -name '*.java' \) -print | wc -l`.
각 후보의 빌드 파일도 함께 열어 스택을 파악하고(Gradle Kotlin DSL·`kotlin("jvm")` → Kotlin,
`pom.xml`의 java 컴파일러 설정 → Java 등), 결과를 표로 전부 보여준다.

| 경로 | 감지 근거 | 추정 스택 | kt/java 소스 | 판정 |
|---|---|---|---|---|
| `backend` | `settings.gradle.kts` | Kotlin/Spring | 있음(412) | 제안 |
| `frontend` | `package.json` | Node | 0건 | 감지됨 — 검사 불가 |

지켜야 할 것:

- **스택 추측을 제외 판정에 쓰지 않는다.** "package.json이니까 프런트엔드라서 뺀다"는 금지다 —
  제외의 유일한 근거는 kt/java 소스 0건이고, 스택 추측은 안내 문구의 정확도에만 쓴다.
- **범위 외 후보를 숨기지 않는다.** 표에 남겨야 "왜 빠졌는지"를 안다. **최종 확정은 사용자다.**
- **소스 0건인 후보도 사용자가 원하면 넣을 수 있다.** 파서는 거부하지 않는다 — 선언이 코드보다
  먼저 서는 것은 정상 플로우다(3단계). 대신 둘을 함께 한다. ① 그 프로젝트의 컨텍스트는
  `check_imports.py`의 **`skipped[]`**(생략)로 빠져 격리 검사가 아무것도 보지 못한다고 알린다 —
  `[0건 경고]`가 아니다(skill-protocol §6).
  ② **`- 기본 패키지:`는 파서가 프로젝트마다 무조건 요구하므로 물어서 확정한다** — 비-JVM
  프로젝트에는 그런 값이 없고, 지어낸 값은 불변 1 위반이면서 **어떤 소스에도 매칭되지 않는
  프로젝트를 조용히 거버넌스에 올린다.** 그 사실을 `### 근거`에 남기고, 자리를 만드는 것은
  `/superdomain:sync`의 [패키지 생성]임을 안내한다.

## 3. 후보 0개 — 그린필드 설계 인터뷰

**오류가 아니다.** 코드가 없어도 `DOMAIN.md`는 설계서로 먼저 성립한다. 프로젝트 절의 `- 경로:`는
아직 없는 **예정 경로**로 선언할 수 있고, 그 자리를 실제 디렉터리로 만드는 것은
`/superdomain:sync`다.

**한 번에 하나씩 묻는다.** 답을 받을 때마다 지금까지 확정된 것을 두세 줄로 되짚어 준다.

1. **"이 시스템이 해결하는 문제를 한 문단으로 말해 주세요."** → 상단 자유 서술(개요)이 된다.
2. **"그 안에 서로 다른 용어를 쓰는 업무 영역이 있나요? 같은 단어를 서로 다른 뜻으로 쓰는
   곳은요?"** → 컨텍스트 **후보** 목록. 여기서 확정하지 않는다.
3. **"함께 바뀌는 것과 따로 바뀌는 것은 무엇인가요?"** → 경계 후보의 보강·병합 근거.
4. **"팀은 몇 개이고 각 영역을 누가 소유하나요?"** → 5-a 소유권 휴리스틱의 입력.
5. **"초기 규모와 12개월 안의 계획은 어떻게 되나요?"** → 경계를 지금 나눌지 미룰지의 입력.

이어서 프로젝트 절의 **필수 라벨 둘**을 채운다. 코드가 없으므로 둘 다 물어야 한다 — 프로젝트
이름과 **`- 경로:`**(단일 프로젝트면 `.`), 그리고 **`- 기본 패키지:`**(`com.acme` 형태). 뒤엣것은
컨텍스트 패키지의 규약 기본값 `{기본 패키지}.{컨텍스트}..`의 앞자리에 그대로 들어가므로 각
조각이 유효한 패키지 세그먼트여야 한다 — 아니면 파서가 거부한다.

### 도메인이 흐릿할 때

2번 질문에서 영역을 하나도 못 고르거나 용어가 계속 흔들리면, 경계를 억지로 긋지 말고 이벤트
스토밍을 먼저 권한다. 진행 규약의 정본은
`${CLAUDE_PLUGIN_ROOT}/references/knowledge/strategic/event-storming.md`이고 세션은
`/superdomain:model`의 스토밍 모드가 진행한다 — **이 스킬이 대신 진행하지 않는다.** 선택은
사용자에게 맡긴다.

- 도메인이 정리될 때까지 init을 중단하고 `/superdomain:model`을 권한다(권장). 스토밍이 내는
  것은 경계 **후보**이고 그것을 컨텍스트 선언으로 바꾸는 것은 돌아온 이 스킬의 일이다
  (`event-storming.md` R3 — 스토밍 세션은 `DOMAIN.md`를 고치지 않는다).
- 또는 컨텍스트 하나로 시작하고 경계가 드러나면 그때 나눈다. 이 선택은 근거 절에 기록한다.

그린필드는 4단계에 관측할 코드가 없다. 바로 **5단계로 간다.**

## 4. 기존 코드 스캔 — 패키지 구조에서 컨텍스트 후보를 읽는다

확정된 프로젝트마다 아래를 관측한다. **관측 → 추정 → 확인 질문** 순서를 지키고, 승인받지 않은
추정은 문서에 넣지 않는다.

```bash
find "<프로젝트 경로>" -type d \( \
     -name build -o -name out -o -name target -o -name .git -o -name .gradle \
  -o -name .idea -o -name .kotlin -o -name .settings -o -name .venv -o -name node_modules \
  -o -path '*/src/test*' -o -path '*/src/*Test' \) -prune \
  -o \( -name '*.kt' -o -name '*.java' \) -exec grep -hE '^[[:space:]]*package[[:space:]]' {} + \
  | sed -E 's/^[[:space:]]*package[[:space:]]+//; s/[;[:space:]]*$//' \
  | sort | uniq -c | sort -rn
```

**가지치기 목록은 `check_imports.py`의 `SKIP_DIRS`와 테스트 소스셋 규칙을 그대로 옮긴 것이다**
(`skills/sync/SKILL.md` 2-b와 같은 명령). 좁히면 이 관측만 보는 파일이 생겨 실제로 검사받는
코드와 후보 목록이 갈린다.

### 후보 추정 — 두 단계이고 둘 다 확인받는다

1. **`- 기본 패키지:` 후보** — 관측된 패키지들의 **최장 공통 접두**다(`com.acme.claim.domain`과
   `com.acme.billing.api` → `com.acme`). 갈래가 여럿이면 뭉뚱그리지 말고 다 보여주고 묻는다.
2. **컨텍스트 후보** — 그 기본 패키지 **바로 아래 세그먼트**들이다. 세그먼트마다 파일 수를 붙여
   표(`패키지 | 파일 수 | 추정`)로 제시하고, 어느 것이 컨텍스트이고 어느 것이 아닌지를 **사용자가
   확정한다** — 예: `com.acme.claim` 41개 → 컨텍스트 후보, `com.acme.config` 4개 → 조립·설정.

지켜야 할 것:

- **"패키지 하나 = 컨텍스트 하나"라고 단정하지 않는다.** 조립·설정·공용 유틸이 섞여 있고, 반대로
  한 컨텍스트가 여러 패키지에 흩어져 있을 수도 있다(후자는 5-c에서 `- 패키지:`로 적는다).
  **관측되지 않은 컨텍스트를 사용자가 말하면 그것도 후보다** — 코드가 아직 없을 뿐이다.
- **이름을 바꿔 제안하지 않는다.** `orders`를 관측했는데 `order`가 낫다고 보면 근거와 함께 말하되,
  이름과 실제 패키지가 갈리면 5-c에서 어떻게 이어 붙일지까지 함께 정한다.
- **소스를 하나도 읽지 못했으면 그 사실을 그대로 말한다.** 빈 관측 위에서 지어낸 후보가 선언이
  되면 이후 모든 스킬이 그것을 사실로 읽는다.

## 5. 경계·분류·패키지·관계 확정 — 인터뷰의 핵심

여기가 이 스킬이 존재하는 이유다. **이 시점에** `${CLAUDE_PLUGIN_ROOT}/references/INDEX.md`를
읽고 아래 단계가 지시하는 문서만 연다(경로 규칙은 skill-protocol §5).

### 5-a. 경계

`bounded-contexts.md`의 휴리스틱 H1~H4를 후보마다 **질문으로** 적용한다. 문서의 문항을 그대로
쓰고 이 스킬이 다시 쓰지 않는다. 휴리스틱이 서로 어긋나면 그 문서의 "휴리스틱이 서로 어긋날
때" 절을 따른다. 마지막에 R2의 "경계가 잘못 그어졌다는 신호" 체크리스트를 한 번 돌린다.

**컨텍스트 이름은 유효한 패키지 세그먼트여야 한다** — 영문자나 밑줄로 시작하고 그 뒤는
영문·숫자·밑줄이다. `- 패키지:`를 명시하지 않는 한 이 이름이 규약 기본값
`{기본 패키지}.{컨텍스트}..`의 세그먼트 자리에 그대로 들어가므로 `order-mgmt` 같은 이름은
**파서가 거부한다** — 어떤 소스에도 매칭되지 않는 패턴이 만들어져 그 컨텍스트의 격리 검사가
0건을 검사한 채 통과하기 때문이다. 하이픈이 든 업무 용어를 쓰려면 이름을 세그먼트로 바꿔 그
사실을 `### 근거`에 적거나, 5-c에서 `- 패키지:`로 실제 자리를 명시한다.

### 5-b. 분류

컨텍스트마다 `domain-classification.md`의 Q1~Q4를 묻고 종합 판정 절차를 따른다. 전부 끝나면
R2 리뷰 체크리스트를 돌린다 — 특히 "core가 절반을 넘는가"는 init에서 가장 흔한 과설계 신호다.

정규 값은 `core`·`supporting`·`generic` 셋뿐이고 이 라벨은 **필수**다. 투자·리뷰 강도의 근거이고
**기계 강제는 붙지 않는다**(`skills/adr/SKILL.md` ②와 같은 사실) — "일단 core"는 게이트를 통과
하지만 그 뒤 사람이 하는 검토를 통째로 무겁게 만든다.

### 5-c. 패키지 — 규약 기본값과 다른 컨텍스트만 명시한다

`- 패키지:`는 **선택 라벨**이고, 없으면 규약 기본값 `{기본 패키지}.{컨텍스트}..`가 그 컨텍스트의
자리다. **기본값으로 맞는 컨텍스트에는 이 라벨을 적지 않는다** — 같은 값을 손으로 다시 적으면
이름을 바꿀 때 두 곳이 갈리고, 그때 갈라진 쪽이 격리 검사의 귀속 범위가 된다. 명시가 필요한
경우는 셋이고, 4단계 관측과 대조해 **컨텍스트마다 한 번씩 확인한다.**

| 관측 | 처방 |
|---|---|
| 실제 패키지 세그먼트가 컨텍스트 이름과 다르다(`order` vs `...orders...`) | 이름을 바꾸거나 `- 패키지:`로 실제 자리를 적는다 |
| 한 컨텍스트가 여러 패키지에 산다 | `- 패키지:`에 쉼표로 나열한다 |
| 이름을 유효한 세그먼트로 만들 수 없다 | `- 패키지:`가 유일한 길이다(5-a) |

- **값은 접두 패턴이다.** `com.acme.claim`은 "그 패키지와 그 아래 전부"를 뜻하고, 파서가 후행
  점을 떼어 `com.acme.claim..`으로 정규화한다.
- **컨텍스트 패키지끼리 접두로 겹치면 파서가 거부한다.** 그 사이의 코드가 어느 컨텍스트 소유인지
  문서만으로 정해지지 않기 때문이다. 겹침은 표기 문제가 아니라 경계 문제이므로 5-a로 돌아간다.
- **잘못 좁히면 그 코드가 검사에서 통째로 사라진다.** 이 값이 격리 검사의 귀속 범위다(정본:
  `check_imports.py`의 `_owning_context`). 근거를 붙여 제안하되 확정은 사용자다.
- **프로젝트가 둘 이상이면 컨텍스트마다 `- 프로젝트:` 소속을 묻는다.** 파서가 강제하는 라벨이고,
  규약 기본값이 **그 프로젝트의 `기본 패키지`**로 만들어지므로 엉뚱한 쪽에 붙이면 격리 검사가
  0건을 매칭한 채 통과한다. 프로젝트가 하나뿐이면 파서가 자동 귀속하므로 적지 않는다.
- **코드를 옮기는 처방은 여기서 하지 않는다.** 선언과 디스크가 갈렸다는 관측은
  `/superdomain:sync`, 경계를 넘는 참조를 끊는 것은 `/superdomain:migrate`다.

### 5-d. 관계

컨텍스트가 둘 이상이면 서로 참조해야 하는 쌍이 있는지 묻는다. `### 관계` 표는 문서가 아니라
**컨텍스트 간 직접 참조의 allow-list**이므로, 적지 않은 쌍은 닫힌다. 유형 6종의 선택 기준과
`계약` 칸 작성 규범은 `context-mapping.md`가 정본이며, 언제 선언하지 않는지도 그 문서에 있다.

- **허용 단위는 쌍이고 방향이 없으며, 한 줄이 그 두 컨텍스트 사이의 격리 검사를 영구히 끈다**
  (skill-protocol §7). 그래서 여기서 여는 쌍도 7-d의 ADR 대상이고, 초기화 이후에 새 쌍을 여는
  진입점은 `/superdomain:adr`이다.
- **"지금 참조하고 있다"와 "참조해도 된다"는 다르다.** 4단계 관측에서 넘나드는 참조가 보여도 그것을
  근거로 표를 채우지 않는다 — 열지 않기로 한 쌍의 기존 참조는 6단계의 baseline 동결이 받는다.

### 5-e. 이 목록 중 하나라도 모델이 혼자 정했다면 되돌아간다

컨텍스트 목록과 이름 · 분류 · 패키지 · **소속 프로젝트** · **`- 패턴:`** · 관계 · 거버넌스 대상
프로젝트 — **불변 1과 6단계가 가리키는 정본 목록이 이것이다.** 확인 없이 들어간 값이 있으면 그
항목을 다시 묻는다. **소속 프로젝트와 `- 패턴:`은 파서가 값의 "옳음"까지 보지 않아 조용히 채워지기
쉽다** — 앞엣것은 프로젝트가 둘 이상이면 **필수**이고(5-c) 잘못 붙이면 규약 기본값이 엉뚱한
`기본 패키지`로 서며, 뒤엣것은 apply·review의 지식 문서 집합을 바꾼다(채택 결정은 `adr`이다).

## 6. DOMAIN.md 작성과 파서 게이트

**지금** `${CLAUDE_PLUGIN_ROOT}/references/governance/domain-template.md`를 읽는다. 스켈레톤을
뼈대로 쓰고, 라벨·표 사전으로 값 형식을 맞추고, 구현 세부(괄호 주석 처리, 표의 위치 규칙)를
확인한다. 라벨과 정규 값은 그 문서가 정본이므로 기억에 의존하지 않는다.

작성할 때 함께 지킬 것:

- **문서 상단의 템플릿 버전 마커**를 빠뜨리면 파서가 문서 전체를 거부한다.
- **생성 구역 안내를 문서에 남긴다.** 마커로 감싼 구역은 스킬이 갱신하고 그 밖은 자유 서술이라는
  사실을 한 문장으로 적어, 읽는 사람이 어디를 손대면 안 되는지 알게 한다.
- **각 컨텍스트의 `### 근거`에 한 문장 이상**을 남긴다. 왜 이 경계이고 왜 이 분류인지를 적지
  않으면 다음 세션에 다시 추측된다.
- **템플릿이 표현하지 못하는 것이 나오면 필드를 발명하지 않는다.** 표현할 수 없다는 사실을 말하고
  내용은 자유 서술로 남긴다. 구 템플릿에서 넘어온 퇴역 라벨은 파서가 **명시 거부**한다(정본:
  `scripts/parse_domain.py`의 `RETIRED_LABELS`) — 조용히 무시되지 않는다.
- **그린필드에서는 `- 경로:`가 예정 경로다.** 아직 없는 경로도 파서가 허용한다.

### 파서 게이트 (건너뛰지 않는다)

git 루트에서 실행한다. 이것이 `DOMAIN.md`의 유일한 해석기다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/parse_domain.py" docs/superdomain/DOMAIN.md
```

- 실패하면 `<파일>:<줄>: <메시지>`로 나오고 exit 1이다. 지목된 줄을 고치고 **다시 실행**한다(exit
  2는 사용법 오류 — 인자를 고친다). 통과 출력은 `OK: 프로젝트 N, 컨텍스트 M`이고, **두 수가 의도한
  개수와 같은지 확인한다** — 헤딩 오타는 오류가 아니라 "없는 섹션"이 되어 조용히 개수를 줄인다.
- 문서가 "맞아 보인다"는 이유로 생략하지 않는다 — 통과한 적 없는 문서가 다음 스킬들의 SSOT가 된다.

파서가 거부할 때 무엇을 고쳐도 되는지는
`${CLAUDE_PLUGIN_ROOT}/references/governance/derived-artifacts.md` §4다. 이 스킬에서 '사용자가
결정한 값'의 목록은 5-e다.

### baseline 동결 — 실측한 뒤 사용자에게 묻는다

게이트를 통과했으면 지금의 컨텍스트 격리 위반을 **실측한다.** 그린필드에는 잴 것이 없으므로 이
절을 건너뛴다. exit 코드가 세 갈래를 가른다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_imports.py" docs/superdomain/DOMAIN.md --json
```

| exit | 뜻 | 처분 |
|---|---|---|
| 2 | 해석 불가 — 검사를 세우지 못했다 | 동결하지 않는다. stderr의 `경로:라인: 메시지`를 고치고 다시 실행 |
| 0 | 위반 0건 | **파일을 만들지 않는다.** 빈 baseline은 래칫이 있는 척하는 상태라 더 나쁘다 |
| 1 | 위반 N건 | 아래 질문으로 간다 |

- 넷(`zero_match`·`skipped`·`unreadable`·`ambiguous_package`)을 그대로 보고한다(skill-protocol §6).
- **exit 1이면 동결 여부를 묻는다. 이 결정은 모델이 하지 않는다.** 총 건수·컨텍스트 쌍별
  분포·대상 파일 요약을 먼저 제시하고 두 갈래를 나란히 놓는다.

| 선택 | 뜻 |
|---|---|
| **동결한다** | 지금의 위반이 `[기존 부채]`로 강등돼 exit 코드에서 빠지고, 그 뒤의 새 위반만 blocker가 된다. 갚는 경로는 `/superdomain:migrate` 하나다 |
| **동결하지 않는다** | 지금부터 이 위반들이 전부 blocker다. 경계를 방금 그은 브라운필드에서는 첫 리뷰부터 빨강이 된다 |

- **순서는 하나뿐이다 — 요약 제시 → 명시 승인 → 실행.** "동결하겠습니다"는 통보지 확인이 아니다.
  **"나머지는 알아서 확정해 달라"는 진행 속도의 요청이지 확정 권한의 위임이
  아니므로**(불변 1·skill-protocol §4) 그 답을 받아도 동결 승인만은 따로 받는다 — 이후 모든
  판정의 기준선을 정하는 결정이다.
- 승인받았으면 `violations[]`의 각 항목을 `{"rule": <rule_id>, "path": <path>}` 한 줄 JSON으로
  바꿔 (rule, path)로 중복을 없애고 그 순서로 정렬해 **`docs/superdomain/state/baseline.jsonl`**에 쓴다.
  출력에 없는 항목은 지어내지 않고 `note`는 넣지 않는다(메시지는 재실행으로 다시 얻는다).
  **`path`는 git 루트 기준 상대경로이고 구분자는 `/`다** — 로더가 위반의 표시 경로와 글자 그대로
  대조하므로, 표기가 어긋난 줄은 아무것도 강등하지 못한 채 항목 수만 채운다.
- **이미 `docs/superdomain/state/baseline.jsonl`이 있으면 덮어쓰지 않는다.** 재초기화 실행의 `violations[]`는
  그 baseline이 이미 걸러 낸 목록이라 그대로 쓰면 부채가 조용히 줄어든다 — 래칫이 거꾸로 도는
  것이다. 파일은 그대로 두고 현재 건수만 보고한다(축소는 migrate만).
- **승인 전에는 동결을 완료형으로 적지 않는다.** `### 근거`를 포함해 "위반 전량을 동결했다"류는
  파일이 실제로 생긴 뒤에 쓴다 — 거부되면 문서만 거짓말을 한 채 남는다.
- 만든 뒤 **한계 둘을 그대로 말하고 근거 절에도 남긴다** — skill-protocol §6의 한계(부채 매칭:
  같은 파일의 **새 위반도 부채로 흡수된다**)와 한계(검사 범위: 같은 패키지 안의 참조와 FQN은 세지
  않았으니 **동결 목록에 없는 위반이 있을 수 있다**)다.
- **init은 baseline을 줄이지 않는다.** 축소 경로는 `/superdomain:migrate` 하나뿐이다.

### 게이트가 잡지 않는 것

게이트 통과는 "선언이 해석된다"는 뜻이지 "선언이 옳다"는 뜻이 아니다 — 정규 값을 지킨 오답은
기계가 잡지 못한다. 특히 **이름과 실제 패키지의 어긋남**은 파서도 격리 검사도 오류로 만들지
않는다. 그 자리를 보는 것은 `/superdomain:sync`의 대조 축이다.

### 7-d. 그 밖의 ADR — 이번 초기화의 실질적 결정

ADR을 쓸지 말지는 `adr-template.md` §1의 기준으로 판단한다. 해당하지 않으면 만들지 않는다 —
빈 ADR을 양산하면 아무도 ADR을 읽지 않게 된다. 전형적으로 해당하는 것:

- **초기화 시점에 연 관계 쌍** — 한 줄이 그 두 컨텍스트 사이의 격리 검사를 영구히 끄므로 ADR이
  필수다(skill-protocol §7)
- baseline 동결 결정(건수와 그때의 판단), 규약 기본값을 벗어난 `- 패키지:` 선언
- 경계를 지금 나누지 않고 컨텍스트 하나로 출발하기로 한 결정

**기각한 대안은 인터뷰에서 사용자가 실제로 검토하고 물리친 것만 적는다.** 그럴듯한 대안을
지어내 칸을 채우면 그것은 ADR이 아니라 날조된 결정 기록이고, 반년 뒤 "그때 그걸 봤다"는 거짓
근거로 쓰인다. 대안이 오간 적이 없다면 그 결정은 애초에 ADR 대상이 아니다(`adr-template.md` §1).

### 7-e. 파서 재검증 (7-b가 SSOT를 다시 고쳤다)

`derived-artifacts.md` §5-4의 마지막 게이트다. 6단계의 게이트는 7-b **이전**의 문서를 통과시킨
것이다. 7-b가 `DOMAIN.md`에 마커와 mermaid 블록을 삽입했으므로 그때 통과한 문서는 더 이상 존재하지
않는다. git 루트에서 한 번 더 돌린다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/parse_domain.py" docs/superdomain/DOMAIN.md
```

프로젝트·컨텍스트 개수가 6단계와 **같아야 한다.** 달라졌다면 삽입한 블록이 섹션 구조를 건드린
것이다(알 수 없는 `##` 헤딩은 열려 있던 섹션을 닫는다). 이 실행의 `OK:` 출력이 이 스킬의 완료
조건이다. 실패·불일치를 고칠 때도 `derived-artifacts.md` §4가 그대로 적용된다.

## 8. 마무리

1. **CLAUDE.md 한 줄 추가 제안(선택).** 승인받은 뒤에만 편집하고, 파일이 없으면 새로 만들지 말고
   제안만 한다.
   > 도메인 경계: `docs/superdomain/DOMAIN.md`를 따른다. 요약은 `docs/superdomain/summary.md`.
2. **git pre-commit 훅은 이 스킬이 설치하지 않는다.** 결정적 검사(`parse_domain.py`·
   `check_imports.py`·`check_invariants.py`)는 실재하지만 훅 설치는 사용자의 결정이므로 그런
   장치를 둘 수 있다는 안내까지만 한다.
3. **다음 단계를 알려준다.** 불변식·애그리거트를 말로 정리하는 것은 `/superdomain:model`,
   변경 검토는 `/superdomain:review`, 선언만 있고 패키지 자리가 없으면 `/superdomain:sync`,
   동결했으면 갚는 것은 `/superdomain:migrate`, 7-d에서 미룬 결정은 `/superdomain:adr`이
   받는다. 실행 여부는 사용자가 정한다.
4. **커밋은 사용자가 한다.** 명령만 제안한다. 실제로 쓴 파일만 넣는다.
   ```bash
   git add docs/superdomain/DOMAIN.md docs/superdomain/summary.md docs/superdomain/adr
   git commit -m "chore: 도메인 경계 선언 초기화"
   ```
5. **결과 보고** — 생성·수정한 파일 목록, 확정된 컨텍스트 표(분류·패키지·관계), 범위 외로 표시한
   후보, 동결한 baseline 건수(또는 동결하지 않기로 한 결정과 그때의 위반 건수), 검사가 판정하지
   못한 범위(`zero_match`·`skipped`·`unreadable`·`ambiguous_package`), 미룬 것(훅).

## 하지 말 것

- **사용자 대신 도메인 결정을 내리는 것.** 5-e의 목록을 확인 없이 채웠다면 그 자체가 실패다.
- **파서 실패 상태로 종료하는 것.** SSOT를 마지막으로 고친 뒤(= 7-e) 받은 `OK:` 출력이 완료
  조건이고, 6단계의 통과는 그 뒤 편집으로 무효가 된다.
- **게이트를 통과시키려고 사용자가 결정한 값을 바꾸는 것.** 고쳐도 되는 것은 형식뿐이다.
- **관측된 참조를 근거로 `### 관계` 표를 채우는 것.** "지금 참조하고 있다"는 "참조해도 된다"가
  아니다 — 그 한 줄이 격리 검사를 영구히 끈다.
- **`knowledge/`를 통째로 또는 디렉터리 단위로 읽는 것.** 언제나 INDEX 경유 선별 로드다.
- **실측 없이 `baseline.jsonl`을 쓰는 것.** 빈 파일도, 지어낸 항목도 안 된다 — 근거는 방금 돌린
  `check_imports`의 출력 하나뿐이다. **동결 여부를 모델이 정하는 것**, 이미 있는 baseline을
  덮어써 부채를 조용히 줄이는 것도 같다.
- **검사가 판정하지 못한 범위를 "위반 없음"으로 보고하는 것.** `zero_match`·`skipped`·
  `unreadable`·`ambiguous_package`는 침묵이지 통과가 아니다.
- **템플릿에 없는 라벨·필드를 발명하는 것.** 표현할 수 없으면 그 사실을 말하고 자유 서술로 남긴다.
- **스택 추측으로 거버넌스 대상을 제외하는 것**(근거는 kt/java 소스 0건뿐), **`- 기본 패키지:`를
  지어내는 것**, **관측 없이 컨텍스트 후보를 지어내는 것.** 빈 관측 위에 세운 선언을 이후 모든
  스킬이 사실로 읽는다.
- **파생물을 직접 고치도록 유도하는 것**(항상 SSOT를 고치고 다시 만든다), **`docs/superdomain/summary.md`
  를 `docs/superdomain/contexts/` 안에 두는 것**(매 실행 거짓 경고).
- **실재하지 않는 스킬·스크립트를 안내하는 것.** `skills/` 아래 이름과 `scripts/`의 파일명은
  기억이 아니라 확인으로 댄다.
- **산출물을 하위 디렉터리에 만드는 것.** 산출물은 git 루트의 `docs/superdomain/` 아래다.
