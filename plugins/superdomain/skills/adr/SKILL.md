# 도메인 결정 기록 (ADR)

이 스킬은 결정을 내리지 않는다. 결정은 인터뷰·모델링·리뷰에서 이미 났고, 여기서 하는 일은 그
결정을 **반년 뒤에도 근거를 되짚을 수 있는 형태**로 고정하고, 결정이 SSOT를 바꾸면 그 편집 자리를
짚어 주는 것이다. 형식은 정본이 정하고 이 스킬은 절차만 갖는다. 그래서 불변이 셋이다.

1. **확정은 사용자의 것이다.** `proposed` → `accepted` 전이, supersede 판정, 그리고 문서로
   남길지 말지 — 무엇도 확인 없이 확정하지 않는다. 이것은 판단을 아끼라는 뜻이 **아니다.**
   관측과 대화를 근거로 제목 문장·대안·결과를 **적극적으로 제안**하는 것이 이 스킬의 인터뷰이고,
   금지되는 것은 확인 없는 **확정** 하나뿐이다.
2. **논의되지 않은 것을 적지 않는다.** 특히 「검토한 대안」이다. 그럴듯한 대안을 지어내 표를
   채우면 그것은 결정 기록이 아니라 **날조된 근거**이고, 반년 뒤 "그건 그때 이미 봤다"는 거짓
   종결로 쓰인다. 없으면 없다고 적는다(3-b).
3. **과거를 고쳐 쓰지 않는다.** `accepted` 문서의 본문은 동결이다. 결정이 바뀌었으면 새 ADR을
   쓰고 옛 문서를 `superseded`로 만든다(7단계). 오타·깨진 링크만 예외다.

## 형식의 정본

`${CLAUDE_PLUGIN_ROOT}/references/governance/adr-template.md`가 형식의 정본이다 — 쓸지 말지의
기준(§1), 파일명(§2), 상태 생명주기(§3), 템플릿 본문(§4), supersede와 `조정됨` 마커(§5), 좋은
ADR의 조건(§6), 선언과의 연결(§7). **이 스킬은 그 내용을 복제하지 않는다** — 각 단계가 지시하는
시점에 그 절을 읽는다. 정본이 바뀌면 이 스킬은 고치지 않아도 맞는다. 아래의 §N은 전부 이 문서를
가리킨다. `references/knowledge/`는 읽지 않는다 — 결정의 재료는 사용자와 저장소에 있다.

## 0. 위치·게이트·선언 로드

### 0-a. 게이트

```bash
git rev-parse --show-toplevel
```

ADR은 **저장소 하나에 한 벌**이다 — 프로젝트가 여럿이어도 `docs/superdomain/adr/` 하나에 모인다.
결정은 저장소 단위로 읽히고, 디렉터리가 흩어지면 "어디까지 봐야 결정을 다 본 것인가"의 답이
사람마다 달라진다. 하위 디렉터리에서 시작했어도 git 루트로 올라와서 작업한다. 그 경로에
`DOMAIN.md`가 없으면 아래를 알리고 **중단**한다.

> superdomain이 초기화되지 않았습니다. `/superdomain:init`으로 도메인 경계 선언을 먼저 세우세요.

### 0-b. 선언 로드 — 있는지 보는 것이 아니라 읽는 것이다

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/parse_domain.py" docs/superdomain/DOMAIN.md
```

**exit 0**이면 선언이 해석 가능하다는 뜻이고, 그 다음 `DOMAIN.md`를 직접 읽어 셋을 만든다 —
프로젝트는 `## 프로젝트: <이름>` 헤딩, 컨텍스트는 `## 컨텍스트: <이름>` 헤딩, 그리고 컨텍스트마다
`- 분류:`·`- 패키지:`와 `### 관계` 표의 행(상대·유형·계약). 이 셋이 5단계 `- 관련:` 검증과 8단계
처방의 재료다. **이 스킬은 파서의 게이트 결과만 쓰고 선언을 고치지 않는다.**

**exit 1은 해석 오류**다(**exit 2는 사용법 오류** — 인자를 고쳐 다시 돌린다). `check_imports.py`와
뜻이 갈리는 숫자는 **1**이다 — 그쪽의 1은 "위반 발견"이라는 정상 판정이고 해석 실패는 2로 나간다.
2가 사용법 오류인 것은 두 스크립트가 같다. 오류 줄(`경로:라인: 메시지`)을 그대로 보여주되 **중단하지는
않는다** — 깨진 선언을 어떻게 할지 정한 결정이야말로 ADR 감이다. 대신 이번 실행 전체를 **신뢰
불가**로 표시한다: 해석되지 않은 문서에서 읽은 이름은 "실재한다"는 근거가 되지 못하는 상태이고,
그 상태의 하류 처분은 5단계와 8단계가 정한다.

## 1. 모드 판정

요청에서 하나를 고른다. 흐릿하면 관측(어떤 파일이 언급됐는지, 그 문서의 현재 상태가 무엇인지)을
근거로 하나를 제안하고 확인받는다.

| 모드 | 들어오는 말 | 진행 |
|---|---|---|
| **신규** | "이 결정 ADR로", "결정 기록 남겨줘" | 2 → 3 → 4 → 5 |
| **승인** | "그 ADR 승인", "`open-claim-admin-pair` accepted로" | 6 |
| **대체·조정** | "`open-claim-admin-pair`를 대체", "supersede", "그 결정 뒤집자" | 3 → 4 → 5 → 7 |
| **선언 연결만** | "이 ADR을 선언에 반영하려면?" | 8 |

`git status --short docs/superdomain/adr/`로 작업 중인 초안이 있는지 함께 본다.

## 2. 신규 — 쓸 것인가부터 판정한다

`adr-template.md` **§1을 지금 읽고** 그 체크리스트로 대조한다. 해당하지 않으면 만들지 않는다 —
빈 ADR을 양산하면 아무도 ADR을 읽지 않게 되고, 그러면 진짜 결정도 함께 묻힌다. 대신 갈 곳을
말한다: 취향 수준 컨벤션은 `docs/superdomain/conventions/`, 코드를 읽으면 자명한 것은 아무 데도.

판정 결과를 근거와 함께 제시하고 확인받는다. **판단이 서지 않으면 쓰는 쪽**이다(§1 마지막 줄).

**한 ADR에 한 결정.** 인터뷰에서 결정이 둘로 갈라지면 문서도 둘이다. 한 문서에 묶으면 나중에
한쪽만 뒤집힐 때 supersede가 문서 단위로 성립하지 않는다(§5).

## 3. 신규 — 인터뷰

한 번에 하나씩 묻고 받은 답을 즉시 초안에 반영해 보여준다. **관측을 근거로 초안 문장을 먼저
제안**하고 사용자가 고치게 하는 편이 빈 질문보다 빠르다 — 다만 확정은 사용자다.

| 항목 | 묻는 것 | 실패 신호 |
|---|---|---|
| 제목 | 이 결정을 한 문장 **결정문**으로 (§6) | "인증 방식 검토" 같은 명사구 |
| 문제 상황 | 무엇이 이 결정을 강제했는가 — 제약·요구·관측된 문제 | 배경 설명이 본문의 절반을 넘김 |
| 결정 | 무엇을 하기로 했는가 — 능동태·단정형 | "~를 고려한다" |
| 검토한 대안 | 실제로 오간 대안과 기각 이유 | 3-b |
| 결과 | 긍정 / 부정 / 후속 작업 | 부정 칸이 빔 |

- **부정적 결과가 비면 한 번 더 묻는다**(§6). 모든 아키텍처 결정에는 대가가 있고, 빈 칸은
  검토가 부족했다는 신호다. 그래도 없다고 하면 사용자의 답을 그대로 적고 보고에 남긴다 —
  없는 대가를 지어내는 것은 대안을 지어내는 것과 같은 실패다.
- **길이는 한 화면(40~60줄)**(§6). 넘치는 배경은 `knowledge/`나 domain 문서로 보내고 링크한다.
- 도메인 모델(불변식·애그리거트) 정리는 `/superdomain:model`이다. **선언이 바뀌는 결정이면
  여기서 끝나지 않는다** — `- 분류:`·`- 패키지:`·`- 패턴:`·`### 관계` 표 넷 중 어느 자리를 고쳐야
  하는지 짚는 것은 **이 스킬의 8단계**이고, 편집은 사용자가 한다. `/superdomain:init`으로
  보내는 것은 컨텍스트를 새로 세우거나 합쳐 **경계 자체를 다시 긋는** 경우뿐이다(§8 ②).

### 3-b. 검토한 대안 — 이 스킬이 가장 쉽게 실패하는 곳

표에 들어갈 자격은 하나다: **그 대안이 실제로 검토되고 기각되었을 것.**

- 사용자가 말한 대안, 또는 **모델이 제안한 대안을 사용자가 "그것도 봤다"고 확인한 것**만 적는다.
  대안을 제안하는 것 자체는 인터뷰다(불변 1) — 확인 없이 표에 넣는 것이 금지다.
- **기각 이유에도 같은 규율이 걸린다.** 대안 이름만 사용자에게서 받고 이유를 그럴듯하게 채우면
  그것도 날조다. 이유를 모르면 이유를 묻는다.
- 대안이 없으면 표를 지우고 이 한 줄로 대신한다.

  ```markdown
  **검토한 대안** — 검토한 대안 없음.
  ```

- 그리고 되짚는다. 대안이 없었다는 것은 보통 ADR을 쓸 일이 아니라는 뜻이다(§1·§6). **예외는
  하나** — `### 관계` 표에 **새 쌍을 여는 결정**은 대안이 없어도 ADR이 필수다. 쌍이 열리면 두
  컨텍스트 사이의 격리 검사가 그 자리에서 영구히 꺼지므로, 무엇을 대가로 열었는지가 문서에 남아
  있어야 한다. 해당하지 않으면 2단계 판정을 사용자와 다시 확인한다.

## 4. 파일명 (오늘 날짜 + slug)

```bash
date +%F
ls docs/superdomain/adr/ 2>/dev/null | sort
```

**채번하지 않는다**(§2). 파일명은 오늘 날짜가 정하므로 디렉터리를 세어 다음 값을 구하는 단계가
없고, 그래서 두 브랜치가 같은 이름을 집는 일도 없다. **그래도 목록은 본다** — 이름을 정하는 데
필요해서가 아니라, 같은 결정을 두 번 쓰고 있지는 않은지와 이 디렉터리가 어떤 상태인지는 목록에서만
보이기 때문이다.

- **새 파일명 = `date +%F`의 출력 + `-` + slug**(§2). 결정이 어제 났더라도 기준은 문서를 쓰는
  오늘이고, 머리의 `- 날짜:`(5단계)와 같은 값이다.
- **같은 날짜에 같은 slug가 이미 있으면 멈추고 알린다.** 같은 결정을 두 번 쓰고 있거나 slug가 너무
  뭉뚱그려졌다는 뜻이고, 어느 쪽인지는 사용자만 안다.
- **ADR이 아닌 파일이 섞여 있으면 고지한다.** 다음 파일명을 오염시키지는 않지만 `ls`로 결정을
  훑는 사람을 헷갈리게 하고, 이 디렉터리에 무엇이 사는지는 사용자만 안다.
- **목록이 비면** `docs/superdomain/adr/`가 없거나 비었다는 뜻이다. 그대로 만들되, init이 만드는
  `*-record-architecture-decisions.md`가 없다는 사실을 함께 알린다.
- 한 세션에서 ADR을 여럿 만들면 만들 때마다 다시 관측한다.

`slug`는 소문자 영문 kebab-case다(§2). 제목이 한국어면 요지를 영문으로 줄여 **제안하고
확인받는다** — 파일명은 나중에 바꾸지 않고, 다른 문서가 **이 문자열로** 이 결정을 가리키게
되므로(7-c) 읽고 무슨 결정인지 알 만큼 구체적으로 짓는다. `misc`·`fix`처럼 무엇이든 될 수 있는
slug는 나중에 그 참조를 찾을 수 없게 만든다.

## 5. 신규 — 파일 작성

`adr-template.md` **§4의 템플릿을 그대로** 채운다. 절 이름·표 형태를 바꾸지 않는다 — **예외는
3-b 하나다.** 검토한 대안이 없을 때 대안 표를 지우고 "검토한 대안 없음" 한 줄로 대신하는 것은
형태를 무너뜨린 것이 아니라 3-b가 정한 처분이다.

- `- 상태: proposed` — 신규는 언제나 여기서 시작한다(§3). 예외는 supersede로 들어온 새 ADR로,
  그 경우는 7단계가 정한다.
- `- 날짜:` 는 `date +%F` — 4단계에서 파일명에 쓴 날짜와 같은 값이다.
- `- 관련:` 은 컨텍스트 이름·프로젝트 이름·다른 ADR 파일명. **0-b에서 로드한 선언에 실재하는
  이름만 적는다** — 목록에 없으면 지어내지 말고 그 목록을 보여준 뒤 확인받는다. 이번 결정으로
  비로소 생길 컨텍스트라면 `관련`이 아니라 본문에 쓴다(선언하는 것은 init의 일이다). 적을 것이
  없으면 **줄째로 생략**한다.
- **생성물 헤더(`<!-- GENERATED … -->`)를 넣지 않는다.** ADR은 파생물이 아니라 사람이 쓰는
  기록물이다.

**0-b가 신뢰 불가로 표시한 실행이면 목록에 있는 이름이라도 확인을 받는다.** 그 목록은 해석에
실패한 문서에서 나왔으므로 "실재한다"는 근거가 되지 못한다 — 이름을 보여주고 확인을 받되, 답이
없으면 `관련` 줄을 비운다.

쓰기 전에 **초안 전문을 보여주고 확정받는다.** 확정 후 `docs/superdomain/adr/yyyy-MM-dd-slug.md`로
저장하고, 결정이 선언 변경을 함의하는지 8단계로 이어간다.

## 6. 승인 — `proposed` → `accepted`

전이는 사용자의 명시적 확정으로만 일어난다. "읽어 봤다"는 승인이 아니다. 그 ADR을 `accepted`로
올릴지 **묻고 답을 받는다.** 바꾸는 것은 `- 상태:` 한 줄뿐이다.

- **`proposed` 문서의 본문은 고쳐도 된다.** 동결은 `accepted`가 되는 순간부터다(§3). 승인 직전이
  본문을 다듬을 마지막 기회이므로, 부정적 결과 칸과 대안 표를 한 번 더 같이 본다.
- **철회**는 문서 삭제다(§3). 확정을 받고 지우되, 그 파일명은 다시 쓰지 않는다(§2).
- 이미 `superseded`인 문서는 종착이다. 되살리려면 새 ADR을 쓴다.

> **`/superdomain:evolve`가 신호에서 만드는 `proposed` 초안도 승격 경로는 이 단계 그대로다.**
> 그 스킬은 `accepted` 전이를 하지 않는다 — 상태를 올리는 자리는 여기 하나다.

## 7. 대체와 조정

### 7-a. 판정 — supersede인가 조정인가

옛 결정이 **전면 무효**면 supersede다. **부분만 바뀌었으면 supersede가 아니다**(§5) — 상태는
문서 단위이지 문장 단위가 아니다. 어느 쪽인지 근거와 함께 제안하고 확인받는다.

- **부분 조정이면**: 새 ADR 본문에 "`<옛 ADR 파일명>`의 X 부분을 조정한다"고 쓰고, 옛 문서는
  `accepted`로 둔 채 **머리(메타데이터)에만** `- 조정됨: [<새 ADR 파일명>](<새 ADR 파일명>.md)` 한
  줄을 추가한다. 메타데이터라 본문 동결에 걸리지 않는다(§5). 조정이 쌓이면 줄을 나열한다.
  **이 줄을 빠뜨리지 않는다** —
  옛 문서에 먼저 도착한 독자가 조정된 부분을 모른 채 결정을 적용하는 것이 이 줄이 막는 상황이다.
- 옛 문서가 이미 `superseded`면 그것을 또 대체하지 않는다. `대체됨:` 링크를 따라가 현재 유효한
  문서를 찾고, 그것을 대상으로 7-a를 다시 판정한다.

### 7-b. 양방향 링크 — 한쪽만 걸고 끝내지 않는다

`adr-template.md` **§5의 체크리스트를 지금 읽고** 실행한다. **단 다섯째 항목(옛 ADR을 참조하던
문서를 새 파일명으로 갱신)은 여기서 하지 않는다** — 7-c가 대신하고 이유도 거기 있다. 나머지 요지는
셋이다.

- 새 ADR은 `- 상태: accepted`로 쓰고 `- 대체함: [<옛 ADR 파일명>](<옛 ADR 파일명>.md)`을 넣는다 —
  신규가 `proposed`로 출발하는 것(§3·§4)과 달리 여기서만 `accepted`다. **이 상태도 확정을 받고
  쓴다**(불변 1).
- 옛 ADR은 `- 상태: superseded`로 바꾸고 `- 대체됨: [<새 ADR 파일명>](<새 ADR 파일명>.md)`을 넣는다.
- **옛 ADR의 본문은 한 글자도 고치지 않는다.** 손대는 곳은 머리뿐이다.

어느 문서에 먼저 도착한 독자도 현재 유효한 결정에 닿아야 한다. 한쪽 링크만 걸린 상태는 절반이
아니라 실패다 — 옛 문서를 읽은 사람이 폐기된 결정을 그대로 적용하게 된다. 다른 ADR 본문이 옛
파일명을 인용하고 있어도 **고치지 않는다** — 그 문서들도 `accepted`이고, 방금 건 양방향 링크가
독자를 현재 결정으로 데려간다.

### 7-c. 옛 ADR을 참조하던 곳 — 재검토를 안내한다

여기가 근거가 낡는 지점이다. §5 체크리스트의 "참조 문서를 새 파일명으로 갱신한다" 항목은 이
스킬에서 **안내로 처리한다** — 새 결정이 그 참조의 근거 자체를 없앴을 수 있고, 그때 필요한 것은
갱신이 아니라 제거이기 때문이다. 옛 ADR을 가리키는 곳을 전부 찾는다.

**slug 하나가 세 표기를 전부 덮는다.** 링크도 `- 관련:`도 자유 서술도 파일명을 쓰고, 파일명은
slug를 포함한다 — 날짜를 떼고 slug만 적은 서술까지 같은 문자열로 걸린다. 아래 예시에서 옛 ADR은
`2026-03-11-open-claim-admin-pair.md`다.

| 무엇이 만드는가 | 문자열 모양 | 어디에 |
|---|---|---|
| `- 대체함:` · `- 대체됨:` · `- 조정됨:` 링크(§5) | `[2026-03-11-open-claim-admin-pair](2026-03-11-open-claim-admin-pair.md)` | 다른 ADR의 머리 |
| `- 관련:`(§4) | `2026-03-11-open-claim-admin-pair` — **확장자가 없다** | 다른 ADR의 머리 |
| 자유 서술의 임의 표기 | 파일명 그대로, 또는 **slug만**(`open-claim-admin-pair`) | `DOMAIN.md`의 `### 근거`, `### 관계` 표의 `계약` 칸, domain 문서, 다른 ADR의 본문 |

```bash
grep -rnF "open-claim-admin-pair" DOMAIN.md docs/
```

- **날짜가 아니라 slug로 찾는다.** 날짜를 떼고 slug만 적은 서술("open-claim-admin-pair 결정에서")도
  같은 명령에 걸린다. 대신 slug가 흔한 말이면 무관한 줄이, 같은 slug를 쓰는 다른 날짜의 ADR이
  있으면 그것도 함께 걸리므로 **히트는 날짜 접두까지 보고 눈으로 갈라낸다.**
- **0건으로 끝났다면 패턴이 좁았던 것은 아닌지 먼저 의심한다.** slug도 파일명도 쓰지 않고 결정의
  요지로만 인용한 문장은 어느 grep에도 걸리지 않는다.
- 방금 7-b가 건 신·구 링크는 **이 목록에서 뺀다.** 그것은 낡은 참조가 아니라 이번에 만든 것이다.

파일·라인·원문을 그대로 보여주고 셋 중 하나를 고르게 한다.

| 갈래 | 언제 | 결과 |
|---|---|---|
| 참조 갱신 | 새 결정에서도 그 근거가 유효하다 | 참조를 새 ADR 파일명으로 |
| 참조 제거 | 새 결정이 그 근거를 없앴다 | 그 문장·행을 지운다 |
| 보류 | 지금 판단할 재료가 없다 | 그대로 두고 리포트에 남긴다 |

**참조만 갈아 끼우는 자동 처리를 하지 않는다.** 근거가 사라진 문장이 새 ADR의 권위를 입는 것이
가장 나쁜 결과다. 그리고 **이 스킬은 `DOMAIN.md`를 고치지 않는다** — 고칠 줄과 고칠 내용을
정확히 제시하고 편집은 사용자가 한다. 편집 뒤에 알릴 것은 8-③과 같다: 관계 표의 행이 사라지거나
생기면 격리 검사의 판정이 함께 바뀐다.

**다른 ADR의 본문에 있는 히트는 고치지 않는다**(7-b) — 그 문서들도 `accepted`이고, 방금 건
양방향 링크가 독자를 현재 결정으로 데려간다. 다만 **머리의 `- 관련:` 줄은 본문이 아니므로**
목록에 올려 사용자가 처분하게 한다(§5가 머리 편집을 본문 동결에서 제외한다).

**0건이면 "없음"이라고 적되, 어떤 패턴으로 찾았는지 함께 적는다.** 찾지 않은 표기가 있으면 그
보고는 검증한 척하는 침묵이다.

## 8. 결정이 SSOT 변경을 함의하면 — 드리프트 방지

ADR만 쓰고 끝내면 "결정은 났는데 선언은 옛 상태인" 문서가 남고, 그 상태가 이 플러그인이 없애려는
드리프트다(§7). SSOT는 `DOMAIN.md` 하나이고, 이 스킬이 짚는 것은 **그 안의 어느 자리를 고쳐야
하는가**다. 순서대로 판정한다.

**0-b가 신뢰 불가면 이 단계에서 편집 위치를 제시하지 않는다.** 선언을 해석하지 못한 상태라 어느
컨텍스트·관계가 실재하는지 모르고, 그 위에 세운 처방은 근거가 없다. `parse_domain.py`의 오류 줄을
먼저 해소하도록 안내하고 이 단계를 그 뒤로 미룬다 — ADR 기록 자체는 5단계에서 이미 끝났다.

**① 선언이 바뀌는 결정인가.** "적절한 크기", "응집도가 높을 것"처럼 기준이 사람의 해석에 달려
있는 결정은 선언에 자리가 없다. ADR로 끝내고 필요하면 `docs/superdomain/conventions/`의 리뷰 체크리스트로
보낸다 — 선언에 억지로 밀어 넣은 판정은 오탐을 만들고, 오탐이 반복되면 팀이 선언 전체를 무시하기
시작한다(§7).

**② 넷 중 어디인가.** `DOMAIN.md`가 담는 결정은 넷이고, 결정의 성격이 자리를 정한다.

| 결정이 말하는 것 | 고칠 자리 | 바뀌는 것 |
|---|---|---|
| 두 컨텍스트가 서로를 직접 참조해도 되는가 | 해당 컨텍스트의 `### 관계` 표 행(상대·유형·계약) | **격리 검사의 허용 목록.** 허용 단위는 **쌍**이고 방향을 구분하지 않는다 — 한 줄이 양쪽을 연다. 유형(customer-supplier·acl 등)은 허용 방향을 바꾸지 않고 계약의 성격만 적는다 |
| 이 컨텍스트가 core인가 supporting인가 generic인가 | `- 분류:` | 투자·리뷰 강도의 근거. 기계 강제는 붙지 않는다 |
| 이 컨텍스트가 어느 패키지에 사는가 | `- 패키지:`(없으면 규약 기본값 `<기본 패키지>.<컨텍스트>..`) | **격리 검사의 귀속 범위.** 잘못 좁히면 그 코드가 검사에서 통째로 사라진다. **이 자리만 편집까지 `/superdomain:init`이 받는다** — 아래 불릿 |
| 이 컨텍스트가 어떤 패턴을 채택하는가 | `- 패턴:`(쉼표 목록 — `cqrs`·`outbox`·`event-sourcing`) | **`apply`·`review`가 읽는 지식 문서 집합.** 선언되지 않은 패턴은 구현에 들이지 않고, 선언된 패턴의 규칙은 그때부터 리뷰 근거가 된다. 기계 강제는 붙지 않는다 |

- 격리 규칙과 관계 표의 정본은
  `${CLAUDE_PLUGIN_ROOT}/references/governance/domain-template.md`다 — 값의 형식이 헷갈리면 그
  문서를 읽고, 이 표를 근거로 쓰지 않는다.
- **컨텍스트를 새로 세우거나 합치는 결정이면 자리를 짚는 것으로 끝나지 않는다** — 경계·분류·관계를
  다시 정하는 인터뷰가 필요하고 그것은 `/superdomain:init`이다. 이 ADR은 그 변경의 근거로
  남는다.
- **`- 패키지:`가 바뀌는 결정도 같다 — 넷 중 이 자리만 예외다.** 그 값이 격리 검사의 귀속 범위라
  컨텍스트의 소유 범위가 통째로 뒤집히므로, 편집과 그 뒤의 게이트·파생물까지 경계 인터뷰의 일부로
  `/superdomain:init`이 받는다(같은 목적지를 `skills/init/SKILL.md` 1단계 프런트매터와
  `skills/evolve/SKILL.md` 9-a도 말한다). 나머지 세 자리(`### 관계`·`- 분류:`·`- 패턴:`)는 자리를
  짚는 것으로 끝나고 편집은 사용자가 한다 — 예외는 `evolve`가 **자기 제안의 수락분**으로
  `### 관계`·`- 분류:`를 확정받아 직접 반영하는 경로 하나이고(그 스킬 9-a), 그것도 이 스킬을
  거치지 않는 별 경로가 아니라 같은 자리에 대한 같은 처방이다.

**자유 서술 구역**(`DOMAIN.md`의 설명 문단·`### 근거`, 다른 ADR의 본문)은 **이 스킬의 소관이
아니다.** 이 결정 때문에 낡은 서술이 생겼으면 어디가 낡았는지 지적하고 멈춘다 — 사용자가 직접
편집한다.

> **`/superdomain:sync`도 자유 서술은 고지만 한다** — 그 스킬이 기계 대조하는 것은 파생물과
> 생성 구역이다. 그러므로 여기서도 처분은 "지적한다" 하나뿐이다.

**③ 편집은 사용자, 재실행 권유는 여기서.** ①~② 어느 경로든 `DOMAIN.md`를 고치는 것은 이 스킬의
일이 아니다. 고칠 곳을 정확히 제시하고, 편집 뒤에 두 가지를 권한다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/parse_domain.py" docs/superdomain/DOMAIN.md
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_imports.py" docs/superdomain/DOMAIN.md
```

앞은 선언이 여전히 해석되는지, 뒤는 **그 편집으로 위반이 새로 드러나거나 사라졌는지**다. 관계 표에서
행을 지우면 그때까지 통과하던 참조가 위반으로 돌아서므로, 그 결과를 보지 않은 채 "반영 완료"라고
말하지 않는다. 마지막으로 **결정한 것을 ADR의 「후속 작업」 칸에 그대로 적는다.** 해당 사항이 없으면
"없음"이라고 명시한다(§7) — 그 칸이 이 연결을 잊지 않게 하는 장치다.

## 9. 마무리 보고

1. **파일** — 생성한 ADR 경로, 머리만 고친 옛 ADR 경로. 그 밖에 쓴 파일은 없다.
2. **파일명 근거** — 파일에 쓴 날짜와 확정한 slug. 디렉터리에 ADR이 아닌 파일이 섞여 있으면
   고지한다.
3. **supersede/조정이면 양방향 확인** — 신·구 두 링크가 각각 어느 줄에 들어갔는지.
4. **사용자 처분이 남은 것** — 7-c의 옛 ADR 참조 목록(갈래별), 8단계가 제안한 편집.
5. **커밋은 사용자가 한다.** 명령만 제안한다.

   ```bash
   git add docs/superdomain/adr/
   git commit -m "docs: ADR <결정 요지>"
   ```

## 하지 말 것

- **검토한 대안을 지어내는 것.** 없으면 "검토한 대안 없음"이다. 기각 이유를 그럴듯하게 채우는
  것, 사용자가 확인하지 않은 제안을 표에 넣는 것도 같은 실패다. 결과 칸도 마찬가지다.
- **확인 없이 `accepted`로 올리는 것.** 상태 전이는 전부 사용자 확정이다.
- **`accepted` 문서의 본문을 고치는 것.** 정정은 새 ADR이다. 손대도 되는 곳은 머리의 상태·링크
  줄과 오타·깨진 링크뿐이다.
- **양방향 링크 중 한쪽만 거는 것**, 옛 문서의 상태를 `superseded`로 바꾸지 않고 두는 것,
  부분 조정에서 `조정됨:` 줄을 빠뜨리는 것.
- **일련번호로 채번하는 것**, 기존 ADR의 파일명을 바꾸는 것(§2).
- **옛 ADR 참조를 확인 없이 갈아 끼우는 것.** 근거가 사라진 문장이 새 파일명을 입는다.
- **`DOMAIN.md`를 고치는 것** — 관계 표·분류·패키지 라벨 전부. 이 스킬은 어느 줄을 어떻게 고칠지
  제시하는 데까지다.
- **관계 표의 한 줄이 한쪽 방향만 연다고 말하는 것.** 허용 단위는 쌍이고 방향을 구분하지 않는다.
- **기계로 판정할 수 없는 결정을 선언에 밀어 넣는 것.** 오탐이 선언 전체의 신뢰를 깎는다.
- **§1에 해당하지 않는데 ADR을 만드는 것**, 한 문서에 결정을 여럿 담는 것.
- **후속 작업 칸을 비워 두는 것.** 해당 없으면 "없음"이라고 적는다.
