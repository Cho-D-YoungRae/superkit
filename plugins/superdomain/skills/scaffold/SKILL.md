# 선언에서 코드 골격으로

이 스킬은 `ARCHITECTURE.md`가 이미 말한 것을 디스크에 옮긴다. 무엇을 만들지는 선언이 정하고,
골격의 모양은 프로파일 템플릿의 `MANIFEST.md`가 정하고, 패키지 위치는 `resolve_rules.py`의
정규화 결과가 정한다. 여기서 새로 발명하는 구조는 없다. 다만 **선언에 아직 없는 것을 만들려면
선언부터 세워야 하므로**, 이 스킬은 init 다음으로 SSOT를 편집하는 스킬이다. 그래서 불변이 넷이다.

1. **사용자 확정 없이 SSOT를 고치지 않는다.** 프로젝트 등록, 컨텍스트 이름·분류·스타일·모듈
   구성·관계, 모듈 표와 애플리케이션 표, 기존 컨텍스트의 `- 프로젝트:` 소속 —
   인터뷰 결과를 **표로 보여주고 확정을 받은 뒤에** 적는다.
   이것은 판단을 아끼라는 뜻이 아니다. 관측과 지식 문서를 근거로 **판단을 적극적으로 제안**하는
   것이 이 스킬의 일이고, 금지는 확인 없는 **확정** 하나뿐이다.
   **"알아서 확정하고 진행해 주세요"는 확정 권한의 위임이 아니라 진행 속도의 요청이다.** 그 답을
   받았다고 표를 일괄로 적지 않는다 — 값과 근거를 한 줄로 제시하고 확인을 받고 다음으로 가는
   **항목별 순회를 빠르게** 돈다(model 7-a와 같은 관례). 사용자가 보지 못한 값이 `ARCHITECTURE.md`에
   들어가는 일이 없어야 한다. 이 규율은 2단계·4-a·5단계의 모든 확정 자리에 걸린다.
2. **파서가 거부하는 상태로 끝내지 않는다.** `ARCHITECTURE.md`를 고칠 때마다 게이트를 통과시킨다.
   **완료 조건은 SSOT를 마지막으로 고친 뒤 받은 `OK:` 출력**이며, 파생물 재생성이 그 마지막
   편집이다(5단계).
3. **템플릿·선언 밖의 구조를 지어내지 않는다.** 프리셋이면 그 스타일의 `MANIFEST.md`를 읽고 그대로,
   커스텀이면 스타일 선언에서 유도한다(4-e). "비슷하게"는 선택지가 아니다 — 검증된 적 없는 골격은
   같은 스킬군이 만들 검사에 걸린다.
4. **있는 것을 덮거나 옮기지 않는다.** 골격은 빈 자리를 채우는 동작이다. 기존 코드를 스타일에 맞게
   옮기는 것은 이 스킬이 아니다.

> **구현 상태 — `migrate`는 Phase 5다.** 기존 코드를 목표 스타일로 옮기는 스킬은 아직 없다.
> `이행`이 선언된 컨텍스트에서도 이 스킬은 **없는 것만 만들고**, 있는 코드는 그대로 둔다.

## 지식 참조 프로토콜

지식이 필요하면 **먼저 `${CLAUDE_PLUGIN_ROOT}/references/INDEX.md`를 읽고** 필요한 문서만 연다.
`knowledge/`를 통째로 또는 디렉터리 단위로 읽는 것은 금지다. 고르는 기준은 셋이다.

- INDEX의 `read_when`에 `scaffold`가 있고 **이번 작업에 실제로 해당하는** 문서 — 모듈 구성을
  정하면 `module-composition`, 패키지 자리를 정하면 `package-conventions`, 대상 컨텍스트의
  `스타일` 문서, `패턴` 선언이 있으면 그 key의 문서(4-f).
- 신규 컨텍스트의 분류·경계 인터뷰에 필요한 문서 — `domain-classification`, `bounded-contexts`,
  관계를 적으면 `context-mapping`(init 5단계와 같은 경로를 쓴다).
- 대상 프로젝트의 `docs/architecture/conventions/`·`styles/` 문서. 같은 주제면 **로컬이 이긴다.**

이 문서는 라벨 목록·MANIFEST의 배치 규칙·플레이스홀더 표를 복제하지 않는다. 각 단계가 "지금 이
파일을 읽어라"라고 지시하는 대로 그 시점에 정본을 읽는다. 정본이 바뀌면 이 스킬은 맞는 채로 남는다.

## 0. 위치와 초기화 게이트

```bash
git rev-parse --show-toplevel
```

git 루트의 `ARCHITECTURE.md`가 유일한 입력이다. 하위 디렉터리에서 시작했어도 여기로 올라와서
작업한다. 파일이 없으면 아래를 알리고 **중단**한다 — 선언 없이 만든 골격은 아무도 강제하지 않는다.

> superarchitect가 초기화되지 않았습니다. `/superarchitect:init`으로 아키텍처 거버넌스를 먼저 세우세요.

## 1. 선언을 읽는다 — 이 명령이 입장 게이트다

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md --json
```

- **exit 1이면 멈춘다.** 오류는 stderr에 `경로:라인: 메시지`로 나온다. 그 줄을 **그대로** 보여주고
  중단한다. 들어올 때 이미 깨져 있던 선언을 이 스킬이 고치는 것은 범위 밖이다 — 사용자가 고치거나
  `init`의 게이트 절차를 따른 뒤 다시 부른다. 깨진 선언 위에 골격을 얹으면 무엇이 원인인지 사라진다.
- exit 0이면 stdout 전체가 JSON이고 키는 넷이다: `projects`(name·path·profile·base_package·
  test_location), `effective`(project·context·rule_id·primitive·params·resolved·**layer_patterns**),
  `derived`, `warnings`.
- **`layer_patterns`가 골격의 패키지 위치를 전부 정한다.** 레이어명 → 패턴 목록이고, 이 값은
  기본 관례든 패키지 규약 표든 이미 정규화를 거친 결과다. 이것이 4-c의 유일한 입력이다.
- `warnings`(공허 레이어 고지)를 삼키지 않는다. 각 항목의 `message`를 그대로 보여준다. 이 스킬에는
  뜻이 하나 더 있다 — **골격을 만든 뒤에도 그 컨텍스트의 경고가 남아 있으면 모듈 표가 레이어를
  덮지 못한 것**이다(5단계에서 다시 본다).

`--json` 없이 한 번 더 돌려 집계 줄(`OK: 컨텍스트 N, 유효 규칙 M (…)`)을 받아 둔다. 이 줄이 이번
작업의 **출발 수치**이고, 마지막 게이트의 수치와 비교하는 대상이다.

### 트리거 분기 — 무엇을 만들 것인가

| 상황 | 판정 근거 | 절 |
|---|---|---|
| 모노레포에 새 백엔드가 생겼다 | 그 경로가 `projects[]`에 없다 | 2 → 3 → 4 → **5 → 6** |
| 선언된 프로젝트가 디스크에 없다(그린필드) | `path`에 빌드 파일이 없다 | 3 → 4 → **5 → 6** |
| 새 컨텍스트를 만든다 | 선언에 그 컨텍스트가 없다 | 4-a → 4-b → **5 → 6** |
| 선언된 컨텍스트에 코드가 없다 | 모듈 경로·패키지가 비어 있다 | 4-b → **5 → 6** |
| app-embedded 컨텍스트를 앱에 깐다 | `- 모듈 구성: app-embedded` | 4-b → **4-d** → **5 → 6** |
| `패턴` 선언을 골격에 반영한다 | 컨텍스트에 `- 패턴:`이 있다 | 4-f → **5 → 6** |

여러 개가 동시에 걸리면 **위에서부터** 한다 — 프로젝트가 없으면 컨텍스트를 놓을 자리가 없다.
그리고 **어느 분기든 5(선언 마무리 → 게이트 → 파생물 재생성)와 6(자가 확인)으로 끝난다** — 만든
것이 검사에 걸리는지는 돌려 봐야 안다.

> **구현 상태 — sync 위임 분기는 Phase 5다.** "선언됐는데 디스크에 없음" 드리프트를 감지해 이
> 스킬로 넘기는 `sync`는 아직 없다. 그때까지 그 판정은 사용자 또는 위 표가 한다.

## 2. 신규 프로젝트 증분 등록

선언에 없는 프로젝트를 거버넌스에 올린다. 신규 컨텍스트 등록(4-a)과 대칭이며, **인터뷰 → 표 확정
→ 기록 → 게이트** 순서를 지킨다.

한 번에 하나씩 묻는다. 라벨의 뜻과 값 형식은
`${CLAUDE_PLUGIN_ROOT}/references/governance/architecture-template.md` §4가 정본이다.

- **이름**과 **경로**(저장소 루트 기준. 단일 레포는 `.`). 아직 없는 경로도 선언할 수 있다.
- **프로파일** — 지금 `ls "${CLAUDE_PLUGIN_ROOT}/profiles"`를 실행해 그 결과 중에서 고르게 한다.
  대응 프로파일이 없는 스택이면 init 2단계와 같은 처분이다: 파서가 정규 값으로 거부하므로 프로파일이
  생길 때까지 범위 밖으로 두기를 권한다.
- **기본 패키지**(`com.acme` 꼴)와 **아키텍처 테스트 위치**(프로젝트 경로 기준 상대 경로).
- **필요하면 세 표** — `### 애플리케이션`·`### 공용 모듈`·`### 패키지 규약`. 어느 표가 언제 필요한지는
  같은 문서 §3 「세 표는 언제 필요한가」가 정본이고, 도출 절차는 init 4단계 「멀티 애플리케이션이면
  세 표를 도출한다」와 같다. **지어내지 않는다** — 관측할 코드가 없으면 인터뷰 답으로 채우고 전부
  확인받는다.
- **앱 이름은 받는 자리에서 전개를 함께 본다.** 앱 이름은 하이픈을 점으로 바꿔 패키지에 들어가고
  (`core-api` → `core.api`), 그 조각 하나하나가 유효한 패키지 세그먼트여야 한다. 파서는 `### 패키지
  규약`에 `{앱}` 행이 **있을 때만** 이 검사를 한다 — 그런데 그 행이 없어도 앱 메인 클래스의 패키지는
  `{{basePackage}}.{{app}}`으로 전개되므로(3단계 「앱 실행 모듈」) `api-2` → `api.2`처럼 전개가
  불법인 이름은 게이트를 통과하고 **골격 단계에서** 컴파일되지 않는 패키지를 만든다. 전개가 불법이면
  그 자리에서 지적하고 다른 이름을 받는다 — 4-a의 컨텍스트 이름 제약과 같은 이유다.

확정한 값을 표 하나로 보여주고 동의를 받은 뒤에 프로젝트 섹션을 추가한다.

**프로젝트가 둘이 되는 순간 기존 컨텍스트가 전부 깨진다.** 파서는 프로젝트가 2개 이상이면 모든
컨텍스트에 `- 프로젝트: <이름>` 라벨을 요구한다(`컨텍스트 'x': 프로젝트가 여러 개이므로 …`). 첫
증분 등록에서는 기존 컨텍스트 섹션마다 이 라벨을 더해야 하고, 그 값은 **원래 속해 있던 프로젝트**다.
어느 컨텍스트가 어디 속하는지가 조금이라도 불분명하면 묻는다 — 이 라벨을 잘못 적으면 규칙이 다른
프로젝트의 기본 패키지로 정규화된다.

기록한 뒤 **게이트**(1단계의 명령)를 돌린다. 프로젝트만 등록한 상태에서는 그 프로젝트의 유효 규칙이
0이다 — 정상이다. 컨텍스트는 4-a에서 붙인다.

## 3. 프로젝트 골격 생성

선언은 있는데 디스크에 프로젝트가 없을 때다.

```bash
ls "<프로젝트 경로>"/settings.gradle* "<프로젝트 경로>"/pom.xml 2>/dev/null
```

만드는 것은 **선언이 말한 것뿐**이다: 디렉터리, `settings.gradle.kts`, 선언된 모듈의 빌드 스크립트와
소스 골격(4단계가 스타일별로 만든다), `### 애플리케이션` 표가 있으면 앱 실행 모듈(아래 절),
아키텍처 테스트 위치의 디렉터리와 그 모듈의 빌드 스크립트.

- **settings는 더한다, 덮지 않는다.** 파일이 없으면 `rootProject.name = "<프로젝트 이름>"`으로
  시작하고, 있으면 include 줄만 추가한다. 각 스타일의 `settings.gradle.kts.fragment`가 그 줄의
  정본이다(레이아웃에 따라 줄이 줄거나 사라지는 규칙은 MANIFEST에 있다).
- **아키텍처 테스트 위치가 별도 모듈이면 include에 넣고 빌드 스크립트를 함께 만든다.** include만
  있고 스크립트가 없으면, 또는 스크립트만 있고 include가 없으면 fitness가 만들 테스트는 영원히
  실행되지 않는다. 조각은 `templates/_shared/build.gradle.kts.archtest`이고(계약 ② 「파일 구성」),
  검증 도구 좌표에는 버전이 없다 — 아래 「버전 규약」이 그 자리를 정하게 한다. **테스트 소스는 여기서
  만들지 않는다**(fitness 소관).
- **gradle wrapper는 만들지 않는다.** 명령만 안내한다. `gradle`이 없으면 그 사실을 알린다.

  ```bash
  gradle wrapper --gradle-version <버전>
  ```

### 버전 규약이 없으면 구성 단계에서 실패한다

프로파일의 빌드 조각은 **버전을 박지 않는다**(계약 ② 「파일 구성」). 대상 프로젝트가 버전을 정하는
자리를 갖고 있다는 전제이며, 그린필드에는 그 자리가 아직 없다. 규약이 없으면 골격은 컴파일이 아니라
**구성 단계**에서 죽는다. 그러니 전개 전에 확인하고, 없으면 선택지를 제시해 사용자가 고르게 한다.

- 루트 `build.gradle.kts`의 `plugins { … version "<x>" apply false }`
- `gradle/libs.versions.toml` 버전 카탈로그
- Spring Boot 의존성 관리(BOM)

**버전 숫자는 지어내지 않는다.** 사용자가 정하거나, 확인한 값(카탈로그의 기존 항목, `gradle --version`,
대상 프로젝트의 다른 모듈)을 근거와 함께 제안하고 확정받는다. single-module 레이아웃에서는 프로덕션
소스까지 컴파일되므로 첫 빌드에서 곧바로 드러나지만, multi-module에서 아키텍처 테스트만 돌리면
한참 뒤에 드러난다.

### 앱 실행 모듈 — 조각은 `_shared/`에 있다

실행 단위(앱) 모듈에는 스타일이 정하는 것이 하나도 없다. 그래서 그 조각은 스타일 디렉터리가 아니라
**`templates/_shared/`에 하나** 있고, 프리셋 4종이 그것을 공유한다. 4-b의 `templates/<스타일>/`만
보면 닿지 못하므로 여기서 따로 찾는다.

```bash
ls "${CLAUDE_PLUGIN_ROOT}/profiles/<프로파일>/templates/_shared/"
```

- `build.gradle.kts.app` — 앱 모듈의 빌드 스크립트(실행 산출물 플러그인·`plugin.spring`·조립 의존)
- `<앱 메인 클래스>` — 실행 진입점(kotlin-spring은 `{{App}}Application.kt`)

계약은 `${CLAUDE_PLUGIN_ROOT}/profiles/README.md` ② 「앱 실행 모듈」이 갖는다 — **지금 읽는다.**
배치·패키지·의존·금지의 규약이 그 표에 있고, 이 스킬이 다시 쓰지 않는다. 전개할 때 짚을 네 가지만
적어 둔다.

- **배치는 `### 애플리케이션` 표의 `모듈 경로`**이고, `settings.gradle.kts`에 그 경로의 include 줄을
  함께 더한다. 빠뜨리면 앱 모듈이 빌드에 없는 상태가 되고, 그 위에 만든 레이어 패키지는 컴파일도
  검사도 되지 않는다.
- **`{{#app.contextModules}}`의 항목은 각 `포함 컨텍스트`의 가장 바깥 레이어 모듈 하나씩**이다.
  어느 레이어가 그것인지는 **그 컨텍스트 스타일의 MANIFEST 「앱 실행 모듈」 한 줄**이 적는다
  (hexagonal은 `:{{context}}:adapter`). 표에 없는 컨텍스트를 의존에 더하지 않는다 — 의존이 아니라
  표를 먼저 고친다(4-a).
- **커스텀 스타일에는 그 MANIFEST가 없다.** 그때 가장 바깥 레이어는 그 스타일 `layer-order`
  인스턴스의 **`layers` 파라미터 마지막 항목**이다 — 그 파라미터는 언제나 안→밖이기 때문이다.
  **스타일의 `레이어` 라벨 순서를 대신 쓰지 않는다**: `layered-simple`의 라벨은 위→아래 호출
  방향이라 마지막이 가장 안쪽이라는 반례가 `rule-vocabulary.md` §3.1에 명시돼 있다. 그 스타일에
  `layer-order`가 없거나 `layers`가 레이어 전부를 담지 않아 판정이 갈리면 유도하지 말고 **사용자에게
  묻는다**(§3.1 — `layers`는 전 레이어 나열을 요구하지 않는다).
- **메인 클래스 패키지**는 그 표의 「메인 클래스 패키지」 행이 정한다. 여기서 다시 적지 않는다 —
  4-c의 손 조립 금지가 이 자리에도 그대로 걸린다.

**`_shared/`가 없는 프로파일이면**(그때는 진짜로 조각이 없다) 지어내지 않는다. 디렉터리·소스 자리·
include 줄까지만 만들고, 그 모듈이 필요로 하는 항목을 목록으로 안내한 뒤 사용자가 정하게 한다 —
실행 산출물·의존성 관리 플러그인, `포함 컨텍스트`가 정하는 조립 의존, 메인 클래스, 프록시 대상이
있으면 `kotlin("plugin.spring")`(6단계).

## 4. 컨텍스트 골격

### 4-a. 신규 컨텍스트면 먼저 등록한다

**이름 제약을 먼저 알린다.** 기본 관례에서는 컨텍스트 이름이 그대로 패키지 세그먼트가 되므로
하이픈·점·대문자가 든 이름은 **파서가 오류로 거부한다**(`컨텍스트 이름 '…'이(가) 유효한 패키지
세그먼트가 아닙니다`). 영문 소문자 식별자로 짓게 하고, 하이픈을 꼭 쓰고 싶다면 그것은 패키지 규약
표로 세그먼트를 명시 매핑해야 하는 별개의 결정임을 말한다. 이름을 먼저 잡는 이유는 단순하다 —
등록을 마친 뒤에 거부당하면 인터뷰를 처음부터 다시 해야 한다.

인터뷰는 init 5단계와 **같은 문서·같은 순서**를 쓴다. 이 스킬이 체크리스트를 다시 쓰지 않는다.

| 정할 것 | 정본 | 규율 |
|---|---|---|
| 경계 | `bounded-contexts.md` H1~H4 | 기존 컨텍스트와 겹치면 새로 만들지 말고 합칠지 묻는다 |
| 분류 | `domain-classification.md` Q1~Q4 → 종합 판정 → R4 | core가 절반을 넘으면 과설계 신호 |
| 스타일 | 같은 문서 R1의 분류 → 스타일 기본 매핑 | 제안은 이 스킬이, 결정은 사용자가. 벗어나면 ADR |
| 모듈 구성 | `module-composition.md` 「선택 절차」 | 위에서부터 먼저 걸리는 것이 답이다 |
| 관계 | `context-mapping.md` | 관계 표는 allow-list다 — 적지 않은 쌍은 닫힌다 |

프리셋이 맞지 않으면 커스텀 스타일을 선언한다. 형식은 `architecture-template.md` §7이고, **선언
체크리스트는 `rule-vocabulary.md` §5**(「새 커스텀 스타일을 선언할 때」 — init 5-c와 같은 경로다).
그 앞에 "정말 **새 규칙**이 필요한가"를 먼저 거르는 것은 같은 문서 **§6**이며, 둘은 다른
체크리스트다. 파일은 대상 프로젝트의 `docs/architecture/styles/<이름>.md`이고 골격은 4-e가 유도한다.

확정한 값을 표로 보여주고 동의를 받은 뒤 컨텍스트 섹션을 쓴다. **모듈 표를 이때 함께 쓴다** —
그 모양은 고를 스타일의 MANIFEST 「ARCHITECTURE.md 등록」이 정하고, 규율은 하나다: **행은 레이어마다
하나씩.** single-module이어도 `모듈`·`경로` 값만 반복될 뿐 행이 줄지 않는다. 한 행으로 줄이면서
레이어를 `all`로 적으면 그 스타일의 규칙이 **전부** 아무것도 검사하지 않게 된다(실측).

`app-embedded`면 모듈 표는 **금지**이고, 대신 프로젝트에 `### 애플리케이션`·`### 패키지 규약` 표가
필수다(2단계). 그리고 **그 컨텍스트를 담을 앱의 `포함 컨텍스트` 칸을 함께 갱신한다**(`all`이면
이미 열려 있다) — 빠뜨리면 방금 만든 코드가 그 앱에서 참조 금지 대상이 되고, 6단계 자가 확인이
`앱 '<이름>'이(가) '포함 컨텍스트'에 없는 코드를 …`으로 잡는다.

기록한 뒤 **게이트**를 돌린다. 컨텍스트 수가 1 늘고 유효 규칙 수가 그 스타일의 규칙만큼 는다.
**여기서 통과해야 다음 단계의 입력(`layer_patterns`)이 생긴다.**

### 4-b. 스타일 확인과 템플릿 로드

```bash
ls "${CLAUDE_PLUGIN_ROOT}/profiles/<프로파일>/templates/<스타일>/MANIFEST.md"
```

있으면 **지금 읽는다.** 그 여섯 절이 골격의 계약 전부다 — 통과해야 하는 규칙, 파일 목록, 레이아웃
3형 배치(multi-module / single-module 병합 규칙 / app-embedded), ARCHITECTURE.md 등록, 치환,
수용 기준. 이 스킬은 그것을 재서술하지 않고 **읽어서 그대로 따른다.**

없으면 지어내지 않는다. 프로파일에 그 스타일의 템플릿이 없다는 사실을 알리고 멈춘다.

> **구현 상태 — 템플릿이 있는 프로파일은 `kotlin-spring`뿐이다.** `java-spring`은 Phase 6이며
> `rule-mappings.md`도 아직 없다. 선언은 유효하고, 도착하면 같은 절차가 그대로 돈다.

### 4-c. 치환 — 패키지는 해석기에서 받는다

변수의 뜻과 목록은 `${CLAUDE_PLUGIN_ROOT}/profiles/README.md`의 「플레이스홀더 규약」이 정본이다.
파일 이름과 디렉터리 이름에도 같은 치환을 적용한다.

- **`{{pkg:<레이어>}}`는 1단계 JSON의 `layer_patterns[<레이어>]`에서 받아 끝의 `..`를 뗀 값이다.**
  `{기본 패키지}.{컨텍스트}.{레이어}`로 손 조립하지 않는다 — 패키지 규약 표가 있는 프로젝트에서
  그 조립은 틀린다.
- **패턴이 둘 이상이면 패턴마다 한 벌씩 전개한다.** app-embedded에서 `{앱}`이 든 레이어가 그렇고,
  "앱마다 레이어 패키지 하나씩"이 이 규칙 하나에서 나온다.
- `{{Context}}`는 PascalCase, `{{app}}`은 모듈 경로에서는 원형·패키지 위치에서는 하이픈을 점으로.
- `layer_patterns`는 `effective` 항목에 실려 온다. 그 컨텍스트의 `effective`가 비어 있으면(규칙이
  전부 `규칙 예외`로 빠진 경우) 패턴을 얻을 수 없다 — 그 사실을 알리고, 손으로 만들지 말고 사용자에게
  확인한다.

### 4-d. 레이아웃 3형

배치의 정본은 MANIFEST의 「레이아웃 3형 배치」다. 이 스킬이 지킬 것은 셋이다.

- **multi-module** — settings 조각의 include 줄을 루트에 **더하고**, 레이어마다 빌드 조각을 그 모듈에
  둔다.
- **single-module** — 빌드 조각 여럿을 하나로 합쳐야 한다. **단순히 이어 붙이면 `plugins` 블록이
  여럿이 되어 Gradle이 구성 단계에서 거부한다.** MANIFEST의 병합 규칙 표(헤더 주석·`plugins`·
  `dependencies`·자기 참조 `project(":…")`·`tasks.test`)를 요소별로 그대로 적용한다. 병합 뒤
  `testRuntimeOnly("org.junit.platform:junit-platform-launcher")`와 `useJUnitPlatform()`이 남아
  있는지 확인한다 — Gradle 8+에서 둘 중 하나가 빠지면 테스트가 실행 시점에 죽는다(실측).
- **app-embedded** — 모듈도 빌드 조각도 만들지 않고 소스 파일만 규약 패턴 위치에 둔다. `{앱}`이 든
  레이어는 앱마다 하나씩, 없는 레이어는 앱들이 함께 의존하는 **비실행 모듈**에 하나만 둔다. 그 모듈
  경로는 선언 어디에도 없다 — 관측으로 찾고, 찾지 못하면 **묻는다.**

### 4-e. 커스텀 스타일 — 템플릿이 아니라 유도

커스텀 스타일에는 템플릿을 두지 않는다(계약 ②). 골격은 그 스타일의 `## 선언`(레이어 목록 + 규칙
인스턴스 표)에서 유도한다. 유도는 규칙 primitive마다 함의가 정해져 있다.

| primitive | 골격에 대한 함의 |
|---|---|
| `layer-order` | 모듈·패키지 의존을 선언된 순서 한 방향으로만. 빌드 조각의 `project(":…")`가 그 방향을 따른다 |
| `forbid-import` | 그 import를 골격에 넣지 않는다. 빌드 조각에서 해당 의존도 함께 뺀다 |
| `confine-type` | 그 타입(예: JPA 엔티티)을 선언하는 파일을 허용 레이어에만 하나 둔다 |
| `naming-suffix` | 그 레이어의 **최상위** public 타입 이름이 전부 그 접미사로 끝나게. 나머지는 중첩 타입으로 내린다 |
| `forbid-sibling-dependency` | 같은 레이어의 형제 모듈 사이에 의존을 만들지 않는다 |

여기에 레이아웃과 무관한 규율이 하나 붙는다 — **레이어마다 소스 파일이 최소 하나.** `strict = true`인
규칙은 검사 대상 0건도 실패이므로, 비워 둔 레이어는 골격을 통과하지 못하게 만든다.

`{{layer}}` 변수가 사는 곳이 여기다. 레이어 이름을 선언에서 읽어 모듈 경로·조각 파일 이름·패키지
경로에 전개한다.

**가장 가까운 프리셋의 MANIFEST는 참고로만 제시한다** — 레이어 수·이름·방향이 가장 비슷한 것을
고르고 "이 형태가 참고가 된다"고 말한다. 배치와 파일 구성을 통째로 복사하지 않는다.

**다만 금지되는 복사와 권장되는 재사용은 다르다.** 복사하면 안 되는 것은 **스타일의 정체성** — 규칙
id, 규칙의 근거, "이 의존을 더하면 어느 규칙이 잡는다"류의 규칙 주석이다. 커스텀 스타일의 골격이
남의 규칙 id를 근거로 서면 나중에 아무도 이유를 찾지 못한다. 반대로 빌드 조각의 **기계적 부분**은
가장 가까운 프리셋 조각을 **출처를 밝히고 재사용한다** — `kotlin("jvm")` 플러그인 블록, JUnit
배선(`testImplementation`·런처 `testRuntimeOnly`·`useJUnitPlatform()`), 컴파일러 플러그인 조건
(`plugin.jpa`·`plugin.spring` — 6단계), 버전을 박지 않는 규약(§3). 이것들은 스타일과 무관한
kotlin-spring 공통 배선이고, 다시 짜면 T1이 실행으로 잡아낸 결함(런처 누락 등)을 그대로 재현한다.
재사용한 조각의 주석에 **어느 프리셋에서 왔는지** 남기고, 규칙 주석은 커스텀 스타일 자신의 규칙 id로
다시 쓴다.

유도한 골격은 **검증된 적 없다**(프리셋과 다른 점이다). 파일 목록을 먼저 보여주고 확정받은 뒤 만들고,
6단계의 자가 확인을 특히 성실하게 돌린다.

### 4-f. `패턴` 선언 반영

컨텍스트에 `- 패턴:`이 있으면 INDEX에서 그 key의 문서를 찾아 **지금 읽는다**(`cqrs`·`event-sourcing`·
`outbox`). 규율은 둘이다.

- **선언이 곧 최고 단계는 아니다.** 문서의 「적용 기준」을 먼저 읽고 지금 어느 단계인지 사용자에게
  확인한 뒤, 그 단계가 요구하는 구조만 만든다. cqrs를 예로 들면 command/query 패키지를 가르는 것은
  L2 이상의 이야기이고, 문서는 그 값이 생기는 조건(Q·W 계수)을 정해 두었다. 선언만 보고 최대치를
  깔면 그것이 문서가 막으려는 과설계다.
- **패턴이 만드는 것은 레이어 안쪽의 패키지다.** 레이어 패턴은 `..`로 끝나므로 하위 패키지는 이미
  그 안에 든다 — **모듈 표를 바꾸지 않는다.** 패턴 문서의 R 규칙은 기계 규칙이 아니라 리뷰 판정
  도구이므로 골격이 그것을 위반하지 않게만 만든다(예: cqrs R3 — command·query 패키지는 서로를
  import하지 않는다).

### 4-g. 이미 있는 파일은 건드리지 않는다

전개 대상 경로에 파일이 있으면 **쓰지 않는다.** 무엇이 있어서 건너뛰는지 목록으로 보여주고, 사용자가
원하면 그때 diff를 보여준 뒤 확인을 받는다.

```bash
diff -u "<기존 파일>" "<새 내용 임시 파일>"
```

임시 파일은 `mktemp`로 만들고 대상 프로젝트 트리에 남기지 않는다. 기존 코드를 다른 레이어로 옮기는
것은 이 스킬이 아니다(위 구현 상태 — `migrate`).

**아키텍처 테스트는 만들지 않는다.** 그것은 fitness의 생성물이고 배치 규약은 프로파일
`rule-mappings.md` §0.1이 갖는다. 골격이 함께 만들면 정본이 둘이 된다.

## 5. 선언 마무리 → 게이트 → 파생물 재생성

전개 결과가 선언과 어긋난 자리를 먼저 맞춘다. **모두 사용자 확정 대상이다.**

- **모듈 표** — 4-a에서 이미 썼다면 실제로 만든 모듈 경로와 대조만 한다. 기존 컨텍스트에 레이어를
  더했다면 행을 추가한다(레이어마다 한 행).
- **애플리케이션 표** — 앱을 새로 만들었거나 `포함 컨텍스트`가 늘었으면 갱신한다. `포함 컨텍스트`는
  "지금 참조한다"가 아니라 **"참조해도 된다"**는 선언이므로 반드시 확인받는다.
- **공용 모듈 표** — 컨텍스트에 속하지 않는 모듈을 새로 만들었을 때만. app-embedded의 비실행
  모듈(4-d)은 컨텍스트에 속하므로 **이 표에 적지 않는다.**

고쳤으면 **게이트**를 돌린다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/resolve_rules.py" ARCHITECTURE.md
```

1단계의 출발 수치와 비교한다. **컨텍스트 수와 유효 규칙 수가 의도한 만큼 늘었는가.** 그리고 이번에
만든 컨텍스트의 **공허 레이어 경고가 0인지** 본다 — 남아 있으면 모듈 표가 그 레이어를 덮지 못한
것이고, 그 레이어를 참조하는 규칙은 아무것도 검사하지 않는다.

**고쳐도 되는 것과 안 되는 것**의 경계는 init 6단계 「고쳐도 되는 것과 안 되는 것」과 같다: 형식
오류(라벨 오타·표 위치·구분선·화살표)는 고치고, 사용자가 결정한 값(이름·분류·스타일·모듈 구성·
관계·프로파일)은 게이트를 통과시킬 목적으로 바꾸지 않는다. 같은 오류가 두 번 반복되면 멈추고
파서 출력 원문을 보여주며 묻는다.

**자유 서술 구역**(문서 제목, 설명 문단, `### 근거`)은 **이 스킬의 소관이 아니다.** 이번 변경으로
그 서술이 낡거나 거짓이 되었어도(예: 골격을 만들어 "아직 코드가 없다"가 거짓이 됨) **고치지 말고
지적한다** — 사용자가 직접 편집한다. 형식 오류와 달리 무엇이 맞는 서술인지는 사용자만 안다.

> **구현 상태 — 자유 서술 동기화는 Phase 5 `sync`다.** 선언 변경에 따라 낡은 서술을 찾아 갱신을
> 제안하는 스킬은 아직 없다. 그때까지 이 스킬의 처분은 "지적한다" 하나뿐이며, 세션마다 갈리지
> 않는다.

### 파생물 재생성 — 이것이 마지막 SSOT 편집이다

관례는 init 7-a·7-b와 같고, 여기서 다시 정하지 않는다.

- `docs/architecture/summary.md` — 프로젝트·컨텍스트 표에 이번 변경을 반영한다. 30줄 이하를 유지하고,
  전역 핵심 규칙 목록을 **바꿔야 할 때만** 사용자에게 확인받는다(매 세션 자동 주입되는 유일한
  산출물이다).
- 컨텍스트 맵 생성 구역과 `structure:<컨텍스트>` 구역 — 마커 문자열의 정본은
  `architecture-template.md` 「생성 구역 마커」다. **여는 마커가 이미 있으면 새로 쓰지 않고 그 쌍
  사이만 교체한다.** 닫는 마커가 없는 여는 마커를 발견하면 갱신하지 말고 오류로 보고한다.

생성 구역을 고쳤으면 `ARCHITECTURE.md`가 다시 바뀐 것이다. **한 번 더 게이트를 돌린다.** 컨텍스트·
유효 규칙 수가 직전 실행과 같아야 하고, **이 실행의 `OK:` 출력이 이 스킬의 완료 조건이다.**

## 6. 자가 확인 — 만든 골격이 스킬군의 검사에 걸리지 않는가

템플릿의 수용 기준은 하나다: 그대로 전개한 골격은 `check_imports` 클린이고 fitness가 만든 테스트를
통과한다. 통과하지 못하는 골격은 미완성이 아니라 **틀린 것**이다.

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_imports.py" ARCHITECTURE.md
```

- **exit 0**이어야 하고, `[0건 경고]`가 **없어야** 하고, 푸터의 `생략:` 줄이 **없어야** 한다.
  "위반 없음"과 "아무것도 검사하지 않음"은 다른 상태이며, 골격이 레이어를 다 채웠는지는 뒤의 둘이
  말해 준다.
- 위반이 나오면 **골격을 고친다.** 통과시키려고 선언·규칙 예외를 손대지 않는다.
- 커스텀 유도(4-e)에서는 이 확인이 유일한 사전 검증이다. 실패하면 유도가 틀린 것이므로 스타일 선언과
  대조해 다시 만든다.

### 구조 검사가 보지 못하는 것 — 컴파일러 플러그인

`check_imports`도 fitness도 import와 이름만 본다. `@Entity`의 no-arg 생성자와 `@Transactional`의
프록시(Kotlin 클래스는 기본이 final)는 어느 쪽에도 걸리지 않으므로, 빠지면 골격이 **두 검사를 다
통과하고 부팅에서 깨진다.** 전개한 모듈에 `@Entity`가 있으면 `kotlin("plugin.jpa")`, 프록시 대상
(`@Transactional`·`@Configuration`)이 있으면 `kotlin("plugin.spring")`이 그 모듈의 빌드 스크립트에
붙었는지 확인한다. 프리셋 조각에는 해당 레이어에 이미 배선돼 있다 — 커스텀 유도와 single-module
병합에서 떨어뜨리기 쉬운 자리다.

## 7. 마무리 보고

1. **파일 목록** — 생성(앱 모듈의 include 줄처럼 선언 파일에 **더한** 줄도 포함) / 건너뜀(사유별) /
   사용자가 정해야 하는 것(wrapper, 버전 규약, 그리고 `_shared/`가 없는 프로파일이면 앱 모듈 빌드
   스크립트의 **내용**).
2. **선언 변경분** — 추가·수정한 섹션과 표를 표로 보여주고, 게이트의 `OK:` 줄을 출발 수치와 나란히
   인용한다.
3. **자가 확인 결과** — `check_imports`의 exit와 `[0건 경고]`·`생략` 유무를 그대로 적는다. 돌리지
   않았으면 돌리지 않았다고 적는다.
4. **다음 단계** — `/superarchitect:fitness`로 이 골격을 강제할 테스트를 만든다. 분류 → 스타일 기본
   매핑을 벗어났거나 커스텀 스타일을 도입했다면 `/superarchitect:adr`로 근거를 남긴다. 변경분 검토는
   `/superarchitect:review`다. 실행 여부는 사용자가 정한다.
5. **커밋은 사용자가 한다.** 명령만 제안한다.

## 하지 말 것

- **사용자 확정 없이 `ARCHITECTURE.md`를 고치는 것.** 인터뷰 결과는 표로 보여주고 동의를 받은 뒤에
  적는다. 프로젝트 등록·컨텍스트 이름·분류·스타일·모듈 구성·관계·모듈 표·애플리케이션 표, 그리고
  **기존 컨텍스트에 붙이는 `- 프로젝트:` 라벨**(2단계 — 값이 곧 그 컨텍스트의 소속 결정이다) 전부다.
- **게이트를 통과시키려고 사용자가 결정한 값을 바꾸는 것.** 고쳐도 되는 것은 형식뿐이다.
- **파서 실패 상태로 끝내는 것.** 완료 조건은 파생물 재생성 뒤 받은 `OK:` 출력이다.
- **MANIFEST를 읽지 않고 기억으로 배치하는 것**, 템플릿이 없는 스타일·프로파일의 골격을 지어내는 것.
- **패키지를 손으로 조립하는 것.** 정규화 결과는 `layer_patterns`에 이미 있다.
- **모듈 표를 `all` 한 행으로 줄이는 것.** 그 스타일의 규칙이 전부 아무것도 검사하지 않게 된다.
- **기존 파일을 확인 없이 덮는 것**, 기존 코드를 다른 레이어로 옮기는 것(`migrate`는 Phase 5다).
- **gradle wrapper를 만들거나 버전 숫자를 지어내는 것.** 명령과 선택지를 안내하고 사용자가 정한다.
- **아키텍처 테스트를 함께 만드는 것.** 그것은 fitness의 생성물이다.
- **`[0건 경고]`·`생략`·공허 레이어 경고를 조용히 넘기는 것.** 전부 사유와 함께 보고에 남는다.
- **파생물을 직접 고치도록 유도하는 것.** 항상 SSOT를 고치고 파생물을 다시 만든다.
- **아직 없는 스킬(`sync`·`evolve`·`migrate`)을 있는 것처럼 안내하는 것.**
