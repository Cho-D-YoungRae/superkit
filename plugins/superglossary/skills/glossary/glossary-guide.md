# 용어 사전 기준

용어 사전의 형식, 등록 규칙, 분리 절차다. `glossary` 스킬과 `check` 스킬, `glossary-scanner`가 같은 기준을 읽는다.

## 1. 형식

용어 사전은 사용자 프로젝트의 `docs/superglossary/`에 있다. 사람과 Claude가 같은 파일을 읽고 고치므로 생성물이나 중간 형식(JSON 등)을 두지 않는다.

### 분리 전 — `glossary.md` 한 파일

처음 만들 때는 아래를 그대로 쓴다. 표의 세 용어가 기본 용어다.

```markdown
# 용어 사전

이름(클래스·변수·함수·컬럼·테이블·API 필드)에 쓰는 단어 목록이다. /superglossary:glossary가 관리한다.

- 단어별로 등록하고 조합해 쓴다 (체결수량 → 체결 execution + 수량 quantity → execution_quantity). 같은 단어의 활용형은 문맥에 맞게 쓴다 (체결일시 → executed_at).
- 영문은 기본 표기, 축약은 허용된 줄임말이다. 둘 다 쓸 수 있으며 설명에 정한 용도별 표기를 따른다.
- 금지는 해당 행의 의미·용도에 적용한다. 같은 표기라도 다른 의미이면 그 의미의 항목을 따른다.
- 현재 사전의 명시적인 표준·금지·예외는 기존 코드 관례보다 우선한다. 사전에 정하지 않은 사항은 기존 관례를 참고하고, 기존 이름을 임의로 바꾸지 않는다.

| 한글 | 영문 | 축약 | 금지 | 설명 |
| --- | --- | --- | --- | --- |
| 식별자 | identifier | id |  | 데이터를 고유하게 식별하는 값. {엔티티}_id 형식 |
| 이름 | name |  |  | 대상을 지칭하는 명칭 |
| 일시 | datetime | at |  | 날짜와 시각. created_at처럼 _at 접미사로 쓴다 |
```

- 행은 한글 가나다순으로 둔다. 찾기 쉽고, 같은 위치에 넣으므로 diff가 작다.
- 금지 열은 쉼표로 구분한 단어들이다. 설명은 뜻·유사 개념과의 구분·필요한 용도/예외를 한두 구절로 쓴다. 코드 경로나 구현 상세를 길게 나열하지 않는다. 문맥을 위한 열을 추가하지 않는다.
- 셀 안에 `|`를 쓸 때는 `\|`로 쓴다. 그대로 쓰면 표의 열이 어긋난다.

### 분리 후 — `glossary.md` + 도메인 파일

```
docs/superglossary/
  glossary.md   ← 규칙 + 도메인 index + 공통 용어 표
  <도메인>.md    ← 같은 열의 표, 그 도메인 용어만
```

`glossary.md`는 규칙 → `## 도메인` → `## 공통 용어` 순서다.

```markdown
# 용어 사전

(분리 전과 같은 머리말과 규칙)

## 도메인

| 도메인 | 파일 | 코드 범위 | 설명 |
| --- | --- | --- | --- |
| 주문 | order.md | src/order/** | 주문·결제 요청 |

## 공통 용어

| 한글 | 영문 | 축약 | 금지 | 설명 |
| --- | --- | --- | --- | --- |
| 식별자 | identifier | id |  | 데이터를 고유하게 식별하는 값. {엔티티}_id 형식 |
```

도메인 파일:

```markdown
# 주문 용어

| 한글 | 영문 | 축약 | 금지 | 설명 |
| --- | --- | --- | --- | --- |
| 주문 | order |  |  | 구매 요청 |
```

- **코드 범위**는 먼저 읽을 도메인을 고르는 힌트다. 여러 범위에 맞으면 관련 도메인을 모두 참고하고, 맞는 범위가 없으면 공통 용어와 관련 도메인에서 찾는다. 파일 위치만으로 의미나 금지 적용 범위를 정하지 않는다.
- 여러 도메인이 함께 쓰는 같은 개념은 공통 용어에 둔다. 같은 의미·용도의 항목은 한 파일에만 둔다. 표기가 같아도 뜻이 다른 항목은 각각 둘 수 있다.
- 규칙은 `glossary.md`에만 적는다.

## 2. 필요한 부분 읽기

사전은 Markdown 원문을 검색해 읽는다. 별도 파서·생성물·색인 파일을 만들지 않는다.

1. `glossary.md`의 머리말·규칙과 `## 도메인` 인덱스를 필요한 구간만 읽는다. 큰 용어 표 전체를 처음부터 읽지 않는다.
2. 작업에서 필요한 개념과 식별자를 정한다. check는 코드의 검사 대상을 먼저 추린다. 사전에 검색된 단어만 검사 대상으로 삼지 않는다.
3. `docs/superglossary/`의 **모든 md 파일**에서 한글 의미·영문·축약·금지 표기를 대소문자를 가리지 않고 검색한다. 활용형과 문맥상 다른 표기도 함께 찾는다(`executed`/`execution`, 갱신/`renew`/`refresh`). 도메인 파일은 우선순위이지 검색의 경계가 아니다.
4. 파일명·줄 번호가 있는 결과에서 해당 행의 다섯 열을 읽는다. 영문·축약·금지·설명 중 어디에 일치했는지 구분하고 **설명까지** 확인한다. 완전한 행이 이미 출력되었으면 반복해서 읽지 않는다. 표의 제목·규칙이 필요하거나 행이 잘렸으면 그 구간을 추가로 읽는다.
5. 검색 0건만으로 미등록을 확정하지 않는다. 한글 의미·동의어·활용형으로 보완하고, 여전히 불확실하면 관련 구간이나 도메인 파일로 읽기를 넓힌다. 의미가 불분명하면 확인 필요로 남긴다.

검색·읽기 결과가 잘리면 이어 읽거나 범위를 나눠 끝까지 확인한다. 읽지 못한 항목은 이유와 함께 미검토로 남긴다. 표가 깨져 열을 구분할 수 없으면 추측으로 판정하지 않는다. 사전 전체 정리·분리는 구간별로 전체 항목을 확인한다.

## 3. 등록 규칙

**단어별로 등록한다.** `매도호가체결`을 한 행으로 두지 않고 단어마다 한 행을 둔다. 이미 있는 단어는 다시 넣지 않고 조합해 쓴다. 합성어를 통째로 등록하면 사전이 금방 커지고, 같은 단어가 합성어마다 다르게 번역되기 쉽다.

**나누는 기준은 영문이다.** 합성어의 영문이 부분 영문을 이어 붙인 것과 같으면 나눈다. 다르거나, 전체 개념을 가리키는 통용 약어가 있으면 한 항목으로 등록할 수 있다. 약어가 있는 경우에도 풀어 쓴 영문과 축약을 각 열에 나눠 적는다.

| 예 | 처리 | 이유 |
|---|---|---|
| 체결수량 → 체결 + 수량 | 나눈다 | execution + quantity |
| 매도호가 → ask | 한 항목 | 업계 용어(매수호가는 bid). 나누면 sell_quote가 된다 |
| 국제증권식별번호 → internationalSecuritiesIdentificationNumber / isin | 한 항목 | 전체 개념의 영문과 표준 약어를 구분 |
| 재시도 → retry | 한 항목 | 영문이 한 단어 |

**누가 확정하나.**

- 단어별 등록은 Claude가 스스로 하고 한 줄로 알린다.
- 합성어를 한 항목으로 두는 예외는 도메인 지식이 걸린 판단이다. 근거(업계 용어, 통용 약어, 영문 한 단어)를 들어 사용자 확인을 받은 뒤 등록한다. 이미 해당 예외와 표기를 승인했다면 다시 묻지 않는다.
- 영문을 고를 때는 그 분야에서 실제로 쓰는 표기를 따른다. 확신이 없으면 후보와 근거를 보여 주고 묻는다.

**충돌.** 추가·수정 전에 사전 전체에서 한글·영문·축약·금지가 겹치는 항목과 같은 의미의 항목을 찾고 설명을 대조한다. 영문·축약·금지는 대소문자를 가리지 않는다. 표기 일치는 검토 단서이며 그 자체로 충돌은 아니다.

| 조건 | 처리 |
| --- | --- |
| 같은 의미·용도, 같은 표기 | 기존 항목 재사용 |
| 같은 의미·용도, 다른 표기 | 기존 표준 사용. 표준 변경은 사용자 결정 |
| 같은 표기, 다른 의미 | 설명에 구분을 적어 별도 등록 가능(색인/지수의 index) |
| 같은 의미, 용도별 다른 표준이 이미 명시됨 | 그 용도를 설명에 적어 구분(저장소 갱신 renew / 정기 갱신 요청 refresh) |
| 표준·축약과 금지의 적용 범위가 겹침 | 등록·수정 보류, 충돌 항목과 근거 제시 |
| 기존 설명·합의로 의미나 적용 범위를 구분할 수 없음 | 확인 필요. 새 의미 구분이나 금지 예외를 임의로 만들지 않음 |

모듈이나 경로가 다르다는 이유만으로 같은 개념을 나누지 않는다. 예를 들어 주문과 회원의 identifier는 공통 항목을 재사용한다. 새 금지 표기도 다른 항목의 영문·축약과 의미·범위를 대조한다. 변경안을 먼저 확인한 뒤 쓰고, 쓴 행도 같은 기준으로 다시 확인한다.

**활용형.** 한 단어는 한 형태로만 등록한다. 코드에서는 같은 단어의 활용형(execute·executed·execution, cancel·canceled)을 문맥에 맞게 써도 같은 단어로 보고, 활용형을 따로 등록하지 않는다 — `체결일시`는 `executed_at`이다. 등록할 형태는 그 개념을 가리킬 때 이 프로젝트가 주로 쓰는 형태로 고른다.

**영문과 축약.** 영문 열에는 기본 영문 표기, 축약 열에는 허용된 줄임말을 둔다. `investorRelations | ir`, `chiefExecutiveOfficer | ceo`처럼 구분한다. 둘 다 허용하며 축약을 항상 강제하지 않는다. `URL 필드는 irUrl을 사용한다`처럼 용도별 선호·제한을 설명에 정했다면 그 조건을 따른다. 새 약어를 영문 열에만 넣지 않는다. 통용 약어의 풀네임이 확실하지 않으면 임의로 확장하지 않고 확인한다.

**금지 단어.** 해당 행의 의미·용도에서 사용하지 않을 표기다. 단어 단위로 적고(`cust_no`가 아니라 `cust`) 코드의 전체 식별자와 의미를 함께 보고 판정한다.

| 항목 | 금지 | 설명 |
| --- | --- | --- |
| 발급 → grant | issue | 새 토큰을 받는 동작. 기존 OAuth 필드 issuedAt은 허용 |
| 발행 → issue | | 증권·채권을 발행하는 것 |

이 사전에서 issueToken은 위반, issueBond는 허용, 토큰의 issuedAt은 명시된 예외로 허용한다. 용도를 알 수 없는 issue는 확인 필요다. 다른 행의 표준이라는 사실만으로 현재 의미의 금지를 면제하지 않는다. 반대로 다른 의미에 적용된 금지를 전역 금지로 확대하지 않는다. 기존 금지와 일치했는데 설명으로 적용 여부를 정할 수 없으면 확인 필요로 남기며 금지를 삭제·완화하지 않는다. 빈도나 기존 관례만으로 예외를 만들지 않는다.

## 4. 분리 절차

용어가 300개를 넘으면 분리를 제안한다. 사용자가 동의할 때만 아래를 한다.

1. **도메인 후보 제안**: 프로젝트에 도메인 정의 문서(예: `docs/superdomain/DOMAIN.md`)가 있으면 그 도메인 이름과 코드 위치를 따른다. 없으면 모듈·패키지 구조에서 후보를 뽑는다. 후보마다 코드 범위와 옮겨 갈 용어 수를 보여 준다.
2. **확인**: 도메인 목록과 코드 범위를 사용자에게 확인받는다.
3. **공통 용어 판정**: 여러 도메인의 코드에서 쓰이는 단어와 기본 용어(식별자·이름·일시)는 공통 용어로 둔다. 판정이 애매한 단어는 목록으로 보여 주고 묻는다.
4. **파일 생성**: 도메인마다 `<도메인>.md`를 만들고 해당 행을 옮긴다. 파일 이름은 영문 소문자 kebab-case다.
5. **index 작성**: `glossary.md`에 `## 도메인` 표를 쓰고, 남은 행을 `## 공통 용어` 표로 둔다.
6. **확인**: 옮기기 전과 후의 전체 행 수가 같은지, 같은 의미·용도의 항목을 두 파일에 중복 배치하지 않았는지 확인하고 결과를 보고한다. 표기가 같아도 의미가 다른 행을 삭제하거나 합치지 않는다.
