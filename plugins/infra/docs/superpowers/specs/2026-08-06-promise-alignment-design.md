## 1. 목표와 배경

검토 보고서의 P0 4건은 조치했다(D15). 남은 P1 9건·P2 8건 중 **불특정 외부에 공개 배포하기 전에 반드시 닫아야 할 것**만 골라 한 묶음으로 만든다.

고른 기준은 기능의 많고 적음이 아니라 **문서가 약속한 것과 실제 동작이 어긋나는가**다. 낯선 사람이 README만 보고 쓰는 상황에서 가장 먼저 신뢰를 깨는 것은 기능이 없는 게 아니라 적힌 대로 되지 않는 것이기 때문이다. 현재 어긋나 있는 지점:

- `sync`는 온프렘 provider를 대조하지 않고도 "확인 불가 0건"을 보고한다 — 조용한 거짓 안심
- `init`은 "`secrets` 스킬로 가서 초기 암호화하라"고 인계하는데 그 스킬에 해당 절이 없다 — 막다른 길
- 스펙은 `secrets_format` 키를 정의했지만 어떤 코드도 읽지 않는다 — 죽은 약속
- `CLAUDE.md`는 스킬이 9종이라 하고, 스펙 상세 절은 D9 시점에 멈춰 있다
- 파서 오류 메시지가 들여쓰기 실수를 "중첩 구조 미지원"으로 오진한다
- hook은 "mutating 작업 후 기록을 남기라"고 하지만 서버 작업(ssh·apt·docker)에는 뜨지 않는다

**목표 한 줄**: 문서에 적힌 경로를 따라갔을 때 막다른 길도, 조용한 거짓말도 없게 만든다.

## 5. 코드 변경 설계

### 5.1 C1·C2 — `sync`가 확인하지 않은 것을 확인했다고 말하지 않게

**현재 결함**: `scripts/sync_snapshot.py`의 diff 단계가 `if prov.get("kind") not in ("aws", "gcp"): continue`로 온프렘을 통째로 삼킨다. 수집 명령 생성 단계도 `cli_profile`이 없으면 조용히 명령을 만들지 않는다. 결과적으로 온프렘 하네스는 4구획 전부 0건으로 나와 "문서와 실제가 일치"처럼 읽힌다.

**설계 원칙**: 4구획 구조(누락 / 유령 / 버전 불일치 / 확인 불가)는 **바꾸지 않는다**. 스펙 §7.8이 이미 "자격 증명이 없거나 수집 명령이 실패한 대상은 '확인 불가'로 구분 보고한다(오탐 방지)"를 규정했으므로, 새 개념 도입이 아니라 기존 규정의 이행이다. "확인 불가"의 **사유를 세분화**한다.

| 상황 | 보고 메시지 |
|---|---|
| `kind`가 aws/gcp가 아님 | `<pid>: <kind> provider는 자동 수집기가 없습니다 — 확인 불가(수동 확인 필요)` |
| aws인데 `regions` 미기재 | `<pid>: regions 미기재로 리전을 특정할 수 없습니다 — 확인 불가` |
| `cli_profile` 미기재 | `<pid>: cli_profile 미기재 — 확인 불가` |
| 수집 명령 실패 | 기존 메시지 유지 (`<pid>: provider 수집 실패 — 확인 불가`) |

**`--region` 처리**: `provider.regions`를 소비해 **리전당 수집 명령 하나씩** 생성하고, 같은 provider의 결과를 합집합으로 병합한다. gcloud는 기본이 전 존 조회라 리전 지정이 불필요하므로 **aws에만** 적용한다.

**수집 결과 병합**: `collect()`가 같은 `(target, kind)` 항목을 여러 번 받을 수 있게 되므로, 인스턴스 목록을 덮어쓰지 않고 누적한다. 한 리전이라도 수집에 실패하면 그 provider는 부분 결과이므로 **"확인 불가"로 표기**한다 — 일부만 본 것을 전부 본 것처럼 보고하지 않는다.

### 5.2 C3 — 들여쓰기 오진

**현재 결함**: `scripts/harness_lib.py:74`가 선행 공백을 만나면 `중첩 구조 미지원`을 던진다. 그러나 코드 흐름상 **진짜 중첩 맵은 그 앞줄(`key:` 빈 값)에서 다른 예외로 이미 걸린다.** 이 분기에 도달하는 것은 사실상 단순 들여쓰기 실수뿐인데 원인을 엉뚱하게 지목한다.

**설계**:
- 선행 공백 분기 → `frontmatter는 들여쓰기 없이 'key: value' 형태여야 합니다 — 선행 공백 발견: <원문>`
- 빈 값 분기(진짜 중첩 시도) → `중첩 맵은 지원하지 않습니다(엔티티 frontmatter는 플랫 구조): <원문>`

### 5.3 C4 — `secrets_format` 검증

**현재 결함**: 스펙 §4.4가 키를 정의하고 템플릿이 의도값 `sops-age`를 주석으로 안내하지만, 어떤 코드도 읽지 않아 `secrets_format: pgp` 같은 오설정이 통과한다.

**설계**: `audit`의 `check_harness_yaml`에 검증을 추가한다. 어휘는 `{"sops-age"}`.

| 조건 | 판정 |
|---|---|
| `secrets_mode: encrypted` + 값이 어휘 밖 | **실패** |
| `secrets_mode: encrypted` + 키 없음 | **경고** (보안 임계는 `secrets_recipients`가 이미 실패로 담당) |
| `secrets_mode ≠ encrypted` + 키 있음 | **경고** (무의미한 키) |

스키마에서 제거하지 않는 이유는 팀 표준을 문서로 남기는 값이기 때문이다.

### 5.4 C5 — hook mutating 패턴 확장

**현재 결함**: `hooks/scripts/change_reminder.py`의 패턴이 terraform·kubectl·helm·argocd 4계열뿐이라 서버 작업에는 리마인드가 뜨지 않는다.

**설계**: 아래를 추가한다. `ssh <host> '<명령>'`은 전체 명령 문자열이 매치 대상이므로 **별도 ssh 패턴 없이 자동으로 커버**된다.

| 계열 | 매치 | 제외 |
|---|---|---|
| `systemctl` | restart·stop·start·enable·disable·mask·daemon-reload | status·list-units·show |
| 패키지 | `apt`/`apt-get`/`yum`/`dnf`/`apk` + install·remove·purge·upgrade | list·search·show·info |
| `docker` | run·rm·stop·start·restart·kill·exec, `compose up|down|restart` | ps·logs·inspect·images |
| DB | `psql`/`mysql`의 `-c`/`-e` 안에 INSERT·UPDATE·DELETE·CREATE·DROP·ALTER·GRANT·TRUNCATE | SELECT만 있는 경우 |
| `aws` | `create-`·`delete-`·`update-`·`put-`·`modify-`·`terminate-`·`reboot-` 접두 | `describe-`·`list-`·`get-` |

`gcloud`는 `config set` 같은 로컬 설정까지 걸릴 위험이 커서 이번 범위에서 제외한다. 기존 `--dry-run` 전역 제외는 유지한다. PostToolUse는 어떤 경우에도 차단하지 않으므로(D6) 오탐 비용은 알림 한 줄뿐이며, 미탐(기록 누락)이 더 비싸다.

## 6. 문서 변경 설계

### 6.1 D1 — 끊긴 인계 경로 복구

**현재 결함**: `skills/init/SKILL.md`가 "`secrets` 스킬로 넘어가 `.sops.yaml` 생성과 초기 암호화를 진행하라"고 인계하지만, `skills/secrets/SKILL.md`는 수신자 관리(온보딩·오프보딩·재키잉)와 **기존** 암호문 편집만 다룬다. 사용자가 문서를 따라가면 막다른 길에 닿고, 그 틈을 메우는 가장 쉬운 방법이 평문 파일을 잠깐 두는 것이라 **원칙 위반을 유도하는 구조**다.

**설계**: `secrets` 스킬에 "신규 시크릿 생성·최초 암호화" 절을 추가한다. 원칙 1을 지켜야 하므로 **클로드가 값을 만들지도 보지도 않고, 사용자가 실행할 명령을 안내하는** 형태다.

1. `.sops.yaml` creation_rules 작성 — 경로별로 나눠 단일 키 침해가 최소 데이터만 침해하게 한다(NIST SP 800-57 Part 1 Rev.5 권고)
2. 최초 암호화 — 사용자가 자기 터미널에서 `sops <파일>`을 직접 실행한다. 클로드는 대신 실행하거나 출력을 캡처하지 않는다(기존 편집 절차와 동일 규약)
3. 값 생성 — 비밀번호·토큰 생성도 사용자가 수행한다. 클로드가 생성하면 값이 컨텍스트에 들어오므로 금지한다
4. 생성 방향 end-to-end 체인 — 계정 생성(사용자) → `keys.md` 행 등록(`register`) → `secrets/` 파일 최초 암호화(사용자) → 접속 검증(`ops`)의 각 단계가 어느 스킬 소관인지 연결한다

**경계**: 이번엔 문서로 경로를 잇는 데까지다. 검토 §3.7이 제안한 `secret_new` 스크립트 자동화는 P1-7과 함께 다음 묶음으로 둔다.

### 6.2 D2 — 문서 드리프트를 테스트로 고정

**현재 결함**: `CLAUDE.md:18`이 "스킬 9종"(실제 10종), `CLAUDE.md:52`가 plan 문서 1개만 열거(실제 3개).

**설계**: 수치를 고치는 것과 **동시에 검증 테스트를 추가한다.** 손으로 고치는 것만으로는 재발한다 — P0 작업 중에도 테스트 수와 D 범위가 다시 어긋나 손으로 고쳤다. `tests/test_docs_consistency.py`(신규)가 검사한다:

- `CLAUDE.md`·`README.md`가 말하는 스킬 수 == `skills/` 실제 디렉터리 수
- `CLAUDE.md`의 D 범위 상한 == 스펙 D 결정표의 최대 번호
- `CLAUDE.md`가 열거한 plan 문서 목록 == `docs/superpowers/plans/` 실제 파일

P0-4에서 시크릿 규율을 카나리 테스트로 고정한 것과 같은 패턴이다 — 사람 규율에 맡기지 않는다.

**신규 규약 D16**: "문서가 코드 구조를 수치로 언급하면 그 정합성은 테스트로 강제한다"를 스펙 §2의 D 결정표에 **D16으로 추가**한다.

**D16 추가와 테스트의 순환에 주의한다.** D2의 검사 중 하나가 "`CLAUDE.md`의 D 범위 상한 == 스펙 D 결정표의 최대 번호"인데, D2 자신이 D16을 추가하므로 같은 작업 안에서 세 가지가 함께 움직여야 한다: ①스펙에 D16 행 추가 ②`CLAUDE.md`의 D 범위를 `D1~D16`으로 갱신 ③테스트 추가. 셋 중 하나라도 빠지면 새로 넣은 테스트가 곧바로 실패한다. 이것은 결함이 아니라 이 규약이 의도한 작동이다.

### 6.3 D3 — 스펙 상세 절 동기화

**현재 결함**: 스펙은 D 결정표(§2)만 D15까지 진화했고 상세 절은 D9 시점이다. 그래서 §1은 "스킬 9종", §5 트리에는 `secrets`가 없고, §8.1 audit 검사 표는 6개(실제 10개), §12는 fixture 2개(현재 3개)다. **§7에는 `secrets` 스킬 명세 절이 아예 없어 스펙만으로는 그 스킬의 절차를 알 수 없다.**

**설계**: §1·§5·§8.1·§12를 **이 묶음이 끝난 시점의 구현**에 맞추고, §7에 `secrets` 스킬 명세 절을 신설한다(적용 원칙, 절차, 인접 스킬 경계). §10 템플릿 표는 D15에서 이미 갱신했다.

**주의 — 동기화 대상은 "현재"가 아니라 "완료 후" 상태다.** 이 묶음 자체가 스펙이 서술하는 값을 바꾼다. 반영해야 할 변화:

- fixture 수: 현재 3종 → C1이 온프렘 전용 fixture를 추가하므로 **4종**
- audit 검사 항목: C4가 `secrets_format` 검증을 더하므로 §8.1 표에 반영
- hook mutating 패턴: C5가 서버 계열을 더하므로 §9 패턴 목록에 반영
- 테스트 구성: 신규 테스트 파일(`test_docs_consistency.py`)과 C1~C5 회귀 테스트를 §12에 반영

그래서 §9 구현 순서에서 D3은 **코드 변경(C1~C5)이 모두 끝난 뒤**에 온다.

### 6.4 D4 — 공개 준비 문서

**설계**: 낯선 사용자가 README만으로 설치·시작할 수 있게 한다.

1. **설치 경로 정식화** — 현재 README는 `claude --plugin-dir`를 "개발 모드"로 소개하고 marketplace는 범위 밖이라 적고 있다. `git clone` + `--plugin-dir`를 **정식 설치 경로**로 다시 쓴다. marketplace 구성은 이번 범위 밖이며 그렇게 명시한다
2. **마이그레이션 절차** — D15로 `.claude/settings.local.json`이 없는 기존 git 하네스는 audit이 실패한다. 절차를 문서화하고, 더해 **`init`의 기존-하네스 감지 분기가 누락된 보호 설정을 보완 제안**하게 한다. 사용자는 "하네스 점검해줘" 한 마디로 끝난다
3. **기여자 마찰 기록** — 플러그인 저장소가 cwd 아래에 있으면 `Read(secrets/**)` 계열 deny가 `skills/secrets/`까지 매치하므로 `git show <ref>:<path>` 경유로 열람한다는 것을 기여 문서에 남긴다
4. **i18n 선행조건 명시** — 스킬 본문·산출 문서가 한국어 고정이며, 이것이 실제 공개 배포의 선행 조건임을 README에 적는다
