# sync — 인벤토리 drift 감지

하네스 인벤토리 문서(서버·k8s 클러스터·컴포넌트)와 실제 인프라 상태(클라우드 인스턴스·
k8s 노드·helm 릴리스)를 `scripts/sync_snapshot.py`로 read-only 대조해 drift(문서 누락·
유령 항목·버전 불일치)를 찾아 **보고**하는 스킬이다. "문서랑 실제 상태 맞는지 확인해줘",
"인벤토리 최신이야?" 같은 요청이나 정기 점검에 쓴다. 대조 결과를 스스로 문서에 반영하지
않고 사용자가 확인한 항목만 하나씩 갱신한다 — 문서 자체(참조 무결성·시크릿 등)의 정합성
검사는 audit, 엔티티에 대한 개별 명령 실행·조작은 ops가 맡는다.

## 1. 적용 원칙

이 스킬이 반드시 지키는 원칙은 다음 네 가지다.

- **원칙 1 — 시크릿 값의 컨텍스트 유입 금지, 참조 실행만**: 수집 명령은 전부 상태 조회용
  read-only 명령(`kubectl get nodes`, `helm list`, `aws ec2 describe-instances` 등)이며
  자격 증명 raw 파일을 읽거나 값을 출력하는 명령은 절대 포함하지 않는다. "확인 불가"로
  분류된 대상을 다시 확인하겠다고 `~/.aws/credentials`나 kubeconfig를 직접 열어보지
  않는다 — 접근이 안 되면 connect로 재구성을 제안한다(§3).
- **원칙 3 — 묻기 전에 스캔**: 수집(`--collect`)을 실행하기 전에 항상 dry 모드로 어떤
  명령이 실행될지 먼저 보여주고(§2), 리포트를 얻은 뒤에도 문서에 반영하기 전에 항목마다
  사용자 확인을 받는다(§3). 스캔·대조 결과 없이 사용자의 기억만으로 문서를 고치지 않는다.
- **원칙 4 — 하네스는 지도 + 조종석이지 엔진이 아니다**: 상태의 SSOT는 클러스터·클라우드의
  실제 상태이지 인벤토리 문서가 아니다. 대조 결과가 문서와 다르면 문서 쪽 해석을 우선하지
  않고, 실제 상태를 기준으로 4구획 리포트에 있는 그대로 보고한다.
- **원칙 6 — 암묵 컨텍스트 금지**: 수집 명령에는 항상 대상 엔티티에 기록된
  `--context`/`--kube-context`/`--profile`을 명시한다(`sync_snapshot.py`가 조립하는 명령에
  이미 반영되어 있다). 현재 kubectl 컨텍스트나 기본 aws profile에 의존하는 수집 결과는
  신뢰하지 않는다.

## 2. 절차

1. cwd에서 상위 디렉터리 방향으로 `harness.yaml`을 상향 탐색해 `HARNESS_ROOT`를 정한다
   (전 스킬이 공유하는 하네스 발견 규약). 찾지 못하면 진행하지 않고 "하네스 디렉터리에서
   세션을 열거나 init으로 하네스를 먼저 생성하세요"라고 안내한 뒤 중단한다.
2. 먼저 `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/sync_snapshot.py --root <HARNESS_ROOT>`를
   `--collect` 없이(dry) 실행해 기대 스냅샷(문서 기준 엔티티 수)과 **앞으로 실행할 수집
   명령 목록**을 사용자에게 그대로 보여준다. 이 단계는 아무 명령도 실제로 실행하지 않는다.
3. 사용자가 수집 진행을 확인하면 같은 명령에 `--collect`를 추가해 실행한다 — 이때
   실행되는 명령은 전부 read-only이며(`kubectl get nodes`, `helm list -A`, `aws ec2
   describe-instances`, `gcloud compute instances list`), 각 명령에는 대상 엔티티의
   `--context`/`--profile`이 이미 명시되어 있다(원칙 6).
4. 스크립트 출력의 4구획 리포트를 그대로 보고한다 — **실제에만 있음(문서 누락)**,
   **문서에만 있음(유령)**, **버전 불일치**, **확인 불가**(자격 증명 부재·수집 명령 실패
   등으로 판정 자체가 안 된 대상 — 오탐 방지를 위해 별도 구획으로 분리 보고한다).

## 3. 자동 수정 금지 — 반영은 항목 단위 확인 후

sync는 어떤 경우에도 리포트 결과를 스스로 문서에 반영하지 않는다. 4구획 리포트를 사용자와
항목 하나씩 확인해 반영 여부를 정한다.

- **문서 누락(실제엔 있는데 문서에 없음)**: 반영하기로 하면 register 절차로 새 엔티티를
  등록하게 안내한다 — sync가 직접 엔티티 파일을 만들지 않는다.
- **유령(문서엔 있는데 실제에 없음)**: 파일을 바로 삭제하자고 제안하지 않는다. 대신 왜
  유령이 됐는지(폐기됨·아직 프로비저닝 전·일시 중지 등) 본문에 사유를 기록해 두는 쪽을
  제안하고, 실제 삭제 여부는 사용자 판단에 맡긴다.
- **확인 불가**: 문서를 건드리지 않는다. 대신 connect로 해당 엔티티의 로컬 접근(자격
  증명·kubeconfig context 등)을 복구하자고 제안하고, 복구 후 sync를 다시 실행해 재확인
  하도록 안내한다.
- **버전 불일치**: 어느 쪽이 맞는지 스스로 판단하지 않고, 실제 버전과 문서 기록
  (`installed_by`) 중 문서를 어떻게 갱신할지 사용자에게 확인받는다.

## 4. 명명 규약 불일치 의심 시 오탐 알림

sync의 대조는 **명명 규약(register §7)** — 컴포넌트 `id` == helm 릴리스 이름, 서버 `id`
== 클라우드 Name 태그 — 이 지켜졌다는 전제로 동작한다. 문서 누락과 유령이 비슷한 시점에
비슷한 이름으로 동시에 나타나면(예: 유령으로 `victoria-metrics`, 문서 누락으로
`vm-monitoring`이 동시 보고) 실제로는 이름만 다를 뿐 같은 대상을 가리키는 **오탐일 수
있다**는 점을 사용자에게 함께 알린다. 이 경우 자동으로 병합하거나 어느 한쪽을 지우지
않고, 사용자에게 실제로 같은 대상인지부터 확인받은 뒤 §3의 절차를 이어간다.
