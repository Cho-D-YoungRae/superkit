# secrets — 팀 시크릿 라이프사이클 관리

하네스가 공유(`git`/`shared-drive`)되고 `secrets_mode: encrypted`(SOPS+age 표준, D11)로
운영될 때 그 위에서 도는 **팀 단위** 라이프사이클 — 팀원 온보딩·오프보딩, 복구 수신자
유지, 개별 암호문 편집·재암호화 — 을 담당하는 스킬이다. 시크릿의 값 자체를 조회하거나
위치를 찾는 작업은 lookup, `secrets_recipients`·`secrets/` 정책 위반 여부를 점검하는
작업은 audit이 맡는다 — secrets는 항상 "수신자 집합을 바꾸고 그에 맞춰 암호문 자체를
갱신하는" 작업까지만 한다.

## 1. 적용 원칙

이 스킬이 반드시 지키는 원칙은 다음 세 가지다.

- **원칙 1 — 시크릿 값의 컨텍스트 유입 금지, 참조 실행만**: 이 스킬이 다루는 모든 작업은
  "암호문을 누가 열 수 있는가"를 바꾸는 것이지 "내용이 무엇인가"를 들여다보는 것이
  아니다. `sops updatekeys`는 파일의 데이터 키만 새 수신자 목록으로 재포장할 뿐 페이로드
  평문을 출력하지 않으므로 클로드가 Bash로 직접 실행해도 안전하다. 반면 `sops <파일>`
  편집은 에디터에 복호된 내용을 잠깐 띄우는 작업이라 **사용자가 자신의 터미널에서 직접
  실행**하며, 클로드는 이 명령을 대신 실행하거나 그 출력을 캡처하지 않는다(§7). 어떤
  절차에서도 복호 결과·시크릿 값을 대화 컨텍스트·stdout·로그·`changes/` 기록에 남기지
  않는다.
- **원칙 2 — 시크릿 저장 정책은 공유 모드에 종속**: 이 스킬 자체가 "공유 + encrypted"
  조합(원칙 2가 허용하는 유일한 하네스 내부 보관 경로)을 전제로 존재한다. `sharing: local`
  하네스는 `secrets/`에 평문 보관이 허용되므로 이 스킬의 수신자·재키잉 절차가 필요 없다
  (평문 파일을 직접 다루면 된다).
- **원칙 8 — 정책은 데이터**: 팀 구성(누가 복호 가능한가)은 `harness.yaml`의
  `secrets_recipients`에 데이터로 존재한다. 이 스킬은 그 데이터를 갱신하고 `.sops.yaml`·
  암호문을 그에 맞춰 재생성할 뿐, 수신자 목록을 스킬 코드나 대화 맥락에만 존재하는
  일회성 정보로 다루지 않는다.

## 2. 공통 규약

작업을 시작하기 전에 항상 cwd에서 상위 디렉터리 방향으로 `harness.yaml`을 상향 탐색해
`HARNESS_ROOT`를 정한다(전 스킬이 공유하는 하네스 발견 규약). 찾지 못하면 진행하지 않고
"하네스 디렉터리에서 세션을 열거나 init으로 하네스를 먼저 생성하세요"라고 안내한 뒤
중단한다. `harness.yaml`의 `secrets_mode`가 `encrypted`가 아니면(`none`/`plaintext`) 이
스킬이 다루는 수신자·재키잉 절차 자체가 적용되지 않는다는 점을 안내하고 중단한다 —
`secrets_mode: none`으로 외부 매니저를 쓰는 하네스는 §9의 백엔드 참조만 해당된다.

## 3. 온보딩 — 팀원 추가

1. 새 팀원의 age **공개키**(`age1...`)를 받는다. 공개키는 비밀이 아니므로 대화·이슈·PR
   어디서 주고받아도 안전하다 — 개인키(`AGE-SECRET-KEY-1...`)와 절대 혼동하지 않는다.
2. `harness.yaml`의 `secrets_recipients`에 `<이름>: <age공개키>` 행을 추가한다(중첩 맵 —
   `harness_lib.parse_yaml_subset`이 지원하는 `key: value` 형태만 가능하고 리스트-of-맵은
   지원하지 않으므로 항상 이 형태를 유지한다).
3. 갱신된 `secrets_recipients` 전체 목록으로 하네스 루트의 `.sops.yaml`을 재생성한다
   (수신자 age 공개키 목록을 `.sops.yaml`의 규칙에 반영 — 파일이 없으면 이번에 새로
   만든다).
4. `sops updatekeys <파일>`을 `secrets/` 아래 기존 암호문 각각에 실행해 새 `.sops.yaml`
   수신자 목록으로 재키잉한다. 이 명령은 데이터 키만 재포장하고 페이로드 평문은 출력하지
   않는다(§1 원칙 1).
5. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/audit.py`를 실행해 `secrets_recipients` 형태와
   `recovery` 수신자 존재를 확인한다(D11, `check_recipients`).

## 4. 오프보딩 — 팀원 이탈 회수 (3단계 필수)

팀원 이탈 시 아래 세 단계를 **모두** 수행해야 실제로 접근이 회수된다. ①만으로는
불충분하다.

1. **수신자 제거 + 재키잉**: `harness.yaml`의 `secrets_recipients`에서 이탈한 팀원의
   항목을 지우고, `.sops.yaml`을 갱신된 수신자 목록으로 재생성한 뒤 `sops updatekeys
   <파일>`을 `secrets/` 전 암호문에 실행한다.
2. **하위 자격증명 로테이션(진짜 회수)**: ①만으로는 불충분하다 — 이탈한 팀원이 재키잉
   *이전에* 로컬에 내려받아 둔 구버전 암호문(git 히스토리, 백업, 로컬 클론 등에 남아
   있을 수 있다)은 그 사람의 개인키로 여전히 복호 가능하다. 재키잉은 "새 암호문을 그
   사람이 못 여는 것"만 보장하지, "그 사람이 이미 알고 있던 값"을 무효화하지 않는다.
   그러므로 `secrets/` 안 암호문이 담고 있던 실제 자격증명(비밀번호, API 토큰, ssh 키
   등)을 해당 서비스·프로바이더에서 **재발급/변경**해야 회수가 완성된다(`access/keys.md`
   행의 `kind`에 맞는 로테이션 — ssh 키는 새 키페어 교체, 토큰은 재발급, 비밀번호는
   변경). 로테이션된 새 값을 `secrets/` 암호문에 반영하는 것은 §7(편집·재암호화)을
   따른다.
3. **`changes/`에 기록**: 로테이션 사실(대상 자격증명, 사유 — 팀원 이탈, 일시)을 change
   스킬 절차로 `changes/`에 남긴다. 값 자체는 기록하지 않고 "무엇을 로테이션했는지"만
   남긴다(원칙 1).

**히스토리 재작성(예: `git filter-repo`, BFG로 과거 커밋의 암호문을 지우는 것)은 일상적인
팀원 이탈 회수 수단이 아니다** — 이 스킬의 온보딩·오프보딩 절차는 히스토리를 건드리지
않는다. 히스토리 재작성은 실제 유출 사고(암호문이 아니라 평문이 커밋됐음이 audit의
`[시크릿]` 검출로 확인된 경우 등)에 대응하는 별도의 인시던트 대응 절차이며, 이 스킬의
범위 밖이다 — 필요한 상황이면 그 사실만 알리고 별도 판단을 안내한다.

## 5. 복구 수신자

`secrets_recipients`에는 **항상** 조직 복구 수신자(예: `recovery: age1...`)를 포함한다 —
개별 팀원이 갑자기 이탈하거나 개인키를 분실해도 하네스 전체가 복호 불가능 상태에 빠지지
않도록 하는 안전망이다. audit이 `encrypted`인데 `recovery` 항목이 없으면 실패로
보고한다(D11, `check_recipients`). 복구 수신자의 개인키는 특정 개인의 개인키를 공유하는
것이 아니라 **조직이 별도로 발급·보관하는 전용 키페어**여야 한다 — 팀원 개인의 개인키를
"복구용"이라며 여러 사람이 공유해 쓰는 것은 금지한다(개인키는 그 소유자만 갖는다는 전제가
깨지면 오프보딩 시 회수가 애초에 불가능해진다).

## 6. 신규 시크릿 생성·최초 암호화

`init`이 `secrets_mode: encrypted`로 하네스를 만들면 `harness.yaml`의 수신자 매니페스트만
준비된 상태다. 실제 암호화는 여기서 시작한다. **클로드는 시크릿 값을 만들지도 보지도
않는다**(원칙 1) — 아래 명령은 사용자가 자기 터미널에서 직접 실행한다.

### 6.1 `.sops.yaml` 생성

하네스 루트에 `.sops.yaml`을 만들고 `harness.yaml`의 `secrets_recipients` 공개키를 옮겨
적는다. **경로별로 규칙을 나눈다** — 단일 키가 침해됐을 때 노출 범위를 그 경로로 묶기
위해서다(NIST SP 800-57 Part 1 Rev.5의 "단일 키 침해가 최대한 적은 데이터만 침해하도록"
권고).

```yaml
creation_rules:
  - path_regex: secrets/prod/.*
    age: age1prodaaaa...,age1recovery...
  - path_regex: secrets/.*
    age: age1alice...,age1bob...,age1recovery...
```

`recovery` 수신자는 **모든 규칙에** 포함한다(§5). 빠지면 개인 이탈 시 복호 불능이 되고
`audit`가 실패로 잡는다.

### 6.2 최초 암호화

값 자체는 사용자가 만든다. 클로드는 값을 생성하지 않는다 — 생성하는 순간 값이 컨텍스트에
들어오기 때문이다.

```bash
# 사용자가 자기 터미널에서 실행한다
sops secrets/prod/db-app.env      # 편집기가 열리고, 저장하면 암호문으로 기록된다
```

클로드는 이 명령을 **대신 실행하거나 출력을 캡처하지 않는다**(§2 공통 규약과 동일).
암호화가 끝나면 `audit`로 형식을 확인한다: 하네스에서 "하네스 점검해줘".

### 6.3 생성 방향 end-to-end 체인

"DB 계정을 추가한다" 같은 요청은 여러 스킬에 걸친다. 각 단계의 소관은 이렇다.

| 단계 | 소관 | 비고 |
|---|---|---|
| 1. DB에 계정 생성 | 사용자 | `CREATE USER`/`GRANT`는 사용자가 실행한다. 값이 argv에 남지 않게 주의 |
| 2. `access/keys.md`에 행 추가 | `register` | `kind: account`/`password`, 값이 아니라 **위치 참조**만 |
| 3. `secrets/` 암호문 최초 생성 | 사용자 (§6.2) | 클로드는 경로와 명령만 안내한다 |
| 4. 접속 검증 | `ops` | `usage` 컬럼의 참조 실행 레시피로 확인한다 |
| 5. 변경 기록 | `change` | 롤백 방법(계정 회수 절차) 필수 |

`secrets_mode: none`으로 외부 매니저(Vault·1Password 등)를 쓰는 하네스는 이 절 대신 §9의
백엔드 참조를 따른다 — 값 생성·보관은 그 매니저의 몫이다.

## 7. 편집·재암호화

기존 암호문의 내용을 바꿔야 할 때(로테이션된 새 값 반영 등)는 `sops <파일>`로 연다 —
이 명령은 **사용자가 자신의 터미널에서 직접 실행**한다. sops가 파일을 복호해 `$EDITOR`에
띄우고, 저장하면 자동으로 다시 암호화한다. 클로드는 이 명령을 Bash로 대신 실행하지
않는다 — 대신 실행하면 비대화형 환경이라 에디터가 뜰 수 없거나, 설사 뜨더라도 그 결과가
도구 출력으로 캡처돼 복호된 내용이 대화 컨텍스트에 남는 경로가 생긴다(원칙 1). 이
스킬의 역할은 어떤 파일을 열어야 하는지 안내하고, 사용자가 저장을 마친 뒤에는 age/SOPS
헤더가 여전히 유효한지(즉 다시 암호화됐는지, `audit`의 `_classify_encrypted`가 확인하는
것과 같은 기준)만 확인하는 것까지다. 평문은 어떤 경우에도 stdout·로그·`changes/` 기록에
남기지 않는다 — `changes/`에는 "무엇을 바꿨는지"만 적고 바뀐 값 자체는 적지 않는다.

## 8. 공유 드라이브 주의

`sharing: shared-drive`인 하네스는 `secrets/`의 암호문도 다른 파일과 똑같이 동시 편집에
취약하다. 암호문은 병합 가능한 텍스트가 아니라 **단일 작성자/읽기 위주 아티팩트**로
취급한다 — 두 사람이 동시에 같은 암호문을 열어 재암호화하면 드라이브 동기화 클라이언트가
`파일 (1).age`류의 conflict-copy를 만들 수 있다. 단, audit의 구조 검사(`[구조]`)는
`providers/`·`inventory/`의 `.md` **엔티티** 충돌 사본만 탐지한다 — `secrets/`의 암호문
충돌 사본(`.age` 등)은 audit 범위 밖이라 자동으로 잡히지 않는다. 따라서 재암호화 후에는
`secrets/`에 conflict-copy가 생겼는지 **사람이 직접 확인**해, 어느 쪽이 최신인지 판단한 뒤
하나만 남기고 나머지는 지운다(자동 병합하지 않는다).

## 9. 외부 백엔드는 별도 참조

Vault·1Password·AWS Secrets Manager 같은 외부 시크릿 매니저는 수신자·재키잉 개념이 이
스킬과 다르다(각 매니저 자체의 접근 제어를 그대로 쓴다). 위치 참조가 `op://`·`vault://`·
`aws-secretsmanager://`(D14)라면 이 스킬의 온보딩·오프보딩 절차 대신
`references/backends.md`의 백엔드별 참조 실행 관례를 따른다 — 값은 그 경우에도 조회·
출력하지 않는다.
