# audit — 하네스 정합성 검증

하네스 문서 자체의 정합성 — 스키마 필수 필드, id-파일명 일치, 엔티티 참조 무결성,
엔티티 구조(중복 id·충돌 사본 의심 파일), `secrets/` 밖 시크릿 패턴 유출,
`sharing`·`secrets_mode` 정책 조합, 자격증명 kind 어휘·위치 참조, `secrets_recipients`의
recovery 수신자, 키·인증서 만료 임박 — 을 `scripts/audit.py`로 검증하고 결과를 보고하는
스킬이다. "하네스 점검해줘", "시크릿 유출 없나 확인해줘" 같은 요청이나 init·register
직후 점검에 쓴다. 실제 인프라 상태와의 대조는 sync, 발견된 문제의 실제 수정(엔티티
등록·필드 수정 등)은 각 스킬(register 등)이 맡는다 — audit은 항상 "검증하고 보고하는"
것까지만 한다.

## 1. 적용 원칙

이 스킬이 반드시 지키는 원칙은 다음 세 가지다.

- **원칙 1 — 시크릿 값의 컨텍스트 유입 금지, 참조 실행만**: `audit.py`의 시크릿 스캔이
  FAIL을 검출해도 그 값을 다시 읽거나 대화에 출력하지 않는다. 스크립트 출력 자체가 이미
  파일 경로와 패턴 종류(예: "AWS Access Key ID(AKIA...)")만 담고 있으므로 그 형태 그대로
  전달하고, "진짜 맞는지 보자"며 해당 파일을 열어 검출된 문자열을 다시 옮겨 적지 않는다
  (§3).
- **원칙 2 — 시크릿 저장 정책은 공유 모드에 종속**: `[정책]` 실패는 `sharing`과
  `secrets_mode` 조합 규칙(로컬이 아니면 평문 금지, 암호화 모드면 `secrets/` 파일이
  age/SOPS 헤더를 가져야 함) 위반을 그대로 보고한 것이다. 수정 방법을 제안할 때도 이
  조합 규칙을 따른다(§2).
- **원칙 8 — 정책은 데이터**: 정책 위반의 수정은 스킬 코드가 아니라 `harness.yaml`의
  `sharing`/`secrets_mode` 값을 바꾸거나 그 값에 맞춰 실제 파일 보관 형태를 바꾸는 것으로
  이루어진다. audit 자신은 정책 위반을 판단해 보고할 뿐 강제로 바꾸지 않는다.

## 2. 절차

1. cwd에서 상위 디렉터리 방향으로 `harness.yaml`을 상향 탐색해 `HARNESS_ROOT`를 정한다
   (전 스킬이 공유하는 하네스 발견 규약). 찾지 못하면 진행하지 않고 "하네스 디렉터리에서
   세션을 열거나 init으로 하네스를 먼저 생성하세요"라고 안내한 뒤 중단한다.
2. `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/audit.py --root <HARNESS_ROOT>`를 실행한다.
3. 출력의 `FAIL`/`WARN` 줄을 카테고리별로 해설하고 수정 방법을 제안한다.
   - `[스키마]`/`[참조]`: 필수 필드 누락, id-파일명 불일치, provider/runs_on/depends_on이
     존재하지 않는 id를 가리킴, `keys.md#앵커` 없음 → 대상 엔티티가 아직 없으면 register로
     등록하고, 이미 있는데 오탈자 등으로 어긋난 것이면 해당 문서의 필드를 직접 수정하도록
     안내한다.
   - `[구조]`(D13): 중복 id(`id 'X' 중복 — <경로들>`) → 두 파일이 같은 id를 쓰고 있다는
     뜻이므로, 어느 쪽이 실제 대상인지 확인한 뒤 한쪽의 파일명과 frontmatter `id`를 함께
     바꿔 유일하게 만들도록 안내한다. 충돌 사본 의심 파일(`충돌 사본 의심 파일: <경로>`,
     `conflicted copy`·`(1).md` 등 파일명 패턴) → 동기화 도구가 남긴 사본일 가능성이
     크므로, 원본과 내용을 대조해 최신 쪽만 남기고 나머지 사본은 사람이 직접 삭제하도록
     안내한다(자동 병합 금지 — audit은 판단·보고만 하고 삭제는 하지 않는다).
   - `[키]`(D12): `access/keys.md` 행의 `kind`가 어휘(`ssh-key`/`tls-cert`/`api-token`/
     `cloud`/`account`/`password`) 밖의 값이면(`알 수 없는 kind`) 해당 행의 `kind`를 이
     어휘 중 맞는 값으로 교정하도록 안내하고, 위치 참조 칸이 비어 있거나 `-`뿐이면(`위치
     참조 누락`) 실제 시크릿이 있는 곳(`secrets/파일` 또는 `op://`·`vault://`·
     `aws-secretsmanager://` 등 외부 참조)을 채우도록 안내한다 — 이 칸에도 값 자체는
     절대 적지 않는다.
   - `[시크릿]`: `secrets/` 밖에서 시크릿 패턴이 검출된 경우 → 그 자리의 값을 지우고 위치
     참조(`secrets/파일` 또는 `op://vault/item` 등)로 교체하도록 안내하며, **이미 노출됐던
     값이므로 참조 교체만으로 끝내지 말고 해당 키·토큰 자체의 로테이션**을 함께 권고한다.
     검출된 값 자체는 어떤 경우에도 재출력하지 않는다(§3). `읽을 수 없어 스캔하지
     못했습니다`는 오염 검출이 아니라 **그 파일만 스캔하지 못했다**는 뜻이다(퍼미션 등) —
     나머지 파일 스캔은 정상 수행됐으므로, 해당 파일의 권한을 고쳐 다시 돌리도록 안내한다.
   - `[정책]`: `sharing`/`secrets_mode` 조합 위반이거나 `secrets/` 파일이 암호문 헤더가
     아닌 경우 → `harness.yaml`의 `sharing`/`secrets_mode` 값을 조정하거나, 평문으로 남아
     있는 해당 파일을 age/SOPS로 암호화하는 전환 절차를 안내한다. 다음 세 가지 신규
     서브케이스도 같은 카테고리로 보고된다. ① `secrets/` 안의 심볼릭 링크(`심볼릭 링크는
     허용하지 않는다(내용 미확인)`) → 대상 내용을 확인하지 않은 채(추종해 읽지 않고)
     그대로 보고된 것이므로, 링크를 지우고 실제 파일이나 정식 위치 참조로 바꾸도록
     안내한다. ② `secrets_mode: none`인데 `secrets/`에 시크릿 페이로드 파일이 남아 있는
     경우(`secrets_mode: none인데 시크릿 페이로드 파일이 있다`) → 그 모드에서는 시크릿을
     하네스에 두지 않는 것이 전제이므로, 해당 파일을 삭제하거나 `secrets_mode`를 실제
     보관 방식(`plaintext`/`encrypted`)에 맞게 변경하도록 안내한다. ③ `secrets_mode:
     encrypted`인데 `secrets_recipients`에 `recovery` 수신자가 없는 경우(D11, `recovery
     수신자가 없다`) → 등록자 개인이 이탈해도 조직이 시크릿에 계속 접근할 수 있어야
     하므로, `secrets` 스킬로 recovery 수신자를 `secrets_recipients`에 추가하도록
     안내한다.
   - `[보호]`(D15): `secrets/` 읽기 차단 설정의 드리프트·구멍이다. `.claude/settings.json`이
     없거나 deny 규칙이 빠졌으면(`init을 다시 실행하세요`) 차단이 사라진 상태이므로 **init에
     인계**해 보호 설정을 다시 심도록 안내한다. `.claude/settings.local.json`에 규칙이
     없다는 보고는 **git 하네스**에만 나오며(하네스 하위 디렉터리에서 연 세션이 차단을 받지
     못한다 — `settings.json`은 부모 폴백 없이 cwd에서만 로드된다), `settings.json`과 같은
     내용으로 그 파일을 만들도록 안내한다(`sharing: git`이면 커밋해 팀 전체가 같은 보호를
     받게 한다). **git이 아닌 하네스**는 이 파일로 메울 수 없으므로 "세션을 하네스 루트에서
     열라"는 경고만 나온다. `secrets_mode`가 `plaintext`/`encrypted`면 FAIL, `none`이면
     지킬 로컬 값이 없으므로 WARN이다.
   - `[harness.yaml]`: 필수 키 누락, 알 수 없는 `sharing`/`secrets_mode` 값 → `harness.yaml`
     자체를 직접 수정하도록 안내한다. `secrets_format`도 같은 카테고리로 보고된다 — 값이
     허용 어휘(`sops-age`) 밖이면 FAIL이고, `secrets_mode: encrypted`인데 키가 없거나
     반대로 encrypted가 아닌데 키가 있으면(무시되는 키) WARN이다. 각각 팀 표준 암호화
     형식을 명시하거나 불필요한 키를 지우도록 안내한다.
   - `[만료]`(WARN): 키·인증서가 30일 이내 만료 예정이거나 이미 만료됨 → 로테이션 일정을
     안내한다. 경고일 뿐이므로 종료 코드에는 영향을 주지 않는다.
   - `[내부오류]`: 그 검사가 예외로 **중단됐다**는 뜻이다 — "문제 없음"이 아니라 **확인하지
     못함**이다. 특히 `[내부오류] 시크릿 스캔`은 오염이 없다는 보장이 아니므로, 다른 검사가
     모두 통과했더라도 "시크릿 스캔은 수행되지 않았다"고 명시해 보고한다. 값 비유출을 위해
     예외 메시지는 버리고 타입만 남기므로 원인은 여기서 알 수 없다 — 조건을 바꿔(예: 문제
     파일 권한 수정) 다시 돌려 보도록 안내하고, 그래도 재현되면 트레이스백을 보는 `--debug`
     재실행은 **사용자가 자신의 터미널에서 직접** 하도록 안내한다(클로드가 붙이는 옵션이
     아니다 — 트레이스백에는 값이 실릴 수 있다).
4. 종료 코드를 그대로 보고에 반영한다 — `FAIL`이 한 건이라도 있으면 스크립트가 exit 1을
   반환하므로 보고 맨 앞에 **"감사 실패"**임을 명확히 표시하고 실패/경고 건수 요약("실패
   N건 / 경고 M건")을 함께 전달한다. `FAIL` 없이 `WARN`만 있으면 exit 0이며 "통과(경고
   N건)"로 보고한다.

## 3. 시크릿 검출 시 재출력 금지

`[시크릿]` FAIL이 있을 때 절대 하지 않는 것: 검출된 파일을 다시 열어 매치된 줄이나 값을
그대로 인용·복사해 보여주는 것, `cat`/`grep -o`로 값 자체를 뽑아 확인하는 것. `audit.py`
출력은 이미 "파일 경로 + 패턴 종류"만 담고 있으므로 사용자에게는 그 정보만 전달한다 —
어떤 파일에 어떤 종류의 패턴이 있는지는 알려주되, 그 값이 정확히 무엇인지는 알려주지
않는다. 정책 검사(`[정책]`)의 암호문 헤더 판별도 같은 이유로 헤더 매직 판별 결과만 쓰고
파일 내용을 출력하지 않는다.
