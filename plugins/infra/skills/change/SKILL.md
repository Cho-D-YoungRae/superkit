# change — 인프라 변경 기록

방금 실행된(또는 실행 중인) 인프라 변경을 하네스 `changes/`에 날짜 기반 기록으로 남긴다.
ops의 mutating 파이프라인 마지막 단계에서 자동 호출되거나, hook의 변경기록 리마인드
(`change_reminder`)가 뜬 직후, 혹은 "방금 작업 기록 남겨줘"처럼 수동으로도 호출된다.
명령을 실제로 실행하는 일 자체는 ops, 구조·기술 선택의 배경을 남기는 일은 decide가
맡는다 — change는 항상 "이미 벌어진 변경 하나를 사후에 기록하는" 작업만 한다.

## 1. 적용 원칙

이 스킬이 반드시 지키는 원칙은 다음 두 가지다.

- **원칙 9 — 기록은 작업의 부산물**: 변경 기록은 별도의 일이 아니라 ops 파이프라인과 hook에서
  자동 생성·유도된다. `changes/`는 날짜 기반 append-only 구조라 git 없이도 성립한다 —
  저장 방식(git·공유 드라이브·로컬)과 무관하게 **`changes/`가 변경 이력의 SSOT**다.
- **원칙 8 — 정책은 데이터**: hook이 리마인드를 띄울지는 `harness.yaml`의
  `hooks.change_reminder` 값에 따라 결정되며 이 스킬 본문과는 무관하다. change는 리마인드로
  호출되든 사용자가 직접 호출하든 절차상 동일하게 동작한다.

## 2. 절차

1. cwd에서 상위 디렉터리 방향으로 `harness.yaml`을 상향 탐색해 `HARNESS_ROOT`를 정한다
   (전 스킬이 공유하는 하네스 발견 규약). 찾지 못하면 기록을 진행하지 않고 "하네스
   디렉터리에서 세션을 열거나 init으로 하네스를 먼저 생성하세요"라고 안내한 뒤 중단한다.
2. 직전 대화 맥락(ops 실행 결과, 사용자 발화)에서 아래 항목을 최대한 자동으로 채운다.
   - **date**: 오늘 날짜(대화에서 다른 날짜가 명시되면 그 값).
   - **targets**: 변경 대상 엔티티 id 목록(예: `[prod-db-01]`).
   - **변경 내용**: 무엇을 바꿨는지 요약.
   - **실행 명령/방법**: 실제로 실행한 명령을 `--context`/`--profile` 등 옵션까지 **그대로**
     옮겨 적는다(축약·일반화하지 않는다). 단 명령에 시크릿 값이 리터럴로 들어가서는 안
     되며, `${VAR}` 환경변수나 키 경로 같은 참조 형태로만 기록한다(원칙 1 — `changes/`는
     git 등으로 공유되는 SSOT일 수 있다). ops가 애초에 참조 실행만 조립하므로 통상
     자동으로 충족된다.
   - **결과·검증**: 실행 결과, 수행한 검증(rollout status, 헬스체크 등).
   - **롤백 방법**: 대화에 이미 언급돼 있으면 채운다.
3. **롤백 방법을 대화 맥락에서 확정할 수 없으면(비어 있으면), 반드시 사용자에게 직접
   묻는다** — "이 변경을 되돌리려면 어떻게 해야 합니까?" **답을 받기 전에는 기록 작성을
   완료 처리하지 않는다.** 사용자가 "롤백 불가"라고 답하면 그 사실 자체를 롤백 방법 칸에
   명시적으로 적는다(빈 칸으로 남기지 않는다).
4. slug를 정한다 — 변경 내용을 요약한 영문 kebab-case(예: `pg16-upgrade`,
   `argocd-sync-fix`).
5. `changes/{YYYY}` 디렉토리가 없으면 새로 만든다. `${CLAUDE_PLUGIN_ROOT}/templates/change.md`
   를 읽어 `{{date}}`/`{{targets}}`/`{{title}}`과 각 섹션을 2~3번에서 채운 값으로 채운 뒤
   `changes/{YYYY}/{MM}-{DD}-{slug}.md`로 저장한다.
6. 관련 ADR이 있으면(이 변경의 배경이 되는 결정이 decide로 이미 기록돼 있으면) "사유"
   섹션에 `../../decisions/ADR-NNNN-slug.md` 상대 경로로 링크한다.
7. 생성한 파일 경로를 사용자에게 보고한다.

## 3. append-only

기존 `changes/` 파일은 **어떤 이유로도 수정하지 않는다**. 기록한 내용에 오류가 있거나
이후 상황이 바뀌어도 그 파일을 고치지 않고, 정정 내용을 담은 **새 change 기록**을
추가한다(새 기록의 "변경 내용"에 어떤 과거 기록을 정정하는지 상대 경로로 명시한다).
하네스가 git이 아닌 공유 드라이브·로컬 전용이어도 이 append-only 규칙은 동일하게
적용된다.

## 4. 파일명 충돌 처리

같은 날 같은 slug로 이미 `changes/{YYYY}/{MM}-{DD}-{slug}.md`가 존재하면(하루에 같은
요약의 변경이 두 번째로 발생한 경우) 파일명에 `-2` 접미사를 붙인다
(`{MM}-{DD}-{slug}-2.md`). 그 이름도 이미 있으면 `-3`, `-4`처럼 다음으로 비어 있는
번호까지 순서대로 올린다 — 기존 파일을 덮어쓰는 일은 없다.
