# connect — 인프라 접근 재구성

하네스에 기록된 `access_recipe`를 실행해 k8s 클러스터·서버의 로컬 접근(kubeconfig
context, ssh 설정 등)을 재구성한다. 새 머신 세팅, 자격 만료 후 재인증, "이 클러스터
kubeconfig 잡아줘"처럼 **로컬 접근 자체가 안 될 때** 쓴다. 접속 방법이 무엇인지 정보만
필요하면 lookup, 접근이 이미 구성돼 있고 그 위에서 명령을 실행·조회하려면 ops가 맡는다 —
connect는 항상 "로컬 접근을 재구성하는 그 자체"만 한다.

## 1. 적용 원칙

이 스킬이 반드시 지키는 원칙은 다음 세 가지다.

- **원칙 1 — 레시피 실행은 자격증명 생성 도구에 위임**: `access_recipe`(`aws eks
  update-kubeconfig`, `gcloud container clusters get-credentials` 등)는 클라우드 CLI가
  자격증명을 만들어 kubeconfig에 써 넣는 것이지, connect가 그 파일을 직접 만들거나 값을
  다루는 게 아니다. 실행 전후 어떤 시점에도 `~/.kube/config` 같은 kubeconfig **파일의
  내용을 읽어 컨텍스트로 들이지 않는다** — 그 안에 인증서·토큰 값이 그대로 들어 있기
  때문이다. 재구성 결과 확인은 `kubectl config get-contexts -o name`처럼 메타데이터만
  출력하는 명령으로 한다.
- **원칙 3 — 묻기 전에 스캔**: 레시피를 실행하기 전에 로컬에서 확인 가능한 사실 —
  레시피가 요구하는 CLI의 설치 여부(`command -v <cli>`), 이미 같은 이름의 context/profile이
  존재하는지(`kubectl config get-contexts -o name`, `aws configure list-profiles`) — 를
  먼저 스캔해 사용자 확인 질문의 근거로 붙인다. "그냥 실행할까요?"가 아니라 "이미
  `prod-k8s`라는 컨텍스트가 있는데 덮어써도 됩니까?"처럼 스캔 결과를 반영해 구체적으로
  묻는다.
- **원칙 6 — 암묵 컨텍스트 금지**: 실행 결과를 검증하는 명령에도 반드시 대상 엔티티의
  `context`/`profile`을 명시한다(`kubectl --context <c> get nodes`). "현재 컨텍스트로
  확인"하는 방식은 방금 재구성한 접근이 맞는지 보장하지 못하므로 쓰지 않는다.

## 2. 절차

1. cwd에서 상위 디렉터리 방향으로 `harness.yaml`을 상향 탐색해 `HARNESS_ROOT`를 정한다
   (전 스킬이 공유하는 하네스 발견 규약). 찾지 못하면 진행하지 않고 "하네스 디렉터리에서
   세션을 열거나 init으로 하네스를 먼저 생성하세요"라고 안내한 뒤 중단한다.
2. 요청에서 대상 엔티티(k8s-cluster 또는 server)를 식별한다. 이름만으로 후보가 여럿이면
   lookup과 같은 방식으로 후보를 표로 제시해 사용자가 하나를 고르게 한다.
3. 대상 엔티티 파일의 `access_recipe` 필드 내용을 **그대로** 사용자에게 보여준다. 온프렘
   처럼 파일 복사형 레시피면 §3에 따라 절차만 안내하고 대신 실행하지 않는다.
4. 사용자 확인을 받은 뒤에만 레시피에 적힌 명령을 그대로 실행한다. 실행 도중 자격증명
   관련 출력(브라우저 SSO 리다이렉트 안내 등)이 있어도 그 값을 컨텍스트에 옮겨 적거나
   요약하지 않는다.
5. 실행 후 read-only 명령으로 검증한다 — k8s-cluster면 `kubectl --context <엔티티의
   context> get nodes`, server면 `ssh -i <keys.md 위치 참조> <host> 'true'` 같은 최소
   연결 확인 명령. 실패하면 원인을 보고하고 CLI 부재(§4)인지 레시피 자체의 문제인지
   구분해 안내한다.
6. 검증 결과(성공/실패, 재구성된 context/profile 이름)를 사용자에게 보고한다.

## 3. 온프렘 레시피(파일 복사형)

`access_recipe`가 클라우드 CLI 한 줄이 아니라 "어디서 무엇을 어떻게 복사하라"는 절차
서술이면(예: k3s 마스터 노드의 `/etc/rancher/k3s/k3s.yaml`을 scp로 가져오라는 안내),
connect는 그 **절차를 안내만** 한다 — scp를 대신 실행하거나 원격 파일 내용을 읽어와
컨텍스트에 붙여넣지 않는다. kubeconfig 내용이 원격 서버의 다른 파일에 있다는 사실 자체가
이미 원칙 1이 보호하려는 대상이므로, connect가 그 파일을 대신 열어보는 순간 레시피를 텍스트
절차로 남겨 둔 이유가 무너진다. 사용자가 직접 복사를 마치고 알려주면(연결 재구성 명령 자체를
connect가 대신 실행하지 않으므로 §2의 4단계는 건너뛰고) §2의 5~6단계(검증·보고)만 이어서
수행한다.

## 4. CLI 부재 시

레시피가 요구하는 CLI(`aws`, `gcloud`, `kubectl` 등)가 `command -v`로 확인되지 않으면
실행을 진행하지 않고 설치 방법을 안내한다 — 패키지 매니저 명령(예: `brew install
awscli`/`brew install kubectl`) 또는 각 도구의 공식 설치 문서를 참고하도록 안내한다.
설치가 끝났다고 확인되면 §2의 1단계(하네스 재탐색은 필요 없음)부터 다시 시작한다.
