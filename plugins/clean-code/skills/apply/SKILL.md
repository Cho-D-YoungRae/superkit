# Clean Code 적용

코드를 쓰거나 고칠 때 『Clean Code』의 원칙을 판단 근거로 쓴다. 원칙은 `${CLAUDE_SKILL_DIR}/references/`에 챕터별로 요약되어 있다.

## 레퍼런스 찾기

레퍼런스는 지금 내릴 판단에 필요한 만큼만 읽는다. 챕터 파일 하나가 200~500줄이라, 여러 파일을 통째로 읽으면 시간과 컨텍스트만 들고 판단은 나아지지 않는다.

1. 아래 표에서 작업에 맞는 파일을 고른다. 대개 1~2개면 된다. 표로 정할 수 없을 때만 `references/index.md`(책 전체 목차와 챕터별 한 줄 요약)를 본다.
2. 고른 파일은 처음부터 끝까지 읽지 않는다. 헤딩 줄 번호를 먼저 찾고(예: `grep -n '^##' <파일>`), `## 핵심`과 `## 체크리스트` 절만 그 범위로 읽는다.
3. 원칙 절(어떻게·왜·예시)은 체크리스트에서 걸린 항목이나 지금 내려야 할 판단에 필요한 절만 연다.
4. `chapter_17_smells_and_heuristics.md`는 위쪽의 `## 목차` 표(휴리스틱 66개를 한 줄씩)만 먼저 읽는다. 해당하는 휴리스틱이 있으면 그 항목(`### G25:` 같은 헤딩)만 찾아 읽고, 근거가 더 필요하면 항목 끝의 '관련' 링크를 따라간다.
5. 통째로 읽은 파일이 둘을 넘으면, 정말 필요한지 다시 본다.

챕터 파일은 `핵심` → 원칙 절 → `체크리스트` → `관련` → (있으면) `원서 밖 보충` 순서다. 14·16장은 원칙 절 대신 교훈 절과 `변환 패턴`을, 17장은 목차 표와 카테고리 절(신호·처방·이유)을 둔다. 체크리스트는 모든 항목에 "예"라고 답할 수 있으면 통과다.

## 작업별 흐름

### 코드를 새로 쓸 때

1. 작업에 해당하는 챕터의 `핵심`을 읽고 쓴다. 판단이 서지 않는 부분만 해당 원칙 절을 연다.
2. 다 쓰면 그 챕터의 `체크리스트`로 이번에 쓴 코드만 점검하고, 어긋난 곳을 고친다.
3. 처음부터 완벽하게 쓰려 하지 않는다. 동작하는 초안을 테스트로 고정한 뒤 다듬는 것이 원서가 권하는 순서다(`chapter_14_successive_refinement.md`).

### 리팩터링할 때

1. 바꾸려는 동작을 지켜 줄 테스트가 있는지 먼저 본다. 없거나 부족하면 테스트부터 보강한다. 경계값이나 오류가 겹칠 때의 우선순위처럼 구조를 바꾸다 깨지기 쉬운 동작이 빠져 있으면 부족한 것이다. 테스트 없이 구조를 바꾸면 동작이 바뀌어도 알 수 없다(`chapter_16_refactoring_serialdate.md`의 First, Make It Work).
   - 사용자가 준 테스트·검증 파일을 늘리거나 고쳤다면 응답에서 그 사실을 알린다. 어느 파일에 어떤 검사를 몇 개, 왜 더했는지 쓴다. 원래 있던 검사는 지우거나 바꾸지 않는다. 그 파일은 사용자가 관리하므로, 말없이 바뀌면 사용자가 리뷰에서 놓치거나 의도와 다른 검사가 섞일 수 있다.
2. 테스트가 계속 통과하는 작은 단계로 나눠 바꾼다. 한 번에 다시 쓰지 않는다(`chapter_14_successive_refinement.md`의 On Incrementalism).
3. 무엇을 고칠지는 `chapter_17_smells_and_heuristics.md`의 목차 표로 찾고, 처방의 세부는 해당 항목과 링크된 챕터에서 확인한다.
4. 동작은 바꾸지 않는다. 버그를 발견하면 리팩터링과 섞지 말고 따로 알린다.

### 리뷰를 요청받았을 때

고치지 않고 검토만 원하는 요청이면 `review` 스킬(`/clean-code:review`)을 쓴다. 읽기 전용 리뷰어가 별도 컨텍스트에서 레퍼런스를 읽고 판정하므로, 이 대화의 컨텍스트를 아끼고 리뷰 결과의 형식도 일정하다. 이 스킬에서는 고치는 중에 냄새를 확인할 때만 17장 목차 표를 직접 본다.

## 적용 기준

- **프로젝트 규칙이 먼저다.** 대상 프로젝트의 지침 파일(AGENTS.md·CLAUDE.md), 린터·포매터 설정, 기존 코드의 일관된 관례, 함께 켜진 컨벤션 스킬(예: superdomain의 `conventions`)과 부딪치면 그쪽을 따르고, 부딪친 사실을 사용자에게 알린다. 원서도 개인 취향보다 팀 규칙을 앞세운다(`chapter_05_formatting.md`의 Team Rules).
- **언어의 관용을 따른다.** 레퍼런스 예시는 원서와 같은 Java지만 원칙은 언어를 가리지 않는다. Kotlin·TypeScript·Python 등에서는 그 언어에서 자연스러운 형태로 옮긴다. Java에만 해당하는 조언은 각 챕터의 `원서 밖 보충`에 적힌 오늘날 관행을 함께 본다.
- **원서와 보충을 구분한다.** 챕터 파일의 `원서 밖 보충` 절은 원서 이후의 관행과 작성자 의견을 덧붙인 것이고 원서의 주장이 아니다. 사용자에게 근거를 댈 때 둘을 섞지 않는다.
- **수치는 방향이다.** 함수 길이·인수 개수 같은 원서의 수치는 더 작고 단순하게 가라는 방향으로 쓴다. 숫자를 맞추려고 의미 없는 함수로 쪼개지 않는다.
- **범위를 지킨다.** 요청받은 코드와 그 주변을 조금 더 깨끗하게 남기는 것(The Boy Scout Rule)까지가 이 스킬의 범위다. 요청 범위 밖의 넓은 정리는 하지 않고 제안만 한다.

## 하지 않는 것

- 원칙을 이유로 동작을 바꾸지 않는다.
- 레퍼런스에 없는 내용을 원서의 주장처럼 말하지 않는다.
- 사용자가 요청하지 않은 대규모 리팩터링을 하지 않는다.
