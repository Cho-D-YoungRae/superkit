# 클린 코드 리뷰

코드를 『Clean Code』 기준으로 검토한다. 판정은 `clean-code:clean-code-reviewer`가 맡는다. 이 스킬은 대상을 정하고, 리뷰어를 띄우고, 결과를 한 리포트로 정리한다.

**핵심 원칙:** 판정은 리뷰어가 한다. 이 스킬이 코드를 직접 읽고 판정하지 않는다. 레퍼런스를 읽는 일도 리뷰어의 컨텍스트에서 일어나게 해서 이 대화의 컨텍스트를 아낀다. 코드는 사용자가 요청할 때만 고친다.

## 1. 대상 결정

인자(`$ARGUMENTS`)가 없으면 사용자 요청에서 대상을 찾는다. 요청에 파일이나 디렉터리가 있으면 그것이 대상이다.

| 대상 | 모드 | 보는 것 |
|---|---|---|
| 경로(파일·디렉터리) | 파일 검토 | 그 파일 전체(디렉터리면 그 아래 소스 파일) |
| 커밋 범위(`A..B`) | 변경 검토 | 그 범위의 커밋 변경 |
| 없음 | 변경 검토 | 기준 브랜치와의 merge-base 이후의 모든 변경(커밋된 것 + 커밋하지 않은 것 + 새 파일) |
| `전체` | 전체 점검 | 프로젝트 전체 |

변경 검토의 변경 목록은 git 루트(`git rev-parse --show-toplevel`)에서 이렇게 구한다. 커밋 범위면 기준 브랜치와 BASE는 구하지 않고 `<BASE>` 대신 `A..B`를 쓰며, 새 파일 목록은 만들지 않는다.

```bash
git symbolic-ref --quiet --short refs/remotes/origin/HEAD   # 기준 브랜치 (예: origin/main)
git merge-base HEAD <기준 브랜치>                            # BASE
git diff --name-status <BASE>                                # 추적 중인 파일의 변경과 상태 (A·M·D·R)
git ls-files --others --exclude-standard                     # 아직 추적하지 않는 새 파일
```

- 대상이 없는데 git 저장소가 아니거나, `origin/HEAD`가 없거나, 변경이 없으면 추측하지 말고 무엇을 볼지 사용자에게 묻는다.
- 없는 경로면 사용자에게 묻는다.

## 2. 리뷰어 호출

`clean-code:clean-code-reviewer`를 Agent 도구로 호출한다. `model`은 지정하지 않는다(에이전트 파일에 정해져 있다). 세션 대화는 넘기지 않고 아래만 넘긴다. 사용자가 요청에서 밝힌 관심사나 제약(예: "성능은 보지 마", "이 함수만")이 있으면 `요청`에 한 줄로 옮긴다.

```
모드: 파일 검토 | 변경 검토 | 전체 점검
프로젝트 루트: <절대 경로>
기준 문서: ${CLAUDE_PLUGIN_ROOT}/skills/apply/references/
대상: <파일 목록, 또는 변경을 보는 git 명령과 상태를 붙인 파일 목록, 또는 "프로젝트 전체">
요청: <사용자의 관심사·제약, 없으면 생략>
```

- 변경을 보는 명령은 리뷰어가 직접 실행할 수 있게 `git -C <프로젝트 루트> diff <BASE>`(커밋 범위면 `diff A..B`) 꼴로 쓴다. 추적하지 않는 새 파일은 `새 파일 — 파일 전체가 변경`으로, 삭제된 파일은 `삭제됨`으로 적고, 삭제된 파일은 대상에서 뺀다.
- 소스 파일이 많으면(대략 20개를 넘으면) 디렉터리나 모듈 단위로 나눠 리뷰어 여러 개를 **한 메시지에서 동시에** 띄운다.

## 3. 합치기

- 심각도 순(Critical → Important → Minor)으로 모은다.
- 리뷰어를 여럿 띄웠다면 같은 위치의 같은 문제는 하나로 합친다.
- 위치나 근거가 없는 지적은 빼고, 뺐다는 사실을 적는다.
- 리뷰어가 단 근거(휴리스틱 코드·챕터 절)와 `(원서 밖)` 표시는 빼거나 바꾸지 않고 그대로 옮긴다. 근거는 사용자가 레퍼런스에서 지적을 확인하는 단서다.
- 지적된 위치의 코드를 확인해 리뷰어의 지적이 틀렸다고 보이면 근거와 함께 그렇게 말하고 그대로 옮기지 않는다. 이 스킬이 새 지적을 더하지는 않는다.

## 4. 보고와 후속

```markdown
## 리뷰 결과 — <대상 요약>
### Critical
### Important
### Minor
- `경로:줄` 문제 — 근거(`G5` Duplication 등) — 제안
### 원서 밖 의견
### 질문
### 검토 범위
```

- 코드 수정은 사용자가 요청할 때만 한다. 요청받으면 Critical부터 고치고, 고치는 일은 apply 스킬의 리팩터링 흐름(테스트 먼저, 작은 단계, 동작 보존)을 따른다.

## 하지 않는 것

- 자동으로 코드를 고치지 않는다.
- 리뷰 결과를 파일로 저장하지 않는다(사용자가 요청하면 저장한다).
- 리뷰어의 모델을 지정하거나 덮어쓰지 않는다.
